#T INTRO Narzędzia, które wyłapią błędy za Ciebie
Zanim zaczniesz pisać komponenty, ustaw trzy narzędzia, które będą Ci towarzyszyć w każdej lekcji: ESLint (wyłapuje błędy i złe wzorce), Prettier (formatuje kod) i React DevTools (pokazuje drzewo komponentów, props i state w przeglądarce). Kilka minut konfiguracji oszczędza godziny szukania błędów.

#T DEFINITION ESLint i reguły hooków
ESLint analizuje kod bez uruchamiania go. Szablon Vite ma już konfigurację (`eslint.config.js`) z dwoma ważnymi wtyczkami:
- **eslint-plugin-react-hooks** — pilnuje zasad hooków (hooki tylko na najwyższym poziomie komponentu) i kompletności zależności w `useEffect`. To najcenniejsza reguła w całym projekcie React.
- **eslint-plugin-react-refresh** — ostrzega, gdy plik eksportuje coś, co psuje odświeżanie HMR.

W projekcie TS dochodzi `typescript-eslint`, który rozumie składnię typów.

#T CODE_JSX Błąd wykryty przez ESLint (JSX)
Hook wywołany warunkowo. ESLint zgłosi: „React Hook useState is called conditionally”.
```
import { useState } from 'react';

export function TicketBadge({ ticket }) {
  if (!ticket) {
    return null;
  }
  const [open, setOpen] = useState(false); // błąd: hook po warunkowym return
  return <span onClick={() => setOpen(!open)}>{ticket.status}</span>;
}
```

#T CODE_TSX Ten sam błąd w TSX
TypeScript nie zgłasza tu żadnego błędu typów — kod jest poprawny typowo. Zasady hooków sprawdza wyłącznie ESLint. Dlatego linter jest potrzebny także w projekcie TS.
```
import { useState } from 'react';
import type { Ticket } from '../types';

export function TicketBadge({ ticket }: { ticket: Ticket | null }) {
  if (!ticket) {
    return null;
  }
  const [open, setOpen] = useState(false); // ESLint: hook wywołany warunkowo
  return <span onClick={() => setOpen(!open)}>{ticket.status}</span>;
}
```

#T NOTE JSX ↔ TSX — kto łapie jaki błąd
- **ESLint** — zasady hooków, nieużywane zmienne, brakujące zależności efektów. Działa w obu wersjach.
- **TypeScript** — złe typy props, literówki w nazwach pól (`ticket.titel`), wywołanie funkcji z błędnymi argumentami, możliwy `null`. Tylko w TSX.
- **React w konsoli przeglądarki** — brak `key` w listach, błędy renderowania, ostrzeżenia o przestarzałych API. W obu wersjach, ale dopiero po uruchomieniu.

W JSX część błędów, które TypeScript zgłosiłby od razu w edytorze, zobaczysz dopiero w przeglądarce — albo wcale.

#T STEP_BY_STEP Skonfiguruj edytor (VS Code)
1. Zainstaluj rozszerzenia: **ESLint** i **Prettier – Code formatter**.
2. W projekcie zainstaluj Prettiera: `npm install -D prettier`.
3. Utwórz plik `.prettierrc` z ustawieniami, np. `{ "singleQuote": true, "semi": true, "printWidth": 100 }`.
4. W ustawieniach VS Code włącz „Format On Save” i wybierz Prettiera jako domyślny formater.
5. Uruchom `npm run lint` w terminalu — powinno przejść bez błędów.
6. Wpisz celowo w komponencie nieużywaną zmienną i sprawdź, że edytor ją podkreśla.

#T DEFINITION React DevTools
Rozszerzenie przeglądarki (Chrome, Firefox, Edge) dodające dwie zakładki w narzędziach deweloperskich:
- **Components** — drzewo komponentów zamiast drzewa DOM. Po kliknięciu komponentu widzisz jego props, state i hooki, a wartości możesz zmieniać na żywo.
- **Profiler** — nagrywa renderowania i pokazuje, który komponent ile czasu się renderował (rozdział 16).

Opcja „Highlight updates when components render” podświetla na ekranie komponenty, które właśnie się przerenderowały — świetne do zrozumienia, co się dzieje po kliknięciu.

#T STEP_BY_STEP Obejrzyj aplikację w DevTools
1. Zainstaluj React Developer Tools ze sklepu rozszerzeń przeglądarki.
2. Uruchom szablon Vite z licznikiem (jeśli usunąłeś go w poprzedniej lekcji, utwórz na chwilę nowy projekt).
3. Otwórz narzędzia deweloperskie (F12) i zakładkę **Components**.
4. Kliknij `App` — w panelu po prawej zobaczysz hook `State` z wartością licznika.
5. Zmień wartość stanu w DevTools na 100 — przycisk na stronie pokaże 100.
6. Włącz „Highlight updates” i kliknij przycisk — `App` zostanie podświetlony przy każdym renderze.

#T DEFINITION StrictMode i podwójne wywołania w trybie deweloperskim
`main.jsx` opakowuje aplikację w `<StrictMode>`. W trybie deweloperskim React celowo wywołuje funkcje komponentów dwa razy, a efekty montuje, odmontowuje i montuje ponownie. Robi to, żeby ujawnić błędy: komponenty, które przy każdym wywołaniu dają inny wynik, i efekty bez poprawnego sprzątania. W wersji produkcyjnej nic nie jest wywoływane podwójnie.

#T CODE_WRONG Nieczysty komponent wykryty przez StrictMode
`console.log` pojawi się dwa razy, a licznik rośnie o 2 zamiast o 1 — bo komponent zmienia zmienną spoza siebie podczas renderowania.
```
let renders = 0;

export function Header() {
  renders++; // efekt uboczny w trakcie renderu
  console.log('render', renders);
  return <h1>DevDesk (render #{renders})</h1>;
}
```

#T CODE_RIGHT Komponent bez efektów ubocznych w renderze
```
export function Header() {
  return <h1>DevDesk</h1>;
}
```

#T PITFALL Wyłączanie StrictMode, żeby „naprawić” podwójne logi
Gdy ktoś widzi podwójne `console.log` albo podwójne zapytanie do API, często usuwa `<StrictMode>`. To jak wyłączenie czujnika dymu, bo piszczy. Podwójne wywołanie jest sygnałem, że komponent albo efekt nie jest poprawnie napisany. W rozdziale 07 nauczysz się pisać efekty, które działają poprawnie także przy podwójnym montowaniu.

#T SUMMARY Podsumowanie
ESLint z regułami hooków łapie błędy, których nie wyłapie ani JavaScript, ani TypeScript. Prettier formatuje kod przy zapisie. React DevTools pokazuje drzewo komponentów z props i state oraz podświetla rendery. StrictMode w trybie deweloperskim celowo wywołuje komponenty i efekty podwójnie, by ujawnić błędy. Kryterium akceptacji: `npm run lint` przechodzi, kod formatuje się przy zapisie, a w zakładce Components widzisz komponent `App` i jego stan.
