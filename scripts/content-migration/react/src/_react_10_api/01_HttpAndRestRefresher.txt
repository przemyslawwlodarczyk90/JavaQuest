#T INTRO Rozgrzewka i problem: DevDesk żyje w pamięci przeglądarki
Rozgrzewka: Czym jest komponent headless? Co robi prop getter? Kiedy wybierasz komponent złożony zamiast tablicy konfiguracji?

Problem: wszystkie tickety DevDesk pochodzą z pliku `data/tickets` i giną po odświeżeniu (poza preferencjami w localStorage). Prawdziwa aplikacja pobiera dane z serwera przez HTTP i zapisuje je tam. Zanim napiszesz pierwszy `fetch` w komponencie, w tej lekcji uporządkujesz wiedzę o HTTP i REST z perspektywy frontendu i zaprojektujesz **kontrakt API** DevDesk — umowę, której będą się trzymać frontend i backend.

#T DEFINITION HTTP w pigułce dla frontendu
Żądanie HTTP ma: **metodę**, **adres** (ścieżka + parametry zapytania), **nagłówki** i opcjonalne **ciało**. Odpowiedź ma: **kod statusu**, nagłówki i ciało (u nas JSON).

Metody w REST:
- `GET /api/tickets` — pobierz listę (bez ciała, bezpieczne do powtórzenia),
- `GET /api/tickets/42` — pobierz jeden zasób,
- `POST /api/tickets` — utwórz (ciało: dane nowego ticketu; odpowiedź: utworzony ticket z ID),
- `PATCH /api/tickets/42` — zmień część pól,
- `PUT /api/tickets/42` — zastąp cały zasób,
- `DELETE /api/tickets/42` — usuń.

#T API_REFERENCE Kody statusu, które obsługujesz w UI
- `200 OK` — sukces z danymi; `201 Created` — utworzono (często z nagłówkiem `Location`); `204 No Content` — sukces bez ciała (typowe dla DELETE),
- `400 Bad Request` — błędne dane (np. walidacja) — pokaż komunikaty przy polach,
- `401 Unauthorized` — brak lub wygasłe logowanie — przekieruj do logowania,
- `403 Forbidden` — zalogowany, ale bez uprawnień — pokaż „Brak dostępu”,
- `404 Not Found` — zasób nie istnieje — pokaż „Nie znaleziono ticketu”,
- `409 Conflict` — konflikt (np. ktoś zmienił ticket w międzyczasie) — zaproponuj odświeżenie,
- `422 Unprocessable Entity` — dane poprawne składniowo, ale niepoprawne biznesowo,
- `429 Too Many Requests` — za dużo żądań — odczekaj i spróbuj ponownie,
- `500`/`502`/`503` — błąd serwera — komunikat ogólny z przyciskiem „Spróbuj ponownie”.

Ważne: `fetch` **nie rzuca wyjątku** dla 4xx i 5xx — odpowiedź z kodem 500 to dla niego sukces sieciowy. Wyjątek dostaniesz tylko przy błędzie sieci (brak połączenia, CORS, przerwanie).

#T CODE_JSX Kontrakt API DevDesk — opis w JavaScripcie
W JS kontrakt istnieje jako dokumentacja (np. specyfikacja OpenAPI z backendu) i przykładowe odpowiedzi.
```
// api/contract.js — dokumentacja kontraktu
/*
GET    /api/tickets?status=OPEN&q=api&page=1&pageSize=10&sort=createdAt:desc
       → 200 { items: Ticket[], total: number, page: number, pageSize: number }
GET    /api/tickets/:id            → 200 Ticket | 404 { message }
POST   /api/tickets   body: { title, description, priority, assignee }
       → 201 Ticket | 400 { message, fieldErrors: { title?: string[] } }
PATCH  /api/tickets/:id body: { status?, priority?, assignee?, title? } → 200 Ticket | 404 | 409
DELETE /api/tickets/:id            → 204 | 404
*/
export const API_BASE = '/api';
```

#T CODE_TSX Kontrakt API DevDesk jako typy
W TSX kontrakt jest kodem: frontend nie skompiluje się, jeśli użyje pola, którego w kontrakcie nie ma. Typy możesz też wygenerować ze specyfikacji OpenAPI backendu (rozdział 11).
```
// api/contract.ts
import type { Ticket, TicketStatus } from '../types';

export const API_BASE = '/api';

export type TicketListQuery = {
  status?: TicketStatus;
  q?: string;
  page?: number;
  pageSize?: number;
  sort?: `${'createdAt' | 'priority' | 'title'}:${'asc' | 'desc'}`;
};

export type Page<T> = { items: T[]; total: number; page: number; pageSize: number };

export type CreateTicketBody = Pick<Ticket, 'title' | 'description' | 'priority' | 'assignee'>;
export type UpdateTicketBody = Partial<Pick<Ticket, 'title' | 'status' | 'priority' | 'assignee'>>;

export type ApiError = { message: string; fieldErrors?: Partial<Record<keyof CreateTicketBody, string[]>> };
```

#T NOTE JSX ↔ TSX — typy kontraktu a dane w czasie działania
Typ `Page<Ticket>` mówi kompilatorowi, czego się spodziewasz, ale — przypomnienie z rozdziału 01 — nie sprawdza odpowiedzi serwera. Jeśli backend zwróci `{ data: [...] }` zamiast `{ items: [...] }`, wersja TSX skompiluje się i wybuchnie dokładnie tak samo jak JSX. Dlatego w kolejnych lekcjach odpowiedzi z API będziesz walidować schematem Zod w jednym miejscu (warstwa klienta API) — to daje bezpieczeństwo w obu wersjach. Szablonowy typ literałowy `` `${'createdAt' | 'priority'}:${'asc' | 'desc'}` `` w TSX dopuszcza tylko poprawne wartości parametru `sort`.

#T DEFINITION Parametry zapytania i URLSearchParams
Filtry, wyszukiwanie, sortowanie i paginację przekazujesz w **parametrach zapytania** (`?status=OPEN&page=2`). Budujesz je obiektem `URLSearchParams`, który poprawnie koduje znaki specjalne (spacje, polskie litery, `&`). Nie skleja się ich ręcznie z tekstów.

#T CODE_BASIC Budowanie adresu z filtrów
```
import type { TicketListQuery } from './contract';

export function ticketsUrl(query: TicketListQuery): string {
  const params = new URLSearchParams();
  for (const [key, value] of Object.entries(query)) {
    if (value !== undefined && value !== '') params.set(key, String(value));
  }
  const qs = params.toString();
  return qs ? `/api/tickets?${qs}` : '/api/tickets';
}

// ticketsUrl({ status: 'OPEN', q: 'błąd logowania', page: 2 })
// → "/api/tickets?status=OPEN&q=b%C5%82%C4%85d+logowania&page=2"
```

#T CODE_PRACTICAL Zakładka Network: czytanie żądań
Zanim zaczniesz debugować kod, naucz się czytać ruch sieciowy w narzędziach deweloperskich. Na każdym żądaniu sprawdź po kolei:
```
1. Metoda i adres     → czy to właściwy endpoint i parametry?        GET /api/tickets?status=OPEN
2. Status             → 200? 404? 500? (czerwone wiersze = błędy)    200
3. Request Headers    → Content-Type, Authorization, Accept          content-type: application/json
4. Payload            → co wysłał frontend (POST/PATCH)               {"title":"Błąd eksportu"}
5. Response / Preview → co zwrócił serwer                             {"items":[...],"total":124}
6. Timing             → ile trwało, czy czekało w kolejce             312 ms
7. Initiator          → która linia kodu wysłała żądanie              api/tickets.ts:14
```

#T DEFINITION CORS — dlaczego przeglądarka blokuje żądanie
Gdy frontend (`http://localhost:5173`) wysyła żądanie do backendu pod innym adresem (`http://localhost:8080`), to żądanie **między źródłami** (cross-origin). Przeglądarka wpuści odpowiedź tylko wtedy, gdy serwer zezwoli na to nagłówkami CORS (`Access-Control-Allow-Origin`). Błąd CORS widzisz w konsoli, a w kodzie — jako `TypeError: Failed to fetch`. To ustawienie **serwera**, nie frontendu. W trakcie pracy omija się go proxy w Vite (rozdział 11), a w produkcji — serwując frontend i API z jednej domeny albo konfigurując CORS na backendzie.

#T STEP_BY_STEP Budujemy razem: kontrakt i adresy DevDesk
1. Utwórz katalog `src/api/` i plik `contract.js` (`.ts`) z opisem endpointów z lekcji.
2. W wersji TS dodaj typy `Page<T>`, `CreateTicketBody`, `UpdateTicketBody`, `ApiError`, `TicketListQuery`.
3. Napisz `ticketsUrl(query)` z `URLSearchParams` i sprawdź w konsoli wynik dla tekstu z polskimi znakami i spacją.
4. Otwórz dowolną stronę (np. publiczne API pogody) z narzędziami deweloperskimi i przeczytaj kilka żądań w zakładce Network według siedmiu punktów z listy.
5. Zapisz w `contract` decyzje: format dat (ISO), ID jako liczby, brak wartości jako `null`, błędy zawsze `{ message, fieldErrors? }`.
6. W następnej lekcji „podstawisz” pod ten kontrakt udawany serwer (MSW), żeby frontend mógł działać bez backendu.

#T PITFALL Sukces fetch to nie sukces żądania
`const res = await fetch(url); const data = await res.json();` — przy statusie 500 kod przejdzie dalej, a `data` będzie obiektem błędu (albo `res.json()` rzuci, bo serwer zwrócił HTML strony błędu). Zawsze sprawdzaj `res.ok` (status 200–299) i obsługuj błędy jawnie. Zrobisz to raz, w warstwie klienta API (lekcja 7).

#T SUMMARY Kryterium akceptacji i podsumowanie
REST: metody GET/POST/PATCH/PUT/DELETE na zasobach, kody statusu mówią, co pokazać w UI (400 — błędy pól, 401 — logowanie, 404 — brak zasobu, 409 — konflikt, 5xx — ogólny błąd z ponowieniem). `fetch` nie rzuca dla 4xx/5xx — sprawdzaj `res.ok`. Parametry zapytania budujesz przez `URLSearchParams`. CORS to ustawienie serwera. Kontrakt API ustalasz przed kodem; w TSX zapisujesz go jako typy, ale odpowiedzi i tak walidujesz w czasie działania.

Kryterium akceptacji: DevDesk ma w `src/api/` opis kontraktu (a w TS — typy kontraktu) oraz funkcję `ticketsUrl` poprawnie kodującą filtry, a Ty potrafisz odczytać w zakładce Network metodę, status, ciało i czas dowolnego żądania.
