#T INTRO Rozgrzewka i problem: tabela „mruga” przy zmianie strony
Rozgrzewka: Co robi `invalidateQueries` i jak działa klucz-przedrostek? Jakie kroki ma aktualizacja optymistyczna? Dlaczego mutacji nie wywołujesz w efekcie?

Problem: z TanStack Query każda nowa strona tabeli to nowy klucz zapytania — więc przy przejściu na stronę 2 przez chwilę nie ma danych i tabela znika, a pager „skacze”. Dodatkowo w panelu „Aktywność” (lista zdarzeń z całego systemu) użytkownicy wolą przewijać niż klikać numery stron — potrzebna jest **nieskończona lista** z doładowywaniem przy przewijaniu. Ta lekcja: płynna paginacja serwerowa, wstępne pobieranie następnej strony i `useInfiniteQuery`.

#T DEFINITION placeholderData: stare dane do czasu nowych
Opcja `placeholderData: keepPreviousData` (funkcja z biblioteki) sprawia, że przy zmianie klucza zapytania komponent nadal dostaje **dane z poprzedniego klucza**, dopóki nowe nie przyjdą. Pole `isPlaceholderData` mówi, że wyświetlasz dane zastępcze — możesz przyciemnić tabelę i zablokować przycisk „Następna”. To dokładnie to zachowanie „odświeżania”, które pisałeś ręcznie w lekcji 4.

**Wstępne pobieranie** (`queryClient.prefetchQuery`) następnej strony, gdy użytkownik ogląda bieżącą, sprawia, że kliknięcie „Następna” jest natychmiastowe.

#T CODE_JSX Płynna paginacja (JSX)
```
// useTicketPages.js
import { keepPreviousData, useQuery, useQueryClient } from '@tanstack/react-query';
import { useEffect } from 'react';
import { fetchTicketPage } from '../api/tickets';

export function useTicketPages(filters, page, pageSize = 10) {
  const queryClient = useQueryClient();
  const key = (p) => ['tickets', 'list', { ...filters, page: p, pageSize }];

  const query = useQuery({
    queryKey: key(page),
    queryFn: ({ signal }) => fetchTicketPage({ ...filters, page, pageSize }, signal),
    placeholderData: keepPreviousData,
  });

  const pageCount = query.data ? Math.max(1, Math.ceil(query.data.total / pageSize)) : 1;

  // wstępnie pobierz następną stronę (synchronizacja cache z bieżącą stroną)
  useEffect(() => {
    if (!query.isPlaceholderData && page < pageCount) {
      void queryClient.prefetchQuery({
        queryKey: key(page + 1),
        queryFn: ({ signal }) => fetchTicketPage({ ...filters, page: page + 1, pageSize }, signal),
      });
    }
  });

  return { ...query, pageCount };
}
```

#T CODE_TSX Płynna paginacja (TSX)
`isPlaceholderData` jest częścią wyniku — w TSX dostępne z podpowiedziami. Typ filtrów jest jawny, bo trafia do klucza i do API.
```
// useTicketPages.ts
import { keepPreviousData, useQuery, useQueryClient } from '@tanstack/react-query';
import { useEffect } from 'react';

type Filters = { status?: string; q?: string };
type Page<T> = { items: T[]; total: number };
declare function fetchTicketPage(params: Filters & { page: number; pageSize: number }, signal: AbortSignal): Promise<Page<{ id: number; title: string }>>;

export function useTicketPages(filters: Filters, page: number, pageSize = 10) {
  const queryClient = useQueryClient();
  const key = (p: number) => ['tickets', 'list', { ...filters, page: p, pageSize }] as const;

  const query = useQuery({
    queryKey: key(page),
    queryFn: ({ signal }) => fetchTicketPage({ ...filters, page, pageSize }, signal),
    placeholderData: keepPreviousData,
  });

  const pageCount = query.data ? Math.max(1, Math.ceil(query.data.total / pageSize)) : 1;

  useEffect(() => {
    if (!query.isPlaceholderData && page < pageCount) {
      void queryClient.prefetchQuery({
        queryKey: key(page + 1),
        queryFn: ({ signal }) => fetchTicketPage({ ...filters, page: page + 1, pageSize }, signal),
      });
    }
  });

  return { ...query, pageCount };
}
```

#T NOTE JSX ↔ TSX — efekt bez tablicy zależności
Efekt wstępnego pobierania nie ma tablicy zależności — uruchamia się po każdym renderze, a `prefetchQuery` sam nic nie robi, jeśli dane są w cache i świeże. To świadoma decyzja: lista zależności (filtry jako obiekt, funkcja `key`) byłaby długa i zmieniała się przy każdym renderze. Ten wzorzec działa identycznie w obu wersjach; TypeScript nie ma tu nic do powiedzenia, a ESLint nie zgłasza ostrzeżenia, bo efekt bez tablicy zależności jest poprawny składniowo. W TSX `as const` przy kluczu zachowuje dokładny typ krotki, z którego biblioteka wnioskuje typ danych w `setQueryData`.

#T DEFINITION useInfiniteQuery: lista doładowywana
`useInfiniteQuery` przechowuje **kolejne strony** jednej listy:
- `queryFn({ pageParam })` — pobiera stronę dla parametru (numer strony albo kursor z poprzedniej odpowiedzi),
- `initialPageParam` — parametr pierwszej strony,
- `getNextPageParam(ostatniaStrona)` — zwraca parametr następnej strony albo `undefined`, gdy to koniec,
- wynik: `data.pages` (tablica stron), `fetchNextPage()`, `hasNextPage`, `isFetchingNextPage`.

Paginacja **kursorem** („podaj elementy po ID 812”) jest lepsza od numerów stron dla list, do których ciągle dochodzą nowe elementy — numer strony przesuwa się wtedy i elementy się powtarzają.

#T CODE_BASIC Nieskończona lista aktywności
```
// useActivityFeed.ts
import { useInfiniteQuery } from '@tanstack/react-query';

type ActivityPage = { items: { id: number; text: string }[]; nextCursor: number | null };
declare function fetchActivity(cursor: number | null, signal: AbortSignal): Promise<ActivityPage>;

export function useActivityFeed() {
  return useInfiniteQuery({
    queryKey: ['activity'],
    queryFn: ({ pageParam, signal }) => fetchActivity(pageParam, signal),
    initialPageParam: null as number | null,
    getNextPageParam: (lastPage) => lastPage.nextCursor ?? undefined,
  });
}
```

#T CODE_PRACTICAL Doładowanie przy przewinięciu (Intersection Observer)
Niewidoczny element na końcu listy obserwowany przez `IntersectionObserver` — gdy wjedzie w widok, pobierz kolejną stronę. Zostaw też przycisk „Pokaż więcej” dla klawiatury i jako zapas.
```
import { useEffect, useRef } from 'react';
import { useActivityFeed } from './useActivityFeed';

export function ActivityFeed() {
  const feed = useActivityFeed();
  const sentinelRef = useRef<HTMLDivElement>(null);
  const { hasNextPage, isFetchingNextPage, fetchNextPage } = feed;

  useEffect(() => {
    const el = sentinelRef.current;
    if (!el) return;
    const observer = new IntersectionObserver(([entry]) => {
      if (entry.isIntersecting && hasNextPage && !isFetchingNextPage) void fetchNextPage();
    }, { rootMargin: '200px' });
    observer.observe(el);
    return () => observer.disconnect();
  }, [hasNextPage, isFetchingNextPage, fetchNextPage]);

  if (feed.isPending) return <p>Ładowanie aktywności…</p>;
  if (feed.isError) return <p role="alert">Nie udało się wczytać aktywności.</p>;

  return (
    <section aria-label="Aktywność">
      <ul>{feed.data.pages.flatMap((p) => p.items).map((it) => <li key={it.id}>{it.text}</li>)}</ul>
      <div ref={sentinelRef} />
      {hasNextPage ? (
        <button type="button" disabled={isFetchingNextPage} onClick={() => void fetchNextPage()}>
          {isFetchingNextPage ? 'Wczytywanie…' : 'Pokaż więcej'}
        </button>
      ) : (
        <p>To już wszystko.</p>
      )}
    </section>
  );
}
```

#T STEP_BY_STEP Budujemy razem: płynna tabela i panel aktywności
1. Przepisz tabelę na `useTicketPages` z `placeholderData: keepPreviousData`; przy `isPlaceholderData` przyciemnij tabelę i zablokuj „Następna”.
2. Dodaj wstępne pobieranie następnej strony; w Network zobaczysz żądanie strony 2 zaraz po wyświetleniu strony 1, a kliknięcie „Następna” nie wysyła nic nowego.
3. Dodaj w MSW endpoint `GET /api/activity?cursor=` zwracający po 20 zdarzeń i `nextCursor` (ID ostatniego elementu albo `null` na końcu, np. po 120 zdarzeniach).
4. Zbuduj `ActivityFeed` z `useInfiniteQuery` i obserwatorem przewijania w zakładce „Aktywność” karty lub w osobnym panelu.
5. Przewiń do końca — kolejne strony doładowują się same; na końcu widać „To już wszystko”.
6. Sprawdź klawiaturą: przycisk „Pokaż więcej” działa niezależnie od przewijania.
7. Zmień filtr tabeli na stronie 5 — strona wraca na 1 (handler), a placeholder pokazuje poprzednie dane do czasu nowych.

#T PITFALL Nieskończona lista bez końca pamięci
Przy tysiącach doładowanych elementów DOM rośnie, przewijanie zwalnia, a cache trzyma wszystkie strony. Rozwiązania: ograniczenie liczby przechowywanych stron (opcja `maxPages` w `useInfiniteQuery`), wirtualizacja listy (rozdział 16) albo powrót do zwykłej paginacji dla danych, które ktoś przegląda wyrywkowo (tabela ticketów z filtrami). Nieskończona lista pasuje do „strumieni” (aktywność, powiadomienia), a nie do tabel.

#T SUMMARY Kryterium akceptacji i podsumowanie
`placeholderData: keepPreviousData` pokazuje poprzednią stronę do czasu nowej (`isPlaceholderData` pozwala ją przyciemnić), a `prefetchQuery` pobiera następną z wyprzedzeniem. `useInfiniteQuery` przechowuje kolejne strony (`data.pages`) z parametrem z `getNextPageParam` — najlepiej kursorem — i udostępnia `fetchNextPage`, `hasNextPage`, `isFetchingNextPage`. Doładowanie przy przewijaniu robisz `IntersectionObserver` z przyciskiem „Pokaż więcej” jako alternatywą. W TSX `initialPageParam` z typem określa typ `pageParam`.

Kryterium akceptacji: zmiana strony tabeli nie powoduje znikania danych, kliknięcie „Następna” jest natychmiastowe dzięki wstępnemu pobieraniu, a panel „Aktywność” doładowuje zdarzenia przy przewijaniu i przyciskiem, kończąc komunikatem „To już wszystko”.
