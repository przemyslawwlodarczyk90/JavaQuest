#T INTRO Rozgrzewka i problem: ręczne pobieranie ma granice
Rozgrzewka: Za co odpowiada klient API? Dlaczego w TSX `request` ze schematem nie potrzebuje rzutowania `as`? Jak zamienić dowolny błąd w komunikat dla użytkownika?

Problem: ręczny `useAsync` działa, ale lista problemów rośnie: po powrocie z karty szczegółów do tabeli dane ładują się od nowa (brak pamięci podręcznej), dwa komponenty potrzebujące tego samego ticketu wysyłają dwa żądania, dane nie odświeżają się po powrocie do karty przeglądarki, nie ma automatycznego ponawiania po chwilowym błędzie, zależności efektu są wyciszone. To wszystko są problemy **stanu serwera** — i właśnie dla nich powstała biblioteka **TanStack Query** (dawniej React Query).

#T DEFINITION Stan serwera to nie stan UI
**Stan UI** (otwarty modal, tekst w wyszukiwarce, zaznaczony wiersz) należy do przeglądarki — Ty jesteś jego właścicielem. **Stan serwera** (tickety, użytkownicy) należy do serwera: w przeglądarce masz tylko **kopię z pewnej chwili**, która może być nieaktualna, którą dzielą różne ekrany i którą trzeba odświeżać. TanStack Query zarządza tą kopią:
- **cache** — wyniki zapytań są zapamiętane pod **kluczem zapytania** (`['tickets', { status, page }]`),
- **deduplikacja** — wiele komponentów z tym samym kluczem = jedno żądanie,
- **świeżość** — dane są „świeże” przez `staleTime`; nieświeże są odświeżane w tle (przy montowaniu, powrocie do karty, odzyskaniu sieci),
- **ponawianie** — nieudane zapytania są automatycznie ponawiane (domyślnie 3 razy z rosnącym odstępem),
- **sprzątanie** — nieużywane dane są usuwane z cache po `gcTime` (domyślnie 5 minut).

#T STEP_BY_STEP Instalacja i konfiguracja
1. `npm install @tanstack/react-query` oraz narzędzia: `npm install -D @tanstack/react-query-devtools`.
2. Utwórz jeden `QueryClient` na poziomie modułu (nie w komponencie — inaczej cache znikałby przy renderze).
3. Opakuj aplikację w `<QueryClientProvider client={queryClient}>` (najlepiej w `AppProviders`).
4. Dodaj `<ReactQueryDevtools />` w trybie deweloperskim — w rogu ekranu pojawi się panel z listą zapytań, ich kluczami i stanem.

#T CODE_JSX Konfiguracja klienta i pierwsze zapytanie (JSX)
```
// queryClient.js
import { QueryClient } from '@tanstack/react-query';

export const queryClient = new QueryClient({
  defaultOptions: {
    queries: { staleTime: 30_000 }, // dane świeże przez 30 s
  },
});

// TicketsPage.jsx
import { useQuery } from '@tanstack/react-query';
import { fetchTickets } from '../api/tickets';

export function TicketsPage({ status, page }) {
  const query = useQuery({
    queryKey: ['tickets', { status, page }],
    queryFn: ({ signal }) => fetchTickets(new URLSearchParams({ status, page: String(page) }).toString(), signal),
  });

  if (query.isPending) return <p>Ładowanie…</p>;
  if (query.isError) return <p role="alert">Błąd: {query.error.message}</p>;

  return (
    <>
      {query.isFetching && <small role="status">Odświeżanie…</small>}
      <ul>{query.data.items.map((t) => <li key={t.id}>{t.title}</li>)}</ul>
    </>
  );
}
```

#T CODE_TSX Konfiguracja klienta i pierwsze zapytanie (TSX)
Typ `data` wynika z typu zwracanego przez `queryFn` (u nas — ze schematu Zod w kliencie API). Po sprawdzeniu `isPending` i `isError` TypeScript wie, że `data` jest zdefiniowane.
```
// TicketsPage.tsx
import { QueryClient, useQuery } from '@tanstack/react-query';
import { z } from 'zod';

export const queryClient = new QueryClient({
  defaultOptions: { queries: { staleTime: 30_000 } },
});

const pageSchema = z.object({ items: z.array(z.object({ id: z.number(), title: z.string() })), total: z.number() });

async function fetchTickets(qs: string, signal: AbortSignal) {
  const res = await fetch(`/api/tickets?${qs}`, { signal });
  if (!res.ok) throw new Error(`Błąd ${res.status}`);
  return pageSchema.parse(await res.json());
}

export function TicketsPage({ status, page }: { status: string; page: number }) {
  const query = useQuery({
    queryKey: ['tickets', { status, page }],
    queryFn: ({ signal }) => fetchTickets(new URLSearchParams({ status, page: String(page) }).toString(), signal),
  });

  if (query.isPending) return <p>Ładowanie…</p>;
  if (query.isError) return <p role="alert">Błąd: {query.error.message}</p>;

  return (
    <>
      {query.isFetching && <small role="status">Odświeżanie…</small>}
      <ul>{query.data.items.map((t) => <li key={t.id}>{t.title}</li>)}</ul>
    </>
  );
}
```

#T NOTE JSX ↔ TSX — inferencja typu z queryFn
Nie piszesz `useQuery<Page<Ticket>>` — TypeScript wnioskuje typ `data` z `queryFn`, więc jeśli funkcja zwraca dane zwalidowane schematem, `query.data` ma dokładnie ten typ. Stany w TanStack Query to unia z dyskryminatorem (`status: 'pending' | 'error' | 'success'`), dlatego po `if (query.isPending) return` i `if (query.isError) return` `query.data` nie jest już `undefined` — to ta sama technika co w Twoim `AsyncState` z lekcji 4. W JSX `query.data.items` przed sprawdzeniem stanów da wyjątek przy pierwszym renderze.

#T API_REFERENCE Najważniejsze pola i opcje useQuery
Wynik:
- `data`, `error`, `status` (`'pending' | 'error' | 'success'`), `isPending`, `isError`, `isSuccess`,
- `isFetching` — trwa jakiekolwiek pobieranie (także odświeżanie w tle), `isLoading` — pierwsze pobieranie (`isPending && isFetching`),
- `refetch()` — ręczne odświeżenie.

Opcje:
- `queryKey` — tablica jednoznacznie opisująca dane (zmiana klucza = nowe zapytanie),
- `queryFn` — funkcja pobierająca; dostaje `{ signal, queryKey }` — przekaż `signal` do `fetch`, a przestarzałe żądania będą przerywane,
- `staleTime` — jak długo dane są świeże (domyślnie 0),
- `gcTime` — jak długo przechowywać nieużywane dane (domyślnie 5 min),
- `enabled` — `false` wstrzymuje zapytanie (np. dopóki nie ma ID),
- `retry`, `retryDelay` — ponawianie (np. `retry: (count, error) => error.status !== 404 && count < 3`),
- `refetchOnWindowFocus`, `refetchInterval` — odświeżanie przy powrocie do karty, cykliczne,
- `select` — przekształcenie danych dla komponentu (np. tylko liczba ticketów).

#T DEFINITION Klucze zapytań i fabryka kluczy
Klucz zapytania to **tożsamość danych**: wszystko, od czego zależy wynik `queryFn`, musi być w kluczu (status, strona, wyszukiwany tekst, ID). Tak jak zależności efektu — ale biblioteka porównuje je głęboko, więc obiekty w kluczu są w porządku. Żeby nie pisać kluczy ręcznie w wielu miejscach, trzymaj je w jednej **fabryce kluczy** — przyda się przy unieważnianiu cache w następnej lekcji.

#T CODE_BASIC Fabryka kluczy i własne hooki zapytań
```
import { useQuery } from '@tanstack/react-query';

type TicketFilters = { status?: string; q?: string; page: number };

declare function fetchTicketPage(filters: TicketFilters, signal: AbortSignal): Promise<{ items: { id: number; title: string }[]; total: number }>;
declare function fetchTicketById(id: number, signal: AbortSignal): Promise<{ id: number; title: string; description: string }>;

export const ticketKeys = {
  all: ['tickets'] as const,
  lists: () => [...ticketKeys.all, 'list'] as const,
  list: (filters: TicketFilters) => [...ticketKeys.lists(), filters] as const,
  detail: (id: number) => [...ticketKeys.all, 'detail', id] as const,
};

export function useTicketList(filters: TicketFilters) {
  return useQuery({ queryKey: ticketKeys.list(filters), queryFn: ({ signal }) => fetchTicketPage(filters, signal) });
}

export function useTicketDetail(id: number | null) {
  return useQuery({
    queryKey: ticketKeys.detail(id ?? -1),
    queryFn: ({ signal }) => fetchTicketById(id!, signal),
    enabled: id !== null,
  });
}
```

#T CODE_PRACTICAL Dwa komponenty, jedno żądanie
Nagłówek i karta czytają ten sam ticket — jedno żądanie, wspólny cache. Po powrocie do ticketu w ciągu `staleTime` dane pojawiają się natychmiast.
```
import { useTicketDetail } from './ticketQueries';

export function TicketHeader({ id }: { id: number }) {
  const { data } = useTicketDetail(id);
  return <h2>{data ? `#${data.id} ${data.title}` : '…'}</h2>;
}

export function TicketBody({ id }: { id: number }) {
  const { data, isPending } = useTicketDetail(id);
  if (isPending) return <p>Ładowanie…</p>;
  return <p>{data?.description}</p>;
}
```

#T STEP_BY_STEP Budujemy razem: DevDesk na TanStack Query
1. Zainstaluj bibliotekę i devtools, utwórz `queryClient` z `staleTime: 30_000`, dodaj `QueryClientProvider` do `AppProviders` i `ReactQueryDevtools`.
2. Utwórz `queries/tickets` z fabryką `ticketKeys` oraz hookami `useTicketList(filters)` i `useTicketDetail(id)` korzystającymi z klienta API.
3. Zastąp `useAsync` w tabeli przez `useTicketList` — komponent `TicketsView` z lekcji 4 dostosuj do pól `isPending`, `isError`, `isFetching`.
4. Zastąp `useTicket` w karcie szczegółów przez `useTicketDetail(selectedId)` z `enabled`.
5. Sprawdź cache: przełącz stronę 1 → 2 → 1 — strona 1 pojawia się od razu (z cache), a w Network nie ma nowego żądania, dopóki dane są świeże.
6. Przełącz kartę przeglądarki i wróć po 30 s — dane odświeżają się w tle (widać „Odświeżanie…”).
7. Ustaw `?scenario=error` — biblioteka ponawia żądanie 3 razy (widać w Network) i dopiero wtedy pokazuje błąd; dla 404 wyłącz ponawianie opcją `retry`.
8. Usuń `useAsync` i jego wyciszenie lintera — nie jest już potrzebny.

#T PITFALL Kopiowanie danych z zapytania do stanu
`const { data } = useQuery(...); const [tickets, setTickets] = useState([]); useEffect(() => { if (data) setTickets(data.items); }, [data]);` — tworzysz drugą prawdę, która nie odświeża się razem z cache i omija wszystkie mechanizmy biblioteki. Dane z zapytania używasz bezpośrednio (`data.items`), a zmiany robisz mutacjami (następna lekcja). Przekształcenia — przez `select` lub zwykłe obliczenia w renderze.

#T SUMMARY Kryterium akceptacji i podsumowanie
Stan serwera to kopia danych serwera w przeglądarce: TanStack Query trzyma ją w cache pod kluczem zapytania, deduplikuje żądania, odświeża nieświeże dane w tle, ponawia błędy i sprząta nieużywane wpisy. `useQuery({ queryKey, queryFn })` zwraca `data`, `error`, `isPending`, `isError`, `isFetching`; `queryFn` dostaje `signal`. Wszystko, od czego zależą dane, musi być w kluczu — klucze trzymaj w fabryce. W TSX typ `data` wynika z `queryFn`, a stany zawężają typ jak unia.

Kryterium akceptacji: tabela i karta szczegółów DevDesk korzystają z `useQuery` przez własne hooki z fabryką kluczy, powrót do odwiedzonej strony jest natychmiastowy, dane odświeżają się w tle po powrocie do karty przeglądarki, a w devtools widać zapytania z ich kluczami i stanem.
