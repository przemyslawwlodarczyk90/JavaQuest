#T INTRO Rozgrzewka i problem: UI zależny od danych
Rozgrzewka: Co można wstawić w `{ }` w JSX, a czego nie? Jak zapisać atrybut `class` i `for` w JSX? Co wyświetli `{false}`, a co `{0}`?

Problem: ticket bez przypisanej osoby ma pokazywać „Nieprzypisany” zamiast pustego miejsca, pilne tickety mają mieć ikonę ostrzeżenia, a gdy lista jest pusta — komunikat „Brak ticketów”. Wszystko to jest renderowaniem warunkowym: różny JSX w zależności od danych.

#T DEFINITION Cztery sposoby renderowania warunkowego
1. **`if` z wczesnym `return`** — gdy cały komponent wygląda inaczej (np. „brak danych”),
2. **operator `?:`** — wybór jednej z dwóch wersji wewnątrz JSX,
3. **operator `&&`** — „pokaż albo nic”,
4. **zmienna lub obiekt-mapa** — gdy wariantów jest więcej niż dwa.

Komponent może też zwrócić `null` — wtedy nie renderuje nic.

#T CODE_JSX Karta ticketu z warunkami
```
// TicketCard.jsx
export function TicketCard({ ticket }) {
  if (!ticket) {
    return <p className="empty">Wybierz ticket z listy</p>;
  }

  const isUrgent = ticket.priority === 'CRITICAL' || ticket.priority === 'HIGH';

  return (
    <article className="ticket-card">
      <h3>
        {isUrgent && <span aria-label="pilne">⚠️ </span>}
        #{ticket.id} {ticket.title}
      </h3>
      <p>{ticket.assignee ? `Przypisany: ${ticket.assignee}` : 'Nieprzypisany'}</p>
      {ticket.tags.length > 0 && <p>Tagi: {ticket.tags.join(', ')}</p>}
    </article>
  );
}
```

#T CODE_TSX Karta ticketu z warunkami w TSX
`ticket: Ticket | null` mówi wprost: komponent może nie dostać ticketu. Po `if (!ticket) return` TypeScript zawęża typ i w dalszej części `ticket` jest już `Ticket`.
```
// TicketCard.tsx
import type { Ticket } from '../types';

export function TicketCard({ ticket }: { ticket: Ticket | null }) {
  if (!ticket) {
    return <p className="empty">Wybierz ticket z listy</p>;
  }

  const isUrgent = ticket.priority === 'CRITICAL' || ticket.priority === 'HIGH';

  return (
    <article className="ticket-card">
      <h3>
        {isUrgent && <span aria-label="pilne">⚠️ </span>}
        #{ticket.id} {ticket.title}
      </h3>
      <p>{ticket.assignee ? `Przypisany: ${ticket.assignee}` : 'Nieprzypisany'}</p>
      {ticket.tags.length > 0 && <p>Tagi: {ticket.tags.join(', ')}</p>}
    </article>
  );
}
```

#T NOTE JSX ↔ TSX — zawężanie typu w gałęziach
To, co w JSX jest tylko dobrym nawykiem, w TSX jest wymuszone. Bez warunku `if (!ticket)` wersja TSX nie skompiluje się: „'ticket' is possibly 'null'”. Wersja JSX skompiluje się i wybuchnie w przeglądarce błędem „Cannot read properties of null (reading 'priority')”, gdy nic nie będzie wybrane. Podobnie z `ticket.assignee` — TS wie, że to `string | null`, i w gałęzi `?` po sprawdzeniu wie, że to `string`.

#T PITFALL Liczba 0 przed &&
`{count && <Badge />}` przy `count === 0` wyświetli na ekranie cyfrę „0”. Operator `&&` zwraca lewą stronę, gdy jest fałszywa, a React renderuje liczby (także zero). `false`, `null` i `undefined` nie są renderowane, ale `0` i `NaN` — są.

#T CODE_WRONG Zero wyświetlone na ekranie
```
export function UnreadBadge({ count }) {
  return <span>Komentarze {count && <b>({count} nowe)</b>}</span>;
  // count = 0 → „Komentarze 0”
}
```

#T CODE_RIGHT Jawny warunek logiczny
```
export function UnreadBadge({ count }) {
  return <span>Komentarze {count > 0 && <b>({count} nowe)</b>}</span>;
}
```

#T DEFINITION Wiele wariantów: obiekt zamiast łańcucha warunków
Gdy wariantów jest więcej niż dwa, zagnieżdżone `?:` stają się nieczytelne. Lepiej przygotować obiekt-mapę „wartość → JSX/tekst” albo osobną zmienną obliczoną przed `return`.

#T CODE_JSX Ikona statusu przez mapę
```
// StatusIcon.jsx
const ICONS = {
  OPEN: '🟢',
  IN_PROGRESS: '🟡',
  CLOSED: '⚪',
};

export function StatusIcon({ status }) {
  return <span title={status}>{ICONS[status] ?? '❔'}</span>;
}
```

#T CODE_TSX Ikona statusu przez Record
`Record<TicketStatus, string>` gwarantuje ikonę dla każdego statusu, więc zapasowe `?? '❔'` nie jest potrzebne.
```
// StatusIcon.tsx
import type { TicketStatus } from '../types';

const ICONS: Record<TicketStatus, string> = {
  OPEN: '🟢',
  IN_PROGRESS: '🟡',
  CLOSED: '⚪',
};

export function StatusIcon({ status }: { status: TicketStatus }) {
  return <span title={status}>{ICONS[status]}</span>;
}
```

#T STEP_BY_STEP Budujemy razem: panel szczegółów ticketu
1. Utwórz `components/TicketCard.jsx` (`.tsx`) według przykładu.
2. W `Main` wyrenderuj `<TicketCard ticket={tickets[0]} />` — pokazuje się pierwszy ticket.
3. Zmień na `<TicketCard ticket={null} />` — pojawia się „Wybierz ticket z listy”.
4. Dodaj komponent `StatusIcon` i wstaw go w nagłówku karty przed tytułem.
5. Ustaw w danych ticket bez tagów (`tags: []`) i bez osoby (`assignee: null`) — sprawdź, że karta nie pokazuje pustej linii „Tagi:” i wyświetla „Nieprzypisany”.
6. Dodaj licznik komentarzy `UnreadBadge` i sprawdź zachowanie dla `count={0}` — na ekranie nie może być zera.

#T WHEN_TO_USE Który zapis wybrać
- Cały komponent wygląda inaczej (brak danych, ładowanie, błąd) → `if` i wczesny `return`.
- Jedna z dwóch wersji fragmentu → `?:`.
- Fragment pokazany albo nie → `&&` z jawnym warunkiem logicznym (`> 0`, `!== null`, `Boolean(...)`).
- Trzy i więcej wariantów → obiekt-mapa albo zmienna liczona przed `return`.
- Element tylko ukryty, ale nadal w DOM (np. dla animacji) → atrybut `hidden` albo klasa CSS, a nie warunek.

#T SUMMARY Kryterium akceptacji i podsumowanie
Renderowanie warunkowe w React to zwykły JavaScript: `if` z wczesnym `return`, `?:`, `&&` i obiekty-mapy. Uważaj na `0 && ...`. W TSX typ `Ticket | null` wymusza obsługę braku danych, a `Record<TicketStatus, ...>` pilnuje kompletności wariantów.

Kryterium akceptacji: karta ticketu pokazuje komunikat przy braku ticketu, ikonę ostrzeżenia tylko dla pilnych, „Nieprzypisany” przy `assignee: null`, nie pokazuje pustej linii tagów i nigdy nie wyświetla samotnego „0”.
