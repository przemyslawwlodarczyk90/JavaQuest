#T INTRO Rozgrzewka i problem: status jako kolorowa plakietka
Rozgrzewka: Czym są props i dlaczego są tylko do odczytu? Jak przekazać do komponentu liczbę, a jak tekst?

Problem: w tabeli ticketów status jest teraz zwykłym tekstem „IN_PROGRESS”. Chcemy kolorowych plakietek (badge): zielona „Otwarty”, żółta „W toku”, szara „Zamknięty” — i podobnych dla priorytetów. To przykład komponentu z **wariantami**: jeden komponent, kilka wyglądów sterowanych przez props.

#T DEFINITION Komponent z wariantami
Wariant to prop, który zmienia wygląd lub zachowanie komponentu, np. `variant`, `size`, `tone`. Komponent tłumaczy wariant na klasę CSS (albo styl) i zachowuje jednolity wygląd w całej aplikacji. Zamiast pisać w każdym miejscu `<span className="badge badge--green">`, piszesz `<Badge tone="success">`. To pierwszy krok do własnego „design systemu”.

#T CODE_JSX Badge i StatusBadge w JSX
Badge jest ogólny (ton + treść). StatusBadge zna statusy ticketów i tłumaczy je na ton i etykietę.
```
// Badge.jsx
export function Badge({ tone = 'neutral', size = 'md', children }) {
  return <span className={`badge badge--${tone} badge--${size}`}>{children}</span>;
}

// StatusBadge.jsx
const STATUS_VIEW = {
  OPEN: { tone: 'success', label: 'Otwarty' },
  IN_PROGRESS: { tone: 'warning', label: 'W toku' },
  CLOSED: { tone: 'neutral', label: 'Zamknięty' },
};

export function StatusBadge({ status }) {
  const view = STATUS_VIEW[status];
  return <Badge tone={view.tone}>{view.label}</Badge>;
}
```

#T CODE_TSX Badge i StatusBadge w TSX
Unie literałów dla `tone` i `size`, a `Record<TicketStatus, ...>` wymusza opis każdego statusu.
```
// Badge.tsx
import type { ReactNode } from 'react';
import type { TicketStatus } from '../types';

type Tone = 'neutral' | 'success' | 'warning' | 'danger';

type BadgeProps = {
  tone?: Tone;
  size?: 'sm' | 'md';
  children: ReactNode;
};

export function Badge({ tone = 'neutral', size = 'md', children }: BadgeProps) {
  return <span className={`badge badge--${tone} badge--${size}`}>{children}</span>;
}

const STATUS_VIEW: Record<TicketStatus, { tone: Tone; label: string }> = {
  OPEN: { tone: 'success', label: 'Otwarty' },
  IN_PROGRESS: { tone: 'warning', label: 'W toku' },
  CLOSED: { tone: 'neutral', label: 'Zamknięty' },
};

export function StatusBadge({ status }: { status: TicketStatus }) {
  const view = STATUS_VIEW[status];
  return <Badge tone={view.tone}>{view.label}</Badge>;
}
```

#T NOTE JSX ↔ TSX — unie literałów w props
To jeden z najbardziej praktycznych zysków TypeScriptu w React. Pisząc `<Badge tone="` edytor pokaże listę `neutral | success | warning | danger`. `tone="succes"` to błąd kompilacji, a w JSX — plakietka bez koloru i klasa `badge--succes`, której nikt nie zauważy w code review. Druga korzyść: gdy dodasz do typu `TicketStatus` status `'BLOCKED'`, TypeScript zgłosi, że w `STATUS_VIEW` brakuje jego opisu — w JSX dowiesz się o tym z błędu „Cannot read properties of undefined (reading 'tone')” w przeglądarce.

#T CODE_PRACTICAL PriorityBadge — ten sam wzorzec dla priorytetu
```
import type { TicketPriority } from '../types';
import { Badge } from './Badge';

const PRIORITY_VIEW = {
  LOW: { tone: 'neutral', label: 'Niski' },
  MEDIUM: { tone: 'neutral', label: 'Średni' },
  HIGH: { tone: 'warning', label: 'Wysoki' },
  CRITICAL: { tone: 'danger', label: 'Krytyczny' },
} as const satisfies Record<TicketPriority, { tone: 'neutral' | 'success' | 'warning' | 'danger'; label: string }>;

export function PriorityBadge({ priority }: { priority: TicketPriority }) {
  const view = PRIORITY_VIEW[priority];
  return <Badge tone={view.tone} size="sm">{view.label}</Badge>;
}
```

#T NOTE Słowo satisfies
W przykładzie PriorityBadge użyto `satisfies` — sprawdza, czy obiekt pasuje do typu (każdy priorytet opisany, ton z dozwolonej listy), ale nie „poszerza” typu obiektu. Dzięki `as const` TypeScript pamięta dokładne wartości. To wygodna alternatywa dla adnotacji `: Record<...>`; oba zapisy są poprawne.

#T STEP_BY_STEP Budujemy razem: plakietki w DevDesk
1. Utwórz `components/Badge.jsx` (`.tsx`) i dopisz style wariantów do `App.css`.
2. Utwórz `StatusBadge` i `PriorityBadge` korzystające z `Badge`.
3. W karcie ticketu (`TicketCard`) zastąp tekst statusu komponentem `<StatusBadge status={ticket.status} />` i dodaj `<PriorityBadge priority={ticket.priority} />`.
4. Wyrenderuj pod kartą wszystkie warianty `Badge` obok siebie (tymczasowa „ściąga” wyglądu) i sprawdź kolory.
5. W wersji TS dodaj na próbę `'BLOCKED'` do `TicketStatus` w `types.ts` — zobacz błąd w `STATUS_VIEW`, dodaj opis albo cofnij zmianę.
6. W wersji JS zrób to samo i otwórz ticket ze statusem `'BLOCKED'` — zobacz błąd w konsoli przeglądarki. Porównaj, kiedy wykryłeś problem w każdej wersji.

#T PITFALL Logika domeny w ogólnym komponencie
Gdy `Badge` zaczyna znać statusy ticketów (`if (status === 'OPEN') ...`), przestaje być ogólny — nie użyjesz go dla ról użytkowników. Trzymaj podział: komponent ogólny (`Badge`: ton, rozmiar, treść) i cienki komponent domenowy (`StatusBadge`: tłumaczy status na ton i etykietę).

#T CODE_WRONG Ogólny komponent zna domenę
```
export function Badge({ status }) {
  const tone = status === 'OPEN' ? 'success' : status === 'IN_PROGRESS' ? 'warning' : 'neutral';
  return <span className={`badge badge--${tone}`}>{status}</span>;
}
```

#T CODE_RIGHT Ogólny komponent + komponent domenowy
```
export function Badge({ tone = 'neutral', children }) {
  return <span className={`badge badge--${tone}`}>{children}</span>;
}

export function StatusBadge({ status }) {
  const tone = status === 'OPEN' ? 'success' : status === 'IN_PROGRESS' ? 'warning' : 'neutral';
  return <Badge tone={tone}>{status}</Badge>;
}
```

#T SUMMARY Kryterium akceptacji i podsumowanie
Warianty (`tone`, `size`, `variant`) to props sterujące wyglądem; komponent zamienia je na klasy CSS. Dziel komponenty na ogólne (Badge) i domenowe (StatusBadge, PriorityBadge). W TSX unie literałów dają podpowiedzi i błędy przy literówkach, a `Record` pilnuje, żeby każdy status miał swój opis.

Kryterium akceptacji: karta ticketu pokazuje kolorowe plakietki statusu i priorytetu, wszystkie budowane z jednego komponentu `Badge`, a wersja TS zgłasza błąd po dodaniu nowego statusu bez opisu.
