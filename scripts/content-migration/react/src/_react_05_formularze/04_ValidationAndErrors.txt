#T INTRO Rozgrzewka i problem: ticket z tytułem „a”
Rozgrzewka: Czym różni się `defaultValue` od `value`? Co zwraca `FormData.get` dla niezaznaczonego checkboxa? Kiedy wybierasz pole niekontrolowane?

Problem: formularz nowego ticketu przyjmuje wszystko — pusty tytuł, tytuł „a”, przypisanie do nieistniejącej osoby, szacowany czas −5 godzin. Walidacja HTML pomaga tylko częściowo i pokazuje komunikaty w stylu przeglądarki. Potrzebujesz własnej walidacji: zasady w jednym miejscu, komunikaty przy polach, dostępność dla czytników ekranu i rozsądny moment pokazywania błędów.

#T DEFINITION Walidacja jako funkcja danych
Najprostszy i najczystszy model: funkcja `validate(values)` dostaje wartości formularza i zwraca obiekt błędów — klucz to nazwa pola, wartość to komunikat. Pusty obiekt oznacza poprawny formularz. Błędy **nie są stanem** — wyliczasz je z wartości przy każdym renderze (to dane wyliczane z rozdziału 04). Stanem jest tylko informacja, *które* błędy pokazać: czy użytkownik dotknął pola (`touched`) albo próbował wysłać formularz (`submitted`).

#T CODE_JSX Funkcja walidacji (JSX)
```
// validateTicket.js
const PEOPLE = ['anna', 'piotr', 'kasia'];

export function validateTicket(values) {
  const errors = {};
  const title = values.title.trim();

  if (!title) errors.title = 'Tytuł jest wymagany.';
  else if (title.length < 5) errors.title = 'Tytuł musi mieć co najmniej 5 znaków.';
  else if (title.length > 120) errors.title = 'Tytuł może mieć najwyżej 120 znaków.';

  if (values.assignee !== null && !PEOPLE.includes(values.assignee)) {
    errors.assignee = 'Wybierz osobę z listy.';
  }
  if (values.estimateHours !== '' && values.estimateHours < 0) {
    errors.estimateHours = 'Czas nie może być ujemny.';
  }
  if (values.priority === 'CRITICAL' && !values.description.trim()) {
    errors.description = 'Ticket krytyczny wymaga opisu.';
  }
  return errors;
}
```

#T CODE_TSX Funkcja walidacji (TSX)
Typ błędów wyprowadzony z typu wartości: `Partial<Record<keyof Values, string>>` — błąd można przypisać tylko istniejącemu polu.
```
// validateTicket.ts
import type { TicketPriority } from '../types';

export type TicketFormValues = {
  title: string;
  description: string;
  priority: TicketPriority;
  assignee: string | null;
  estimateHours: number | '';
};

export type FormErrors<T> = Partial<Record<keyof T, string>>;

const PEOPLE = ['anna', 'piotr', 'kasia'];

export function validateTicket(values: TicketFormValues): FormErrors<TicketFormValues> {
  const errors: FormErrors<TicketFormValues> = {};
  const title = values.title.trim();

  if (!title) errors.title = 'Tytuł jest wymagany.';
  else if (title.length < 5) errors.title = 'Tytuł musi mieć co najmniej 5 znaków.';
  else if (title.length > 120) errors.title = 'Tytuł może mieć najwyżej 120 znaków.';

  if (values.assignee !== null && !PEOPLE.includes(values.assignee)) {
    errors.assignee = 'Wybierz osobę z listy.';
  }
  if (values.estimateHours !== '' && values.estimateHours < 0) {
    errors.estimateHours = 'Czas nie może być ujemny.';
  }
  if (values.priority === 'CRITICAL' && !values.description.trim()) {
    errors.description = 'Ticket krytyczny wymaga opisu.';
  }
  return errors;
}
```

#T NOTE JSX ↔ TSX — błędy przypisane do pól
W TSX `errors.titel = '...'` jest błędem kompilacji, bo `titel` nie należy do `keyof TicketFormValues`. W JSX taki błąd byłby zapisany, ale nigdy nie wyświetlony przy żadnym polu — formularz „przepuściłby” niepoprawny tytuł. Zwróć też uwagę na `values.estimateHours < 0`: w TSX porównanie jest dozwolone dopiero po wykluczeniu `''` (zawężenie typu `number | ''` do `number`). Typ `FormErrors<T>` jest generyczny — użyjesz go w każdym formularzu.

#T DEFINITION Kiedy pokazywać błędy
- **Od razu przy każdym znaku** — irytujące: „Tytuł musi mieć 5 znaków” pojawia się po wpisaniu pierwszej litery.
- **Po opuszczeniu pola (blur)** — dobry kompromis: użytkownik kończy pisać, przechodzi dalej i dopiero wtedy widzi problem.
- **Po próbie wysłania** — wszystkie błędy naraz, fokus przenoszony na pierwsze błędne pole.

Typowy wzorzec: pokazuj błąd pola, gdy `touched[pole] || submitted`. Gdy błąd już się pojawił, znika natychmiast po poprawieniu (bo błędy liczysz przy każdym renderze).

#T CODE_PRACTICAL Pole z komunikatem i dostępnością
`aria-invalid` informuje czytnik ekranu, że pole jest błędne, a `aria-describedby` wiąże pole z komunikatem — czytnik odczyta go po nazwie pola. `useId` daje stabilne, unikalne identyfikatory.
```
// TextField.tsx
import { useId, type ChangeEvent } from 'react';

type TextFieldProps = {
  label: string;
  value: string;
  error?: string;
  onChange: (value: string) => void;
  onBlur?: () => void;
};

export function TextField({ label, value, error, onChange, onBlur }: TextFieldProps) {
  const id = useId();
  const errorId = `${id}-error`;
  return (
    <div className="field">
      <label htmlFor={id}>{label}</label>
      <input
        id={id}
        value={value}
        onChange={(e: ChangeEvent<HTMLInputElement>) => onChange(e.target.value)}
        onBlur={onBlur}
        aria-invalid={error ? true : undefined}
        aria-describedby={error ? errorId : undefined}
      />
      {error && <p id={errorId} className="field__error" role="alert">{error}</p>}
    </div>
  );
}
```

#T CODE_BASIC Formularz z touched i submitted
```
import { useState } from 'react';
import { validateTicket, type TicketFormValues } from './validateTicket';
import { TextField } from './TextField';

const INITIAL: TicketFormValues = { title: '', description: '', priority: 'MEDIUM', assignee: null, estimateHours: '' };

export function ValidatedTicketForm({ onCreate }: { onCreate: (v: TicketFormValues) => void }) {
  const [values, setValues] = useState(INITIAL);
  const [touched, setTouched] = useState<Partial<Record<keyof TicketFormValues, boolean>>>({});
  const [submitted, setSubmitted] = useState(false);

  const errors = validateTicket(values); // wyliczane przy każdym renderze
  const isValid = Object.keys(errors).length === 0;
  const show = (field: keyof TicketFormValues) => (touched[field] || submitted ? errors[field] : undefined);

  return (
    <form
      noValidate
      onSubmit={(e) => {
        e.preventDefault();
        setSubmitted(true);
        if (isValid) onCreate(values);
      }}
    >
      <TextField
        label="Tytuł"
        value={values.title}
        error={show('title')}
        onChange={(title) => setValues((v) => ({ ...v, title }))}
        onBlur={() => setTouched((t) => ({ ...t, title: true }))}
      />
      <button type="submit">Utwórz</button>
    </form>
  );
}
```

#T STEP_BY_STEP Budujemy razem: walidacja formularza ticketu
1. Utwórz `validateTicket` z regułami z lekcji (tytuł 5–120 znaków, osoba z listy, czas nieujemny, opis wymagany dla `CRITICAL`).
2. Utwórz `TextField` z `aria-invalid` i `aria-describedby`; analogiczny `TextAreaField` dla opisu.
3. W formularzu dodaj stany `touched` i `submitted`, a błędy licz z wartości.
4. Dodaj `noValidate` do `<form>`, żeby wyłączyć dymki przeglądarki — teraz komunikaty są Twoje.
5. Po nieudanej próbie wysłania przenieś fokus na pierwsze błędne pole: `document.getElementById(...)?.focus()` w handlerze (w rozdziale 08 zrobisz to przez ref).
6. Pokaż nad formularzem podsumowanie „Popraw 2 pola” z `role="alert"`, gdy `submitted && !isValid`.
7. Ustaw priorytet `CRITICAL` bez opisu i sprawdź regułę zależną od dwóch pól.
8. Przetestuj czytnikiem ekranu: po przejściu do błędnego pola czytnik odczytuje nazwę i komunikat.

#T PITFALL Wyłączony przycisk zamiast komunikatów
`<button disabled={!isValid}>` bez komunikatów przy polach zostawia użytkownika z pytaniem „dlaczego nie mogę kliknąć?”. Do tego wyłączony przycisk jest pomijany przez klawiaturę i czytniki ekranu. Lepiej: przycisk aktywny, a po kliknięciu jasne komunikaty przy polach i fokus na pierwszym błędzie.

#T CODE_WRONG Błędy jako osobny stan synchronizowany efektem

const [errors, setErrors] = useState({});
useEffect(() => {
  setErrors(validateTicket(values));
}, [values]);
```

#T CODE_RIGHT Błędy wyliczane podczas renderu

```

#T SUMMARY Kryterium akceptacji i podsumowanie
Walidacja to czysta funkcja `validate(values) → errors`; błędy wyliczasz przy każdym renderze, a w stanie trzymasz tylko `touched` i `submitted`, które decydują, co pokazać. Komunikaty wyświetlasz przy polach i wiążesz przez `aria-invalid` oraz `aria-describedby`. `noValidate` wyłącza dymki przeglądarki, gdy masz własne komunikaty. W TSX `Partial<Record<keyof T, string>>` przypisuje błędy wyłącznie istniejącym polom.

Kryterium akceptacji: formularz nie pozwala utworzyć ticketu z błędnymi danymi, komunikaty pojawiają się po opuszczeniu pola lub próbie wysłania i znikają po poprawieniu, fokus trafia na pierwsze błędne pole, a czytnik ekranu odczytuje komunikat przy polu.
