#T INTRO Rozgrzewka i problem: formularz edycji pokazuje stary ticket
Rozgrzewka: Gdzie wykonujesz skutki wysłania formularza? Dlaczego ID generujesz w handlerze? Jak resetujesz formularz kontrolowany?

Problem: karta szczegółów dostaje przycisk „Edytuj”, który zamienia ją w formularz edycji wybranego ticketu. Działa — do chwili, gdy podczas edycji ticketu #42 klikniesz w tabeli ticket #43. Karta pokazuje teraz nagłówek #43, ale w polach nadal jest tytuł z #42. Zapis nadpisze #43 danymi z #42. Przyczyną jest sposób, w jaki React przypisuje stan do komponentów.

#T DEFINITION Stan jest przypisany do pozycji w drzewie
React przechowuje stan komponentu w miejscu, które ten komponent zajmuje w drzewie (typ komponentu + pozycja wśród rodzeństwa). Gdy rodzic renderuje `<EditTicketForm ticket={t42} />`, a potem `<EditTicketForm ticket={t43} />` w tym samym miejscu, React widzi **ten sam komponent na tej samej pozycji** — zachowuje jego stan i tylko podmienia props. `useState(ticket.title)` użyło `ticket.title` tylko przy pierwszym renderze, więc pola trzymają tytuł #42.

#T DEFINITION Reset stanu przez key
Prop `key` (znany z list) działa na każdym komponencie: inny `key` oznacza dla Reacta **inny komponent**. Stary jest odmontowywany razem ze stanem, nowy montowany od zera. Wystarczy więc: `<EditTicketForm key={ticket.id} ticket={ticket} />` — każdy ticket dostaje świeży formularz zainicjalizowany jego danymi.

#T CODE_JSX Formularz edycji z key (JSX)
```
// EditTicketForm.jsx
import { useState } from 'react';

export function EditTicketForm({ ticket, onSave, onCancel }) {
  // wartość początkowa z props — użyta tylko przy montowaniu
  const [title, setTitle] = useState(ticket.title);
  const [priority, setPriority] = useState(ticket.priority);

  return (
    <form
      onSubmit={(e) => {
        e.preventDefault();
        onSave(ticket.id, { title: title.trim(), priority });
      }}
    >
      <h3>Edycja #{ticket.id}</h3>
      <label htmlFor="edit-title">Tytuł</label>
      <input id="edit-title" value={title} onChange={(e) => setTitle(e.target.value)} />
      <label htmlFor="edit-priority">Priorytet</label>
      <select id="edit-priority" value={priority} onChange={(e) => setPriority(e.target.value)}>
        <option value="LOW">Niski</option>
        <option value="MEDIUM">Średni</option>
        <option value="HIGH">Wysoki</option>
        <option value="CRITICAL">Krytyczny</option>
      </select>
      <button type="submit">Zapisz</button>
      <button type="button" onClick={onCancel}>Anuluj</button>
    </form>
  );
}

// w rodzicu:
// {editing && selected && <EditTicketForm key={selected.id} ticket={selected} onSave={save} onCancel={stopEditing} />}
```

#T CODE_TSX Formularz edycji z key (TSX)
`onSave` przyjmuje ID i zmiany typu `TicketChanges` — tylko pola, które formularz może zmienić.
```
// EditTicketForm.tsx
import { useState } from 'react';
import type { Ticket, TicketPriority } from '../types';

export type TicketChanges = Pick<Ticket, 'title' | 'priority'>;

type Props = {
  ticket: Ticket;
  onSave: (id: number, changes: TicketChanges) => void;
  onCancel: () => void;
};

export function EditTicketForm({ ticket, onSave, onCancel }: Props) {
  const [title, setTitle] = useState(ticket.title);
  const [priority, setPriority] = useState(ticket.priority);

  return (
    <form
      onSubmit={(e) => {
        e.preventDefault();
        onSave(ticket.id, { title: title.trim(), priority });
      }}
    >
      <h3>Edycja #{ticket.id}</h3>
      <label htmlFor="edit-title">Tytuł</label>
      <input id="edit-title" value={title} onChange={(e) => setTitle(e.target.value)} />
      <label htmlFor="edit-priority">Priorytet</label>
      <select id="edit-priority" value={priority} onChange={(e) => setPriority(e.target.value as TicketPriority)}>
        <option value="LOW">Niski</option>
        <option value="MEDIUM">Średni</option>
        <option value="HIGH">Wysoki</option>
        <option value="CRITICAL">Krytyczny</option>
      </select>
      <button type="submit">Zapisz</button>
      <button type="button" onClick={onCancel}>Anuluj</button>
    </form>
  );
}
```

#T NOTE JSX ↔ TSX — inicjalizacja stanu z props
`useState(ticket.priority)` w TSX ma typ `TicketPriority` z inferencji — nie trzeba generyka, bo wartość startowa niesie pełny typ. Rzutowanie `as TicketPriority` przy `select` jest potrzebne, bo `e.target.value` to `string`. Sam problem „stary stan po zmianie props” jest identyczny w obu wersjach — TypeScript go nie wykryje, bo to kwestia działania Reacta, nie typów. Rozwiązanie (`key`) też jest takie samo.

#T CODE_WRONG Synchronizacja stanu z props efektem
Działa „prawie”: pierwszy render po zmianie ticketu pokazuje stary tytuł, a dopiero efekt go poprawia. Do tego niezapisane zmiany giną przy każdej aktualizacji props, nawet tego samego ticketu.
```
const [title, setTitle] = useState(ticket.title);

useEffect(() => {
  setTitle(ticket.title);
}, [ticket]);
```

#T CODE_RIGHT Świeży formularz dla każdego ticketu
```
<EditTicketForm key={selected.id} ticket={selected} onSave={save} onCancel={stop} />
```

#T DEFINITION Zachowanie stanu i pułapka pozycji
Druga strona tej samej zasady: jeśli ten sam typ komponentu jest renderowany na tej samej pozycji w różnych gałęziach warunku (`{isAdmin ? <Form /> : <Form />}`), React zachowa stan między gałęziami. A jeśli między renderami zmieni się typ komponentu na danej pozycji (`<div>` zamiast `<section>`), cały stan poddrzewa przepada. Przy dziwnym „przenoszeniu się” albo „znikaniu” stanu sprawdź, co jest renderowane na danej pozycji i czy ma `key`.

export function applyChanges(tickets: readonly Ticket[], id: number, changes: TicketChanges): Ticket[] {
  return tickets.map((t) => (t.id === id ? { ...t, ...changes } : t));
}

#T STEP_BY_STEP Budujemy razem: edycja w karcie szczegółów
1. Dodaj w `Main` stan `editing` (boolean) i przycisk „Edytuj” w karcie szczegółów.
2. Gdy `editing` jest prawdą, zamiast karty renderuj `EditTicketForm` — **najpierw bez `key`**.
3. Odtwórz błąd: zacznij edycję #42, kliknij w tabeli #43 — w polach nadal są dane #42.
4. Dodaj `key={selected.id}` — po kliknięciu innego ticketu formularz pokazuje jego dane.
5. Zaimplementuj `handleSave` przez `applyChanges` i wyjście z trybu edycji; „Anuluj” tylko wychodzi z trybu edycji.
6. Zdecyduj o zachowaniu przy zmianie zaznaczenia w trakcie edycji: albo kończ edycję (`setEditing(false)` w handlerze wyboru wiersza), albo zostaw — ale świadomie, nie przez przypadek.
7. Dodaj licznik „niezapisane zmiany” (porównanie wartości z `ticket`) — to dane wyliczane, bez dodatkowego stanu.

#T WHEN_TO_USE key do resetu — kiedy to dobry pomysł
Reset przez `key` stosuj, gdy komponent ma reprezentować **inny obiekt** (formularz innego ticketu, czat z inną osobą, odtwarzacz innego pliku). Nie stosuj go do „odświeżania” komponentu po każdej zmianie danych — zmiana `key` przy każdym renderze niszczy stan i wydajność. Jeśli formularz ma reagować na zmianę props tego samego obiektu (np. ktoś inny zmienił ticket), to temat na synchronizację z serwerem w rozdziale 10.

#T SUMMARY Kryterium akceptacji i podsumowanie
React wiąże stan z pozycją komponentu w drzewie: ten sam typ na tej samej pozycji zachowuje stan, nawet gdy zmienią się props. Wartość startowa `useState(props.x)` jest użyta tylko przy montowaniu. Aby dostać świeży stan dla innego obiektu, nadaj komponentowi `key` z jego ID. Nie synchronizuj stanu z props efektem. W TSX typ zmian wyprowadzasz z typu rekordu (`Pick`), a stan z wartości props ma typ z inferencji.

Kryterium akceptacji: edycja ticketu i przełączenie na inny ticket pokazuje w formularzu dane nowego ticketu, „Zapisz” zmienia tylko edytowany ticket, „Anuluj” nie zmienia nic, a w kodzie nie ma efektu kopiującego props do stanu.
