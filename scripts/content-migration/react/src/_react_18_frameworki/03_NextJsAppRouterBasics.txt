#T INTRO Rozgrzewka i problem: SSR bez ręcznego serwera
Rozgrzewka: Czym jest hydratacja? Podaj trzy przyczyny niezgodności hydratacji. Kiedy używasz `ClientOnly`?

Problem: ręczny serwer SSR z lekcji 01 to dopiero początek — brakuje routingu, podziału kodu, streamingu, obsługi błędów, metadanych, budowania produkcyjnego. **Next.js** to najpopularniejszy framework Reacta, który daje to wszystko w konwencji: **App Router** (katalog `app/`), komponenty serwerowe domyślnie, layouty, ładowanie i błędy przez pliki specjalne. W tej lekcji budujesz publiczną **bazę wiedzy DevDesk** w Next.js — z listą artykułów i stroną artykułu pobierającą dane bezpośrednio z API Spring Boot.

#T DEFINITION Routing oparty na plikach
W App Routerze struktura katalogów w `app/` to struktura adresów:
- `app/page.tsx` → `/`; `app/articles/page.tsx` → `/articles`,
- `app/articles/[slug]/page.tsx` → `/articles/reset-hasla` (segment dynamiczny, wartość w `params`),
- `layout.tsx` — układ otaczający wszystkie strony w katalogu i podkatalogach (nie renderuje się ponownie przy nawigacji między nimi),
- `loading.tsx` — automatyczna granica `Suspense` dla segmentu,
- `error.tsx` — granica błędów segmentu (musi być komponentem klienckim),
- `not-found.tsx` — widok dla `notFound()`,
- `(grupa)` w nawiasach — grupowanie bez wpływu na adres; `route.ts` — endpoint API (GET/POST).

Wszystkie komponenty w `app/` są **serwerowe**, dopóki plik nie zacznie się od `'use client'`.

#T CODE_JSX Lista artykułów — projekt w JS (JSX)
`create-next-app` pyta o TypeScript; po wybraniu „No” pliki mają rozszerzenie `.jsx`. Komponent strony jest asynchroniczny i pobiera dane na serwerze.
```
// app/articles/page.jsx
import Link from 'next/link';

export const metadata = { title: 'Baza wiedzy · DevDesk' };

export default async function ArticlesPage() {
  const res = await fetch(`${process.env.API_URL}/api/articles`, { next: { revalidate: 300 } });
  if (!res.ok) throw new Error('Nie udało się pobrać artykułów');
  const articles = await res.json();

  return (
    <main>
      <h1>Baza wiedzy</h1>
      <ul>
        {articles.map((a) => (
          <li key={a.slug}><Link href={`/articles/${a.slug}`}>{a.title}</Link></li>
        ))}
      </ul>
    </main>
  );
}
```

#T CODE_TSX Lista artykułów — projekt domyślny w TS (TSX)
Next.js domyślnie tworzy projekt w TypeScript i sam generuje `tsconfig.json` oraz typy dla tras. Typ `Metadata` pilnuje pól metadanych.
```
// app/articles/page.tsx
import Link from 'next/link';
import type { Metadata } from 'next';

type ArticleSummary = { slug: string; title: string };

export const metadata: Metadata = { title: 'Baza wiedzy · DevDesk' };

export default async function ArticlesPage() {
  const res = await fetch(`${process.env.API_URL}/api/articles`, { next: { revalidate: 300 } });
  if (!res.ok) throw new Error('Nie udało się pobrać artykułów');
  const articles: ArticleSummary[] = await res.json();

  return (
    <main>
      <h1>Baza wiedzy</h1>
      <ul>
        {articles.map((a) => (
          <li key={a.slug}><Link href={`/articles/${a.slug}`}>{a.title}</Link></li>
        ))}
      </ul>
    </main>
  );
}
```

#T NOTE JSX ↔ TSX — Next.js domyślnie w TS
Next.js traktuje TypeScript jako domyślny: generuje `next-env.d.ts`, sprawdza typy przy `next build` (błąd typów przerywa build) i dostarcza typy `Metadata`, `NextRequest`, `PageProps` dla tras. W projekcie JS wszystko działa tak samo, ale błędy (np. literówka w polu `metadata` albo zły kształt `params`) wyjdą dopiero w działaniu. Zwróć uwagę na `process.env.API_URL` — w komponencie serwerowym możesz używać dowolnych zmiennych środowiskowych (także sekretów), bo kod nie trafia do przeglądarki; do klienta trafiają tylko zmienne z prefiksem `NEXT_PUBLIC_`.

#T CODE_BASIC Strona artykułu z segmentem dynamicznym
`params` jest w aktualnych wersjach Next.js **obietnicą** — trzeba ją `await`. `notFound()` przerywa render i pokazuje `not-found.tsx`. `generateMetadata` ustawia tytuł zależny od danych.
```
// app/articles/[slug]/page.tsx
import { notFound } from 'next/navigation';
import type { Metadata } from 'next';
import { HelpfulButton } from './HelpfulButton';

type Article = { slug: string; title: string; body: string; updatedAt: string };
type Props = { params: Promise<{ slug: string }> };

async function getArticle(slug: string): Promise<Article | null> {
  const res = await fetch(`${process.env.API_URL}/api/articles/${encodeURIComponent(slug)}`);
  if (res.status === 404) return null;
  if (!res.ok) throw new Error(`API ${res.status}`);
  return res.json();
}

export async function generateMetadata({ params }: Props): Promise<Metadata> {
  const article = await getArticle((await params).slug);
  return { title: article ? `${article.title} · DevDesk` : 'Nie znaleziono' };
}

export default async function ArticlePage({ params }: Props) {
  const article = await getArticle((await params).slug);
  if (!article) notFound();
  return (
    <article>
      <h1>{article.title}</h1>
      <div>{article.body}</div>
      <HelpfulButton slug={article.slug} />
    </article>
  );
}
```

#T STEP_BY_STEP Budujemy razem: baza wiedzy w Next.js
1. `npx create-next-app@latest devdesk-kb` — wybierz TypeScript (albo JS, jeśli przerabiasz tor JSX), App Router, ESLint; uruchom `npm run dev`.
2. W Spring Boot dodaj (lub zamockuj) endpointy `GET /api/articles` i `GET /api/articles/{slug}`; w `.env.local` ustaw `API_URL=http://localhost:8080`.
3. Utwórz `app/layout.tsx`, `app/articles/page.tsx` i `loading.tsx`; sprawdź w źródle strony (Ctrl+U), że lista jest w HTML-u.
4. Dodaj `app/articles/[slug]/page.tsx` z `generateMetadata` i `notFound()`, oraz `not-found.tsx`; wejdź na nieistniejący slug.
5. Dodaj `HelpfulButton` jako komponent kliencki; w DevTools → Sources zobacz, że w paczce klienta jest tylko jego kod, a nie kod strony.
6. Dodaj `error.tsx` (`'use client'`, props `error` i `reset`) i wyłącz backend — strona pokazuje komunikat z przyciskiem „Spróbuj ponownie”.
7. Uruchom `npm run build` i przeczytaj raport: które trasy są statyczne (○), które dynamiczne (ƒ).

#T PITFALL Pobieranie danych przez własny endpoint API z komponentu serwerowego
Częsty nawyk z SPA: komponent serwerowy wywołuje `fetch('/api/articles')`, czyli **własny** `route.ts` Next.js, który dopiero woła backend. To dodatkowy przeskok sieciowy na tym samym serwerze (i problem z adresem względnym na serwerze). W komponencie serwerowym wołaj bezpośrednio źródło danych (API Spring Boot, bazę, funkcję dostępu do danych); `route.ts` zostaw dla klientów zewnętrznych i komponentów klienckich.

#T SUMMARY Kryterium akceptacji i podsumowanie
App Router Next.js mapuje katalogi `app/` na adresy; pliki `page`, `layout`, `loading`, `error`, `not-found` i `route` mają specjalne znaczenie. Komponenty są serwerowe domyślnie — mogą być `async`, pobierać dane i używać sekretów; `'use client'` oznacza wyspy interakcji. `params` to obietnica, `generateMetadata` ustawia metadane z danych, `notFound()` pokazuje widok 404. Next.js domyślnie używa TypeScriptu i sprawdza typy przy buildzie.

Kryterium akceptacji: baza wiedzy w Next.js ma listę i stronę artykułu renderowane na serwerze (treść widoczna w źródle strony), tytuły z `generateMetadata`, widok 404, obsługę błędu backendu z ponowieniem i jeden komponent kliencki z interakcją.
