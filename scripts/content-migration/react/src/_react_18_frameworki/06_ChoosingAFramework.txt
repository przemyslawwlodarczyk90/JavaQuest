#T INTRO Rozgrzewka i problem: którą drogę wybrać dla DevDesk?
Rozgrzewka: Gdzie wykonuje się `loader` w trybie frameworka React Router? Do czego służy `clientLoader`? Czym różni się aktualizacja danych po mutacji w React Router i w Next.js?

Problem: znasz już Vite SPA, Next.js i React Router w trybie frameworka. Zespół DevDesk ma zdecydować: panel agentów, publiczna baza wiedzy, strona statusu i blog produktu — jedna technologia czy kilka? Wybór frameworka to decyzja na lata, a „wszyscy używają X” nie jest argumentem. W tej lekcji poznasz jeszcze **Astro** (architektura wysp) i nauczysz się podejmować decyzję na podstawie **kryteriów**, zapisując ją jako ADR (Architecture Decision Record).

#T DEFINITION Kandydaci
- **Vite + React (SPA)** — najprostszy model: pliki statyczne, cały UI w przeglądarce, backend (Spring Boot) jako API. Idealny dla aplikacji za logowaniem.
- **Next.js** — pełny framework: komponenty serwerowe, akcje serwerowe, SSR/SSG/ISR, optymalizacja obrazów i czcionek; wymaga serwera Node (lub platformy typu Vercel) i znajomości modelu cache.
- **React Router (framework)** — SSR i prerender z modelem loader/action; naturalna kontynuacja dla aplikacji już używających React Router; może budować się też jako SPA (`ssr: false`).
- **Astro** — framework dla stron **treściowych**: domyślnie generuje czysty HTML bez JavaScriptu, a komponenty React (lub innych bibliotek) są **wyspami** (islands) ładowanymi tylko tam, gdzie potrzebna interakcja (`client:load`, `client:visible`, `client:idle`).

#T CODE_BASIC Wyspa React w Astro
Strona bazy wiedzy w Astro: treść to statyczny HTML, a interaktywna jest tylko wyszukiwarka — jej JS ładuje się, gdy pojawi się w polu widzenia.
```
---
// src/pages/kb/index.astro (sekcja frontmatter wykonuje się przy budowaniu)
import Layout from '../../layouts/Layout.astro';
import { ArticleSearch } from '../../components/ArticleSearch';
const articles = await fetch(`${import.meta.env.API_URL}/api/articles`).then((r) => r.json());
---
<Layout title="Baza wiedzy · DevDesk">
  <h1>Baza wiedzy</h1>
  <ArticleSearch client:visible articles={articles} />
  <ul>
    {articles.map((a) => <li><a href={`/kb/${a.slug}`}>{a.title}</a></li>)}
  </ul>
</Layout>
```

#T CODE_JSX Komponent wyspy (JSX)
Komponent React nie wie, że jest wyspą — to zwykły komponent z propsami serializowalnymi (jak na granicy RSC).
```
// src/components/ArticleSearch.jsx
import { useMemo, useState } from 'react';

export function ArticleSearch({ articles }) {
  const [query, setQuery] = useState('');
  const results = useMemo(
    () => articles.filter((a) => a.title.toLowerCase().includes(query.trim().toLowerCase())).slice(0, 5),
    [articles, query],
  );
  return (
    <search>
      <label htmlFor="kb-q">Szukaj w bazie wiedzy</label>
      <input id="kb-q" type="search" value={query} onChange={(e) => setQuery(e.target.value)} />
      {query && (
        <ul aria-live="polite">
          {results.map((a) => <li key={a.slug}><a href={`/kb/${a.slug}`}>{a.title}</a></li>)}
        </ul>
      )}
    </search>
  );
}
```

#T CODE_TSX Komponent wyspy (TSX)
```
// src/components/ArticleSearch.tsx
import { useMemo, useState } from 'react';

type ArticleSummary = { slug: string; title: string };

export function ArticleSearch({ articles }: { articles: ArticleSummary[] }) {
  const [query, setQuery] = useState('');
  const results = useMemo(
    () => articles.filter((a) => a.title.toLowerCase().includes(query.trim().toLowerCase())).slice(0, 5),
    [articles, query],
  );
  return (
    <search>
      <label htmlFor="kb-q">Szukaj w bazie wiedzy</label>
      <input id="kb-q" type="search" value={query} onChange={(e) => setQuery(e.target.value)} />
      {query && (
        <ul aria-live="polite">
          {results.map((a) => <li key={a.slug}><a href={`/kb/${a.slug}`}>{a.title}</a></li>)}
        </ul>
      )}
    </search>
  );
}
```

#T NOTE JSX ↔ TSX — ten sam komponent w czterech światach
Komponent `ArticleSearch` w JSX lub TSX zadziała bez zmian w Vite SPA, jako komponent kliencki w Next.js (`'use client'`), w module trasy React Router i jako wyspa w Astro — bo zależy tylko od Reacta i propsów. To praktyczna zasada architektury: **komponenty UI niezależne od frameworka**, a pobieranie danych i routing w cienkiej warstwie specyficznej dla frameworka. W TSX typ props (`ArticleSummary[]`) jest kontraktem, który łatwo sprawdzić przy przenoszeniu między projektami; we wszystkich frameworkach dane na granicy serwer → klient muszą być serializowalne.

#T CODE_PRACTICAL Szablon decyzji architektonicznej (ADR)
```
# ADR-007: Technologia frontendu dla części publicznej DevDesk

## Kontekst
Panel agentów: Vite SPA + React Router (tryb danych) + TanStack Query, za logowaniem.
Nowe potrzeby: publiczna baza wiedzy (SEO, podgląd linków), strona statusu (dane bieżące).
Zespół: 3 osoby frontend, backend w Spring Boot, brak doświadczenia z Node w produkcji.

## Decyzja
- Panel agentów zostaje SPA (bez zmian).
- Baza wiedzy: Astro (SSG + wyspa wyszukiwarki), revalidacja przez przebudowanie po publikacji artykułu.
- Strona statusu: renderowana przez Spring Boot (Thymeleaf) albo wyspa w Astro z odświeżaniem po stronie klienta.

## Konsekwencje
+ brak serwera Node w produkcji, hosting statyczny
+ komponenty UI współdzielone (pakiet ui/) między SPA i Astro
− dwa narzędzia budowania; publikacja artykułu wymaga przebudowania (webhook CI)
Do ponownej oceny: gdy pojawi się potrzeba personalizacji stron publicznych → Next.js lub React Router fw.
```

#T STEP_BY_STEP Budujemy razem: decyzja dla DevDesk
1. Wypisz ekrany DevDesk i dla każdego określ: czy jest za logowaniem, czy potrzebuje SEO, jak świeże muszą być dane, ile w nim interakcji.
2. Wypełnij tabelę kryteriów dla swoich warunków (umiejętności zespołu, dostępny hosting, wymagania bezpieczeństwa).
3. Zbuduj szybki prototyp bazy wiedzy w Astro (`npm create astro@latest`, integracja `@astrojs/react`) z wyspą `ArticleSearch` i porównaj ilość JS w Network z wersją Next.js z lekcji 03.
4. Sprawdź, że ten sam komponent `ArticleSearch` działa w SPA, w Next.js (z `'use client'`) i w Astro.
5. Zapisz decyzję jako ADR według szablonu i zaplanuj, kiedy decyzję zweryfikujesz.
6. Zastanów się nad kosztem utrzymania: aktualizacje wersji frameworka (Next.js i React Router zmieniają API szybciej niż Vite), monitoring serwera Node, kompetencje w zespole.

#T PITFALL Framework wybrany przed problemem
„Nowy projekt = Next.js” to częsty odruch, który w aplikacji panelowej za logowaniem dodaje serwer Node, model cache i podział serwer/klient bez żadnej korzyści dla użytkownika. Odwrotnie: publiczna strona marketingowa jako SPA traci SEO i szybkość pierwszego widoku. Zaczynaj od wymagań ekranów (SEO, świeżość danych, interaktywność, hosting, zespół), a technologię wybieraj na końcu — i zapisuj uzasadnienie.

#T SUMMARY Podsumowanie rozdziału 18
Strategie renderowania (CSR, SSR, SSG, ISR, streaming) decydują, gdzie i kiedy powstaje HTML; hydratacja wymaga zgodnego pierwszego renderu. Next.js daje komponenty i akcje serwerowe z cache, React Router w trybie frameworka — SSR na znanych loaderach i akcjach z generowanymi typami, Astro — strony treściowe z wyspami interakcji, a Vite SPA pozostaje najlepszym wyborem dla aplikacji za logowaniem. Komponenty UI niezależne od frameworka przenoszą się między nimi bez zmian. Decyzję podejmuj na podstawie kryteriów i zapisuj jako ADR.

Kryterium akceptacji: masz tabelę ekranów DevDesk z wymaganiami, prototyp bazy wiedzy z wyspą React, porównanie ilości JS z wersją Next.js i zapisany ADR z decyzją, konsekwencjami i warunkiem ponownej oceny.
