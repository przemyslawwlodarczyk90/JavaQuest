#T INTRO Rozgrzewka i problem: szybko u programisty, wolno u użytkownika
Rozgrzewka: Co pokazuje wizualizacja pakietu? Co psuje tree shaking? Dlaczego ciężką bibliotekę PDF ładujesz w handlerze?

Problem: na laptopie programisty z szybkim łączem DevDesk ładuje się w sekundę. Użytkownik na starszym telefonie i słabym zasięgu widzi przez kilka sekund pusty ekran, potem treść „skacze” w dół, gdy doładuje się logo i czcionka, a pierwsze kliknięcie w menu reaguje z opóźnieniem. Do opisu takich wrażeń służą **Core Web Vitals** — trzy wskaźniki mierzone u prawdziwych użytkowników — oraz zestaw technik dla obrazów, czcionek i zasobów.

#T DEFINITION Core Web Vitals
- **LCP (Largest Contentful Paint)** — czas do wyświetlenia największego elementu treści w widoku (obraz, duży blok tekstu, nagłówek). Dobrze: ≤ 2,5 s. Pogarsza go: duży pakiet JS przed renderem, wolny serwer, niezoptymalizowany obraz, renderowanie wyłącznie po stronie klienta.
- **INP (Interaction to Next Paint)** — czas od interakcji (kliknięcie, klawisz) do następnego odmalowania ekranu, w praktyce najgorsze interakcje w czasie wizyty. Dobrze: ≤ 200 ms. Pogarsza go: długie zadania JS (ciężkie rendery, synchroniczne obliczenia w handlerach).
- **CLS (Cumulative Layout Shift)** — suma nieoczekiwanych przesunięć układu. Dobrze: ≤ 0,1. Pogarsza go: obrazy bez wymiarów, wstrzykiwane banery, czcionki zmieniające rozmiar tekstu, treść doładowywana nad tym, co użytkownik czyta.

Wskaźniki mierzy się **w terenie** (u użytkowników — dane rzeczywiste) i **w laboratorium** (Lighthouse w DevTools — powtarzalne warunki).

#T CODE_JSX Pomiar wskaźników u użytkowników (JSX)
Biblioteka `web-vitals` mierzy wskaźniki w przeglądarce użytkownika; wyniki wysyłasz do własnego endpointu lub systemu monitoringu.
```
// vitals.js
import { onCLS, onINP, onLCP } from 'web-vitals';

function send(metric) {
  const body = JSON.stringify({ name: metric.name, value: metric.value, rating: metric.rating, id: metric.id, path: location.pathname });
  // sendBeacon działa także przy zamykaniu karty
  if (!navigator.sendBeacon('/api/vitals', body)) {
    fetch('/api/vitals', { method: 'POST', body, keepalive: true, headers: { 'Content-Type': 'application/json' } });
  }
}

export function startVitals() {
  onLCP(send);
  onINP(send);
  onCLS(send);
}

// main.jsx: startVitals();
```

#T CODE_TSX Pomiar wskaźników u użytkowników (TSX)
Typ `Metric` z biblioteki opisuje pomiar (nazwa, wartość, ocena `good | needs-improvement | poor`).
```
// vitals.ts
import { onCLS, onINP, onLCP, type Metric } from 'web-vitals';

function send(metric: Metric) {
  const body = JSON.stringify({ name: metric.name, value: metric.value, rating: metric.rating, id: metric.id, path: location.pathname });
  if (!navigator.sendBeacon('/api/vitals', body)) {
    void fetch('/api/vitals', { method: 'POST', body, keepalive: true, headers: { 'Content-Type': 'application/json' } });
  }
}

export function startVitals() {
  onLCP(send);
  onINP(send);
  onCLS(send);
}
```

#T NOTE JSX ↔ TSX — pomiar jest niezależny od języka
Web Vitals mierzą to, co widzi użytkownik w przeglądarce, więc wersja JSX i TSX tej samej aplikacji ma identyczne wyniki. W TSX typ `Metric` pomaga zbudować spójny format danych wysyłanych do backendu (np. rekord `VitalDto` w Springu), a unia `rating` pozwala bezpiecznie filtrować tylko złe wyniki. W JSX ten sam kod działa, ale kształt danych znasz tylko z dokumentacji biblioteki.

#T API_REFERENCE Obrazy bez przesunięć i z szybkim LCP
- **wymiary**: zawsze `width` i `height` (albo CSS `aspect-ratio`) — przeglądarka rezerwuje miejsce przed pobraniem, więc nie ma przesunięcia układu (CLS),
- **leniwe ładowanie**: `loading="lazy"` dla obrazów poniżej pierwszego ekranu; **nie** dla obrazu LCP (głównego, widocznego od razu),
- **priorytet**: `fetchPriority="high"` dla obrazu LCP — przeglądarka pobierze go wcześniej,
- **dekodowanie**: `decoding="async"` — dekodowanie poza głównym wątkiem,
- **formaty**: AVIF lub WebP zamiast PNG/JPEG (zwykle kilkukrotnie mniejsze), element `<picture>` z kilkoma źródłami,
- **rozdzielczość**: `srcSet` i `sizes` — przeglądarka wybiera plik odpowiedni do szerokości ekranu i gęstości pikseli,
- **awatary i ikony**: SVG albo małe pliki; dla wielu awatarów — miniatury z serwera, nie pełne zdjęcia skalowane w CSS.

#T CODE_BASIC Komponent obrazu z dobrymi domyślnymi ustawieniami
```
type ImageProps = {
  src: string;
  alt: string;
  width: number;
  height: number;
  priority?: boolean; // obraz LCP
  srcSet?: string;
  sizes?: string;
};

export function Img({ src, alt, width, height, priority = false, srcSet, sizes }: ImageProps) {
  return (
    <img
      src={src}
      srcSet={srcSet}
      sizes={sizes}
      alt={alt}
      width={width}
      height={height}
      loading={priority ? 'eager' : 'lazy'}
      fetchPriority={priority ? 'high' : 'auto'}
      decoding="async"
      style={{ maxWidth: '100%', height: 'auto' }}
    />
  );
}
```

#T DEFINITION Czcionki i zasoby krytyczne
Czcionki internetowe powodują dwa problemy: niewidoczny tekst do czasu pobrania (FOIT) i przesunięcie układu po podmianie czcionki zastępczej. Rozwiązania: `font-display: swap` (tekst od razu w czcionce systemowej), wstępne pobranie najważniejszego pliku czcionki (`<link rel="preload" as="font" crossorigin>`), dopasowanie metryk czcionki zastępczej (`size-adjust`, `ascent-override` w `@font-face`), mniej wariantów (krojów i grubości), format WOFF2 i podzbiory znaków (`unicode-range`, np. łacina z polskimi znakami).

W React 19 zasoby możesz wskazywać z komponentów: funkcje `preload`, `preinit`, `preconnect` i `prefetchDNS` z `react-dom` dodają odpowiednie wskazówki do `<head>` (więcej w rozdziale 17).

#T CODE_PRACTICAL Wskazówki zasobów z komponentu (React 19)
Ekran raportów wie, że za chwilę będzie potrzebował czcionki wykresów i połączenia z serwerem plików — może o tym powiedzieć przeglądarce już przy renderze.
```
import { preconnect, preload } from 'react-dom';

export function ReportsPage() {
  preconnect('https://files.devdesk.example');                       // nawiąż połączenie z wyprzedzeniem
  preload('/fonts/inter-latin-ext.woff2', { as: 'font', type: 'font/woff2', crossOrigin: 'anonymous' });
  return (
    <section>
      <h1>Raporty</h1>
      {/* … */}
    </section>
  );
}
```

#T STEP_BY_STEP Budujemy razem: Web Vitals w DevDesk
1. Zbuduj aplikację i uruchom Lighthouse (DevTools → Lighthouse, tryb mobilny) na buildzie produkcyjnym (`npm run preview`); zapisz LCP, CLS, TBT (laboratoryjny odpowiednik problemów z INP) i ocenę.
2. Dodaj `web-vitals` i wysyłanie pomiarów do endpointu (w MSW lub Springu — prosty kontroler zapisujący do logu).
3. Napraw CLS: dodaj wymiary do logo i awatarów, zarezerwuj miejsce na banery i toasty (pozycjonowanie `fixed`, nie wstawianie nad treścią).
4. Zoptymalizuj obraz LCP (np. ilustracja na pustym dashboardzie): format WebP/AVIF, `fetchPriority="high"`, bez `loading="lazy"`.
5. Ustaw czcionki: `font-display: swap`, preload jednego pliku WOFF2, ograniczenie do potrzebnych grubości.
6. Znajdź najwolniejszą interakcję (Performance → interakcje, albo pomiar INP) i popraw ją technikami z lekcji 2–6 tego rozdziału.
7. Uruchom Lighthouse ponownie i zapisz wyniki po zmianach.

#T PITFALL Lighthouse jako jedyne źródło prawdy
Wynik Lighthouse 100 na szybkim komputerze nie oznacza, że użytkownicy mają dobre wrażenia — laboratorium nie odtworzy ich urządzeń, sieci ani sposobu korzystania (INP zależy od tego, w co ludzie naprawdę klikają). Traktuj Lighthouse jako narzędzie diagnostyczne i porównawcze, a decyzje opieraj na pomiarach z terenu (`web-vitals`, dane z monitoringu).

#T SUMMARY Kryterium akceptacji i podsumowanie
Core Web Vitals opisują doświadczenie użytkownika: LCP (szybkość pokazania głównej treści, ≤ 2,5 s), INP (reakcja na interakcje, ≤ 200 ms) i CLS (stabilność układu, ≤ 0,1). Mierzysz je w terenie (`web-vitals`) i w laboratorium (Lighthouse). Obrazy dostają wymiary, nowoczesne formaty, `srcSet`, leniwe ładowanie poniżej pierwszego ekranu i wysoki priorytet dla obrazu LCP. Czcionki — `font-display: swap`, preload, mniej wariantów. React 19 udostępnia `preload`/`preconnect` z komponentów. Wyniki nie zależą od JSX/TSX.

Kryterium akceptacji: DevDesk wysyła pomiary LCP, INP i CLS do backendu, CLS po poprawkach jest poniżej 0,1, obraz LCP ma wysoki priorytet i nowoczesny format, a w README są wyniki Lighthouse przed i po zmianach.
