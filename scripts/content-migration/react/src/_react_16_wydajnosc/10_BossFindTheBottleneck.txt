#T INTRO Boss rozdziału 16: znajdź prawdziwe wąskie gardło
Ostatni sprawdzian rozdziału wygląda jak prawdziwe zgłoszenie od użytkowników: „ekran raportów jest strasznie wolny”. Dostajesz komponent, w którym ukryto kilka różnych problemów wydajności — każdy wymaga innego narzędzia. Zasada zadania: **żadnej zmiany bez pomiaru przed i po**. Wynikiem jest nie tylko szybszy kod, ale raport: co zmierzyłeś, co znalazłeś, co zmieniłeś i jaki był efekt.

#T DEFINITION Brief zadania
Ekran `ReportsScreen` (kod poniżej) pokazuje: pole wyszukiwania, filtr osoby, licznik i statystyki ticketów, tabelę wszystkich ticketów i listę aktywności. Użytkownicy zgłaszają:
1. pisanie w wyszukiwarce „zacina się”,
2. kliknięcie wiersza (zaznaczenie) trwa długo,
3. przewijanie listy aktywności jest nierówne,
4. pierwsze wejście na ekran trwa kilka sekund na telefonie,
5. po załadowaniu treść „podskakuje”.

Twoje zadanie: zmierzyć, zdiagnozować i naprawić każdy problem odpowiednią techniką z rozdziału, a następnie udokumentować wyniki.

#T CODE_JSX Kod do naprawy (JSX)
```
// ReportsScreen.jsx — wersja z problemami
import { useState } from 'react';
import _ from 'lodash';                       // cała biblioteka dla jednej funkcji
import { BigChart } from './BigChart';        // ciężki wykres w pakiecie startowym

function expensiveStats(tickets) {
  const start = performance.now();
  while (performance.now() - start < 60) { /* symulacja ciężkiego liczenia */ }
  return _.countBy(tickets, 'status');
}

function Row({ ticket, selected, onSelect }) {
  return (
    <tr className={selected ? 'row row--selected' : 'row'} onClick={() => onSelect(ticket.id)}>
      <td>{ticket.id}</td><td>{ticket.title}</td><td>{ticket.assignee ?? '—'}</td>
    </tr>
  );
}

export function ReportsScreen({ tickets, activity }) {
  const [query, setQuery] = useState('');
  const [selectedId, setSelectedId] = useState(null);
  const stats = expensiveStats(tickets);                                   // przy każdym renderze
  const visible = tickets.filter((t) => t.title.toLowerCase().includes(query.toLowerCase()));

  return (
    <section>
      <img src="/report-hero.png" alt="Raport" />                         {/* bez wymiarów */}
      <input aria-label="Szukaj" value={query} onChange={(e) => setQuery(e.target.value)} />
      <p>Otwarte: {stats.OPEN ?? 0} · W toku: {stats.IN_PROGRESS ?? 0}</p>
      <BigChart data={tickets} />
      <table><tbody>
        {visible.map((t) => <Row key={t.id} ticket={t} selected={t.id === selectedId} onSelect={(id) => setSelectedId(id)} />)}
      </tbody></table>
      <ul>{activity.map((a) => <li key={a.id}>{a.text}</li>)}</ul>     {/* 10 000 elementów */}
    </section>
  );
}
```

#T CODE_TSX Kod do naprawy — sygnatura i dane (TSX)
```
// ReportsScreen.tsx — publiczne API ekranu i generator danych do testów wydajności
import type { Ticket } from '../types';

export type ActivityItem = { id: number; text: string };

export type ReportsScreenProps = { tickets: readonly Ticket[]; activity: readonly ActivityItem[] };

export function makeLoadTestData(ticketCount = 5000, activityCount = 10_000): ReportsScreenProps {
  const statuses = ['OPEN', 'IN_PROGRESS', 'CLOSED'] as const;
  const tickets: Ticket[] = Array.from({ length: ticketCount }, (_, i) => ({
    id: i + 1, title: `Ticket ${i + 1}`, description: '', status: statuses[i % 3], priority: 'MEDIUM',
    assignee: i % 4 === 0 ? null : `osoba${i % 20}`, createdAt: new Date(Date.UTC(2026, 9, 1 + (i % 20))).toISOString(), tags: [],
  }));
  const activity = Array.from({ length: activityCount }, (_, i) => ({ id: i + 1, text: `Zdarzenie ${i + 1}` }));
  return { tickets, activity };
}
```

#T STEP_BY_STEP Kryteria akceptacji
1. **Raport pomiarów** (plik `PERFORMANCE.md` lub komentarz w kodzie): dla każdego z 5 zgłoszeń — narzędzie pomiaru, wynik przed, przyczyna, zmiana, wynik po.
2. Pisanie w wyszukiwarce przy 5000 ticketach i CPU ×4 nie blokuje pola: pilne commity dotyczą tylko pola (Profiler).
3. Statystyki nie są przeliczane przy pisaniu w wyszukiwarce ani przy zaznaczaniu wiersza.
4. Kliknięcie wiersza renderuje tylko wiersze, których zaznaczenie się zmieniło.
5. Lista aktywności ma w DOM kilkadziesiąt elementów (wirtualizacja) i płynne przewijanie (Performance).
6. Wykres jest ładowany leniwie (osobny plik w buildzie), a obraz nagłówka ma wymiary i właściwy priorytet; CLS < 0,1.
7. `lodash` zastąpiony natywnym kodem albo importem pojedynczej funkcji w wersji ESM; rozmiar pliku startowego zmniejszony (raport pakietu przed/po).
8. Pozostawiona memoizacja ma w kodzie komentarz z wynikiem pomiaru; nie ma memoizacji „na wszelki wypadek”.
9. W wersji TSX: `npm run build` bez błędów; w obu wersjach — testy z rozdziału 14 nadal przechodzą.

#T NOTE Wskazówka 1 — kolejność diagnozy
Zacznij od pomiaru całego ekranu w Profilerze (wejście, pisanie, kliknięcie, przewijanie) i w Performance przeglądarki. Dla każdego zgłoszenia ustal kategorię problemu: **ciężkie obliczenie** (→ `useMemo` lub przeniesienie), **zbędne rendery** (→ `memo` + stabilne props albo kompilator), **blokowanie interakcji** (→ przejście / wartość odroczona), **liczba węzłów DOM** (→ wirtualizacja), **rozmiar kodu** (→ `lazy`, lżejsze zależności), **stabilność układu** (→ wymiary obrazów). Jedno narzędzie nie naprawi wszystkiego.

#T NOTE Wskazówka 2 — pułapka „memo na wszystko”
Owinięcie `ReportsScreen` w `memo` nie zmieni nic, bo problemy są wewnątrz ekranu, a nie w jego rodzicu. `memo` na `Row` bez stabilnego `onSelect` też nie zadziała (lambda w JSX). A `useMemo` dla `visible` przy pisaniu w wyszukiwarce nie pomoże — `query` zmienia się przy każdym znaku; tu pomaga dopiero przejście lub wartość odroczona połączone z memoizacją tabeli.

#T PITFALL Typowe błędy w tym zadaniu
- Pomiar w trybie deweloperskim bez spowolnienia i bez porównania z buildem produkcyjnym — wyniki zniekształcone.
- Zmiana kilku rzeczy naraz — nie wiadomo, która dała efekt (zmieniaj jedną, mierz, zapisuj).
- `useDeferredValue` bez memoizacji tabeli — render ze starą wartością nadal jest kosztowny.
- Wirtualizacja bez stałej wysokości kontenera — lista renderuje wszystko albo nic.
- Leniwy wykres bez granicy `Suspense` blisko niego — cały ekran pokazuje fallback.

#T SUMMARY Podsumowanie rozdziału 16
W tym rozdziale poznałeś model renderowania z perspektywy wydajności i React DevTools Profiler, memoizację po pomiarze (`memo`, `useMemo`, `useCallback`), React Compiler, leniwe ładowanie z `lazy` i `Suspense`, przejścia i wartości odroczone, wirtualizację długich list, analizę i odchudzanie pakietu oraz Core Web Vitals z optymalizacją obrazów i czcionek. Najważniejsza zasada: zmierz, znajdź przyczynę, zastosuj właściwe narzędzie, zmierz ponownie. Wydajność nie zależy od JSX/TSX, ale typy (`readonly`, `import type`) pomagają pisać kod, który łatwiej zoptymalizować.

Boss zaliczony, gdy wszystkie dziewięć kryteriów akceptacji jest spełnionych, a raport pomiarów pozwala innej osobie odtworzyć każdą diagnozę.
