#T INTRO Trening: memo, useMemo i useCallback
Memoizacja to najczęściej źle używane narzędzie Reacta: albo dokłada się `useCallback` „na wszelki wypadek” wszędzie, albo `memo` nie działa, bo jeden z props jest co render nowym obiektem. Ten trening uczy patrzeć na rendery tak, jak widzi je React: **komponent renderuje się, gdy zmieni się jego stan, kontekst, który czyta, albo gdy renderuje się jego rodzic** — a `memo` przerywa tylko ten trzeci powód i tylko wtedy, gdy wszystkie props są identyczne według `Object.is`.

Narzędzia do każdego zadania:
- `console.log('render', nazwa)` na początku komponentu (pamiętaj o podwójnym renderze w StrictMode),
- React DevTools → Profiler z opcją „Record why each component rendered”,
- komponent `<Profiler id onRender>` w zadaniu 12.

Dwanaście zadań, w tym trzy „przewidź wynik”. Po każdym zadaniu zadaj sobie pytanie z lekcji 02: **czy zmierzyłem problem, zanim dodałem memoizację?**

#T CODE_BASIC Zadanie 1 — przewidź wynik: kto się renderuje
Użytkownik klika „+1”. Które komponenty wypiszą `render` (pomijając podwójny render StrictMode)?
```
// @check-skip
function App() {
  const [count, setCount] = useState(0);
  console.log('render App');
  return (
    <>
      <button onClick={() => setCount((c) => c + 1)}>+1</button>
      <Display value={count} />
      <Header title="DevDesk" />
      <Sidebar>
        <Menu />
      </Sidebar>
    </>
  );
}

function Display({ value }) { console.log('render Display'); return <p>{value}</p>; }
function Header({ title }) { console.log('render Header'); return <h1>{title}</h1>; }
function Sidebar({ children }) { console.log('render Sidebar'); return <aside>{children}</aside>; }
function Menu() { console.log('render Menu'); return <nav>…</nav>; }
```

#T NOTE Odpowiedź do zadania 1
Wszystkie pięć: `App`, `Display`, `Header`, `Sidebar`, `Menu`. Render rodzica renderuje **wszystkie** komponenty, które on tworzy w swoim JSX — niezależnie od tego, czy ich props się zmieniły. `Header` dostaje ten sam napis, a i tak się renderuje. `Menu` też, bo element `<Menu />` jest tworzony w JSX `App`. To nie błąd: render to tanie wywołanie funkcji, a DOM zmieni się tylko w `Display`. Problem zaczyna się dopiero, gdy któryś komponent jest kosztowny albo jest ich tysiące.

#T STEP_BY_STEP Zadanie 2 — memo, które nie działa, i naprawa useCallback
Masz `ProductList` z 500 wierszami `ProductRow`. Każdy wiersz ma przycisk „Do koszyka”. Rodzic ma też pole wyszukiwania i licznik koszyka.

Wymagania:
1. Owiń `ProductRow` w `memo` i dodaj w nim `console.log`.
2. Rodzic przekazuje `onAdd={(id) => setCart((c) => [...c, id])}` — sprawdź, że kliknięcie „Do koszyka” nadal renderuje wszystkie 500 wierszy.
3. Napraw przez `useCallback` z pustą tablicą zależności (setter jest stabilny, a forma funkcyjna nie czyta `cart`).
4. Sprawdź ponownie: kliknięcie renderuje tylko rodzica, a wpisywanie w wyszukiwarkę — tylko wiersze, które się pojawiły lub zniknęły.

Sprawdź się: po naprawie Profiler pokazuje wiersze jako „Did not render” przy dodaniu do koszyka.

#T CODE_JSX Rozwiązanie 2 (JSX)

// ProductList.jsx
import { memo, useCallback, useState } from 'react';

const ProductRow = memo(function ProductRow({ product, onAdd }) {
  console.log('render row', product.id);
  return (
    <li>
      {product.name} — {product.price} zł
      <button type="button" onClick={() => onAdd(product.id)}>Do koszyka</button>
    </li>
  );
});

export function ProductList({ products }) {
  const [query, setQuery] = useState('');
  const [cart, setCart] = useState([]);

  const handleAdd = useCallback((id) => setCart((c) => [...c, id]), []);
  const visible = products.filter((p) => p.name.toLowerCase().includes(query.toLowerCase()));

  return (
    <section>
      <p>W koszyku: {cart.length}</p>
      <input type="search" value={query} onChange={(e) => setQuery(e.target.value)} aria-label="Szukaj" />
      <ul>
        {visible.map((p) => <ProductRow key={p.id} product={p} onAdd={handleAdd} />)}
      </ul>
    </section>
  );
}

// ProductList.tsx
import { memo, useCallback, useState } from 'react';

type Product = { id: number; name: string; price: number };
type ProductRowProps = { product: Product; onAdd: (id: number) => void };

const ProductRow = memo(function ProductRow({ product, onAdd }: ProductRowProps) {
  console.log('render row', product.id);
  return (
    <li>
      {product.name} — {product.price} zł
      <button type="button" onClick={() => onAdd(product.id)}>Do koszyka</button>
    </li>
  );
});

export function ProductList({ products }: { products: Product[] }) {
  const [query, setQuery] = useState('');
  const [cart, setCart] = useState<number[]>([]);

  const handleAdd = useCallback((id: number) => setCart((c) => [...c, id]), []);
  const visible = products.filter((p) => p.name.toLowerCase().includes(query.toLowerCase()));

  return (
    <section>
      <p>W koszyku: {cart.length}</p>
      <input type="search" value={query} onChange={(e) => setQuery(e.target.value)} aria-label="Szukaj" />
      <ul>
        {visible.map((p) => <ProductRow key={p.id} product={p} onAdd={handleAdd} />)}
      </ul>
    </section>
  );

#T NOTE Dlaczego obiekt produktu nie psuje memo
`filter` zwraca nową tablicę, ale **te same obiekty** produktów — `product` w wierszu ma tę samą referencję co w poprzednim renderze, więc `memo` uznaje go za niezmieniony. Gdybyś w renderze mapował produkty na nowe obiekty (`products.map((p) => ({ ...p, label: … }))`), każdy wiersz dostawałby nowy `product` i `memo` przestałoby działać — wtedy pomogłoby `useMemo` na całej przekształconej tablicy.

#T CODE_BASIC Zadanie 3 — przewidź wynik: które props psują memo
`Card` jest owinięty w `memo`. Rodzic renderuje się z powodu zmiany innego stanu. W którym wariancie `Card` się **nie** wyrenderuje?
```
// @check-skip
const Card = memo(function Card(props) { /* … */ });

<Card title="Raport" count={3} />                         {/* A */}
<Card title="Raport" style={{ padding: 8 }} />            {/* B */}
<Card title="Raport" onOpen={() => open(1)} />            {/* C */}
<Card title="Raport"><p>Treść</p></Card>                  {/* D */}
<Card title="Raport" tags={TAGS} />                       {/* E — TAGS to stała poza komponentem */}
<Card title="Raport" tags={['a', 'b']} />                 {/* F */}
<Card title="Raport" onOpen={handleOpen} />               {/* G — handleOpen z useCallback([], …) */}
```

#T NOTE Odpowiedź do zadania 3
Nie wyrenderuje się w **A, E i G**.
- **A** — same wartości proste: `'Raport' === 'Raport'`, `3 === 3`.
- **B** — `{ padding: 8 }` to nowy obiekt przy każdym renderze.
- **C** — nowa funkcja strzałkowa przy każdym renderze.
- **D** — podchwytliwe: `children` to też prop, a `<p>Treść</p>` tworzy nowy obiekt elementu przy każdym renderze rodzica. `memo` z dziećmi w JSX prawie nigdy nie działa.
- **E** — stała modułu ma zawsze tę samą referencję.
- **F** — nowa tablica przy każdym renderze.
- **G** — stabilna funkcja z `useCallback`.

Wniosek: `memo` działa tylko w parze z props prostymi albo **stabilnymi** referencjami.

#T STEP_BY_STEP Zadanie 4 — useMemo dla kosztownego obliczenia
Tabela 5000 ticketów z filtrem, sortowaniem i przełącznikiem motywu (stan w tym samym komponencie).

Wymagania:
1. Funkcja `filterAndSort(tickets, query, sortKey)` — sztucznie spowolnij ją pętlą (`const start = performance.now(); while (performance.now() - start < 30) {}`), żeby problem był widoczny.
2. Bez memoizacji: przełączenie motywu zacina się, bo każdy render liczy filtr od nowa.
3. Owiń wynik w `useMemo` z zależnościami `[tickets, query, sortKey]`.
4. Zmierz przed i po (`console.time` wokół obliczenia albo Profiler).

Sprawdź się: przełącznik motywu reaguje natychmiast; wpisywanie w filtr nadal liczy (bo zmienia zależność) — i to jest poprawne.

#T CODE_JSX Rozwiązanie 4 (JSX)
```
// SlowTable.jsx
import { useMemo, useState } from 'react';

function filterAndSort(tickets, query, sortKey) {
  const start = performance.now();
  while (performance.now() - start < 30) { /* sztuczne spowolnienie */ }
  const q = query.trim().toLowerCase();
  return tickets
    .filter((t) => t.title.toLowerCase().includes(q))
    .toSorted((a, b) => String(a[sortKey]).localeCompare(String(b[sortKey])));
}

export function SlowTable({ tickets }) {
  const [query, setQuery] = useState('');
  const [sortKey, setSortKey] = useState('title');
  const [dark, setDark] = useState(false);

  const visible = useMemo(() => filterAndSort(tickets, query, sortKey), [tickets, query, sortKey]);

  return (
    <section className={dark ? 'theme-dark' : 'theme-light'}>
      <button type="button" onClick={() => setDark((d) => !d)}>Motyw</button>
      <input value={query} onChange={(e) => setQuery(e.target.value)} aria-label="Filtr" />
      <select value={sortKey} onChange={(e) => setSortKey(e.target.value)} aria-label="Sortuj">
        <option value="title">Tytuł</option>
        <option value="status">Status</option>
      </select>
      <p>Wyników: {visible.length}</p>
    </section>
  );
}
```

#T STEP_BY_STEP Zadanie 5 — useMemo dla stabilnej referencji w zależnościach Effectu
Komponent przekazuje obiekt opcji do hooka, który w Effecie łączy się z serwerem: `useLiveTickets({ status, assignee })`. Połączenie restartuje się przy każdym renderze.

Wymagania:
1. Napisz `useLiveTickets(filters)` z Effectem logującym `subscribe` / `unsubscribe` i zależnością `[filters]`.
2. W komponencie wywołaj go z literałem obiektu — zobacz restart przy każdym renderze (np. po kliknięciu niezwiązanego licznika).
3. Napraw na dwa sposoby: (a) `useMemo` na obiekcie filtrów w komponencie; (b) zmiana API hooka — zależności od pól prostych (`filters.status`, `filters.assignee`) zamiast obiektu.
4. Zdecyduj, która naprawa jest lepsza (notatka).

Sprawdź się: kliknięcie niezwiązanego licznika nie loguje `unsubscribe`.

#T CODE_JSX Rozwiązanie 5 (JSX)

// useLiveTickets.jsx
import { useEffect, useMemo, useState } from 'react';

// Wersja (b): hook zależy od wartości prostych, więc wywołujący nie musi niczego memoizować.
export function useLiveTickets({ status, assignee }) {
  useEffect(() => {
    console.log('subscribe', status, assignee);
    return () => console.log('unsubscribe', status, assignee);
  }, [status, assignee]);
}

export function LiveBoard() {

  const filters = useMemo(() => ({ status, assignee: 'me' }), [status]);

      <select value={status} onChange={(e) => setStatus(e.target.value)} aria-label="Status">
        <option value="OPEN">Otwarte</option>
        <option value="CLOSED">Zamknięte</option>
      </select>
      <button type="button" onClick={() => setClicks((c) => c + 1)}>Niezwiązany licznik: {clicks}</button>

  );

#T STEP_BY_STEP Zadanie 6 — useCallback i nieaktualne domknięcie
Ten kod ma zapisywać notatkę, ale zawsze zapisuje pusty tekst:

`const handleSave = useCallback(() => onSave(text), []);`

Wymagania:
1. Odtwórz błąd: `NoteEditor` z polem `text`, przyciskiem „Zapisz” (memo-komponent `SaveButton` z `onClick={handleSave}`).
2. Wyjaśnij, dlaczego zapisuje się pusty tekst.
3. Napraw: dopisz `text` (i `onSave`) do zależności. Sprawdź, ile razy renderuje się teraz `SaveButton` przy pisaniu.
4. Zastanów się, czy memoizacja ma tu w ogóle sens (notatka).

#T NOTE Czy ta memoizacja ma sens
Nie. `handleSave` zależy od `text`, który zmienia się przy każdym znaku — więc funkcja i tak jest tworzona co render, a `SaveButton` renderuje się przy każdym znaku. `memo` i `useCallback` tylko dokładają porównań. Jeśli przycisk byłby naprawdę kosztowny, możesz trzymać najnowszy tekst w refie albo użyć `useEffectEvent`-podobnego wzorca — ale przy jednym przycisku najlepszą optymalizacją jest usunięcie memoizacji. Memoizacja opłaca się tylko wtedy, gdy zależności zmieniają się **rzadziej** niż renderuje się komponent.

#T STEP_BY_STEP Zadanie 8 — zamiast memo: przeniesienie stanu w dół
Często lepszą optymalizacją niż `memo` jest zmiana struktury. `Dashboard` ma pole wyszukiwania (stan `query`) i bardzo kosztowny wykres `ExpensiveChart`, który nie korzysta z `query`.

Wymagania:
1. Wersja wyjściowa: `query` w `Dashboard` → każdy znak renderuje wykres.
2. Technika 1 — **stan w dół**: wydziel `SearchPanel` z własnym stanem `query`; `Dashboard` przestaje się renderować przy pisaniu.
3. Technika 2 — **treść jako children**: gdy stan musi zostać w komponencie-opakowaniu (np. `ScrollTracker` śledzi pozycję przewijania), przekaż wykres jako `children` — element tworzy rodzic, więc zmiana stanu opakowania go nie renderuje.
4. Ani jednego `memo`, `useMemo` ani `useCallback`.

Sprawdź się: Profiler pokazuje, że przy pisaniu w wyszukiwarce i przewijaniu `ExpensiveChart` się nie renderuje.

#T PITFALL Funkcja porównująca, która zapomina o propsie
Gdy dopiszesz prop `onHover`, a `arePropsEqual` go nie porówna, komponent zachowa **starą** funkcję z pierwszego renderu — z nieaktualnymi wartościami w domknięciu. Zasada: funkcja porównująca musi uwzględniać **wszystkie** props (także funkcje), a głębokie porównanie dużych struktur bywa droższe niż sam render. Częściej lepiej naprawić źródło — np. nie tworzyć nowej tablicy, gdy dane się nie zmieniły.

#T STEP_BY_STEP Zadanie 10 — stabilna wartość kontekstu
`TicketsProvider` udostępnia `{ tickets, selectedId, select, remove }`. Konsumentów jest kilkadziesiąt, a Provider renderuje się też z powodu stanu, którego konsumenci nie używają (np. `lastSync`).

Wymagania:
1. `select` i `remove` przez `useCallback` (setter w formie funkcyjnej — puste zależności).
2. `value` przez `useMemo` z zależnościami `[tickets, selectedId, select, remove]`.
3. Stan `lastSync` aktualizowany co 10 s w Providerze — pokaż w konsoli, że konsumenci się **nie** renderują.
4. Komponent `TicketCount` (konsument) owinięty w `memo` i renderowany jako dziecko Providera.

Sprawdź się: zmiana `lastSync` nie renderuje `TicketCount`; usunięcie ticketu — renderuje.

#T CODE_JSX Rozwiązanie 10 (JSX)
```
// TicketsProvider.jsx
import { createContext, memo, useCallback, useContext, useEffect, useMemo, useState } from 'react';

const TicketsContext = createContext(null);

export function TicketsProvider({ initial, children }) {
  const [tickets, setTickets] = useState(initial);
  const [selectedId, setSelectedId] = useState(null);
  const [lastSync, setLastSync] = useState(() => new Date());

  useEffect(() => {
    const id = setInterval(() => setLastSync(new Date()), 10_000);
    return () => clearInterval(id);
  }, []);

  const select = useCallback((id) => setSelectedId(id), []);
  const remove = useCallback((id) => setTickets((list) => list.filter((t) => t.id !== id)), []);
  const value = useMemo(() => ({ tickets, selectedId, select, remove }), [tickets, selectedId, select, remove]);

  return (
    <TicketsContext value={value}>
      <small>Synchronizacja: {lastSync.toLocaleTimeString('pl-PL')}</small>
      {children}
    </TicketsContext>
  );
}

export function useTickets() {
  const ctx = useContext(TicketsContext);
  if (!ctx) throw new Error('useTickets musi być użyty wewnątrz <TicketsProvider>');
  return ctx;
}

export const TicketCount = memo(function TicketCount() {
  const { tickets } = useTickets();
  console.log('render TicketCount');
  return <p>Ticketów: {tickets.length}</p>;
});
```
