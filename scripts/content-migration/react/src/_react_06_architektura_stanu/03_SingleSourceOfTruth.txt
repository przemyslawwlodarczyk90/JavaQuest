#T INTRO Rozgrzewka i problem: licznik zaznaczonych kłamie
Rozgrzewka: Co to znaczy, że komponent jest kontrolowany przez rodzica? Gdzie umieszczasz stan używany przez dwa komponenty? Dlaczego kopiowanie props do stanu tworzy „drugą prawdę”?

Problem: DevDesk dostaje zaznaczanie wielu ticketów checkboxami i pasek akcji zbiorczych: „Zaznaczono 3 — Zamknij — Przypisz do mnie”. Pierwsza wersja trzyma `selectedTickets` (tablicę obiektów) i `selectedCount` (liczbę). Po zamknięciu zaznaczonych ticketów licznik pokazuje 3, w tabeli nic nie jest zaznaczone, a po usunięciu ticketu „zaznaczony” obiekt nadal wisi w tablicy. Ta lekcja uczy zasady **jednego źródła prawdy**.

#T DEFINITION Jedno źródło prawdy
Każda informacja w aplikacji ma dokładnie jedno miejsce, w którym jest przechowywana. Wszystko inne jest z niej wyliczane. Trzy praktyczne reguły:
1. **Przechowuj identyfikatory, nie kopie obiektów** — `selectedIds`, a nie `selectedTickets`. Obiekty bierzesz z głównej listy przy renderze, więc zawsze są aktualne.
2. **Nie przechowuj tego, co da się policzyć** — `selectedCount = selectedIds.size`, „czy zaznaczono wszystkie” = porównanie zbiorów.
3. **Nie trzymaj tej samej informacji w dwóch formach** — np. `isOpen` i `status` naraz; wystarczy `status`.

#T CODE_JSX Zaznaczanie wielu ticketów (JSX)
`Set` przechowuje unikalne ID. W stanie trzymasz nowy `Set` przy każdej zmianie (niemutowalnie).
```
// useSelection.js
import { useState } from 'react';

export function useSelection() {
  const [selectedIds, setSelectedIds] = useState(() => new Set());

  function toggle(id) {
    setSelectedIds((prev) => {
      const next = new Set(prev);
      if (next.has(id)) next.delete(id);
      else next.add(id);
      return next;
    });
  }

  function setAll(ids, selected) {
    setSelectedIds((prev) => {
      const next = new Set(prev);
      ids.forEach((id) => (selected ? next.add(id) : next.delete(id)));
      return next;
    });
  }

  const clear = () => setSelectedIds(new Set());

  return { selectedIds, toggle, setAll, clear };
}
```

#T CODE_TSX Zaznaczanie wielu ticketów (TSX)
`useState<Set<number>>` — generyk mówi, że zbiór przechowuje liczby. Inicjalizacja funkcją `() => new Set()` tworzy zbiór tylko przy pierwszym renderze.
```
// useSelection.ts
import { useState } from 'react';

export function useSelection() {
  const [selectedIds, setSelectedIds] = useState<Set<number>>(() => new Set());

  function toggle(id: number) {
    setSelectedIds((prev) => {
      const next = new Set(prev);
      if (next.has(id)) next.delete(id);
      else next.add(id);
      return next;
    });
  }

  function setAll(ids: readonly number[], selected: boolean) {
    setSelectedIds((prev) => {
      const next = new Set(prev);
      ids.forEach((id) => (selected ? next.add(id) : next.delete(id)));
      return next;
    });
  }

  const clear = () => setSelectedIds(new Set<number>());

  return { selectedIds, toggle, setAll, clear };
}
```

#T NOTE JSX ↔ TSX — typ zbioru i leniwa inicjalizacja
`useState(new Set())` w TSX dałoby typ `Set<unknown>`, więc `next.add(id)` przyjęłoby cokolwiek, a odczyt dawałby `unknown`. Generyk `Set<number>` zapisuje decyzję „przechowuję ID ticketów”. Inicjalizacja funkcją (`useState(() => new Set())`) działa identycznie w obu wersjach: React wywoła funkcję tylko raz, przy montowaniu — bez niej `new Set()` tworzyłby się przy każdym renderze i był wyrzucany. Ma to znaczenie przy kosztownych wartościach startowych (np. odczyt z localStorage).

#T CODE_BASIC Dane wyliczane z zaznaczenia
```
import type { Ticket } from '../types';

export function selectionInfo(visible: readonly Ticket[], selectedIds: ReadonlySet<number>) {
  const selectedVisible = visible.filter((t) => selectedIds.has(t.id));
  return {
    count: selectedIds.size,
    allVisibleSelected: visible.length > 0 && selectedVisible.length === visible.length,
    someVisibleSelected: selectedVisible.length > 0 && selectedVisible.length < visible.length,
    selectedTickets: selectedVisible,
  };
}
```

#T CODE_PRACTICAL Checkbox „zaznacz wszystkie” w stanie pośrednim
Właściwość DOM `indeterminate` (kreska zamiast ptaszka) nie ma atrybutu HTML — ustawiasz ją przez ref callback.
```
type SelectAllProps = { all: boolean; some: boolean; onChange: (selected: boolean) => void };

export function SelectAllCheckbox({ all, some, onChange }: SelectAllProps) {
  return (
    <input
      type="checkbox"
      aria-label="Zaznacz wszystkie widoczne"
      checked={all}
      ref={(el) => {
        if (el) el.indeterminate = some;
      }}
      onChange={(e) => onChange(e.target.checked)}
    />
  );
}
```

#T CODE_WRONG Zduplikowany stan zaznaczenia
```
const [selectedTickets, setSelectedTickets] = useState([]);
const [selectedCount, setSelectedCount] = useState(0);

function toggle(ticket) {
  setSelectedTickets((prev) => [...prev, ticket]); // kopia obiektu — zestarzeje się
  setSelectedCount((c) => c + 1);                  // łatwo zapomnieć przy usuwaniu
}
```

#T CODE_RIGHT Jedno źródło prawdy
```
const { selectedIds, toggle } = useSelection();
const selectedTickets = tickets.filter((t) => selectedIds.has(t.id)); // zawsze aktualne
const selectedCount = selectedTickets.length;                           // zawsze zgodne
```

#T DEFINITION Sprzątanie po usunięciu danych
Gdy ticket zostanie usunięty, jego ID może zostać w `selectedIds`. Jeśli liczysz `selectedTickets` z listy (jak wyżej), „osierocone” ID są nieszkodliwe — nie pojawią się na ekranie. Licznik oparty na `selectedTickets.length` zamiast `selectedIds.size` jest więc bezpieczniejszy. Mimo to porządnie jest usunąć ID w tym samym handlerze, który usuwa ticket — to reakcja na to samo zdarzenie, więc robisz to w handlerze, nie w efekcie.

#T STEP_BY_STEP Budujemy razem: akcje zbiorcze w DevDesk
1. Utwórz `useSelection` i użyj go w `Main`.
2. Dodaj kolumnę z checkboxem w każdym wierszu (`checked={selectedIds.has(t.id)}`, `onChange={() => toggle(t.id)}`) i `SelectAllCheckbox` w nagłówku, działający na ticketach widocznych na bieżącej stronie.
3. Gdy coś jest zaznaczone, pokaż nad tabelą pasek „Zaznaczono N — Zamknij — Przypisz do mnie — Wyczyść”.
4. „Zamknij” zmienia status wszystkich zaznaczonych (`map` z `selectedIds.has`) i czyści zaznaczenie w tym samym handlerze.
5. Przy usuwaniu ticketu usuń też jego ID z zaznaczenia.
6. Sprawdź scenariusz z problemu: zaznacz 3, zamknij przy filtrze „Otwarte” — tickety znikają z listy, licznik pokazuje 0, pasek akcji znika.
7. Zaznacz wszystkie na stronie 1, przejdź na stronę 2 — checkbox w nagłówku jest pusty, a licznik nadal pokazuje zaznaczone z poprzedniej strony (zastanów się, czy to dobre zachowanie dla użytkownika i opisz decyzję w komentarzu).

#T PITFALL Dwa pola opisujące jedno
`{ status: 'CLOSED', isClosed: true, closedAt: '...' }` — trzy pola, z których każde może się rozjechać z pozostałymi. Jeśli `isClosed` zawsze wynika ze `status`, usuń je i licz `ticket.status === 'CLOSED'`. Data zamknięcia jest nową informacją (nie wynika ze statusu), więc może zostać jako osobne pole.

#T SUMMARY Kryterium akceptacji i podsumowanie
Jedno źródło prawdy: każda informacja przechowywana w jednym miejscu, reszta wyliczana. Przechowuj ID zamiast kopii obiektów, nie przechowuj liczników ani flag wynikających z innych danych. Zaznaczenie wielu elementów trzymaj jako `Set` ID, aktualizowany niemutowalnie. W TSX generyk `Set<number>` i `ReadonlySet` dokumentują i chronią strukturę.

Kryterium akceptacji: zaznaczanie wielu ticketów działa z checkboxem „zaznacz wszystkie” w stanie pośrednim, pasek akcji zbiorczych zamyka i przypisuje zaznaczone, a licznik zaznaczonych nigdy nie rozjeżdża się z tabelą — także po zamknięciu i usunięciu ticketów.
