#T INTRO Rozgrzewka i problem: DevDesk rośnie bez planu
Rozgrzewka: Czym są dane wyliczane? Dlaczego formularz edycji potrzebuje `key`? Co zwraca `useActionState`?

Problem: `Main` w DevDesk ma już dziesięć zmiennych stanu, dwadzieścia funkcji i renderuje tabelę, kartę, formularze i modal. Każda nowa funkcja to pytanie: gdzie dodać stan? Który komponent ma go znać? Ta lekcja to metoda „Thinking in React” z oficjalnej dokumentacji — pięć kroków, którymi zaprojektujesz każdy ekran, zanim napiszesz kod. Ćwiczysz ją na nowym ekranie DevDesk: „Mój dzień” (lista moich ticketów pogrupowana według priorytetu z filtrem i licznikami).

#T DEFINITION Pięć kroków Thinking in React
1. **Rozbij UI na hierarchię komponentów** — narysuj ramki na makiecie, nazwij je; jeden komponent = jedna odpowiedzialność.
2. **Zbuduj wersję statyczną** — komponenty renderują dane z props, bez żadnego stanu i interakcji. Dane płyną z góry na dół.
3. **Znajdź minimalny, kompletny stan** — wypisz wszystkie dane i odrzuć te, które: nie zmieniają się w czasie, przychodzą z props albo da się je wyliczyć.
4. **Ustal, gdzie stan ma żyć** — dla każdego kawałka stanu znajdź wszystkie komponenty, które go używają, i ich najbliższego wspólnego rodzica. Tam umieść stan.
5. **Dodaj przepływ danych w górę** — komponenty-dzieci zmieniają stan rodzica przez przekazane im funkcje (`onChange`, `onSelect`).

#T CODE_JSX Krok 2: wersja statyczna (JSX)
Same props, bez stanu — kod łatwy do sprawdzenia i przetestowania.
```
// MyDayPage.jsx
const ORDER = ['CRITICAL', 'HIGH', 'MEDIUM', 'LOW'];

function TicketItem({ ticket }) {
  return <li>#{ticket.id} {ticket.title}</li>;
}

function PriorityGroup({ priority, tickets }) {
  if (tickets.length === 0) return null;
  return (
    <section>
      <h3>{priority} ({tickets.length})</h3>
      <ul>{tickets.map((t) => <TicketItem key={t.id} ticket={t} />)}</ul>
    </section>
  );
}

export function PriorityGroups({ tickets }) {
  return ORDER.map((p) => (
    <PriorityGroup key={p} priority={p} tickets={tickets.filter((t) => t.priority === p)} />
  ));
}
```

#T CODE_TSX Krok 2: wersja statyczna (TSX)
Typy props powstają naturalnie w kroku 2 — opisują dane, które płyną w dół.
```
// MyDayPage.tsx
import type { Ticket, TicketPriority } from '../types';

const ORDER: TicketPriority[] = ['CRITICAL', 'HIGH', 'MEDIUM', 'LOW'];

function TicketItem({ ticket }: { ticket: Ticket }) {
  return <li>#{ticket.id} {ticket.title}</li>;
}

function PriorityGroup({ priority, tickets }: { priority: TicketPriority; tickets: Ticket[] }) {
  if (tickets.length === 0) return null;
  return (
    <section>
      <h3>{priority} ({tickets.length})</h3>
      <ul>{tickets.map((t) => <TicketItem key={t.id} ticket={t} />)}</ul>
    </section>
  );
}

export function PriorityGroups({ tickets }: { tickets: readonly Ticket[] }) {
  return ORDER.map((p) => (
    <PriorityGroup key={p} priority={p} tickets={tickets.filter((t) => t.priority === p)} />
  ));
}
```

#T NOTE JSX ↔ TSX — typy jako produkt uboczny projektowania
W metodzie Thinking in React typy w TSX nie są dodatkową pracą — to zapis decyzji z kroków 1–2: „`PriorityGroup` dostaje priorytet i listę ticketów”. Gdy w kroku 4 przeniesiesz stan wyżej lub niżej, kompilator pokaże wszystkie miejsca, gdzie props trzeba dodać lub usunąć. W JSX tę samą mapę przepływu danych musisz trzymać w głowie albo w dokumentacji — dlatego w JSX szczególnie warto zacząć od narysowania hierarchii.

#T STEP_BY_STEP Krok 3: minimalny stan ekranu „Mój dzień”
Lista wszystkich danych na ekranie i decyzja:
1. Lista wszystkich ticketów — stan (zmienia się), ale **już istnieje** w `Main`; tu przychodzi z props.
2. Login zalogowanej osoby — stały w tej lekcji (później z kontekstu).
3. Tekst wyszukiwania — **stan** (zmienia go użytkownik).
4. „Ukryj zamknięte” — **stan**.
5. Moje tickety — wyliczane (`tickets.filter(t => t.assignee === login)`).
6. Tickety po filtrach — wyliczane.
7. Grupy według priorytetu i ich liczniki — wyliczane.
8. „7 ticketów” w nagłówku — wyliczane.

Wynik: tylko **dwa** nowe kawałki stanu: `query` i `hideClosed`.

#T STEP_BY_STEP Krok 4: gdzie umieścić stan
1. `query` czyta `SearchInput` (wyświetla) i `PriorityGroups` (filtruje przez dane od rodzica) → wspólny rodzic: `MyDayPage`.
2. `hideClosed` czyta `HideClosedToggle` i filtr → wspólny rodzic: `MyDayPage`.
3. Lista ticketów potrzebna jest też ekranowi tabeli → zostaje w `Main` (lub wyżej) i przychodzi do `MyDayPage` przez props.
4. Gdyby jakiś stan był potrzebny tylko jednemu komponentowi (np. „rozwinięta grupa”) — zostaje w tym komponencie.

#T CODE_PRACTICAL Kroki 4–5: stan w rodzicu i przepływ w górę
```
import { useState } from 'react';
import type { Ticket } from '../types';
import { PriorityGroups } from './MyDayPage';

export function MyDayPage({ tickets, login }: { tickets: readonly Ticket[]; login: string }) {
  const [query, setQuery] = useState('');
  const [hideClosed, setHideClosed] = useState(true);

  const q = query.trim().toLowerCase();
  const visible = tickets
    .filter((t) => t.assignee === login)
    .filter((t) => !hideClosed || t.status !== 'CLOSED')
    .filter((t) => !q || t.title.toLowerCase().includes(q));

  return (
    <div>
      <h2>Dzień dobry, {login} — {visible.length} ticketów</h2>
      <input aria-label="Szukaj" value={query} onChange={(e) => setQuery(e.target.value)} />
      <label>
        <input type="checkbox" checked={hideClosed} onChange={(e) => setHideClosed(e.target.checked)} /> Ukryj zamknięte
      </label>
      <PriorityGroups tickets={visible} />
    </div>
  );
}
```

#T PITFALL Zaczynanie od stanu
Najczęstszy błąd projektowy: pisanie `useState` dla wszystkiego, co widać na ekranie, zanim powstanie wersja statyczna. Kończy się zdublowanym stanem (`myTickets`, `groupedTickets`, `count`), który trzeba synchronizować efektami. Wersja statyczna wymusza myślenie „jakie dane wejściowe wystarczą do narysowania ekranu” — i zwykle okazuje się, że dużo mniej niż się wydawało.

#T WHEN_TO_USE Kiedy stosować metodę
Przy każdym nowym ekranie lub większej funkcji — nawet w głowie, w pięć minut. Szczególnie gdy: ekran ma kilka współpracujących części (filtr + lista + liczniki), pojawia się pokusa dodania `useEffect` do synchronizacji dwóch stanów, nie wiesz, w którym komponencie umieścić nowy stan. Kolejne lekcje rozdziału rozwijają kroki 4–5: podnoszenie stanu, jedno źródło prawdy, reducer, kontekst i własne hooki.

#T SUMMARY Kryterium akceptacji i podsumowanie
Thinking in React: (1) hierarchia komponentów, (2) wersja statyczna z props, (3) minimalny stan — odrzuć stałe, props i dane wyliczane, (4) stan w najbliższym wspólnym rodzicu komponentów, które go używają, (5) zmiany w górę przez funkcje w props. W TSX typy props powstają w kroku 2 i pilnują przepływu danych przy przenoszeniu stanu.

Kryterium akceptacji: ekran „Mój dzień” pokazuje tickety zalogowanej osoby pogrupowane według priorytetu, z wyszukiwaniem i przełącznikiem „Ukryj zamknięte”; ekran ma tylko dwa nowe kawałki stanu, a liczniki i grupy są wyliczane.
