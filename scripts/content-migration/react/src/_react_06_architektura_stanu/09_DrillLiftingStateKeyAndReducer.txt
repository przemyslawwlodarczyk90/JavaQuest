#T INTRO Trening: gdzie żyje stan i jak go zmieniać
Trzy mechanizmy z tego rozdziału decydują o tym, czy aplikacja „trzyma się kupy”: **podnoszenie stanu** (wspólny stan w najbliższym wspólnym rodzicu), **pozycja w drzewie i `key`** (kiedy React zachowuje, a kiedy resetuje stan) oraz **`useReducer`** (cała logika zmian w jednej czystej funkcji). Ten trening to dwanaście zadań, w tym cztery „przewidź wynik” — właśnie w zachowaniu i resetowaniu stanu intuicja najczęściej zawodzi.

Pracuj jak w poprzednich treningach: najpierw sam, w `.jsx`, potem w `.tsx`, na końcu porównanie z rozwiązaniem. W zadaniach z reducerem dopisz do każdego reducera 2–3 asercje (`console.assert` albo test Vitest) — reducer to czysta funkcja i testuje się go bez renderowania.

#T STEP_BY_STEP Zadanie 1 — podnoszenie stanu: przelicznik temperatur
Dwa pola: „Celsjusz” i „Fahrenheit”. Wpisanie wartości w jedno aktualizuje drugie.

Wymagania:
1. Komponent `TemperatureInput` (bez stanu) przyjmuje `scale` (`'c' | 'f'`), `value` i `onChange`.
2. Rodzic `Converter` trzyma **jeden** stan: `{ scale, value }` — skalę i tekst ostatnio edytowanego pola.
3. Wartość drugiego pola jest wyliczana (`c = (f − 32) × 5/9`, `f = c × 9/5 + 32`), zaokrąglona do 1 miejsca; pusty lub niepoprawny wpis → drugie pole puste.
4. Pod polami: „Woda wrze” przy ≥ 100 °C.

Sprawdź się: w stanie nie ma dwóch temperatur — jest tylko to, co wpisał użytkownik, i w którym polu.

#T CODE_JSX Rozwiązanie 1 (JSX)
```
// Converter.jsx
import { useState } from 'react';

const NAMES = { c: 'Celsjusz', f: 'Fahrenheit' };
const toC = (f) => ((f - 32) * 5) / 9;
const toF = (c) => (c * 9) / 5 + 32;

function convert(text, fn) {
  const n = Number.parseFloat(text);
  return Number.isNaN(n) ? '' : String(Math.round(fn(n) * 10) / 10);
}

function TemperatureInput({ scale, value, onChange }) {
  return (
    <label>
      {NAMES[scale]}
      <input value={value} onChange={(e) => onChange(e.target.value)} inputMode="decimal" />
    </label>
  );
}

export function Converter() {
  const [temp, setTemp] = useState({ scale: 'c', value: '' });

  const celsius = temp.scale === 'c' ? temp.value : convert(temp.value, toC);
  const fahrenheit = temp.scale === 'f' ? temp.value : convert(temp.value, toF);

  return (
    <fieldset>
      <TemperatureInput scale="c" value={celsius} onChange={(value) => setTemp({ scale: 'c', value })} />
      <TemperatureInput scale="f" value={fahrenheit} onChange={(value) => setTemp({ scale: 'f', value })} />
      {Number.parseFloat(celsius) >= 100 && <p>Woda wrze</p>}
    </fieldset>
  );
}
```

#T STEP_BY_STEP Zadanie 2 — z niekontrolowanego na kontrolowany: akordeon „jeden otwarty”
Masz `Panel` z własnym stanem `open`. Każdy panel otwiera się niezależnie. Nowe wymaganie: **naraz otwarty może być tylko jeden panel**.

Wymagania:
1. Usuń stan z `Panel`; zamiast niego props `isOpen` i `onToggle`.
2. Rodzic `Accordion` trzyma `openId` (albo `null`).
3. Kliknięcie otwartego panelu go zamyka; kliknięcie innego — zamyka poprzedni i otwiera nowy.
4. Panele generowane z tablicy `{ id, title, content }`.

Sprawdź się: `Panel` nie importuje `useState`, a `Accordion` ma dokładnie jeden stan.

#T CODE_JSX Rozwiązanie 2 (JSX)

```
// Accordion.jsx
import { useState } from 'react';

function Panel({ title, isOpen, onToggle, children }) {
  return (
    <section className="panel">
      <h3>
        <button type="button" aria-expanded={isOpen} onClick={onToggle}>{title}</button>
      </h3>
      {isOpen && <div className="panel__body">{children}</div>}
    </section>
  );
}

export function Accordion({ items }) {
  const [openId, setOpenId] = useState(null);

  return (
    <div>
      {items.map((item) => (
        <Panel
          key={item.id}
          title={item.title}
          isOpen={openId === item.id}
          onToggle={() => setOpenId((current) => (current === item.id ? null : item.id))}
        >
          {item.content}
        </Panel>
      ))}
    </div>
  );
}
```

#T CODE_BASIC Zadanie 3 — przewidź wynik: kiedy stan przeżywa
`Counter` ma własny stan `count`. W każdym wariancie użytkownik klika „+1” trzy razy (licznik pokazuje 3), a potem przełącza checkbox, który zmienia `flag`. Co pokaże licznik po przełączeniu?
```
// @check-skip
// A
{flag ? <Counter color="red" /> : <Counter color="blue" />}

// B
{flag ? <Counter /> : <p>Ukryty</p>}
// (i z powrotem — co pokaże licznik po ponownym pojawieniu się?)

// C
{flag ? <div><Counter /></div> : <section><Counter /></section>}

// D
{flag ? <Counter key="red" /> : <Counter key="blue" />}

// E
<>
  {flag && <Banner />}
  <Counter />
</>
```

#T NOTE Odpowiedź do zadania 3
- **A — 3.** Ten sam typ komponentu na tej samej pozycji w drzewie. Dla Reacta to ta sama instancja, zmieniły się tylko props.
- **B — 0** po ponownym pojawieniu się. Gdy w miejscu `Counter` stanął `<p>`, licznik został odmontowany, a jego stan zniszczony.
- **C — 0.** Zmienił się typ elementu-rodzica (`div` → `section`), więc całe poddrzewo jest budowane od nowa.
- **D — 0.** Różne `key` na tej samej pozycji to dla Reacta różne komponenty.
- **E — 3.** To podchwytliwe: `{flag && <Banner />}` zostawia w drzewie „dziurę” (`false`), gdy flaga jest wyłączona, więc `Counter` zawsze zajmuje drugie miejsce wśród dzieci fragmentu. Stan przeżywa.

Zasada: React kojarzy stan z **typem i pozycją** w drzewie, a `key` pozwala tę tożsamość nadać jawnie.

```
// MessengerDrafts.jsx
import { useState } from 'react';

function ChatBox({ contact, draft, onDraftChange, onSend }) {
  return (
    <section>
      <textarea value={draft} onChange={(e) => onDraftChange(e.target.value)} placeholder={`Wiadomość do: ${contact.name}`} />
      <button type="button" disabled={!draft.trim()} onClick={onSend}>Wyślij do {contact.name}</button>
    </section>
  );
}

export function MessengerDrafts({ contacts }) {
  const [selectedId, setSelectedId] = useState(contacts[0].id);
  const [drafts, setDrafts] = useState({});
  const contact = contacts.find((c) => c.id === selectedId);
  const draft = drafts[selectedId] ?? '';

  function send() {
    alert(`Do ${contact.name}: ${draft}`);
    setDrafts((d) => ({ ...d, [selectedId]: '' }));
  }

  return (
    <div className="messenger">
      <nav>
        {contacts.map((c) => (
          <button key={c.id} type="button" aria-pressed={c.id === selectedId} onClick={() => setSelectedId(c.id)}>
            {c.name} {drafts[c.id]?.trim() && '✎'}
          </button>
        ))}
      </nav>
      <ChatBox
        contact={contact}
        draft={draft}
        onDraftChange={(text) => setDrafts((d) => ({ ...d, [selectedId]: text }))}
        onSend={send}
      />
    </div>
  );
}
```

#T STEP_BY_STEP Zadanie 7 — pierwszy reducer: licznik z akcjami
Przepisz licznik z treningu useState na `useReducer`.

#T CODE_JSX Rozwiązanie 7 (JSX)
```
// counterReducer.js
export const initialCounter = { count: 0, step: 1 };

export function counterReducer(state, action) {
  switch (action.type) {
    case 'incremented':
      return { ...state, count: state.count + state.step };
    case 'decremented':
      return { ...state, count: state.count - state.step };
    case 'reset':
      return initialCounter;
    case 'set':
      return { ...state, count: action.value };
    case 'stepChanged':
      return { ...state, step: action.step };
    default:
      throw new Error(`Nieznana akcja: ${action.type}`);
  }
}

// Asercje — reducer testujesz jak zwykłą funkcję:
console.assert(counterReducer({ count: 1, step: 5 }, { type: 'incremented' }).count === 6);
console.assert(counterReducer({ count: 9, step: 1 }, { type: 'reset' }).count === 0);
console.assert(counterReducer(initialCounter, { type: 'set', value: 100 }).count === 100);
```

#T CODE_TSX Rozwiązanie 7 (TSX)
```
// counterReducer.ts
export type CounterState = { count: number; step: number };
export type CounterAction =
  | { type: 'incremented' }
  | { type: 'decremented' }
  | { type: 'reset' }
  | { type: 'set'; value: number }
  | { type: 'stepChanged'; step: number };

export const initialCounter: CounterState = { count: 0, step: 1 };

export function counterReducer(state: CounterState, action: CounterAction): CounterState {
  switch (action.type) {
    case 'incremented':
      return { ...state, count: state.count + state.step };
    case 'decremented':
      return { ...state, count: state.count - state.step };
    case 'reset':
      return initialCounter;
    case 'set':
      return { ...state, count: action.value }; // TS wie, że ta akcja ma value
    case 'stepChanged':
      return { ...state, step: action.step };
    default: {
      const unknownAction: never = action; // brakujący case = błąd kompilacji
      throw new Error(`Nieznana akcja: ${JSON.stringify(unknownAction)}`);
    }
  }
}

console.assert(counterReducer({ count: 1, step: 5 }, { type: 'incremented' }).count === 6);
console.assert(counterReducer({ count: 9, step: 1 }, { type: 'reset' }).count === 0);
console.assert(counterReducer(initialCounter, { type: 'set', value: 100 }).count === 100);
```

```
// ReducerCounter.tsx
import { useReducer } from 'react';
import { counterReducer, initialCounter } from './counterReducer';

export function ReducerCounter() {
  const [state, dispatch] = useReducer(counterReducer, initialCounter);

  return (
    <div className="counter">
      <label>
        Krok
        <input type="number" value={state.step} onChange={(e) => dispatch({ type: 'stepChanged', step: Number(e.target.value) })} />
      </label>
      <button type="button" onClick={() => dispatch({ type: 'decremented' })}>−</button>
      <output>{state.count}</output>
      <button type="button" onClick={() => dispatch({ type: 'incremented' })}>+</button>
      <button type="button" onClick={() => dispatch({ type: 'reset' })}>Reset</button>
      <button type="button" onClick={() => dispatch({ type: 'set', value: 100 })}>Ustaw 100</button>
    </div>
  );
}
```

```
      return { ...state, todos: [...state.todos, { id: action.id, title: action.title, done: false }] };
    case 'toggled':
      return { ...state, todos: state.todos.map((t) => (t.id === action.id ? { ...t, done: !t.done } : t)) };
    case 'renamed':
      return { ...state, todos: state.todos.map((t) => (t.id === action.id ? { ...t, title: action.title } : t)) };
    case 'deleted':
      return { ...state, todos: state.todos.filter((t) => t.id !== action.id) };
    case 'completedCleared':
      return { ...state, todos: state.todos.filter((t) => !t.done) };
    case 'filterChanged':
      return { ...state, filter: action.filter };
    default:
      throw new Error(`Nieznana akcja: ${action.type}`);
  }
}

const s1 = todosReducer(initialTodos, { type: 'added', id: 'x', title: 'Test' });

console.assert(todosReducer(s1, { type: 'toggled', id: 'x' }).todos[0].done === true);
console.assert(JSON.stringify(todosReducer(s1, { type: 'deleted', id: 'x' })) === JSON.stringify(todosReducer(s1, { type: 'deleted', id: 'x' })));
```

```
    case 'completedCleared':
```

#T NOTE JSX ↔ TSX — switch bez default
W TSX reducer z pełną unią akcji może nie mieć `default`: gdy obsłużysz wszystkie warianty, TypeScript wie, że funkcja zawsze zwraca `TodosState`. Jeśli dodasz nową akcję do unii i zapomnisz o `case`, kompilator zgłosi, że funkcja może zwrócić `undefined`. W JSX `default` z `throw` jest konieczny — inaczej literówka w `dispatch({ type: 'toogled' })` zwróci `undefined` jako nowy stan i aplikacja wybuchnie w zupełnie innym miejscu.

#T NOTE Odpowiedź do zadania 9
- **A** — mutacja i zwrócenie tej samej referencji: React porówna stary i nowy stan (`Object.is`), uzna je za identyczne i **nie wyrenderuje** zmian.
- **B** — w StrictMode React wywołuje reducer dwa razy, żeby wykryć nieczystość. Wyniki się różnią (dwa różne UUID) — React użyje jednego, ale zachowanie jest niedeterministyczne, a testy reducera nie mogą przewidzieć ID. Generuj ID w handlerze i przekazuj w akcji.
- **C** — efekt uboczny w reducerze: wykona się dwa razy w StrictMode, a przy ewentualnym ponownym odtworzeniu akcji (narzędzia deweloperskie, time travel) — znowu. Zapis do `localStorage` należy do handlera albo Effectu.
- **D** — nowa tablica, ale zmutowany obiekt zadania, który współdzieli poprzedni stan. W StrictMode podwójne wywołanie przełączy `done` **dwa razy** — kliknięcie pozornie nic nie robi. To jeden z najczęstszych „zagadkowych” błędów z reducerami.

#T STEP_BY_STEP Zadanie 10 — reducer z historią: cofnij i ponów
W treningu niemutowalnych aktualizacji „cofnij” wymagało dwóch stanów zmienianych razem (`history`, `index`). Zamknij je w jednym reducerze.

Wymagania:
1. Stan: `{ past: [], present: wartość, future: [] }`.
2. Akcje: `changed` (nowa wartość), `undone`, `redone`, `cleared` (czyści historię, zostawia `present`).
3. `changed` przenosi `present` do `past`, czyści `future`.
4. `undone` na pustym `past` zwraca **ten sam** stan.
5. Napisz to generycznie: reducer nie wie, czy `present` to lista zadań, tekst czy rysunek.

Sprawdź się: zmień wartość trzy razy, cofnij dwa razy, zmień raz — `future` jest puste, a `past` ma dwa elementy.

#T CODE_JSX Rozwiązanie 10 (JSX)
```
// historyReducer.js
export const createHistory = (present) => ({ past: [], present, future: [] });

export function historyReducer(state, action) {
  switch (action.type) {
    case 'changed':
      return { past: [...state.past, state.present], present: action.value, future: [] };
    case 'undone': {
      if (state.past.length === 0) return state;
      const previous = state.past.at(-1);
      return { past: state.past.slice(0, -1), present: previous, future: [state.present, ...state.future] };
    }
    case 'redone': {
      if (state.future.length === 0) return state;
      const [next, ...rest] = state.future;
      return { past: [...state.past, state.present], present: next, future: rest };
    }
    case 'cleared':
      return createHistory(state.present);
    default:
      throw new Error(`Nieznana akcja: ${action.type}`);
  }
}
```

```
// historyReducer.ts
export type History<T> = { past: T[]; present: T; future: T[] };
export type HistoryAction<T> =
  | { type: 'changed'; value: T }
  | { type: 'undone' }
  | { type: 'redone' }
  | { type: 'cleared' };

export const createHistory = <T,>(present: T): History<T> => ({ past: [], present, future: [] });

export function historyReducer<T>(state: History<T>, action: HistoryAction<T>): History<T> {
  switch (action.type) {
    case 'changed':
      return { past: [...state.past, state.present], present: action.value, future: [] };
    case 'undone': {
      if (state.past.length === 0) return state;
      const previous = state.past[state.past.length - 1];
      return { past: state.past.slice(0, -1), present: previous, future: [state.present, ...state.future] };
    }
    case 'redone': {
      if (state.future.length === 0) return state;
      const [next, ...rest] = state.future;
      return { past: [...state.past, state.present], present: next, future: rest };
    }
    case 'cleared':
      return createHistory(state.present);
  }
}
```

#T STEP_BY_STEP Zadanie 11 — leniwa inicjalizacja reducera

#T STEP_BY_STEP Zadanie 12 — useState czy useReducer: refaktoryzacja koszyka
Weź `MiniCart` z treningu useState (obiekt ilości + przyciski ±, „Wyczyść”) i rozbuduj go o kod rabatowy oraz wybór dostawy, a potem zdecyduj, czy przejść na reducer.

Wymagania:
1. Nowe dane: `coupon` (tekst wpisany przez użytkownika), `appliedCoupon` (kod zatwierdzony przyciskiem), `shipping` (`'courier' | 'pickup'`).
2. Napisz wersję z reducerem: akcje `quantityChanged`, `cartCleared`, `couponTyped`, `couponApplied`, `shippingChanged`. „Wyczyść koszyk” czyści też kupon.
3. Suma, rabat (10% przy kodzie `REACT10`), koszt dostawy (15 zł kurier, 0 zł odbiór, darmowa powyżej 200 zł) — wyliczane w komponencie z funkcji pomocniczej `summarize(state)`.
4. Napisz w dwóch zdaniach, co zyskałeś względem pięciu osobnych `useState` (odpowiedź w notatce).

Sprawdź się: każda reguła biznesowa (rabat, dostawa) jest w czystej funkcji, którą da się przetestować bez Reacta.

#T CODE_JSX Rozwiązanie 12 (JSX)
```
// cartReducer.js
export const PRODUCTS = [
  { id: 'kb', name: 'Klawiatura', price: 179 },
  { id: 'ms', name: 'Mysz', price: 59 },
];

export const initialCart = { quantities: {}, coupon: '', appliedCoupon: null, shipping: 'courier' };

export function cartReducer(state, action) {
  switch (action.type) {
    case 'quantityChanged': {
      const next = Math.max(0, (state.quantities[action.id] ?? 0) + action.delta);
      return { ...state, quantities: { ...state.quantities, [action.id]: next } };
    }
    case 'cartCleared':
      return { ...state, quantities: {}, coupon: '', appliedCoupon: null };
    case 'couponTyped':
      return { ...state, coupon: action.text };
    case 'couponApplied':
      return { ...state, appliedCoupon: state.coupon.trim().toUpperCase() };
    case 'shippingChanged':
      return { ...state, shipping: action.shipping };
    default:
      throw new Error(`Nieznana akcja: ${action.type}`);
  }
}

export function summarize(state) {
  const subtotal = PRODUCTS.reduce((sum, p) => sum + p.price * (state.quantities[p.id] ?? 0), 0);
  const discount = state.appliedCoupon === 'REACT10' ? Math.round(subtotal * 0.1) : 0;
  const shipping = state.shipping === 'pickup' || subtotal - discount > 200 || subtotal === 0 ? 0 : 15;
  return { subtotal, discount, shipping, total: subtotal - discount + shipping };
}
```

#T NOTE Odpowiedź: co dał reducer
Reguły „co się dzieje po akcji” (wyczyszczenie koszyka czyści też kupon) są w jednym miejscu, a nie rozsiane po kilku handlerach wywołujących po trzy settery. Handlery w komponencie mówią tylko, **co się stało** (`dispatch({ type: 'cartCleared' })`), a reducer i `summarize` da się przetestować bez renderowania. Przy jednym–dwóch niezależnych polach `useState` pozostaje prostszy — reducer opłaca się, gdy zmiany dotyczą kilku pól naraz albo akcje mają reguły.

#T SUMMARY Podsumowanie treningu
Przećwiczyłeś trzy decyzje architektoniczne: **gdzie** trzymać stan (najbliższy wspólny rodzic, komponenty kontrolowane przez `value` i `onChange`, słownik po ID, gdy dane mają przetrwać przełączanie), **kiedy** React go zachowuje lub resetuje (typ i pozycja w drzewie, `key`, pułapka komponentu definiowanego w komponencie) oraz **jak** zamknąć logikę zmian w czystym reducerze (akcje jako zdarzenia, ID generowane poza reducerem, brak mutacji i efektów ubocznych, leniwa inicjalizacja, reducer generyczny). W TSX unie akcji z dyskryminatorem `type` pilnowały kompletu pól każdej akcji i kompletu `case` w reducerze.

Kryterium zaliczenia: poprawne odpowiedzi do zadań 3, 5 i 9; każdy reducer z zadań 7–12 ma asercje i przechodzi je także przy podwójnym wywołaniu (StrictMode).
