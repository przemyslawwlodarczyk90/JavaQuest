#T INTRO Rozgrzewka i problem: dziesięć funkcji zmieniających jedną listę
Rozgrzewka: Kiedy React zachowuje stan komponentu, a kiedy go niszczy? Dlaczego zaznaczenie trzymasz jako `Set` ID? Jak sprawić, by notatki przetrwały przełączanie ticketów?

Problem: `Main` w DevDesk ma funkcje `closeTicket`, `reopenTicket`, `deleteTicket`, `assignTicket`, `createTicket`, `updateTicket`, `closeSelected`, `assignSelected`, `addComment`, `addTag`… Każda wywołuje `setTickets` z inną transformacją, a część zmienia też zaznaczenie i komunikat. Logika aktualizacji jest rozproszona po komponencie i trudno ją przetestować. **Reducer** zbiera wszystkie przejścia stanu w jednej czystej funkcji.

#T DEFINITION useReducer
`const [state, dispatch] = useReducer(reducer, initialState)`:
- **reducer** — czysta funkcja `(state, action) => nowyStan`; dostaje aktualny stan i opis zdarzenia, zwraca nowy stan (niemutowalnie),
- **action** — zwykły obiekt opisujący, *co się stało*: `{ type: 'ticketClosed', id: 42 }`,
- **dispatch(action)** — wysyła akcję; React wywołuje reducer i renderuje komponent z nowym stanem.

Komponent przestaje mówić *jak* zmienić stan („zamapuj listę i ustaw status”), a mówi tylko *co się stało* („zamknięto ticket 42”). Cała logika „jak” jest w reducerze.

#T ANALOGY Okienko w urzędzie
Zamiast samemu grzebać w szafie z dokumentami (setState z transformacją), składasz w okienku wniosek na formularzu (akcja): „wniosek o zamknięcie sprawy nr 42”. Urzędnik (reducer) zna procedury dla każdego rodzaju wniosku i aktualizuje dokumenty. Ty nie musisz znać procedur, a wszystkie procedury są w jednym miejscu.

#T CODE_JSX Reducer ticketów (JSX)
```
// ticketsReducer.js
export function ticketsReducer(state, action) {
  switch (action.type) {
    case 'created':
      return { ...state, tickets: [action.ticket, ...state.tickets], selectedId: action.ticket.id };
    case 'closed':
      return {
        ...state,
        tickets: state.tickets.map((t) => (t.id === action.id ? { ...t, status: 'CLOSED' } : t)),
      };
    case 'assigned':
      return {
        ...state,
        tickets: state.tickets.map((t) => (t.id === action.id ? { ...t, assignee: action.assignee } : t)),
      };
    case 'deleted':
      return {
        ...state,
        tickets: state.tickets.filter((t) => t.id !== action.id),
        selectedId: state.selectedId === action.id ? null : state.selectedId,
      };
    case 'selected':
      return { ...state, selectedId: action.id };
    default:
      throw new Error(`Nieznana akcja: ${action.type}`);
  }
}
```

#T CODE_TSX Reducer ticketów (TSX)
Akcje to unia z dyskryminatorem `type` (rozdział 01). W każdej gałęzi `case` TypeScript wie, jakie pola ma akcja — `action.assignee` jest dostępne tylko w `'assigned'`.
```
// ticketsReducer.ts
import type { Ticket } from '../types';

export type TicketsState = { tickets: Ticket[]; selectedId: number | null };

export type TicketsAction =
  | { type: 'created'; ticket: Ticket }
  | { type: 'closed'; id: number }
  | { type: 'assigned'; id: number; assignee: string | null }
  | { type: 'deleted'; id: number }
  | { type: 'selected'; id: number | null };

export function ticketsReducer(state: TicketsState, action: TicketsAction): TicketsState {
  switch (action.type) {
    case 'created':
      return { ...state, tickets: [action.ticket, ...state.tickets], selectedId: action.ticket.id };
    case 'closed':
      return {
        ...state,
        tickets: state.tickets.map((t) => (t.id === action.id ? { ...t, status: 'CLOSED' } : t)),
      };
    case 'assigned':
      return {
        ...state,
        tickets: state.tickets.map((t) => (t.id === action.id ? { ...t, assignee: action.assignee } : t)),
      };
    case 'deleted':
      return {
        ...state,
        tickets: state.tickets.filter((t) => t.id !== action.id),
        selectedId: state.selectedId === action.id ? null : state.selectedId,
      };
    case 'selected':
      return { ...state, selectedId: action.id };
    default: {
      const unknownAction: never = action;
      throw new Error(`Nieznana akcja: ${JSON.stringify(unknownAction)}`);
    }
  }
}
```

#T NOTE JSX ↔ TSX — reducer to miejsce, gdzie TSX błyszczy
Unia akcji daje w TSX trzy zabezpieczenia naraz: `dispatch({ type: 'closd', id: 1 })` (literówka) jest błędem kompilacji, `dispatch({ type: 'assigned', id: 1 })` bez `assignee` — też, a `never` w `default` wymusza obsłużenie każdej nowej akcji dodanej do unii. W JSX literówka w `type` zostanie wykryta dopiero w czasie działania (dlatego `default` rzuca wyjątek — błąd głośny jest lepszy niż cichy). Konwencja nazw: akcje opisują **zdarzenia w czasie przeszłym** (`'closed'`, `'created'`), a nie polecenia (`'setStatus'`).

#T CODE_BASIC Komponent z dispatch
```
import { useReducer } from 'react';
import { tickets as initialTickets } from '../data/tickets';
import { ticketsReducer } from './ticketsReducer';

export function TicketsScreen() {
  const [state, dispatch] = useReducer(ticketsReducer, { tickets: initialTickets, selectedId: null });
  const selected = state.tickets.find((t) => t.id === state.selectedId) ?? null;

  return (
    <div>
      <ul>
        {state.tickets.map((t) => (
          <li key={t.id}>
            <button type="button" onClick={() => dispatch({ type: 'selected', id: t.id })}>{t.title}</button>
            <button type="button" onClick={() => dispatch({ type: 'closed', id: t.id })}>Zamknij</button>
          </li>
        ))}
      </ul>
      {selected && <p>Wybrany: #{selected.id}</p>}
    </div>
  );
}
```

#T CODE_PRACTICAL Reducer jest łatwy do przetestowania
Reducer to czysta funkcja bez Reacta — test to wywołanie z danymi i porównanie wyniku (Vitest w rozdziale 14).
```
import { ticketsReducer, type TicketsState } from './ticketsReducer';

const start: TicketsState = {
  tickets: [{ id: 1, title: 'A', description: '', status: 'OPEN', priority: 'LOW', assignee: null, createdAt: '2026-10-01', tags: [] }],
  selectedId: 1,
};

const afterDelete = ticketsReducer(start, { type: 'deleted', id: 1 });
console.assert(afterDelete.tickets.length === 0, 'ticket usunięty');
console.assert(afterDelete.selectedId === null, 'zaznaczenie wyczyszczone');
console.assert(start.tickets.length === 1, 'stan wejściowy nie został zmieniony');
```

#T DEFINITION Reducer musi być czysty
Reducer podlega tym samym zasadom co komponent: dla tego samego stanu i akcji zwraca ten sam wynik, niczego nie mutuje i nie wykonuje efektów ubocznych (żadnych zapytań do API, `localStorage`, `Date.now()`, `Math.random()`). Wartości zmienne — ID nowego ticketu, data — wylicz w handlerze i przekaż w akcji (`{ type: 'created', ticket }`). W StrictMode React wywołuje reducer dwukrotnie, żeby wykryć nieczystość.

#T CODE_WRONG Efekt uboczny w reducerze
```
case 'created': {
  const ticket = { ...action.values, id: Date.now() }; // inne ID przy każdym wywołaniu
  fetch('/api/tickets', { method: 'POST', body: JSON.stringify(ticket) }); // efekt w reducerze
  state.tickets.push(ticket); // mutacja
  return state;
}
```

#T CODE_RIGHT Dane zmienne z handlera, reducer czysty
```
function handleCreate(values) {
  const ticket = { ...values, id: Date.now(), createdAt: new Date().toISOString() };
  dispatch({ type: 'created', ticket });
}
// w reducerze:
// case 'created': return { ...state, tickets: [action.ticket, ...state.tickets] };
```

#T WHEN_TO_USE useState czy useReducer
`useState` wystarcza dla niezależnych, prostych wartości: tekst wyszukiwania, przełącznik, numer strony. `useReducer` warto wybrać, gdy: wiele zdarzeń zmienia ten sam fragment stanu, jedna akcja zmienia kilka pól naraz (usunięcie ticketu czyści też zaznaczenie), logika aktualizacji jest na tyle złożona, że chcesz ją testować osobno, albo chcesz przekazać w dół jedną funkcję `dispatch` zamiast dziesięciu callbacków. Można mieszać oba w jednym komponencie.

#T SUMMARY Kryterium akceptacji i podsumowanie
`useReducer(reducer, initial)` zwraca `[stan, dispatch]`; reducer to czysta funkcja `(stan, akcja) => nowyStan`, a akcje opisują zdarzenia (`{ type: 'closed', id }`). Wartości zmienne (ID, daty) wyliczasz w handlerze i przekazujesz w akcji. Reducer łatwo testować bez Reacta. W TSX akcje są unią z dyskryminatorem `type`, a `never` w `default` pilnuje obsłużenia każdej akcji.

Kryterium akceptacji: wszystkie zmiany listy ticketów i zaznaczenia w DevDesk przechodzą przez jeden reducer, komponent wywołuje tylko `dispatch`, a reducer przechodzi prosty test bez renderowania.
