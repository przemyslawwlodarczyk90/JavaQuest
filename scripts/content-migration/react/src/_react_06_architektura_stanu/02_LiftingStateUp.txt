#T INTRO Rozgrzewka i problem: dwa komponenty, dwie prawdy
Rozgrzewka: Jakie są trzy pytania, które eliminują dane ze stanu? Gdzie umieszczasz stan potrzebny dwóm komponentom? Dlaczego zaczynasz od wersji statycznej?

Problem: pasek narzędzi DevDesk ma przełącznik „Widok: tabela / karty”, a licznik w nagłówku mówi „Widoczne: 12”. Ktoś umieścił stan widoku w `Toolbar`, a filtr statusu w `TicketTable`. Efekt: licznik w nagłówku nie wie o filtrze, a tabela nie wie, że użytkownik wybrał widok kart. Rozwiązaniem jest **podniesienie stanu** (lifting state up) do wspólnego rodzica.

#T DEFINITION Podnoszenie stanu
Gdy dwa komponenty muszą korzystać z tej samej wartości, usuń stan z obu i umieść go **w najbliższym wspólnym rodzicu**. Rodzic przekazuje wartość w dół przez props, a funkcję zmiany — jako prop `onX`. Komponenty-dzieci stają się **kontrolowane**: nie mają własnego stanu tej wartości, tylko wyświetlają to, co dostały, i zgłaszają chęć zmiany.

To ten sam wzorzec, który znasz z inputu kontrolowanego (`value` + `onChange`) — tylko zastosowany do Twoich komponentów.

#T CODE_JSX Przed: stan zamknięty w dzieciach (JSX)
Każdy komponent ma własną kopię — liczba w nagłówku nie zna filtra z tabeli.
```
// przed — dwie niezależne prawdy
import { useState } from 'react';

function Toolbar() {
  const [view, setView] = useState('table');
  return <button onClick={() => setView(view === 'table' ? 'cards' : 'table')}>Widok: {view}</button>;
}

function TicketList({ tickets }) {
  const [status, setStatus] = useState('ALL');
  const visible = tickets.filter((t) => status === 'ALL' || t.status === status);
  return (
    <>
      <select value={status} onChange={(e) => setStatus(e.target.value)}>
        <option value="ALL">Wszystkie</option>
        <option value="OPEN">Otwarte</option>
      </select>
      <ul>{visible.map((t) => <li key={t.id}>{t.title}</li>)}</ul>
    </>
  );
}

export function Page({ tickets }) {
  return (
    <>
      <h2>Widoczne: ???</h2>
      <Toolbar />
      <TicketList tickets={tickets} />
    </>
  );
}
```

#T CODE_TSX Po: stan w rodzicu, dzieci kontrolowane (TSX)
Rodzic `Page` jest właścicielem `view` i `status`. Liczba widocznych to dane wyliczane w rodzicu.
```
// po — jedno źródło prawdy w Page
import { useState } from 'react';
import type { Ticket, TicketStatus } from '../types';

type View = 'table' | 'cards';
type StatusFilter = TicketStatus | 'ALL';

function Toolbar({ view, onViewChange }: { view: View; onViewChange: (v: View) => void }) {
  return (
    <button type="button" onClick={() => onViewChange(view === 'table' ? 'cards' : 'table')}>
      Widok: {view}
    </button>
  );
}

type ListProps = { tickets: Ticket[]; view: View; status: StatusFilter; onStatusChange: (s: StatusFilter) => void };

function TicketList({ tickets, view, status, onStatusChange }: ListProps) {
  return (
    <>
      <select value={status} onChange={(e) => onStatusChange(e.target.value as StatusFilter)}>
        <option value="ALL">Wszystkie</option>
        <option value="OPEN">Otwarte</option>
      </select>
      <ul className={view === 'cards' ? 'cards' : 'rows'}>
        {tickets.map((t) => <li key={t.id}>{t.title}</li>)}
      </ul>
    </>
  );
}

export function Page({ tickets }: { tickets: readonly Ticket[] }) {
  const [view, setView] = useState<View>('table');
  const [status, setStatus] = useState<StatusFilter>('ALL');
  const visible = tickets.filter((t) => status === 'ALL' || t.status === status);

  return (
    <>
      <h2>Widoczne: {visible.length}</h2>
      <Toolbar view={view} onViewChange={setView} />
      <TicketList tickets={visible} view={view} status={status} onStatusChange={setStatus} />
    </>
  );
}
```

#T NOTE JSX ↔ TSX — refaktoryzacja z kompilatorem
Podnoszenie stanu to refaktoryzacja: usuwasz `useState` z dziecka i dodajesz props. W TSX po zmianie typu props `TicketList` kompilator wskazuje każde miejsce użycia, któremu brakuje `status` i `onStatusChange` — nie da się zapomnieć o żadnym. W JSX zapomniany prop oznacza `undefined` i błąd „onStatusChange is not a function” dopiero po kliknięciu. Dlatego przy większych refaktoryzacjach stanu w projekcie JSX warto mieć testy (rozdział 14).

#T VISUAL_EXAMPLE Przepływ danych po podniesieniu
                 Page  [view, status]  →  visible = filter(tickets, status)
               ┌───────────┼──────────────────────────┐
               ▼           ▼                          ▼
   <h2>Widoczne: {visible.length}>   Toolbar           TicketList
                                     view ▼  ▲ onViewChange   status ▼ ▲ onStatusChange
                                                         tickets={visible} ▼

Wartości płyną w dół (▼), prośby o zmianę — w górę (▲). Każdy kawałek stanu ma jednego właściciela.

#T DEFINITION Komponent, który może działać w obu trybach
Czasem chcesz, żeby komponent działał samodzielnie (z własnym stanem), ale pozwalał rodzicowi przejąć kontrolę. Konwencja: jeśli rodzic poda `value` — komponent jest kontrolowany; jeśli nie — używa własnego stanu z `defaultValue`. Tak działają natywne pola formularza. Zbudujesz taki komponent w rozdziale o wzorcach komponentów; na razie wybieraj jeden tryb świadomie.

#T CODE_PRACTICAL Zakładki statusów sterowane z zewnątrz
```
import type { TicketStatus } from '../types';

type StatusTabsProps = {
  value: TicketStatus | 'ALL';
  counts: Record<TicketStatus | 'ALL', number>;
  onChange: (value: TicketStatus | 'ALL') => void;
};

const TABS: { value: TicketStatus | 'ALL'; label: string }[] = [
  { value: 'ALL', label: 'Wszystkie' },
  { value: 'OPEN', label: 'Otwarte' },
  { value: 'IN_PROGRESS', label: 'W toku' },
  { value: 'CLOSED', label: 'Zamknięte' },
];

export function StatusTabs({ value, counts, onChange }: StatusTabsProps) {
  return (
    <div role="tablist" aria-label="Status">
      {TABS.map((tab) => (
        <button key={tab.value} type="button" role="tab" aria-selected={value === tab.value} onClick={() => onChange(tab.value)}>
          {tab.label} ({counts[tab.value]})
        </button>
      ))}
    </div>
  );
}
```

#T STEP_BY_STEP Budujemy razem: wspólny stan widoku i filtra
1. Znajdź w DevDesk stan, który jest używany przez więcej niż jeden komponent (filtr statusu, wyszukiwanie, widok).
2. Dodaj przełącznik widoku „Tabela / Karty” w pasku narzędzi; stan `view` umieść w `Main`.
3. Przygotuj prosty widok kart (`TicketCards`) i renderuj go zamiast tabeli, gdy `view === 'cards'`.
4. Zastąp listę rozwijaną statusu zakładkami `StatusTabs` z licznikami; liczniki wylicz w `Main` z `tickets`.
5. Sprawdź: zmiana zakładki filtruje oba widoki, liczniki w zakładkach i „Widoczne: N” w nagłówku zawsze się zgadzają.
6. W React DevTools znajdź, gdzie jest stan — powinien być w `Main`, a `Toolbar`, `StatusTabs`, `TicketTable` i `TicketCards` nie mają hooków `State` dla tych wartości.

#T PITFALL Kopiowanie props do stanu dziecka
`function TicketList({ status }) { const [localStatus, setLocalStatus] = useState(status); ... }` tworzy drugą prawdę: zmiana w rodzicu nie zmieni `localStatus` (wartość startowa jest użyta raz). Jeśli wartość ma pochodzić od rodzica — używaj props bezpośrednio. Jeśli to tylko wartość początkowa — nazwij prop jawnie (`initialStatus`, `defaultStatus`), żeby było jasne, że późniejsze zmiany nie mają wpływu.

#T SUMMARY Kryterium akceptacji i podsumowanie
Gdy kilka komponentów potrzebuje tej samej wartości, podnieś stan do ich najbliższego wspólnego rodzica, przekazuj wartość w dół przez props i zmianę przez `onX`. Dzieci stają się kontrolowane i nie mają kopii stanu. Dane zależne od tego stanu (liczniki, przefiltrowana lista) wyliczasz w rodzicu. W TSX kompilator wskazuje wszystkie miejsca do zmiany przy przenoszeniu stanu.

Kryterium akceptacji: przełącznik widoku, zakładki statusów, licznik w nagłówku i oba widoki listy korzystają z jednego stanu w `Main` i zawsze pokazują spójne dane.
