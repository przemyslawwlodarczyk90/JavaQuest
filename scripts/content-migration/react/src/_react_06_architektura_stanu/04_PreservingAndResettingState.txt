#T INTRO Rozgrzewka i problem: stan, który znika albo zostaje nie wtedy, kiedy trzeba
Rozgrzewka: Dlaczego przechowujesz ID zamiast kopii obiektu? Po co inicjalizować stan funkcją? Jak React traktuje komponent z innym `key`?

Problem: w DevDesk dzieją się dwie dziwne rzeczy. Po przełączeniu widoku „Tabela / Karty” znika wpisany komentarz w karcie szczegółów, choć karta nie miała nic wspólnego z widokiem. A w panelu „Szybka notatka”, który pokazuje się dla wybranego ticketu, notatka do #42 pojawia się także przy #43. Obie sytuacje wynikają z tej samej reguły: React zachowuje lub niszczy stan według **pozycji i typu** komponentu w drzewie.

#T DEFINITION Reguły zachowania stanu
1. **Ten sam typ komponentu na tej samej pozycji → stan zachowany**, nawet gdy zmieniają się props.
2. **Inny typ na tej samej pozycji → stan całego poddrzewa zniszczony** (np. `<div>` zamienione na `<section>`, `<TicketTable>` na `<TicketCards>`).
3. **Komponent znika z drzewa → jego stan przepada**; po ponownym pojawieniu się zaczyna od wartości początkowych.
4. **Inny `key` → traktowany jak inny komponent** — stan zniszczony i utworzony od nowa.

„Pozycja” to miejsce w drzewie JSX zwracanym przez rodzica, nie miejsce na ekranie.

#T CODE_JSX Stan niszczony przez zmianę typu opakowania (JSX)
Opakowanie zmienia się z `div` na `section`, więc React uznaje całe poddrzewo za nowe — `CommentBox` traci wpisany tekst.
```
// DetailsPanel.jsx
import { useState } from 'react';

function CommentBox() {
  const [text, setText] = useState('');
  return <textarea aria-label="Komentarz" value={text} onChange={(e) => setText(e.target.value)} />;
}

export function DetailsPanel({ compact }) {
  if (compact) {
    return (
      <div className="details details--compact">
        <CommentBox />
      </div>
    );
  }
  return (
    <section className="details">
      <CommentBox />
    </section>
  );
}
```

#T CODE_TSX Stan zachowany: ta sama struktura, zmienia się tylko klasa (TSX)
Ten sam element i ten sam komponent na tej samej pozycji — tekst w `CommentBox` przetrwa przełączenie trybu.
```
// DetailsPanel.tsx
import { useState } from 'react';
import clsx from 'clsx';

function CommentBox() {
  const [text, setText] = useState('');
  return <textarea aria-label="Komentarz" value={text} onChange={(e) => setText(e.target.value)} />;
}

export function DetailsPanel({ compact }: { compact: boolean }) {
  return (
    <section className={clsx('details', compact && 'details--compact')}>
      <CommentBox />
    </section>
  );
}
```

#T NOTE JSX ↔ TSX — tu typy nie pomogą
Zachowanie i niszczenie stanu to mechanizm Reacta działający w czasie renderowania — TypeScript nie wie nic o pozycjach w drzewie, więc obie wersje zachowują się identycznie i mają te same pułapki. Jedyna różnica w przykładzie to typ props `compact`. Narzędzie, które tu pomaga, to React DevTools: zaznacz komponent, przełącz tryb i sprawdź, czy wartości hooków zostały, czy wyzerowały się.

#T VISUAL_EXAMPLE Pozycja w drzewie
{isEditing ? <EditForm /> : <TicketCard />}
  pozycja 0:  EditForm  ⇄  TicketCard     → inny typ: przełączenie niszczy stan obu

{isEditing && <EditForm />}
{!isEditing && <TicketCard />}
  pozycja 0:  EditForm albo false
  pozycja 1:  false albo TicketCard        → różne pozycje: każdy ma swój stan, ale ukryty jest odmontowany

{tickets.map(t => <Row key={t.id} />)}
  pozycja określona przez key             → kolejność może się zmieniać, stan idzie za kluczem

#T DEFINITION Kiedy resetować, a kiedy zachować
- **Resetuj** (inny `key`), gdy komponent zaczyna pokazywać **inny obiekt**: formularz innego ticketu, notatka do innego ticketu, czat z inną osobą.
- **Zachowaj** (ta sama pozycja i typ), gdy zmienia się tylko **sposób prezentacji** tego samego obiektu: tryb kompaktowy, motyw, rozmiar.
- **Zachowaj mimo ukrycia**: jeśli komponent ma znikać z ekranu, ale pamiętać stan (np. zakładki), albo nie odmontowuj go (ukryj CSS-em lub atrybutem `hidden`), albo podnieś stan do rodzica, który nie znika, albo użyj komponentu `Activity` z React 19.2+ (rozdział 17).

#T CODE_PRACTICAL Notatka per ticket przez key
```
import { useState } from 'react';
import type { Ticket } from '../types';

function QuickNote({ ticketTitle }: { ticketTitle: string }) {
  const [note, setNote] = useState('');
  return (
    <label>
      Notatka do „{ticketTitle}”
      <textarea value={note} onChange={(e) => setNote(e.target.value)} />
    </label>
  );
}

export function NotePanel({ ticket }: { ticket: Ticket }) {
  // key={ticket.id} → każdy ticket ma własną, świeżą notatkę
  return <QuickNote key={ticket.id} ticketTitle={ticket.title} />;
}
```

#T DEFINITION Zachowanie stanu wielu obiektów
Notatka z `key` resetuje się przy przełączeniu ticketu — tekst do #42 przepada, gdy przejdziesz do #43 i z powrotem. Jeśli notatki mają przetrwać przełączanie, stan musi żyć wyżej i być indeksowany ID: `const [notes, setNotes] = useState({})` w rodzicu, a komponent dostaje `value={notes[ticket.id] ?? ''}` i `onChange`. To znowu podnoszenie stanu — tym razem do słownika „ID → wartość”.

#T STEP_BY_STEP Budujemy razem: diagnoza i naprawa
1. Odtwórz problem 1: w karcie szczegółów wpisz komentarz, przełącz widok listy na „Karty”. Jeśli komentarz znika, znajdź w JSX miejsce, gdzie zmienia się typ elementu-rodzica karty lub karta jest renderowana w innej gałęzi warunku.
2. Napraw tak, by karta szczegółów zawsze była na tej samej pozycji (warunek tylko wokół samej listy).
3. Odtwórz problem 2: dodaj `QuickNote` bez `key`, wpisz notatkę do #42, wybierz #43 — notatka zostaje.
4. Dodaj `key={ticket.id}` — notatka jest osobna dla każdego ticketu, ale przepada przy powrocie.
5. Przenieś notatki do słownika w `Main` (`Record<number, string>` w TSX) i przekaż wartość przez props — notatki przetrwają przełączanie.
6. W React DevTools obserwuj hooki `State` w `QuickNote` przy każdym wariancie.

#T PITFALL Komponent zdefiniowany w komponencie — znowu
Komponent zdefiniowany wewnątrz innego (rozdział 02) to szczególny przypadek reguły 2: przy każdym renderze rodzica funkcja komponentu jest nowa, więc typ na danej pozycji jest „inny” i stan zawsze się resetuje. Objaw: pole tekstowe traci fokus i tekst po każdym wpisanym znaku.

#T SUMMARY Kryterium akceptacji i podsumowanie
React zachowuje stan komponentu, dopóki na tej samej pozycji drzewa renderowany jest ten sam typ z tym samym `key`. Zmiana typu (także opakowującego elementu) lub `key` niszczy stan poddrzewa, a odmontowanie kasuje stan na zawsze. Resetuj stan przez `key`, gdy komponent pokazuje inny obiekt; zachowuj go, gdy zmienia się tylko prezentacja; podnoś do słownika w rodzicu, gdy stan wielu obiektów ma przetrwać przełączanie. TypeScript nie pomaga tu — pomagają React DevTools.

Kryterium akceptacji: przełączenie widoku listy nie kasuje komentarza w karcie szczegółów, a szybkie notatki są osobne dla każdego ticketu i przetrwają przełączanie między ticketami.
