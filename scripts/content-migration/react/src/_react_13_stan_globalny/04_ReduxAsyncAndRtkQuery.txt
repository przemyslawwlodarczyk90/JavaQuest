#T INTRO Rozgrzewka i problem: Redux i dane z serwera
Rozgrzewka: Co generuje `createSlice`? Dlaczego w reducerach RTK można „mutować” stan? Jak wyprowadzić `RootState` w TSX?

Problem: w projektach na Reduxie spotkasz dwa sposoby pobierania danych. Starszy: **thunki** (`createAsyncThunk`) — akcja asynchroniczna, która pobiera dane i zapisuje je w slice’ie, z ręczną obsługą stanów `pending/fulfilled/rejected`. Nowszy: **RTK Query** — wbudowana w Redux Toolkit biblioteka danych z cache, bardzo podobna do TanStack Query. W tej lekcji poznasz oba, żeby czytać istniejący kod i świadomie wybierać.

#T DEFINITION createAsyncThunk
`createAsyncThunk('nazwa', async (argument, api) => wynik)` tworzy akcję asynchroniczną. Gdy ją wyślesz (`dispatch(fetchTickets(params))`), RTK automatycznie wysyła trzy akcje: `nazwa/pending`, potem `nazwa/fulfilled` (z wynikiem) albo `nazwa/rejected` (z błędem). Slice reaguje na nie w sekcji `extraReducers`. `api` daje m.in. `signal` (przerwanie), `getState`, `rejectWithValue` (błąd z danymi do pokazania).

Thunk to dobre narzędzie do **logiki wieloetapowej** (np. „zapisz, potem odśwież dwa inne fragmenty stanu, potem pokaż powiadomienie”). Do zwykłego pobierania danych w nowym kodzie lepiej użyć RTK Query lub TanStack Query.

#T CODE_JSX Thunk i stan żądania w slice’ie (JSX)
```
// ticketsSlice.js
import { createAsyncThunk, createSlice } from '@reduxjs/toolkit';

export const fetchTickets = createAsyncThunk('tickets/fetch', async (status, { signal, rejectWithValue }) => {
  const res = await fetch(`/api/tickets?status=${status}`, { signal });
  if (!res.ok) return rejectWithValue(`Błąd ${res.status}`);
  return res.json(); // { items, total }
});

const ticketsSlice = createSlice({
  name: 'tickets',
  initialState: { items: [], status: 'idle', error: null },
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchTickets.pending, (state) => { state.status = 'loading'; state.error = null; })
      .addCase(fetchTickets.fulfilled, (state, action) => { state.status = 'success'; state.items = action.payload.items; })
      .addCase(fetchTickets.rejected, (state, action) => {
        if (action.meta.aborted) return;
        state.status = 'error';
        state.error = action.payload ?? 'Nieznany błąd';
      });
  },
});

export default ticketsSlice.reducer;
// komponent: useEffect(() => { const p = dispatch(fetchTickets('OPEN')); return () => p.abort(); }, [dispatch]);
```

#T CODE_TSX Thunk i stan żądania w slice’ie (TSX)
Generyki `createAsyncThunk<Wynik, Argument, { rejectValue: Typ }>` typują wynik, argument i wartość błędu — w `extraReducers` `action.payload` ma właściwy typ w każdej gałęzi.
```
// ticketsSlice.ts
import { createAsyncThunk, createSlice } from '@reduxjs/toolkit';

type Ticket = { id: number; title: string; status: string };
type TicketsState = { items: Ticket[]; status: 'idle' | 'loading' | 'success' | 'error'; error: string | null };

export const fetchTickets = createAsyncThunk<{ items: Ticket[]; total: number }, string, { rejectValue: string }>(
  'tickets/fetch',
  async (status, { signal, rejectWithValue }) => {
    const res = await fetch(`/api/tickets?status=${status}`, { signal });
    if (!res.ok) return rejectWithValue(`Błąd ${res.status}`);
    return (await res.json()) as { items: Ticket[]; total: number };
  },
);

const initialState: TicketsState = { items: [], status: 'idle', error: null };

const ticketsSlice = createSlice({
  name: 'tickets',
  initialState,
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchTickets.pending, (state) => { state.status = 'loading'; state.error = null; })
      .addCase(fetchTickets.fulfilled, (state, action) => { state.status = 'success'; state.items = action.payload.items; })
      .addCase(fetchTickets.rejected, (state, action) => {
        if (action.meta.aborted) return;
        state.status = 'error';
        state.error = action.payload ?? 'Nieznany błąd';
      });
  },
});

export default ticketsSlice.reducer;
```

#T NOTE JSX ↔ TSX — trzy generyki thunka
`createAsyncThunk<Returned, ThunkArg, ThunkApiConfig>` wygląda groźnie, ale każdy generyk ma sens: co zwraca thunk (trafia do `fulfilled.payload`), co przyjmuje (sprawdzane przy `dispatch(fetchTickets(...))`) i jaki jest typ `rejectWithValue` (trafia do `rejected.payload`). W JSX `action.payload` w `rejected` może być czymkolwiek (także `undefined` przy zwykłym wyjątku) — dlatego w obu wersjach jest `?? 'Nieznany błąd'`. Zwróć uwagę, ile kodu wymaga ręczna obsługa stanów — dokładnie ten kod usuwa RTK Query.

#T DEFINITION RTK Query
RTK Query definiuje **API jako zestaw endpointów** w `createApi`: zapytania (`build.query`) i mutacje (`build.mutation`). Z definicji generuje hooki (`useGetTicketsQuery`, `useCloseTicketMutation`) z cache, deduplikacją, odświeżaniem i stanami ładowania. Zamiast kluczy zapytań używa **tagów**: zapytanie „dostarcza” tagi (`providesTags: [{ type: 'Ticket', id }]`), a mutacja je „unieważnia” (`invalidatesTags`) — wtedy pasujące zapytania pobiorą dane ponownie. Cache żyje w magazynie Reduxa (widoczny w devtools).

#T CODE_BASIC Definicja API w RTK Query
```
// devdeskApi.ts
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';

type Ticket = { id: number; title: string; status: 'OPEN' | 'IN_PROGRESS' | 'CLOSED' };
type Page = { items: Ticket[]; total: number };

export const devdeskApi = createApi({
  reducerPath: 'devdeskApi',
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['Ticket'],
  endpoints: (build) => ({
    getTickets: build.query<Page, { status?: string; page: number }>({
      query: (params) => ({ url: 'tickets', params }),
      providesTags: (result) =>
        result ? [...result.items.map((t) => ({ type: 'Ticket' as const, id: t.id })), { type: 'Ticket', id: 'LIST' }] : [{ type: 'Ticket', id: 'LIST' }],
    }),
    getTicket: build.query<Ticket, number>({
      query: (id) => `tickets/${id}`,
      providesTags: (_r, _e, id) => [{ type: 'Ticket', id }],
    }),
    closeTicket: build.mutation<Ticket, number>({
      query: (id) => ({ url: `tickets/${id}`, method: 'PATCH', body: { status: 'CLOSED' } }),
      invalidatesTags: (_r, _e, id) => [{ type: 'Ticket', id }, { type: 'Ticket', id: 'LIST' }],
    }),
  }),
});

export const { useGetTicketsQuery, useGetTicketQuery, useCloseTicketMutation } = devdeskApi;

// magazyn: configureStore({ reducer: { [devdeskApi.reducerPath]: devdeskApi.reducer, ... },
//   middleware: (getDefault) => getDefault().concat(devdeskApi.middleware) })
```

#T CODE_PRACTICAL Komponent na hookach RTK Query
```
import { useCloseTicketMutation, useGetTicketsQuery } from './devdeskApi';

export function RtkTicketList({ status }: { status?: string }) {
  const { data, isLoading, isError, isFetching, refetch } = useGetTicketsQuery({ status, page: 1 });
  const [closeTicket, closeState] = useCloseTicketMutation();

  if (isLoading) return <p>Ładowanie…</p>;
  if (isError) return <p role="alert">Błąd. <button type="button" onClick={() => refetch()}>Spróbuj ponownie</button></p>;

  return (
    <ul className={isFetching ? 'is-refreshing' : undefined}>
      {data?.items.map((t) => (
        <li key={t.id}>
          {t.title} ({t.status})
          <button type="button" disabled={closeState.isLoading || t.status === 'CLOSED'} onClick={() => closeTicket(t.id)}>
            Zamknij
          </button>
        </li>
      ))}
    </ul>
  );
}
```

#T API_REFERENCE RTK Query a TanStack Query
- **Klucze / tagi**: TanStack — klucze zapytań i unieważnianie przedrostkiem; RTK Query — tagi `providesTags`/`invalidatesTags`.
- **Definicja**: TanStack — hooki w dowolnym miejscu (`useQuery({ queryKey, queryFn })`); RTK Query — centralna definicja API z generowanymi hookami.
- **Cache**: TanStack — własny `QueryClient`; RTK Query — w magazynie Reduxa (devtools Reduxa).
- **Aktualizacje optymistyczne**: TanStack — `onMutate` + `setQueryData`; RTK Query — `onQueryStarted` + `updateQueryData` z „cofnięciem” (`patchResult.undo()`).
- **Kiedy**: aplikacja już na Reduxie → RTK Query (jeden magazyn, jedno devtools); bez Reduxa → TanStack Query (lżejsze wejście, więcej integracji, np. z loaderami routera).
- Obie biblioteki generują hooki z typów (RTK Query może generować całe API z OpenAPI przez `@rtk-query/codegen-openapi`).

#T STEP_BY_STEP Budujemy razem: porównanie na żywym kodzie
1. Na osobnej gałęzi napisz `fetchTickets` jako thunk i slice z `extraReducers`; użyj go w ekranie „Archiwum”.
2. Policz linie kodu potrzebne do obsługi stanów ładowania, błędu i przerwania.
3. Zdefiniuj `devdeskApi` w RTK Query i dodaj go do magazynu (reducer + middleware).
4. Przepisz „Archiwum” na `useGetTicketsQuery` — porównaj ilość kodu i zachowanie (cache przy powrocie na ekran, deduplikacja).
5. Dodaj mutację `closeTicket` z tagami i sprawdź, że po zamknięciu lista odświeża się sama.
6. W Redux DevTools obejrzyj stan `devdeskApi` (zapytania, subskrypcje, cache).
7. Zdecyduj w komentarzu: w DevDesk zostajesz przy TanStack Query (bo Redux służy tylko do małego stanu klienta), ale w projekcie zbudowanym na Reduxie wybrałbyś RTK Query.

#T PITFALL Dwie biblioteki danych naraz
Projekt z TanStack Query **i** RTK Query (albo thunkami zapisującymi dane serwera w slice’ach) ma dwa cache tych samych danych: mutacja w jednym nie unieważnia drugiego, a ekrany pokazują różne wersje ticketu. Wybierz jedną bibliotekę danych serwera na projekt.

#T SUMMARY Kryterium akceptacji i podsumowanie
`createAsyncThunk` tworzy akcję asynchroniczną z automatycznymi akcjami `pending/fulfilled/rejected` obsługiwanymi w `extraReducers` — dobre do logiki wieloetapowej, rozwlekłe do zwykłego pobierania. RTK Query definiuje endpointy w `createApi`, generuje hooki z cache i używa tagów do unieważniania. W aplikacji na Reduxie wybierz RTK Query, bez Reduxa — TanStack Query; nigdy obu naraz. W TSX generyki thunka i endpointów (`build.query<Wynik, Argument>`) typują dane, argumenty i błędy.

Kryterium akceptacji: masz na gałęzi porównanie tej samej funkcji w wersji thunk i RTK Query (z liczbą linii i opisem różnic), RTK Query odświeża listę po mutacji przez tagi, a w DevTools widać stan cache RTK Query.
