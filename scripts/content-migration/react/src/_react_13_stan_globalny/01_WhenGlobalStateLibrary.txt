#T INTRO Rozgrzewka i problem: gdzie trzymać ten stan?
Rozgrzewka: Co trzymasz w adresie URL, a co w stanie komponentu? Do czego służy cache TanStack Query? Dlaczego kontekst nie nadaje się na często zmieniane dane?

Problem: w DevDesk pojawiają się nowe potrzeby: koszyk „szybkich akcji” (zaznaczone tickety z różnych ekranów, do których chcesz wrócić), układ paneli przeciąganych przez użytkownika, historia ostatnio oglądanych ticketów, kolejka akcji offline. W internecie każdy poradnik mówi co innego: „użyj Reduxa”, „Redux jest martwy, użyj Zustand”, „wszystko w Context”. Zanim poznasz biblioteki, ta lekcja daje **mapę rodzajów stanu** — bo większość stanu w aplikacji React wcale nie potrzebuje biblioteki stanu globalnego.

#T DEFINITION Pięć rodzajów stanu
1. **Stan lokalny komponentu** — rozwinięte menu, tekst w polu, podświetlony wiersz. Narzędzie: `useState`, `useReducer`.
2. **Stan współdzielony fragmentu drzewa** — filtry ekranu używane przez pasek narzędzi i tabelę. Narzędzie: podniesienie stanu, własny hook, kontekst dla poddrzewa.
3. **Stan w adresie URL** — filtry, strona, wybrany rekord, zakładka. Narzędzie: router (`useParams`, `useSearchParams`).
4. **Stan serwera** — tickety, użytkownicy, komentarze. Narzędzie: TanStack Query (albo RTK Query, SWR, loadery frameworka).
5. **Stan globalny klienta** — dane należące do przeglądarki, potrzebne w wielu odległych miejscach i zmieniane często: koszyk, otwarte karty robocze, układ paneli, kolejka offline, stan odtwarzacza. Narzędzie: kontekst (gdy rzadko się zmienia) albo **biblioteka stanu** (Zustand, Redux Toolkit, Jotai).

Gdy stan serwera trafi do TanStack Query, a stan widoku do adresu, na kategorię 5 zostaje zwykle niewiele.

#T VISUAL_EXAMPLE Drzewo decyzji
Czy to dane z serwera?                       → TanStack Query
Czy ma przetrwać odświeżenie i dać się udostępnić linkiem? → adres URL
Czy używa go jeden komponent?                → useState / useReducer
Czy używa go kilka komponentów blisko siebie? → podniesienie stanu / własny hook
Czy jest potrzebny w wielu odległych miejscach?
   ├─ zmienia się rzadko (użytkownik, motyw, język) → Context
   └─ zmienia się często / ma dużo logiki         → biblioteka stanu (Zustand, Redux Toolkit, Jotai)

#T DEFINITION Dlaczego Context nie zawsze wystarcza
Kontekst świetnie rozwiązuje przekazywanie danych, ale ma dwa ograniczenia przy stanie globalnym:
- **rerendery**: zmiana wartości kontekstu renderuje **wszystkich** czytelników, nawet tych, którzy używają innego pola obiektu (licznik koszyka renderuje się przy zmianie notatki w koszyku),
- **brak narzędzi**: nie ma selektorów, devtools z historią zmian, trwałego zapisu, middleware.

Biblioteki stanu przechowują stan **poza Reactem** (w magazynie, store) i pozwalają komponentom subskrybować **tylko wybrany fragment** (selektor) — komponent renderuje się wyłącznie, gdy jego fragment się zmieni. Pod spodem używają `useSyncExternalStore` (rozdział 07).

#T CODE_JSX Problem: kontekst z często zmienianym stanem (JSX)
Każda zmiana notatki w „koszyku akcji” renderuje także licznik w nagłówku — choć licznik używa tylko liczby elementów.
```
// QuickCartContext.jsx — wersja z problemem wydajności
import { createContext, useContext, useState } from 'react';

const QuickCartContext = createContext(null);

export function QuickCartProvider({ children }) {
  const [items, setItems] = useState([]);   // [{ ticketId, note }]
  const value = {
    items,
    add: (ticketId) => setItems((prev) => (prev.some((i) => i.ticketId === ticketId) ? prev : [...prev, { ticketId, note: '' }])),
    setNote: (ticketId, note) => setItems((prev) => prev.map((i) => (i.ticketId === ticketId ? { ...i, note } : i))),
  };
  return <QuickCartContext value={value}>{children}</QuickCartContext>;
}

export function QuickCartBadge() {
  const { items } = useContext(QuickCartContext); // renderuje się przy KAŻDEJ zmianie notatki
  return <span className="badge">{items.length}</span>;
}
```

#T CODE_TSX Problem: kontekst z często zmienianym stanem (TSX)
Typy nie zmieniają problemu — to kwestia mechanizmu kontekstu, nie języka.
```
// QuickCartContext.tsx — wersja z problemem wydajności
import { createContext, useContext, useState, type ReactNode } from 'react';

type QuickItem = { ticketId: number; note: string };
type QuickCart = { items: QuickItem[]; add: (ticketId: number) => void; setNote: (ticketId: number, note: string) => void };

const QuickCartContext = createContext<QuickCart | null>(null);

export function QuickCartProvider({ children }: { children: ReactNode }) {
  const [items, setItems] = useState<QuickItem[]>([]);
  const value: QuickCart = {
    items,
    add: (ticketId) => setItems((prev) => (prev.some((i) => i.ticketId === ticketId) ? prev : [...prev, { ticketId, note: '' }])),
    setNote: (ticketId, note) => setItems((prev) => prev.map((i) => (i.ticketId === ticketId ? { ...i, note } : i))),
  };
  return <QuickCartContext value={value}>{children}</QuickCartContext>;
}

export function QuickCartBadge() {
  const cart = useContext(QuickCartContext);
  return <span className="badge">{cart?.items.length ?? 0}</span>;
}
```

#T NOTE JSX ↔ TSX — wybór narzędzia nie zależy od języka
Decyzja „gdzie trzymać stan” jest taka sama w JSX i TSX. Różnica pojawia się przy samych bibliotekach: Zustand, Redux Toolkit i Jotai są pisane w TypeScripcie i w TSX dają pełne typowanie selektorów (komponent wybierający `state.items.length` wie, że dostaje liczbę), akcji i stanu. W JSX działają identycznie — z mniejszą kontrolą przy refaktoryzacji (zmiana nazwy pola w magazynie nie wskaże selektorów, które z niego korzystają).

#T API_REFERENCE Przegląd bibliotek stanu globalnego
- **Zustand** — mały magazyn tworzony jedną funkcją `create`, hook z selektorem, bez providera; najprostszy start (lekcja 2).
- **Redux Toolkit (RTK)** — oficjalny, nowoczesny sposób pisania Reduxa: `configureStore`, `createSlice` (reducer + akcje), Immer w środku, świetne devtools z podróżą w czasie; RTK Query do danych z serwera; standard w dużych, długo rozwijanych aplikacjach i w wielu istniejących projektach (lekcje 3–4).
- **Jotai** — stan atomowy: wiele małych „atomów” i atomy pochodne; dobrze pasuje do stanu rozproszonego i zależnego (lekcja 5).
- **Valtio, MobX** — stan „mutowalny” z automatycznym śledzeniem zmian (proxy); inny model mentalny, rzadziej spotykany w nowych projektach.
- **XState** — maszyny stanów i statecharts dla złożonych przepływów (kreatory, procesy z wieloma krokami).

#T STEP_BY_STEP Ćwiczenie: inwentaryzacja stanu DevDesk
1. Wypisz każdy kawałek stanu w DevDesk (przejrzyj `useState`, `useReducer`, konteksty, cache zapytań, parametry adresu).
2. Przypisz każdy do jednej z pięciu kategorii.
3. Znajdź przypadki „w złym miejscu”: dane serwera skopiowane do stanu, filtry w stanie zamiast w adresie, rzadko zmieniane dane w ciężkim magazynie.
4. Wybierz kandydatów do stanu globalnego klienta: koszyk szybkich akcji, ostatnio oglądane tickety, układ paneli, wersje robocze odpowiedzi do ticketów.
5. Włącz w React DevTools „Highlight updates” i zmień notatkę w kontekście koszyka z przykładu — zobacz, że licznik w nagłówku też się renderuje.
6. W następnych lekcjach przeniesiesz koszyk szybkich akcji do Zustand, a ostatnio oglądane — do Redux Toolkit (dla porównania).

#T PITFALL Wszystko do magazynu globalnego
Najczęstszy błąd w projektach z Reduxem lub Zustandem: wrzucenie tam **wszystkiego** — odpowiedzi z API (zamiast TanStack Query), stanu formularzy, otwarcia modali, filtrów (zamiast adresu). Magazyn rośnie, każda funkcja dotyka globalnego stanu, a testowanie komponentów wymaga konfiguracji całego magazynu. Do magazynu trafia tylko stan globalny klienta (kategoria 5).

#T SUMMARY Kryterium akceptacji i podsumowanie
Stan dzieli się na pięć rodzajów: lokalny, współdzielony fragmentu drzewa, w adresie URL, serwerowy i globalny klienta — każdy ma swoje narzędzie. Biblioteka stanu globalnego jest potrzebna dopiero dla danych klienta używanych w wielu odległych miejscach i zmienianych często. Biblioteki przechowują stan poza Reactem i pozwalają subskrybować fragment przez selektor, co rozwiązuje problem rerenderów kontekstu. Wybór narzędzia nie zależy od JSX/TSX, ale w TSX biblioteki dają pełne typowanie selektorów i akcji.

Kryterium akceptacji: masz listę całego stanu DevDesk przypisaną do pięciu kategorii, poprawione miejsca „w złym narzędziu” i wybranych kandydatów do stanu globalnego, a w DevTools widzisz problem rerenderów kontekstu z przykładu.
