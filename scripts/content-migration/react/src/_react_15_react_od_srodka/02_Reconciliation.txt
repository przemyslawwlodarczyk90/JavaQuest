#T INTRO Rozgrzewka i problem: skąd React wie, co się zmieniło?
Rozgrzewka: Czym jest element React? Dlaczego utworzenie elementu nie renderuje komponentu? Gdzie żyje stan komponentu?

Problem: w rozdziale 06 nauczyłeś się reguł zachowania stanu (pozycja, typ, `key`), a w rozdziale 02 — że index jako klucz psuje listy. Teraz zrozumiesz, **skąd te reguły się biorą**. Porównanie dwóch dowolnych drzew w sposób optymalny jest bardzo kosztowne (algorytmy ogólne mają złożoność rzędu n³). React stosuje proste **heurystyki rekoncyliacji**, które działają w czasie liniowym — i to z nich wynikają wszystkie zasady, których przestrzegasz.

#T DEFINITION Dwie heurystyki rekoncyliacji
1. **Różny typ → różne poddrzewo.** Jeśli na tej samej pozycji element zmienia typ (`div` → `section`, `TicketTable` → `TicketCards`), React nie porównuje ich dzieci: niszczy stare poddrzewo (odmontowanie, utrata stanu, usunięcie DOM) i buduje nowe od zera.
2. **Klucze identyfikują dzieci na liście.** Wśród rodzeństwa React dopasowuje elementy po `key` (a bez klucza — po pozycji). Element z tym samym kluczem to „ten sam” element, nawet jeśli przesunął się na inną pozycję — React przenosi go razem ze stanem i DOM.

Dla elementów tego samego typu na tej samej pozycji React **aktualizuje**: zmienia atrybuty DOM (dla tagów HTML) albo renderuje komponent z nowymi props, zachowując jego stan, i schodzi rekurencyjnie do dzieci.

#T VISUAL_EXAMPLE Lista z kluczami i bez — usunięcie pierwszego elementu
bez kluczy (pozycje):                          z kluczami (ID):
przed: [0] #41  [1] #42  [2] #43               przed: (41) #41  (42) #42  (43) #43
po:    [0] #42  [1] #43                        po:            (42) #42  (43) #43

       pozycja 2 — usuń

#T CODE_JSX Eksperyment: stan i DOM przy zmianie kolejności (JSX)
Każdy wiersz ma niekontrolowane pole notatki (stan w DOM) i licznik kliknięć (stan React). Przełącz klucze i odwróć kolejność.
```
// ReorderDemo.jsx
import { useState } from 'react';

function Row({ ticket }) {
  const [clicks, setClicks] = useState(0);
  return (
    <li>
      #{ticket.id} {ticket.title}
      <button type="button" onClick={() => setClicks((c) => c + 1)}>kliknięto {clicks}</button>
      <input aria-label={`Notatka ${ticket.id}`} defaultValue="" />
    </li>
  );
}

export function ReorderDemo({ tickets }) {
  const [reversed, setReversed] = useState(false);
  const [useIndex, setUseIndex] = useState(false);
  const list = reversed ? [...tickets].reverse() : tickets;

  return (
    <div>
      <button type="button" onClick={() => setReversed((r) => !r)}>Odwróć kolejność</button>
      <label><input type="checkbox" checked={useIndex} onChange={(e) => setUseIndex(e.target.checked)} /> key = index</label>
      <ul>{list.map((t, i) => <Row key={useIndex ? i : t.id} ticket={t} />)}</ul>
    </div>
  );
}
```

#T CODE_TSX Eksperyment: stan i DOM przy zmianie kolejności (TSX)
```
// ReorderDemo.tsx
import { useState } from 'react';
import type { Ticket } from '../types';

function Row({ ticket }: { ticket: Ticket }) {
  const [clicks, setClicks] = useState(0);
  return (
    <li>
      #{ticket.id} {ticket.title}
      <button type="button" onClick={() => setClicks((c) => c + 1)}>kliknięto {clicks}</button>
      <input aria-label={`Notatka ${ticket.id}`} defaultValue="" />
    </li>
  );
}

export function ReorderDemo({ tickets }: { tickets: readonly Ticket[] }) {
  const [reversed, setReversed] = useState(false);
  const [useIndex, setUseIndex] = useState(false);
  const list = reversed ? [...tickets].reverse() : tickets;

  return (
    <div>
      <button type="button" onClick={() => setReversed((r) => !r)}>Odwróć kolejność</button>
      <label><input type="checkbox" checked={useIndex} onChange={(e) => setUseIndex(e.target.checked)} /> key = index</label>
      <ul>{list.map((t, i) => <Row key={useIndex ? i : t.id} ticket={t} />)}</ul>
    </div>
  );
}
```

#T NOTE JSX ↔ TSX — rekoncyliacja jest poza zasięgiem typów
Typy sprawdzają kształt props, ale nie to, czy klucze są stabilne i unikalne. `key={Math.random()}` albo `key={index}` w liście z sortowaniem są poprawne typowo w TSX i działają (błędnie) tak samo jak w JSX. Pilnują tego: ostrzeżenia Reacta w konsoli (brak klucza, zduplikowany klucz), reguła ESLint `react/no-array-index-key` i Twoja wiedza z tej lekcji.

#T DEFINITION Konsekwencje dla codziennego kodu
Z dwóch heurystyk wynika wszystko, czego nauczyłeś się wcześniej:
- **stabilne klucze z ID** (rozdział 02) — żeby stan i DOM szły za rekordem,
- **`key` do świadomego resetu** (rozdział 05) — inny klucz = inny element = świeży stan,
- **nie zmieniaj typu opakowania warunkowo** (rozdział 06) — `div` → `section` niszczy poddrzewo,
- **nie definiuj komponentów w komponentach** — nowa funkcja to nowy typ przy każdym renderze, więc React zawsze buduje poddrzewo od nowa,
- **warunek `{a ? <X /> : <Y />}`** na tej samej pozycji niszczy stan przy przełączaniu (różne typy), a `{a ? <X variant="a" /> : <X variant="b" />}` — zachowuje (ten sam typ).

#T CODE_BASIC Ten sam typ zachowuje stan, inny typ go niszczy
```
import { useState } from 'react';

function Counter({ label }: { label: string }) {
  const [n, setN] = useState(0);
  return <button type="button" onClick={() => setN((x) => x + 1)}>{label}: {n}</button>;
}

function OtherCounter({ label }: { label: string }) {
  const [n, setN] = useState(0);
  return <button type="button" onClick={() => setN((x) => x + 1)}>{label}: {n}</button>;
}

export function TypeDemo() {
  const [admin, setAdmin] = useState(false);
  return (
    <div>
      <label><input type="checkbox" checked={admin} onChange={(e) => setAdmin(e.target.checked)} /> tryb admina</label>
      {/* ten sam typ na tej samej pozycji → licznik ZOSTAJE */}
      {admin ? <Counter label="Admin" /> : <Counter label="Agent" />}
      {/* inny typ → licznik RESETUJE się przy przełączeniu */}
      {admin ? <OtherCounter label="B-admin" /> : <Counter label="B-agent" />}
    </div>
  );
}
```

#T CODE_PRACTICAL Fragmenty z kluczem w listach grup
Gdy element listy to kilka sąsiednich elementów (np. wiersz tabeli i wiersz szczegółów pod nim), klucz trafia na `Fragment` — skrócony zapis `<>` nie przyjmuje klucza.
```
import { Fragment } from 'react';
import type { Ticket } from '../types';

export function TicketRowsWithDetails({ tickets, expandedId }: { tickets: Ticket[]; expandedId: number | null }) {
  return (
    <tbody>
      {tickets.map((t) => (
        <Fragment key={t.id}>
          <tr><td>{t.id}</td><td>{t.title}</td></tr>
          {expandedId === t.id && <tr><td colSpan={2}>{t.description}</td></tr>}
        </Fragment>
      ))}
    </tbody>
  );
}
```

#T STEP_BY_STEP Budujemy razem: eksperymenty z rekoncyliacją
1. Zbuduj `ReorderDemo` z pięcioma ticketami. Kliknij różnie liczniki i wpisz różne notatki w kilku wierszach.
2. Z kluczami `id` odwróć kolejność — liczniki i notatki „jadą” razem z ticketami.
3. Przełącz na `key = index` i odwróć — liczniki i notatki zostają na pozycjach, a tytuły się zmieniają (stan „przeskoczył” na inne tickety).
4. W DevTools przeglądarki (zakładka Elements) obserwuj, które elementy `<li>` migają przy zmianie (przeglądarka podświetla zmienione węzły) — z kluczami ID przy odwróceniu nie powstają nowe węzły, są przenoszone.
5. Zbuduj `TypeDemo` i potwierdź, kiedy stan zostaje, a kiedy się resetuje.
6. Znajdź w DevDesk wszystkie listy i upewnij się, że klucze to stabilne ID; listy grup (wiersz + szczegóły) przenieś na `Fragment` z kluczem.

#T PITFALL Klucz generowany w renderze
`key={crypto.randomUUID()}` albo `key={Math.random()}` daje nowy klucz przy każdym renderze — z punktu widzenia rekoncyliacji każdy element to „nowy element”. React odmontowuje i montuje całą listę przy każdym renderze: utrata stanu, fokusu, pozycji przewinięcia i dużo pracy DOM. Klucz ma być stabilny między renderami — z danych.

#T SUMMARY Kryterium akceptacji i podsumowanie
Rekoncyliacja porównuje nowe drzewo elementów z poprzednim według dwóch heurystyk: inny typ na tej samej pozycji oznacza przebudowę całego poddrzewa (utrata stanu), a klucze dopasowują dzieci listy (stan i DOM idą za kluczem). Ten sam typ na tej samej pozycji oznacza aktualizację z zachowaniem stanu. Z tych zasad wynikają reguły stabilnych kluczy, resetu przez `key`, niezmieniania typu opakowania i niedefiniowania komponentów w komponentach. Typy nie pilnują kluczy — robią to ostrzeżenia Reacta i lintery.

Kryterium akceptacji: w eksperymencie `ReorderDemo` potrafisz pokazać i wyjaśnić różnicę między kluczami ID i index przy odwracaniu listy, a w `TypeDemo` — kiedy stan zostaje, a kiedy się resetuje; wszystkie listy DevDesk mają stabilne klucze.
