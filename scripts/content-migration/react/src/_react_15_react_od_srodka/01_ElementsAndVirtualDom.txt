#T INTRO Rozgrzewka i problem: co właściwie zwraca komponent?
Rozgrzewka: Czym różni się test komponentu od testu E2E? Co sprawdza axe, a czego nie? Dlaczego testy wizualne uruchamia się w stałym środowisku?

Problem: przez 14 rozdziałów używałeś Reacta jak narzędzia. Teraz zaglądasz pod maskę — bo zrozumienie mechanizmów wyjaśnia zachowania, które dotąd przyjmowałeś na wiarę: dlaczego `key` jest tak ważny, dlaczego zmiana typu elementu kasuje stan, dlaczego render nie oznacza zmiany DOM, dlaczego hooki muszą być na najwyższym poziomie. Zaczynasz od podstawy: czym jest **element React** i co znaczy „wirtualny DOM”.

#T DEFINITION Element React to zwykły obiekt
Wyrażenie JSX `<StatusBadge status="OPEN" />` po kompilacji to wywołanie `jsx(StatusBadge, { status: 'OPEN' })`, które zwraca **zwykły, niezmienny obiekt JavaScript** — opis tego, co narysować:
- `type` — typ elementu: tekst (`'div'`, `'button'`) dla elementów HTML albo **funkcja komponentu** (`StatusBadge`),
- `props` — atrybuty i dzieci (`children`),
- `key` — klucz (jeśli podano),
- `$$typeof` — znacznik bezpieczeństwa (`Symbol.for('react.transitional.element')` w React 19), dzięki któremu React nie wyrenderuje obiektu wstrzykniętego jako dane JSON.

Element nie jest komponentem ani węzłem DOM. To lekki opis, tworzony przy każdym renderze i wyrzucany.

#T CODE_JSX Zajrzyj do elementu (JSX)
Wklej w dowolnym komponencie i obejrzyj wynik w konsoli.
```
// inspectElement.jsx
import { StatusBadge } from './StatusBadge';

export function inspect() {
  const el = <StatusBadge status="OPEN" key="badge-1" />;
  console.log(el.type === StatusBadge); // true — typ to funkcja komponentu
  console.log(el.props);                // { status: 'OPEN' }
  console.log(el.key);                  // 'badge-1'

  const div = <div className="row">tekst</div>;
  console.log(div.type);                // 'div' — element HTML to tekst
  console.log(div.props);               // { className: 'row', children: 'tekst' }
  return el;
}
```

#T CODE_TSX Typy elementu i węzła (TSX)
`ReactElement` to typ elementu, `ReactNode` — wszystkiego, co można wyrenderować (element, tekst, liczba, tablica, `null`). Dzięki typom widać, że element ma `type`, `props` i `key`.
```
// inspectElement.tsx
import type { ReactElement, ReactNode } from 'react';

function StatusBadge({ status }: { status: string }) {
  return <span>{status}</span>;
}

export function inspect(): ReactElement<{ status: string }> {
  const el = <StatusBadge status="OPEN" key="badge-1" />;
  console.log(el.type === StatusBadge, el.props, el.key);
  return el;
}

export const renderable: ReactNode[] = [<b key="a">tak</b>, 'tekst', 42, null, false];
```

#T NOTE JSX ↔ TSX — ReactElement a ReactNode
W TSX rozróżnienie jest jawne: `ReactElement` to konkretny obiekt elementu (wynik JSX), a `ReactNode` — szersza unia wszystkiego, co React potrafi wyrenderować. Dlatego `children` typujesz jako `ReactNode` (rozdział 01), a funkcję zwracającą element — jako `ReactElement`. W JSX te same różnice istnieją w czasie działania: `null` i `false` w `children` nic nie renderują, liczba renderuje się jako tekst, a obiekt, który nie jest elementem, rzuca błąd „Objects are not valid as a React child”.

#T DEFINITION Wirtualny DOM — co to naprawdę znaczy
„Wirtualny DOM” to potoczna nazwa drzewa elementów (lekkich obiektów) opisujących UI. Mechanizm:
1. komponent zwraca drzewo elementów (opis „jak ma być”),
2. React porównuje je z poprzednim drzewem (**rekoncyliacja**, następna lekcja),
3. na prawdziwy DOM nanosi tylko różnice (faza **commit**).

Mit: „wirtualny DOM jest szybszy od DOM”. Nie jest — to dodatkowa praca. Jego zaleta to **model programowania**: piszesz deklaratywnie („UI dla tych danych”), a React liczy minimalne zmiany. Ręcznie napisane, idealnie celowane operacje DOM są szybsze — ale trudne do utrzymania przy złożonym UI. Frameworki bez wirtualnego DOM (Svelte, Solid) osiągają podobny model inną drogą (kompilacja, sygnały).

#T VISUAL_EXAMPLE Trzy drzewa
Drzewo elementów (nowe przy każdym renderze)       Drzewo fiberów (trwałe, wewnątrz Reacta)      DOM przeglądarki
{ type: Main, props: {...} }                        Fiber(Main) — stan, hooki, efekty              <main>
 └ { type: 'ul', props: { children: [...] } }        └ Fiber('ul')                                   └ <ul>
    ├ { type: TicketRow, key: 41 }                      ├ Fiber(TicketRow, key 41) — stan wiersza       ├ <li>…</li>
    └ { type: TicketRow, key: 42 }                      └ Fiber(TicketRow, key 42)                      └ <li>…</li>

Elementy są wyrzucane po porównaniu. **Stan nie żyje w elementach ani w komponencie-funkcji** — żyje w trwałych fiberach (lekcja 3). Dlatego stan zależy od pozycji i klucza w drzewie.

#T CODE_BASIC Elementy można tworzyć, przechowywać i przekazywać
Ponieważ element to wartość, możesz go zapisać w zmiennej, przekazać w props (sloty z rozdziału 02) albo w tablicy. React wywoła funkcję komponentu dopiero wtedy, gdy element trafi do drzewa — utworzenie elementu NIE renderuje komponentu.
```
import type { ReactNode } from 'react';

let renders = 0;
function Expensive() {
  renders += 1;
  return <p>Ciężki komponent (render #{renders})</p>;
}

export function Panel({ show, extra }: { show: boolean; extra: ReactNode }) {
  const content = <Expensive />; // tylko obiekt — Expensive jeszcze się nie wykonał
  return <section>{show ? content : <p>Ukryte</p>}{extra}</section>;
}
```

#T CODE_PRACTICAL Komponent wywołany jak funkcja — dlaczego nie
`{TicketRow({ ticket })}` zamiast `<TicketRow ticket={ticket} />` działa „prawie” tak samo — ale React nie widzi komponentu, tylko jego wynik. Hooki z `TicketRow` stają się hookami rodzica (pomieszane stany przy zmianie liczby wierszy), nie działa `key`, nie ma osobnego fibera w DevTools.
```
import { useState } from 'react';

function Row({ label }: { label: string }) {
  const [open, setOpen] = useState(false);
  return <li onClick={() => setOpen((o) => !o)}>{label} {open ? '▲' : '▼'}</li>;
}

export function List({ labels }: { labels: string[] }) {
  return (
    <ul>
      {/* ŹLE: labels.map((l) => Row({ label: l })) — hooki Row trafiają do List */}
      {labels.map((l) => <Row key={l} label={l} />)}
    </ul>
  );
}
```

#T STEP_BY_STEP Budujemy razem: obserwacja elementów i fiberów
1. Wklej `inspect()` i obejrzyj w konsoli `type`, `props`, `key` elementu komponentu i elementu HTML.
2. Wypisz `JSON.stringify(<div>x</div>)` — zobacz, że `$$typeof` (symbol) znika przy serializacji; dlatego obiekt z JSON-a nie zostanie omyłkowo wyrenderowany jako element (ochrona przed wstrzyknięciem).
3. W React DevTools zaznacz `TicketRow` i obejrzyj panel: props, hooki, „rendered by” — to dane z fibera, nie z elementu.
4. Zbuduj `Panel` z przykładu i sprawdź licznik renderów `Expensive` przy `show=false` — komponent się nie wykonuje.
5. Zamień w liście `<Row />` na wywołanie `Row({...})`, zmień liczbę elementów listy i zaobserwuj błąd Reacta o zmianie liczby hooków („Rendered more hooks than during the previous render”). Przywróć JSX.
6. Zanotuj trzy drzewa (elementy, fibery, DOM) — będą wracać w całym rozdziale.

#T PITFALL Mylenie elementu z instancją komponentu
Element (`<TicketRow />`) to opis, a nie „obiekt komponentu” z metodami. Nie da się z niego odczytać stanu ani wywołać metody — w komponentach funkcyjnych nie ma instancji. Dostęp do zachowania komponentu daje props (dane w dół, callbacki w górę) albo ref z `useImperativeHandle` (rozdział 08).

#T SUMMARY Kryterium akceptacji i podsumowanie
JSX tworzy elementy — zwykłe, niezmienne obiekty `{ type, props, key }` opisujące UI. Utworzenie elementu nie wykonuje komponentu; robi to React, gdy element trafi do drzewa. „Wirtualny DOM” to drzewo elementów porównywane z poprzednim w celu wyliczenia minimalnych zmian w DOM — jego zaletą jest model programowania, nie surowa szybkość. Stan żyje w trwałych fiberach, nie w elementach. Komponentów nie wywołuje się jak funkcji. W TSX `ReactElement` to element, `ReactNode` — wszystko renderowalne.

Kryterium akceptacji: potrafisz wypisać i wyjaśnić pola elementu dla komponentu i dla tagu HTML, pokazać, że utworzenie elementu nie renderuje komponentu, oraz odtworzyć i wyjaśnić błąd wywołania komponentu jak funkcji.
