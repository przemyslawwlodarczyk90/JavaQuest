#T INTRO Rozgrzewka i problem: wzorce, które spotkasz w starszym kodzie
Rozgrzewka: Czym są komponenty złożone i jak dzielą stan? Dlaczego hook kontekstu części rzuca błąd poza korzeniem? Kiedy tablica konfiguracji wystarcza?

Problem: zanim pojawiły się hooki (2019), logikę ze stanem współdzielono dwoma wzorcami: **render props** i **komponentami wyższego rzędu (HOC)**. Spotkasz je w starszych projektach, w dokumentacji bibliotek i w kilku miejscach, gdzie nadal są najwygodniejsze (np. render props w listach wirtualnych, w `Controller` z React Hook Form, HOC w integracji z narzędziami). Musisz je umieć przeczytać, napisać i — tam, gdzie to ma sens — zamienić na hook.

#T DEFINITION Render props
Komponent dostaje **funkcję**, którą wywołuje, przekazując jej swoje dane, i renderuje to, co ona zwróci. Funkcja może być propem `render` albo `children`:

`<MousePosition>{({ x, y }) => <p>{x}, {y}</p>}</MousePosition>`

Komponent zarządza logiką (stan, subskrypcje), a wywołujący decyduje, jak wyświetlić wynik. Znasz to już: `Controller` z React Hook Form przyjmuje `render={({ field }) => ...}`.

#T CODE_JSX Render prop: odliczanie do terminu (JSX)
```
// Countdown.jsx
import { useEffect, useState } from 'react';

export function Countdown({ until, children }) {
  const [now, setNow] = useState(() => Date.now());

  useEffect(() => {
    const id = setInterval(() => setNow(Date.now()), 1000);
    return () => clearInterval(id);
  }, []);

  const ms = Math.max(0, Date.parse(until) - now);
  return children({
    hours: Math.floor(ms / 3_600_000),
    minutes: Math.floor((ms % 3_600_000) / 60_000),
    overdue: ms === 0,
  });
}

// użycie:
// <Countdown until={ticket.dueAt}>
//   {({ hours, minutes, overdue }) => overdue ? <b>Po terminie</b> : <span>{hours} h {minutes} min</span>}
// </Countdown>
```

#T CODE_TSX Render prop: odliczanie do terminu (TSX)
Typ `children` jako funkcji: `(t: TimeLeft) => ReactNode`. Wywołujący dostaje podpowiedzi pól `hours`, `minutes`, `overdue`.
```
// Countdown.tsx
import { useEffect, useState, type ReactNode } from 'react';

export type TimeLeft = { hours: number; minutes: number; overdue: boolean };

type CountdownProps = { until: string; children: (time: TimeLeft) => ReactNode };

export function Countdown({ until, children }: CountdownProps) {
  const [now, setNow] = useState(() => Date.now());

  useEffect(() => {
    const id = setInterval(() => setNow(Date.now()), 1000);
    return () => clearInterval(id);
  }, []);

  const ms = Math.max(0, Date.parse(until) - now);
  return children({
    hours: Math.floor(ms / 3_600_000),
    minutes: Math.floor((ms % 3_600_000) / 60_000),
    overdue: ms === 0,
  });
}
```

#T NOTE JSX ↔ TSX — children jako funkcja
W TSX `children: (time: TimeLeft) => ReactNode` sprawia, że przekazanie zwykłego JSX zamiast funkcji (`<Countdown>tekst</Countdown>`) jest błędem kompilacji, a parametr funkcji ma znany typ bez adnotacji w miejscu użycia. W JSX taki błąd kończy się wyjątkiem „children is not a function” w czasie działania. To jedno z miejsc, gdzie TypeScript najmocniej ułatwia korzystanie ze wzorca — dlatego render props są wygodniejsze w TSX niż kiedyś w czystym JS.

#T DEFINITION Komponent wyższego rzędu (HOC)
HOC to **funkcja, która przyjmuje komponent i zwraca nowy komponent** z dodatkowym zachowaniem: `const Enhanced = withSomething(Component)`. Konwencja nazw: `withX`. Typowe zastosowania w starszym kodzie: dostęp do danych zalogowanego użytkownika (`withUser`), ochrona widoku (`withAuth`), logowanie renderów, integracje z bibliotekami (np. dawne `connect` z Redux, `withRouter`).

#T CODE_JSX HOC: blokada widoku dla nieuprawnionych (JSX)
```
// withRole.jsx
import { usePrefs } from './PrefsContext';

export function withRole(Component, requiredRole) {
  function Guarded(props) {
    const { prefs } = usePrefs();
    if (prefs.role !== requiredRole) return <p>Brak uprawnień do tego widoku.</p>;
    return <Component {...props} />;
  }
  Guarded.displayName = `withRole(${Component.displayName ?? Component.name})`;
  return Guarded;
}

// const AdminPanel = withRole(AdminPanelBase, 'admin');
```

#T CODE_TSX HOC: blokada widoku dla nieuprawnionych (TSX)
Generyk `P` przenosi typ props opakowanego komponentu na komponent wynikowy — `AdminPanel` wymaga tych samych props co `AdminPanelBase`.
```
// withRole.tsx
import type { ComponentType } from 'react';

type Role = 'agent' | 'admin';
declare function useCurrentRole(): Role;

export function withRole<P extends object>(Component: ComponentType<P>, requiredRole: Role) {
  function Guarded(props: P) {
    const role = useCurrentRole();
    if (role !== requiredRole) return <p>Brak uprawnień do tego widoku.</p>;
    return <Component {...props} />;
  }
  Guarded.displayName = `withRole(${Component.displayName ?? Component.name})`;
  return Guarded;
}
```

#T DEFINITION Dlaczego hooki zastąpiły oba wzorce
Render props i HOC mają wady, które hooki usuwają:
- **„piekło opakowań”** — kilka HOC-ów lub render props zagnieżdża drzewo komponentów (widać to w DevTools jako wieże `withA(withB(withC(...)))`),
- **kolizje nazw props** — dwa HOC-i wstrzykujące prop `data` nadpisują się nawzajem,
- **niejawność** — nie widać w kodzie komponentu, skąd przychodzi prop wstrzyknięty przez HOC,
- **trudne typowanie** HOC-ów w TypeScripcie (props dodawane i usuwane).

Hook (`const role = useCurrentRole()`) jest jawny, nie zmienia drzewa i typuje się trywialnie.

#T CODE_PRACTICAL Ten sam efekt jako hook i komponent-strażnik
```
import { useEffect, useState, type ReactNode } from 'react';

type Role = 'agent' | 'admin';
declare function useCurrentRole(): Role;

export function useCountdown(until: string) {
  // ta sama logika co w Countdown — zwraca dane zamiast wywoływać funkcję
  const [now, setNow] = useState(() => Date.now());
  useEffect(() => {
    const id = setInterval(() => setNow(Date.now()), 1000);
    return () => clearInterval(id);
  }, []);
  const ms = Math.max(0, Date.parse(until) - now);
  return { hours: Math.floor(ms / 3_600_000), minutes: Math.floor((ms % 3_600_000) / 60_000), overdue: ms === 0 };
}

export function RequireRole({ role, children }: { role: Role; children: ReactNode }) {
  const current = useCurrentRole();
  return current === role ? children : <p>Brak uprawnień do tego widoku.</p>;
}

// <RequireRole role="admin"><AdminPanel /></RequireRole>
```

#T PITFALL HOC wywołany w renderze
`const Guarded = withRole(Panel, 'admin')` zapisane **wewnątrz** komponentu tworzy nowy typ komponentu przy każdym renderze — React odmontowuje i montuje `Panel` od nowa, tracąc jego stan (ten sam problem co definiowanie komponentu w komponencie). HOC wywołuj zawsze na poziomie modułu.

#T SUMMARY Kryterium akceptacji i podsumowanie
Render props: komponent wywołuje przekazaną funkcję (`children` lub `render`) ze swoimi danymi, a wywołujący decyduje o wyglądzie. HOC: funkcja `withX(Component)` zwracająca nowy komponent z dodatkowym zachowaniem, wywoływana na poziomie modułu, z ustawionym `displayName`. Hooki zastąpiły oba wzorce w większości przypadków (jawność, brak opakowań, łatwe typowanie), ale render props nadal są wygodne, gdy wywołujący kontroluje renderowanie. W TSX: `children: (dane: T) => ReactNode` i generyczny HOC z `ComponentType<P>`.

Kryterium akceptacji: kolumna „Termin” pokazuje odliczanie z trzema wariantami wyglądu, widok „Raporty” jest dostępny tylko dla roli admin, a w kodzie potrafisz wskazać, który wzorzec (render prop, HOC, hook) zastosowano i dlaczego.
