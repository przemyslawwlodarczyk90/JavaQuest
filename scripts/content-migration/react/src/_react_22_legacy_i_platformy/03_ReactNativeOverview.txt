#T INTRO Rozgrzewka i problem: „a mamy aplikację na telefon?”
Rozgrzewka: Jakim hookiem zastępujesz parę `componentDidMount` i `componentWillUnmount`? Dlaczego setter `useState` nie scala obiektu jak `setState`? Która część Reacta nadal wymaga klasy?

Problem: technicy w terenie korzystają z DevDesk w PWA (rozdział 21), ale proszą o prawdziwą aplikację mobilną: powiadomienia push o nowym tickecie, zdjęcie usterki aparatem dołączane do zgłoszenia, skanowanie kodu QR z naklejki na serwerze, praca w tle. Część tego da się zrobić w przeglądarce, ale nie wszystko i nie wszędzie tak samo. **React Native** pozwala pisać natywne aplikacje na Androida i iOS tym samym modelem, który znasz: komponenty, props, stan, hooki, kontekst. W tej lekcji zobaczysz, co przenosi się z Reacta w przeglądarce bez zmian, co działa inaczej i jak zacząć z **Expo**.

#T DEFINITION Ten sam React, inne „klocki”
React Native używa tego samego silnika Reacta (komponenty, rekoncyliacja, hooki), ale zamiast elementów DOM renderuje **natywne widoki** platformy:
- `<View>` zamiast `<div>` — kontener układu,
- `<Text>` zamiast `<p>`/`<span>` — **każdy** tekst musi być w `<Text>` (goły tekst w `<View>` to błąd),
- `<Pressable>` / `<TouchableOpacity>` zamiast `<button>` — `onPress` zamiast `onClick`,
- `<TextInput>` zamiast `<input>` — `onChangeText` przekazuje od razu tekst,
- `<Image>`, `<ScrollView>`, `<FlatList>` (wydajna, wirtualizowana lista — jak TanStack Virtual z rozdziału 16, ale wbudowana).

Nie ma DOM, plików CSS, `className` ani `window`. Bez zmian zostaje wszystko, co nie dotyka DOM: `useState`, `useEffect`, `useReducer`, kontekst, własne hooki, TanStack Query, Zustand, Zod, logika biznesowa, klient API.

#T CODE_JSX Lista ticketów w React Native (JSX)
Porównaj z tabelą ticketów z rozdziału 04: stan, filtr i dane wyliczane wyglądają identycznie — zmieniają się tylko komponenty i style.
```
// TicketListScreen.jsx
import { useState } from 'react';
import { FlatList, Pressable, StyleSheet, Text, TextInput, View } from 'react-native';

export function TicketListScreen({ tickets, onOpen }) {
  const [query, setQuery] = useState('');
  const visible = tickets.filter((t) => t.title.toLowerCase().includes(query.toLowerCase()));

  return (
    <View style={styles.screen}>
      <TextInput
        value={query}
        onChangeText={setQuery}
        placeholder="Szukaj ticketu"
        accessibilityLabel="Szukaj ticketu"
        style={styles.search}
      />
      <FlatList
        data={visible}
        keyExtractor={(t) => String(t.id)}
        ListEmptyComponent={<Text style={styles.empty}>Brak ticketów</Text>}
        renderItem={({ item }) => (
          <Pressable
            onPress={() => onOpen(item.id)}
            accessibilityRole="button"
            style={({ pressed }) => [styles.row, pressed && styles.rowPressed]}
          >
            <Text style={styles.title}>{item.title}</Text>
            <Text style={styles.meta}>#{item.id} · {item.status}</Text>
          </Pressable>
        )}
      />
    </View>
  );
}

const styles = StyleSheet.create({
  screen: { flex: 1, padding: 16, backgroundColor: '#fff' },
  search: { borderWidth: 1, borderColor: '#cbd5e1', borderRadius: 8, padding: 12, marginBottom: 12 },
  row: { paddingVertical: 12, borderBottomWidth: 1, borderBottomColor: '#e2e8f0' },
  rowPressed: { backgroundColor: '#f1f5f9' },
  title: { fontSize: 16, fontWeight: '600' },
  meta: { fontSize: 13, color: '#64748b', marginTop: 2 },
  empty: { textAlign: 'center', marginTop: 32, color: '#64748b' },
});
```

#T NOTE JSX ↔ TSX — style jako obiekty z typami
W React Native style to obiekty JavaScript (jak `style={{…}}` w przeglądarce), a nie arkusze CSS — więc TypeScript sprawdza je w pełni: `fontWeight: 'bold-ish'` albo `paddingVertikal` to błędy kompilacji. Domyślnie projekty Expo powstają w TypeScripcie; wersja JS działa tak samo, ale błąd w stylu po prostu nie zadziała na ekranie. Liczby w stylach to **punkty niezależne od gęstości ekranu** (bez `px`, `rem`, `%` tylko w części właściwości).

#T DEFINITION Style i układ w React Native
- **Flexbox wszędzie**, ale z innymi wartościami domyślnymi: `flexDirection: 'column'` (nie `row`), `display: flex` dla każdego `View`, `flex: 1` rozciąga element na dostępne miejsce.
- **Brak kaskady i dziedziczenia** — styl tekstu nie przechodzi z `View` na zagnieżdżony `Text` (tylko z `Text` na zagnieżdżony `Text`). Wspólny wygląd uzyskujesz komponentami (`<AppText variant="title">`) i tokenami w obiekcie motywu.
- **Brak selektorów i pseudoklas** — stan wciśnięcia (`pressed`) dostajesz w funkcji `style` komponentu `Pressable`; tryb ciemny przez `useColorScheme()`.
- **Bezpieczne obszary** — wycięcia ekranu i paski systemowe obsługuje `react-native-safe-area-context` (`SafeAreaView`).
- Biblioteki stylów: NativeWind (klasy Tailwind kompilowane do stylów RN), Tamagui, Unistyles.

#T DEFINITION Expo: start, nawigacja i natywne funkcje
**Expo** to zestaw narzędzi i bibliotek, który jest dziś zalecanym sposobem zaczynania projektów React Native:
- **Start**: `npx create-expo-app@latest devdesk-mobile` — projekt w TypeScript z gotową nawigacją; aplikację uruchamiasz na telefonie przez **Expo Go** (skan kodu QR) albo w emulatorze; szybkie odświeżanie jak HMR w Vite.
- **Nawigacja**: **Expo Router** — trasy z plików w katalogu `app/` (`app/tickets/[id].tsx` → ekran szczegółów), stos ekranów, zakładki, linki głębokie (`devdesk://tickets/42`). Pod spodem React Navigation.
- **Natywne funkcje** jako biblioteki: `expo-camera` (zdjęcie usterki), `expo-notifications` (push), `expo-secure-store` (bezpieczne przechowywanie tokenu — **nie** AsyncStorage dla sekretów), `expo-location`, `expo-barcode-scanner`/kamera ze skanowaniem kodów.
- **Budowanie i publikacja**: EAS Build tworzy pliki dla sklepów (Google Play, App Store) w chmurze, EAS Update wysyła poprawki JavaScriptu bez ponownej publikacji w sklepie (w granicach zasad sklepów).

#T CODE_PRACTICAL Ekran szczegółów w Expo Router ze wspólną logiką
Ekran szczegółów korzysta z tego samego hooka `useTicket` (TanStack Query) i tej samej walidacji Zod, co wersja webowa — wspólny jest kod danych, a nie interfejs.
```
// app/tickets/[id].tsx
import { useLocalSearchParams, Stack } from 'expo-router';
import { ActivityIndicator, Pressable, Text, View } from 'react-native';
import { useTicket, useUpdateTicket } from '@devdesk/shared/tickets'; // ten sam pakiet co w aplikacji webowej

export default function TicketDetailsScreen() {
  const { id } = useLocalSearchParams<{ id: string }>();
  const { data: ticket, isPending, isError, refetch } = useTicket(Number(id));
  const update = useUpdateTicket();

  if (isPending) return <ActivityIndicator style={{ marginTop: 32 }} />;
  if (isError || !ticket) {
    return (
      <View style={{ padding: 16 }}>
        <Text>Nie udało się wczytać ticketu.</Text>
        <Pressable onPress={() => refetch()} accessibilityRole="button"><Text>Spróbuj ponownie</Text></Pressable>
      </View>
    );
  }

  return (
    <View style={{ padding: 16, gap: 12 }}>
      <Stack.Screen options={{ title: `#${ticket.id}` }} />
      <Text style={{ fontSize: 20, fontWeight: '700' }}>{ticket.title}</Text>
      <Text>{ticket.description}</Text>
      <Pressable
        onPress={() => update.mutate({ id: ticket.id, status: 'CLOSED' })}
        disabled={update.isPending}
        accessibilityRole="button"
        accessibilityState={{ disabled: update.isPending }}
      >
        <Text>{update.isPending ? 'Zamykanie…' : 'Zamknij ticket'}</Text>
      </Pressable>
    </View>
  );
}
```

#T WHEN_TO_USE Web, PWA czy React Native
- **Aplikacja webowa / PWA** — jeden kod dla wszystkich urządzeń, natychmiastowe aktualizacje, brak sklepów; ograniczony dostęp do funkcji urządzenia (różny na iOS i Androidzie), słabsze działanie w tle i powiadomienia.
- **React Native (Expo)** — natywny wygląd i wydajność, pełny dostęp do kamery, powiadomień, czujników, pracy w tle; obecność w sklepach. Koszt: osobna aplikacja (interfejs pisany od nowa), proces publikacji i przeglądu w sklepach, testy na urządzeniach.
- **Wspólny kod web + mobile** — monorepo z pakietem `shared` (typy, schematy, klient API, hooki danych, logika biznesowa); interfejs osobno. `react-native-web` pozwala renderować komponenty RN w przeglądarce, ale rzadko opłaca się dla dużej, istniejącej aplikacji webowej.

#T STEP_BY_STEP Budujemy razem: DevDesk Mobile — pierwszy prototyp
1. Utwórz projekt `npx create-expo-app@latest devdesk-mobile` i uruchom go w Expo Go na telefonie.
2. Wydziel z DevDesk pakiet `shared` (monorepo): typy, schematy Zod, klient API, hooki TanStack Query.
3. Ekran listy ticketów z `FlatList`, wyszukiwaniem i odświeżaniem gestem (`refreshing`, `onRefresh`).
4. Ekran szczegółów w Expo Router (`app/tickets/[id].tsx`) z przyciskiem zmiany statusu.
5. Logowanie: token w `expo-secure-store`, kontekst użytkownika jak w wersji webowej.
6. Zdjęcie usterki: `expo-camera` albo `expo-image-picker` i wysłanie pliku do API (`FormData`, rozdział 11).
7. Dostępność: `accessibilityLabel`, `accessibilityRole`, sprawdzenie z TalkBack (Android) i VoiceOver (iOS).
8. Zbuduj wersję testową przez EAS Build i zainstaluj ją na telefonie.

#T PITFALL Przenoszenie nawyków z przeglądarki
Najczęstsze błędy osób przechodzących z Reacta webowego: tekst poza `<Text>` (błąd „Text strings must be rendered within a <Text> component”), oczekiwanie, że styl tekstu odziedziczy się z kontenera, długie listy w `ScrollView` z `map` zamiast `FlatList` (cała lista renderowana naraz — zacięcia i zużycie pamięci), sekrety i tokeny w `AsyncStorage` (niezaszyfrowane), zakładanie, że `fetch` do `localhost` z telefonu trafi do backendu na komputerze (trzeba adresu IP komputera w sieci lokalnej albo tunelu). I jeszcze jedno: aktualizacje przez sklep trwają — użytkownicy miesiącami korzystają ze starych wersji aplikacji, więc API musi być **wstecznie zgodne** dłużej niż przy aplikacji webowej.

#T SUMMARY Kryterium akceptacji i podsumowanie
React Native przenosi model Reacta (komponenty, props, stan, hooki, kontekst) na natywne aplikacje Android i iOS: zamiast DOM masz `View`, `Text`, `Pressable`, `TextInput`, `FlatList`, a style to obiekty z Flexboxem (domyślnie kolumna) bez kaskady. Expo daje start projektu, Expo Go, Expo Router (trasy z plików), biblioteki natywnych funkcji i budowanie w chmurze (EAS). Między wersją webową a mobilną współdzielisz logikę danych i biznesu, a interfejs piszesz osobno. W TSX `StyleSheet` i komponenty RN mają pełne typy.

Kryterium akceptacji: prototyp DevDesk Mobile działa na telefonie, pokazuje listę i szczegóły ticketów z tego samego API, korzysta ze wspólnego pakietu z typami i hookami danych, przechowuje token w bezpiecznym magazynie, a czytnik ekranu poprawnie odczytuje listę i przyciski.
