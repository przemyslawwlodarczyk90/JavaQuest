#T INTRO Rozgrzewka i problem: agent widzi panel administratora
Rozgrzewka: Czym różni się sesja z ciasteczkiem od tokenu JWT? Dlaczego tokenu nie trzymasz w localStorage? Jakie trzy stany ma kontekst uwierzytelnienia?

Problem: po zalogowaniu każdy użytkownik widzi wszystko: zakładkę „Administracja”, przycisk „Usuń ticket”, edycję cudzych ticketów. Backend już odrzuca niedozwolone operacje (403), ale użytkownik klika przycisk i dostaje błąd — to zły interfejs. Frontend powinien **dopasować widok do uprawnień**: ukryć lub zablokować niedostępne akcje, przekierować z niedostępnych ekranów, czytelnie obsłużyć 401 i 403. Routing poznasz w rozdziale 12 — tu budujesz mechanizm, który potem podepniesz pod trasy.

#T DEFINITION Uprawnienia na froncie: tylko dla wygody
Model jest prosty: **serwer jest jedynym strażnikiem**, a frontend **odzwierciedla** uprawnienia, żeby nie pokazywać akcji, które i tak się nie udadzą. Uprawnienia opisuj **akcjami** (`ticket:delete`, `ticket:assign`, `admin:view`), a nie rolami w każdym `if` — wtedy zmiana uprawnień roli to zmiana w jednym miejscu, a komponenty pytają „czy mogę usunąć?”, a nie „czy jestem adminem?”.

#T CODE_JSX Mapa uprawnień i hook can (JSX)
```
// permissions.js
import { useAuth } from './AuthContext';

const ROLE_PERMISSIONS = {
  agent: ['ticket:view', 'ticket:create', 'ticket:comment', 'ticket:close'],
  admin: ['ticket:view', 'ticket:create', 'ticket:comment', 'ticket:close', 'ticket:delete', 'ticket:assign', 'admin:view'],
};

export function useCan() {
  const auth = useAuth();
  return (permission, resource) => {
    if (auth.status !== 'authenticated') return false;
    if (ROLE_PERMISSIONS[auth.user.role]?.includes(permission)) return true;
    // reguła zasobu: autor może edytować własny ticket
    return permission === 'ticket:edit' && resource?.createdBy === auth.user.login;
  };
}

export function Can({ permission, resource, children, fallback = null }) {
  const can = useCan();
  return can(permission, resource) ? children : fallback;
}
```

#T CODE_TSX Mapa uprawnień i hook can (TSX)
Uprawnienia jako unia literałów; `Record<Role, Permission[]>` wymusza przypisanie listy każdej roli.
```
// permissions.tsx
import type { ReactNode } from 'react';
import { useAuth, type User } from './AuthContext';

export type Permission = 'ticket:view' | 'ticket:create' | 'ticket:comment' | 'ticket:close' | 'ticket:delete' | 'ticket:assign' | 'ticket:edit' | 'admin:view';

const ROLE_PERMISSIONS: Record<User['role'], Permission[]> = {
  agent: ['ticket:view', 'ticket:create', 'ticket:comment', 'ticket:close'],
  admin: ['ticket:view', 'ticket:create', 'ticket:comment', 'ticket:close', 'ticket:delete', 'ticket:assign', 'admin:view'],
};

type Resource = { createdBy?: string };

export function useCan() {
  const auth = useAuth();
  return (permission: Permission, resource?: Resource): boolean => {
    if (auth.status !== 'authenticated') return false;
    if (ROLE_PERMISSIONS[auth.user.role].includes(permission)) return true;
    return permission === 'ticket:edit' && resource?.createdBy === auth.user.login;
  };
}

type CanProps = { permission: Permission; resource?: Resource; children: ReactNode; fallback?: ReactNode };

export function Can({ permission, resource, children, fallback = null }: CanProps) {
  const can = useCan();
  return can(permission, resource) ? children : fallback;
}
```

#T NOTE JSX ↔ TSX — literówka w uprawnieniu
Uprawnienia jako zwykłe teksty w JSX to pułapka: `can('ticket:delte')` zawsze zwróci `false` i przycisk zniknie dla wszystkich — bez żadnego komunikatu. W TSX unia `Permission` sprawia, że literówka jest błędem kompilacji, a `Record<User['role'], Permission[]>` — że nowa rola nie zostanie bez listy uprawnień. `User['role']` to typ wyciągnięty z pola innego typu (indexed access type) — gdy dodasz rolę do `User`, mapa uprawnień wymusi jej obsługę.

#T CODE_BASIC Akcje dopasowane do uprawnień
Niedostępna akcja: ukryj, gdy użytkownik nie musi o niej wiedzieć; zablokuj z wyjaśnieniem, gdy powinien wiedzieć, że istnieje.
```
import { Can, useCan } from './permissions';

type T = { id: number; createdBy: string };

export function TicketActions({ ticket, onDelete, onEdit }: { ticket: T; onDelete: () => void; onEdit: () => void }) {
  const can = useCan();
  const canEdit = can('ticket:edit', ticket) || can('ticket:assign');

  return (
    <div className="actions">
      <button type="button" disabled={!canEdit} title={canEdit ? undefined : 'Możesz edytować tylko własne tickety'} onClick={onEdit}>
        Edytuj
      </button>
      <Can permission="ticket:delete">
        <button type="button" className="danger" onClick={onDelete}>Usuń</button>
      </Can>
    </div>
  );
}
```

#T CODE_PRACTICAL Strażnik widoku i obsługa 401/403
Komponent-strażnik dla całego ekranu oraz reakcja klienta API: 401 → stan „anonymous” (ekran logowania), 403 → komunikat bez wylogowania.
```
import type { ReactNode } from 'react';
import { useAuth } from './AuthContext';
import { useCan, type Permission } from './permissions';

export function RequirePermission({ permission, children }: { permission: Permission; children: ReactNode }) {
  const auth = useAuth();
  const can = useCan();
  if (auth.status === 'checking') return <p aria-busy="true">Sprawdzanie uprawnień…</p>;
  if (auth.status === 'anonymous') return <p>Zaloguj się, aby zobaczyć ten widok.</p>;
  if (!can(permission)) {
    return (
      <section role="alert">
        <h2>Brak dostępu</h2>
        <p>Ten widok jest dostępny dla administratorów. Jeśli potrzebujesz dostępu, skontaktuj się z administratorem systemu.</p>
      </section>
    );
  }
  return children;
}

// if (res.status === 401) onUnauthorized();          // → AuthProvider ustawia 'anonymous'
```

#T STEP_BY_STEP Budujemy razem: uprawnienia w DevDesk
1. Dodaj do odpowiedzi logowania pole `role` (backend) i do ticketów pole `createdBy`.
2. Utwórz `permissions` z mapą ról, hookiem `useCan` i komponentem `Can`.
3. Przycisk „Usuń” i zmiana osoby przypisanej — tylko dla `admin`; „Edytuj” — dla autora ticketu lub admina (zablokowany z podpowiedzią dla pozostałych).
4. Zakładka „Administracja” w nawigacji — w `<Can permission="admin:view">`; ekran administracji opakuj w `RequirePermission`.
5. W kliencie API: 401 wywołuje `onUnauthorized`, który w `AuthProvider` ustawia stan `anonymous`; 403 rzuca `ApiError` z czytelnym komunikatem.
6. Zaloguj się jako agent i spróbuj usunąć ticket przez konsolę (`fetch('/api/tickets/1', { method: 'DELETE' })`) — backend zwraca 403, co potwierdza, że prawdziwa ochrona jest na serwerze.
7. Po stronie Springa zabezpiecz `DELETE` adnotacją `@PreAuthorize("hasRole('ADMIN')")` i sprawdź zgodność z mapą uprawnień frontendu.

#T PITFALL Sprawdzanie roli w każdym komponencie
`{user.role === 'admin' && <button>Usuń</button>}` rozsiane po dwudziestu plikach: dodanie roli „kierownik” z prawem usuwania wymaga zmiany każdego z nich, a jeden zostanie pominięty. Komponent pyta o **akcję** (`can('ticket:delete')`), a mapowanie ról na akcje jest w jednym miejscu — najlepiej zgodnym z backendem (np. pobieranym z API razem z danymi użytkownika).

#T SUMMARY Kryterium akceptacji i podsumowanie
Frontend odzwierciedla uprawnienia dla wygody użytkownika, a chroni je wyłącznie serwer. Uprawnienia opisuj akcjami (`ticket:delete`), mapuj role na akcje w jednym miejscu i sprawdzaj hookiem `useCan` / komponentem `Can`, z regułami zasobów (autor ticketu). Niedostępne akcje ukrywaj lub blokuj z wyjaśnieniem; całe ekrany chroń strażnikiem `RequirePermission`. 401 kończy sesję w UI, 403 pokazuje „Brak dostępu”. W TSX unia uprawnień i `Record<Role, Permission[]>` eliminują literówki.

Kryterium akceptacji: agent nie widzi przycisku „Usuń” ani zakładki „Administracja”, może edytować tylko własne tickety (pozostałe — przycisk zablokowany z podpowiedzią), ekran administracji pokazuje „Brak dostępu” dla agenta, a backend odrzuca niedozwolone żądania kodem 403.
