#T INTRO Rozgrzewka i problem: backend zmienił pole, frontend się dowiedział od użytkownika
Rozgrzewka: Czym różni się SSE od WebSocket? Dlaczego zdarzenia z serwera najlepiej traktować jako sygnał do unieważnienia cache? Dlaczego połączenie otwierasz raz?

Problem: zespół backendu zmienił w `TicketDto` pole `assignee` na obiekt `{ login, name }`. Schemat Zod we frontendzie złapał to w czasie działania („nieoczekiwany format”) — ale dopiero po wdrożeniu. Typy TypeScript w frontendzie i rekordy Javy w backendzie są pisane ręcznie i nic ich nie łączy. Rozwiązaniem jest **OpenAPI**: backend publikuje specyfikację swojego API, a frontend **generuje z niej typy** (i opcjonalnie klienta). Zmiana w Javie → nowa specyfikacja → błąd kompilacji we frontendzie przed wdrożeniem.

#T DEFINITION OpenAPI i springdoc
**OpenAPI** to standard opisu API w JSON/YAML: ścieżki, metody, parametry, ciała żądań i odpowiedzi, kody błędów, schematy obiektów. Biblioteka **springdoc-openapi** generuje taką specyfikację automatycznie z kontrolerów Springa i rekordów DTO (z adnotacjami Bean Validation jako ograniczeniami). Po dodaniu zależności specyfikacja jest pod `/v3/api-docs`, a interaktywna dokumentacja (Swagger UI) — pod `/swagger-ui.html`.

#T CODE_BASIC Zależność i adnotacje po stronie Springa
```
// build.gradle / pom.xml:
// implementation 'org.springdoc:springdoc-openapi-starter-webmvc-ui:<aktualna wersja>'

@Tag(name = "Tickets")
@RestController
@RequestMapping("/api/tickets")
class TicketController {

    @Operation(summary = "Lista ticketów z filtrami i paginacją")
    @ApiResponse(responseCode = "200", description = "Strona wyników")
    @GetMapping
    PageDto<TicketDto> list(@RequestParam(required = false) TicketStatus status,
                            @RequestParam(defaultValue = "1") int page) {
        return service.find(status, page);
    }
}

// Specyfikacja: GET http://localhost:8080/v3/api-docs
// Dokumentacja: http://localhost:8080/swagger-ui.html
```

#T DEFINITION Generowanie typów: openapi-typescript
Narzędzie **openapi-typescript** zamienia specyfikację na jeden plik typów TypeScript (`paths`, `components['schemas']`). Biblioteka **openapi-fetch** daje cienkiego klienta `fetch`, który zna ścieżki i typy: `client.GET('/api/tickets/{id}', { params: { path: { id: 42 } } })` zwraca `{ data, error }` z poprawnymi typami. Alternatywy generujące pełnych klientów i hooki TanStack Query: Orval, OpenAPI Generator, Kubb.

#T CODE_JSX Generowanie i użycie w projekcie JS (JSX)
W projekcie JavaScript generowane typy nadal się przydają: edytor czyta je przez JSDoc i podpowiada pola, a klient działa identycznie.
```
// package.json → scripts:
//   "api:types": "openapi-typescript http://localhost:8080/v3/api-docs -o src/api/schema.d.ts"

// api/client.js
import createClient from 'openapi-fetch';

/** @type {import('openapi-fetch').Client<import('./schema').paths>} */
export const api = createClient({ baseUrl: '' });

export async function fetchTicket(id) {
  const { data, error } = await api.GET('/api/tickets/{id}', { params: { path: { id } } });
  if (error) throw new Error('Nie udało się pobrać ticketu');
  return data;
}
```

#T CODE_TSX Generowanie i użycie w projekcie TS (TSX)
Typy ścieżek i odpowiedzi pochodzą z wygenerowanego pliku. Zła ścieżka, brak parametru albo nieistniejące pole w odpowiedzi to błąd kompilacji.
```
// api/client.ts
import createClient from 'openapi-fetch';
import type { components, paths } from './schema';

export type TicketDto = components['schemas']['TicketDto'];

export const api = createClient<paths>({ baseUrl: '' });

export async function fetchTicket(id: number): Promise<TicketDto> {
  const { data, error } = await api.GET('/api/tickets/{id}', { params: { path: { id } } });
  if (error || !data) throw new Error('Nie udało się pobrać ticketu');
  return data;
}

export async function closeTicket(id: number): Promise<TicketDto> {
  const { data, error } = await api.PATCH('/api/tickets/{id}', {
    params: { path: { id } },
    body: { status: 'CLOSED' },
  });
  if (error || !data) throw new Error('Nie udało się zamknąć ticketu');
  return data;
}
```

#T NOTE JSX ↔ TSX — tu TSX pokazuje największą przewagę
To lekcja, w której różnica między wersjami jest największa. W TSX generowany plik `schema.d.ts` łączy backend i frontend **przy kompilacji**: po zmianie `assignee` na obiekt w Javie i ponownym wygenerowaniu typów `npm run build` wskaże każde miejsce we frontendzie, które traktuje `assignee` jak tekst — zanim cokolwiek trafi do użytkowników. W JSX dostajesz podpowiedzi w edytorze (przez JSDoc), ale nie błąd budowania; ochroną zostaje walidacja w czasie działania. Wniosek: przy współpracy z backendem Javy TypeScript + generowane typy to najmocniejsza kombinacja, a walidacja Zod nadal przydaje się dla danych, których nie opisuje specyfikacja (localStorage, zdarzenia SSE).

#T CODE_PRACTICAL Generowane typy z TanStack Query
```
import { useQuery } from '@tanstack/react-query';
import { api, type TicketDto } from './client';

export function useTicketDetail(id: number) {
  return useQuery({
    queryKey: ['tickets', 'detail', id],
    queryFn: async ({ signal }): Promise<TicketDto> => {
      const { data, error } = await api.GET('/api/tickets/{id}', { params: { path: { id } }, signal });
      if (error || !data) throw new Error('Nie udało się pobrać ticketu');
      return data;
    },
  });
}
```

#T STEP_BY_STEP Budujemy razem: kontrakt generowany z backendu
1. Dodaj do projektu Spring Boot zależność springdoc i otwórz `/swagger-ui.html` — przejrzyj endpointy DevDesk i wykonaj kilka żądań z interfejsu.
2. W projekcie frontendu: `npm install -D openapi-typescript` oraz `npm install openapi-fetch`.
3. Dodaj skrypt `api:types` i wygeneruj `src/api/schema.d.ts` przy uruchomionym backendzie.
4. Przepisz `fetchTicket` i `closeTicket` na `openapi-fetch`; w wersji TS usuń ręcznie pisane typy DTO na rzecz `components['schemas'][...]`.
5. Zrób eksperyment: zmień w Javie typ pola `assignee` (np. na rekord `AssigneeDto`), uruchom ponownie backend, wygeneruj typy i `npm run build` — zobacz listę błędów kompilacji we frontendzie. Cofnij zmianę.
6. Dodaj generowanie typów do procesu CI (rozdział 21): krok porównujący wygenerowany plik z zapisanym w repozytorium wykryje niezsynchronizowane zmiany API.
7. Zdecyduj, co z mockami MSW: typy handlerów też możesz oprzeć o `paths` — mocki nie rozjadą się z prawdziwym API.

#T PITFALL Specyfikacja, która kłamie
springdoc opisuje API na podstawie kodu, ale nie zgadnie wszystkiego: wyjątki zamieniane na 404 w `@ExceptionHandler` nie pojawią się w specyfikacji bez `@ApiResponse`, pola, które w praktyce bywają `null`, mogą być oznaczone jako wymagane, a typy generyczne (`PageDto<T>`) czasem wymagają dodatkowych adnotacji. Przejrzyj wygenerowaną specyfikację w Swagger UI i uzupełnij adnotacje — wygenerowane typy są tak dobre, jak specyfikacja.

#T SUMMARY Kryterium akceptacji i podsumowanie
springdoc-openapi generuje specyfikację OpenAPI z kontrolerów Springa (`/v3/api-docs`, Swagger UI). openapi-typescript zamienia ją na typy TS, a openapi-fetch daje klienta znającego ścieżki, parametry i odpowiedzi. Zmiana API w Javie po ponownym wygenerowaniu typów daje błędy kompilacji we frontendzie przed wdrożeniem. W JSX generowane typy działają przez JSDoc w edytorze; ochroną w czasie działania pozostaje walidacja. Specyfikację trzeba przejrzeć i uzupełnić adnotacjami.

Kryterium akceptacji: DevDesk ma skrypt generujący typy z backendu, funkcje API korzystają z `openapi-fetch`, a zmiana typu pola w Javie powoduje błąd `npm run build` w wersji TS we wszystkich miejscach, które z tego pola korzystają.
