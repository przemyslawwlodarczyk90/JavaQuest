#T INTRO Rozgrzewka i problem: kliknąłem i nic się nie dzieje
Rozgrzewka: Co robi loader trasy i kiedy jest wywoływany? Dlaczego loadery eliminują kaskadę ładowania? Co router robi po wykonaniu akcji?

Problem: z loaderami kliknięcie ticketu na wolnym łączu przez sekundę nie zmienia ekranu — stary widok zostaje do czasu danych. Użytkownik klika drugi raz, potem trzeci. Druga sprawa: ktoś edytuje opis ticketu, przypadkiem klika „Archiwum” w menu i traci kilka akapitów tekstu bez ostrzeżenia. Ta lekcja: **stan nawigacji** (globalny wskaźnik ładowania, oznaczenie linku w trakcie) i **blokowanie opuszczenia strony** z niezapisanymi zmianami.

#T DEFINITION useNavigation i stan linku
`useNavigation()` zwraca stan bieżącej nawigacji routera (w trybie danych):
- `state: 'idle'` — nic się nie dzieje,
- `state: 'loading'` — router ładuje dane nowej trasy (loadery),
- `state: 'submitting'` — trwa wysyłanie formularza do akcji,
- `location` — dokąd trwa nawigacja (przydatne do oznaczenia, który link „się ładuje”), `formData` — dane wysyłanego formularza.

`NavLink` dostaje w funkcji `className`/`children` także `isPending` — `true`, gdy trwa nawigacja właśnie do jego trasy.

#T CODE_JSX Globalny pasek ładowania (JSX)
Pasek pojawia się dopiero po 150 ms — krótkie nawigacje nie migają paskiem.
```
// NavigationProgress.jsx
import { useEffect, useState } from 'react';
import { useNavigation } from 'react-router';

export function NavigationProgress() {
  const navigation = useNavigation();
  const busy = navigation.state !== 'idle';
  const [visible, setVisible] = useState(false);

  useEffect(() => {
    if (!busy) {
      setVisible(false);
      return;
    }
    const id = setTimeout(() => setVisible(true), 150);
    return () => clearTimeout(id);
  }, [busy]);

  return (
    <div className={visible ? 'nav-progress nav-progress--active' : 'nav-progress'} role="progressbar" aria-hidden={!visible} aria-label="Ładowanie strony" />
  );
}
```

#T CODE_TSX Globalny pasek ładowania (TSX)
Typ stanu nawigacji to unia `'idle' | 'loading' | 'submitting'` — porównanie z literówką (`'loadng'`) jest błędem.
```
// NavigationProgress.tsx
import { useEffect, useState } from 'react';
import { useNavigation } from 'react-router';

export function NavigationProgress() {
  const navigation = useNavigation();
  const busy = navigation.state !== 'idle';
  const [visible, setVisible] = useState(false);

  useEffect(() => {
    if (!busy) {
      setVisible(false);
      return;
    }
    const id = setTimeout(() => setVisible(true), 150);
    return () => clearTimeout(id);
  }, [busy]);

  return (
    <div className={visible ? 'nav-progress nav-progress--active' : 'nav-progress'} role="progressbar" aria-hidden={!visible} aria-label="Ładowanie strony" />
  );
}
```

#T NOTE JSX ↔ TSX — unie stanów z biblioteki
Wiele bibliotek opisuje stany unią literałów (`useNavigation().state`, `useQuery().status`, `useFetcher().state`). W TSX porównanie `navigation.state === 'submiting'` zostanie zgłoszone jako porównanie typów bez części wspólnej — w JSX zawsze da `false` i warunek po cichu nigdy się nie spełni. Typ `navigation.location` to `Location | undefined` — dostępny tylko w trakcie nawigacji, co TSX wymusza sprawdzić.

#T CODE_BASIC Link oznaczający własne ładowanie
```
import { NavLink } from 'react-router';

export function NavItem({ to, label }: { to: string; label: string }) {
  return (
    <NavLink
      to={to}
      className={({ isActive, isPending }) => ['nav__link', isActive && 'nav__link--active', isPending && 'nav__link--pending'].filter(Boolean).join(' ')}
    >
      {({ isPending }) => (
        <>
          {label}
          {isPending && <span className="spinner spinner--sm" aria-label="ładowanie" />}
        </>
      )}
    </NavLink>
  );
}
```

#T DEFINITION Blokowanie opuszczenia strony z niezapisanymi zmianami
Dwie sytuacje:
1. **Nawigacja wewnątrz aplikacji** (kliknięcie linku, „Wstecz”) — `useBlocker(warunek)` z React Router. Gdy warunek jest prawdziwy, nawigacja zostaje wstrzymana (`blocker.state === 'blocked'`), a Ty pytasz użytkownika i wywołujesz `blocker.proceed()` lub `blocker.reset()`.
2. **Zamknięcie karty, odświeżenie, wpisanie innego adresu** — przeglądarka pokazuje własny komunikat, jeśli w zdarzeniu `beforeunload` wywołasz `event.preventDefault()`. Treści komunikatu nie da się zmienić.

Blokuj tylko wtedy, gdy naprawdę są niezapisane zmiany — blokowanie „na wszelki wypadek” irytuje.

#T CODE_PRACTICAL Hook ochrony niezapisanych zmian
```
import { useEffect } from 'react';
import { useBlocker } from 'react-router';

export function useUnsavedChangesGuard(dirty: boolean) {
  const blocker = useBlocker(({ currentLocation, nextLocation }) => dirty && currentLocation.pathname !== nextLocation.pathname);

  useEffect(() => {
    if (!dirty) return;
    const handler = (e: BeforeUnloadEvent) => e.preventDefault();
    window.addEventListener('beforeunload', handler);
    return () => window.removeEventListener('beforeunload', handler);
  }, [dirty]);

  return blocker;
}

export function UnsavedChangesDialog({ blocker }: { blocker: ReturnType<typeof useBlocker> }) {
  if (blocker.state !== 'blocked') return null;
  return (
    <div role="alertdialog" aria-modal="true" aria-labelledby="unsaved-title" className="modal">
      <h2 id="unsaved-title">Masz niezapisane zmiany</h2>
      <p>Jeśli wyjdziesz teraz, zmiany zostaną utracone.</p>
      <button type="button" onClick={() => blocker.reset()}>Wróć do edycji</button>
      <button type="button" className="danger" onClick={() => blocker.proceed()}>Odrzuć i wyjdź</button>
    </div>
  );
}
```

#T STEP_BY_STEP Budujemy razem: płynna nawigacja w DevDesk
1. Dodaj `NavigationProgress` na górze `AppLayout` i styl: `.nav-progress { position: fixed; top: 0; left: 0; height: 3px; width: 0; background: var(--color-primary); transition: width .3s; } .nav-progress--active { width: 80%; }` (z `prefers-reduced-motion` bez animacji).
2. Zamień linki menu na `NavItem` z oznaczeniem `isPending`.
3. W MSW ustaw opóźnienie 1,5 s dla szczegółów ticketu i przejdź z listy do ticketu — widać pasek i spinner przy linku, stary ekran przyciemnij klasą przy `navigation.state === 'loading'`.
4. W formularzu edycji ticketu wylicz `dirty` (porównanie z zapisanymi danymi albo `formState.isDirty` z React Hook Form) i dodaj `useUnsavedChangesGuard` z `UnsavedChangesDialog`.
5. Zmień opis, kliknij link w menu — pojawia się pytanie; „Wróć do edycji” zostawia Cię w formularzu, „Odrzuć i wyjdź” kontynuuje nawigację.
6. Zmień opis i spróbuj zamknąć kartę — przeglądarka pyta o potwierdzenie. Po zapisaniu zmian obie blokady znikają.
7. Sprawdź „Wstecz” w przeglądarce przy niezapisanych zmianach — `useBlocker` blokuje także tę nawigację.

#T PITFALL Spinner przy każdej nawigacji od pierwszej milisekundy
Wskaźnik pokazywany natychmiast miga przy każdej szybkiej nawigacji (dane z cache, 30 ms), co wygląda gorzej niż jego brak. Opóźnij pokazanie (150–300 ms) i — jeśli już się pojawił — nie chowaj go po kilku milisekundach (minimalny czas wyświetlenia). Ta sama zasada dotyczy skeletonów i przycisków „Zapisywanie…”.

#T SUMMARY Kryterium akceptacji i podsumowanie
`useNavigation()` daje stan nawigacji (`idle`, `loading`, `submitting`) — na jego podstawie pokazujesz globalny pasek ładowania (z opóźnieniem), przyciemniasz stary ekran i blokujesz podwójne wysłanie. `NavLink` udostępnia `isPending` do oznaczenia linku w trakcie ładowania. Niezapisane zmiany chronisz `useBlocker` (nawigacja w aplikacji, z własnym oknem pytania) i `beforeunload` (zamknięcie karty, odświeżenie). W TSX stany nawigacji są uniami literałów.

Kryterium akceptacji: przy wolnym ładowaniu widać pasek u góry i spinner przy klikniętym linku (krótkie nawigacje nie migają), a opuszczenie formularza edycji z niezapisanymi zmianami — linkiem, „Wstecz” lub zamknięciem karty — wymaga potwierdzenia.
