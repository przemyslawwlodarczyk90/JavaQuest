#T INTRO Rozgrzewka i problem: „jak się używa tego przycisku?”
Rozgrzewka: Czego granica błędu nie łapie? Po co `resetKeys`? Gdzie w React 19 podłączasz centralne raportowanie błędów?

Problem: DevDesk ma już kilkadziesiąt komponentów wielokrotnego użytku — `Button`, `Badge`, `StatusBadge`, `Modal`, `TicketTable`, pola formularzy. Nowa osoba w zespole pyta: jakie warianty ma `Button`? Czy `Modal` zamyka się Escape? Jak wygląda `TicketTable` bez danych? Odpowiedzi są rozsiane po kodzie, a żeby zobaczyć pusty stan tabeli, trzeba wyczyścić bazę. W rozdziale 14 poznałeś Storybook jako narzędzie do testów historii. W tej lekcji zrobisz z niego **żywą dokumentację** biblioteki komponentów: kontrolki argumentów, automatyczne strony dokumentacji z typów i komentarzy, dekoratory z motywem i Providerami, dane z MSW w historiach oraz historie używane ponownie w testach.

#T DEFINITION Historia, argumenty i kontrolki
- **Historia (story)** — nazwany stan komponentu: `Primary`, `Disabled`, `Loading`. Plik `Button.stories.tsx` obok komponentu.
- **Argumenty (args)** — props historii zapisane jako dane, a nie w JSX. Storybook renderuje `<Button {...args} />` i pozwala zmieniać je na żywo w panelu **Controls**.
- **argTypes** — opis argumentów: rodzaj kontrolki (`select`, `radio`, `color`, `boolean`), dozwolone wartości, opis, kategoria; dla funkcji (`onClick`) — rejestrowanie wywołań w panelu **Actions** (`fn()` z `storybook/test`).
- **Dekorator** — komponent opakowujący historię (motyw, Provider, router, układ strony).
- **Parametry (parameters)** — ustawienia narzędzi: tło, rozmiar ekranu, układ (`layout: 'centered'`), opcje dodatków.
- **Autodocs** — tag `autodocs` generuje stronę dokumentacji: opis z komentarza JSDoc komponentu, tabelę props (z typów TS albo z `argTypes` w JS) i wszystkie historie z podglądem kodu.

Argumenty dziedziczą się: domyślne w `meta.args`, nadpisywane w historii — każda historia zmienia tylko to, czym się różni.

#T CODE_JSX Historie przycisku z argumentami (JSX)
W JSX Storybook nie zna typów props, więc tabela dokumentacji i kontrolki biorą się z `argTypes` (i częściowo z analizy kodu). Adnotacje JSDoc `@type` dają podpowiedzi w edytorze.
```
// Button.stories.jsx
import { fn } from 'storybook/test';
import { Button } from './Button';

/** @type {import('@storybook/react-vite').Meta<typeof Button>} */
const meta = {
  title: 'DevDesk/Button',
  component: Button,
  tags: ['autodocs'],
  parameters: { layout: 'centered' },
  args: { children: 'Zapisz', variant: 'primary', size: 'md', onClick: fn() },
  argTypes: {
    variant: { control: 'select', options: ['primary', 'secondary', 'danger', 'ghost'], description: 'Wygląd przycisku' },
    size: { control: 'radio', options: ['sm', 'md', 'lg'] },
    loading: { control: 'boolean', description: 'Pokazuje spinner i blokuje kliknięcia' },
    onClick: { table: { category: 'Zdarzenia' } },
  },
};
export default meta;

export const Primary = {};

export const Danger = { args: { variant: 'danger', children: 'Usuń ticket' } };

export const Loading = { args: { loading: true, children: 'Zapisywanie…' } };

export const AllVariants = {
  render: (args) => (
    <div style={{ display: 'flex', gap: 8 }}>
      {['primary', 'secondary', 'danger', 'ghost'].map((variant) => (
        <Button key={variant} {...args} variant={variant}>{variant}</Button>
      ))}
    </div>
  ),
};
```

#T CODE_TSX Historie przycisku z argumentami (TSX)
W TSX `satisfies Meta<typeof Button>` sprawdza, czy argumenty pasują do props komponentu, a `StoryObj<typeof meta>` daje podpowiedzi w historiach. Tabela props w dokumentacji powstaje **z typów** — `argTypes` dopisujesz tylko tam, gdzie chcesz zmienić kontrolkę lub opis.
```
// Button.stories.tsx
import type { Meta, StoryObj } from '@storybook/react-vite';
import { fn } from 'storybook/test';
import { Button } from './Button';

const meta = {
  title: 'DevDesk/Button',
  component: Button,
  tags: ['autodocs'],
  parameters: { layout: 'centered' },
  args: { children: 'Zapisz', variant: 'primary', size: 'md', onClick: fn() },
  argTypes: {
    onClick: { table: { category: 'Zdarzenia' } },
  },
} satisfies Meta<typeof Button>;
export default meta;

type Story = StoryObj<typeof meta>;

export const Primary: Story = {};

export const Danger: Story = { args: { variant: 'danger', children: 'Usuń ticket' } };

export const Loading: Story = { args: { loading: true, children: 'Zapisywanie…' } };

export const AllVariants: Story = {
  render: (args) => (
    <div style={{ display: 'flex', gap: 8 }}>
      {(['primary', 'secondary', 'danger', 'ghost'] as const).map((variant) => (
        <Button key={variant} {...args} variant={variant}>{variant}</Button>
      ))}
    </div>
  ),
};
```

#T CODE_PRACTICAL Komponent opisany dla dokumentacji
Komentarz JSDoc nad komponentem staje się opisem strony dokumentacji, a komentarze nad polami typu props — opisami w tabeli. To ten sam komentarz, który IDE pokazuje po najechaniu na komponent.
```
// Button.tsx
import type { ComponentProps } from 'react';

type ButtonProps = ComponentProps<'button'> & {
  /** Wygląd przycisku. `danger` tylko dla akcji nieodwracalnych. */
  variant?: 'primary' | 'secondary' | 'danger' | 'ghost';
  /** Rozmiar: `sm` w tabelach, `md` domyślnie, `lg` w pustych stanach. */
  size?: 'sm' | 'md' | 'lg';
  /** Pokazuje spinner, ustawia `aria-busy` i blokuje ponowne kliknięcie. */
  loading?: boolean;
};

/**
 * Podstawowy przycisk DevDesk.
 *
 * Używaj zawsze zamiast gołego `<button>` — dba o `type="button"`, stan ładowania i style wariantów.
 */
export function Button({ variant = 'primary', size = 'md', loading = false, disabled, children, ...rest }: ButtonProps) {
  return (
    <button
      type="button"
      className={`btn btn--${variant} btn--${size}`}
      disabled={disabled || loading}
      aria-busy={loading || undefined}
      {...rest}
    >
      {loading && <span className="btn__spinner" aria-hidden="true" />}
      {children}
    </button>
  );
}
```

#T NOTE JSX ↔ TSX — dokumentacja z typów
To jedno z miejsc, gdzie TypeScript daje najwięcej „za darmo”: Storybook czyta typy props (przez `react-docgen` lub `react-docgen-typescript`) i sam buduje tabelę z nazwami, typami, wartościami domyślnymi i opisami z JSDoc — unia `'primary' | 'secondary'` od razu staje się listą w kontrolce `select`. W projekcie JSX tę samą informację musisz powtórzyć w `argTypes` (albo w `PropTypes`), a gdy dodasz wariant w komponencie i zapomnisz o `argTypes`, dokumentacja po cichu się zdezaktualizuje.

#T CODE_JSX Dekoratory i globalny przełącznik motywu (JSX)
`preview` to konfiguracja wspólna dla wszystkich historii. Globalny parametr `theme` dodaje przełącznik na pasku narzędzi, a dekorator ustawia `data-theme` i opakowuje historię Providerami aplikacji.
```
// .storybook/preview.jsx
import '../src/styles/tokens.css';
import { PreferencesProvider } from '../src/preferences';

/** @type {import('@storybook/react-vite').Preview} */
const preview = {
  globalTypes: {
    theme: {
      description: 'Motyw DevDesk',
      toolbar: { icon: 'mirror', items: [{ value: 'light', title: 'Jasny' }, { value: 'dark', title: 'Ciemny' }] },
    },
  },
  initialGlobals: { theme: 'light' },
  decorators: [
    (Story, context) => (
      <div data-theme={context.globals.theme} style={{ padding: 16 }}>
        <PreferencesProvider>
          <Story />
        </PreferencesProvider>
      </div>
    ),
  ],
  parameters: {
    controls: { matchers: { color: /(background|color)$/i } },
    a11y: { test: 'error' }, // naruszenia dostępności oznaczają historię jako błędną
  },
};

export default preview;
```

#T CODE_PRACTICAL Stany danych: tabela z MSW i routerem
Komponenty pobierające dane dokumentujesz z udawanym API: dodatek `msw-storybook-addon` pozwala każdej historii mieć własne handlery MSW (te same, co w testach z rozdziału 14). Dekorator historii dokłada router i `QueryClient`, a każda historia pokazuje inny stan: dane, pusto, ładowanie, błąd.
```
// TicketTable.stories.tsx
import type { Meta, StoryObj } from '@storybook/react-vite';
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';
import { http, HttpResponse, delay } from 'msw';
import { MemoryRouter } from 'react-router';
import { TicketTablePage } from './TicketTablePage';
import { sampleTickets } from '../mocks/data';

const meta = {
  title: 'DevDesk/TicketTablePage',
  component: TicketTablePage,
  decorators: [
    (Story) => (
      <QueryClientProvider client={new QueryClient({ defaultOptions: { queries: { retry: false } } })}>
        <MemoryRouter initialEntries={['/tickets']}>
          <Story />
        </MemoryRouter>
      </QueryClientProvider>
    ),
  ],
  parameters: { layout: 'fullscreen' },
} satisfies Meta<typeof TicketTablePage>;
export default meta;

type Story = StoryObj<typeof meta>;

export const WithData: Story = {
  parameters: { msw: { handlers: [http.get('/api/tickets', () => HttpResponse.json(sampleTickets))] } },
};

export const Empty: Story = {
  parameters: { msw: { handlers: [http.get('/api/tickets', () => HttpResponse.json([]))] } },
};

export const Loading: Story = {
  parameters: { msw: { handlers: [http.get('/api/tickets', async () => { await delay('infinite'); return HttpResponse.json([]); })] } },
};

export const ServerError: Story = {
  parameters: { msw: { handlers: [http.get('/api/tickets', () => new HttpResponse(null, { status: 500 }))] } },
};
```

#T USAGE Strona dokumentacji w MDX
Autodocs wystarcza dla prostych komponentów. Dla złożonych (wzorce użycia, zasady dostępności, „czego nie robić”) piszesz stronę MDX, która łączy tekst z żywymi historiami:
- `import { Meta, Canvas, Controls, ArgTypes } from '@storybook/addon-docs/blocks';` i `import * as ButtonStories from './Button.stories';`,
- `<Meta of={ButtonStories} />` — przypina stronę do komponentu,
- `<Canvas of={ButtonStories.Danger} />` — podgląd historii z kodem,
- `<Controls />` lub `<ArgTypes />` — tabela props,
- zwykły Markdown między blokami: kiedy używać wariantu `danger`, jak opisywać przyciski-ikony (`aria-label`), przykłady złe i dobre.

Dokumentacja żyje obok kodu i renderuje prawdziwe komponenty — zmiana w komponencie od razu jest widoczna w dokumentacji.

#T CODE_JSX Historie ponownie w testach (JSX)
Historie to gotowe przypadki testowe: `composeStories` zamienia je w komponenty z zastosowanymi argumentami, dekoratorami i konfiguracją z `preview`. Nie powtarzasz przygotowania danych w testach.
```
// Button.test.jsx
import { composeStories } from '@storybook/react-vite';
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { expect, it } from 'vitest';
import * as stories from './Button.stories';

const { Primary, Loading } = composeStories(stories);

it('wywołuje onClick po kliknięciu', async () => {
  render(<Primary />);
  await userEvent.click(screen.getByRole('button', { name: 'Zapisz' }));
  expect(Primary.args.onClick).toHaveBeenCalledOnce();
});

it('w stanie ładowania blokuje przycisk', () => {
  render(<Loading />);
  expect(screen.getByRole('button')).toBeDisabled();
});
```

#T WHEN_TO_USE Kiedy Storybook się opłaca
- **Tak:** biblioteka komponentów współdzielona przez kilka ekranów lub zespołów; design system; komponenty z wieloma stanami trudnymi do odtworzenia w aplikacji (błąd serwera, pusty wynik, długie teksty, brak uprawnień); praca z projektantami (przegląd wariantów bez uruchamiania backendu).
- **Tak, ale lekko:** średni projekt — historie tylko dla komponentów ze wspólnego katalogu `ui/`, bez stron.
- **Nie:** mała aplikacja z kilkoma ekranami i bez komponentów wielokrotnego użytku — koszt utrzymania historii przewyższy zysk; wystarczą testy komponentów.

Zasada utrzymania: historia, która się nie buduje, jest gorsza niż jej brak. Uruchamiaj `storybook build` i testy historii w CI (rozdział 21), żeby dokumentacja nie rozjechała się z kodem.

#T STEP_BY_STEP Budujemy razem: katalog komponentów DevDesk
1. Dodaj komentarze JSDoc do `Button`, `Badge`, `StatusBadge` i `Modal` — opis komponentu i każdego propsa.
2. Napisz historie `Button` z argumentami, `fn()` dla `onClick` i tagiem `autodocs`; sprawdź wygenerowaną tabelę props (w JSX — uzupełnij `argTypes`).
3. Skonfiguruj `preview`: tokeny CSS, globalny przełącznik motywu, dekorator z `PreferencesProvider`, parametr `a11y`.
4. Dodaj `msw-storybook-addon` i historie `TicketTablePage`: dane, pusto, ładowanie, błąd 500.
5. Napisz stronę MDX „Przyciski — zasady użycia” z historiami `Primary` i `Danger` oraz sekcją o przyciskach-ikonach.
6. Użyj `composeStories` w testach `Button` i `StatusBadge` — usuń z testów zduplikowane przygotowanie props.
7. Dodaj do skryptów `storybook build` i sprawdź, że cały katalog buduje się bez błędów.

#T PITFALL Historie, które kłamią
Historia z ręcznie wpisanym, „idealnym” zestawem danych (krótkie tytuły, okrągłe liczby, zawsze zalogowany administrator) pokazuje komponent, którego użytkownicy nigdy nie zobaczą. Dodawaj historie dla trudnych przypadków: tytuł na 200 znaków, brak przypisanej osoby, 0 i 10 000 wyników, język z długimi słowami, rola bez uprawnień. Druga pułapka: logika istniejąca **tylko** w dekoratorach historii (np. dane wstrzyknięte inaczej niż w aplikacji) — komponent działa w Storybooku, a w aplikacji nie. Dekoratory mają odtwarzać prawdziwe Providery aplikacji, a nie je zastępować.

#T SUMMARY Kryterium akceptacji i podsumowanie
Storybook to żywa dokumentacja komponentów: historie jako nazwane stany, argumenty z kontrolkami i rejestrowaniem akcji (`fn()`), dziedziczenie argumentów z `meta`, dekoratory z motywem i Providerami, parametry narzędzi, dane z MSW dla każdej historii, strony autodocs i MDX oraz ponowne użycie historii w testach przez `composeStories`. W TSX tabela props i kontrolki powstają z typów i komentarzy JSDoc, a `satisfies Meta<typeof Komponent>` pilnuje zgodności argumentów; w JSX te informacje utrzymujesz w `argTypes`.

Kryterium akceptacji: każdy komponent z katalogu `ui/` ma stronę dokumentacji z opisem i tabelą props, historie obejmują stany trudne (długi tekst, pusto, błąd), przełącznik motywu działa we wszystkich historiach, panel dostępności nie zgłasza naruszeń, a `storybook build` i testy oparte na historiach przechodzą w CI.
