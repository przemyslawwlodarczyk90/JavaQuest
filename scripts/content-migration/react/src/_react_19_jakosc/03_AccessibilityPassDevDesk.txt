#T INTRO Rozgrzewka i problem: audyt całej aplikacji
Rozgrzewka: Kiedy region na żywo nie ogłosi komunikatu? Na czym polega roving tabindex? Jakich trzech poleceń czytnika ekranu użyłeś?

Problem: poprawiłeś pojedyncze komponenty, ale klient przed podpisaniem umowy chce **raportu dostępności** całego DevDesk. Ręczne sprawdzanie każdego ekranu jest powolne, a regresje wracają z każdym nowym komponentem. W tej lekcji przeprowadzisz **audyt** łączący narzędzia automatyczne (axe, Lighthouse), ręczne testy klawiaturą i czytnikiem ekranu oraz zabezpieczysz efekt testami automatycznymi w Vitest i Playwright.

#T DEFINITION Co wykryje automat, a co człowiek
Narzędzia automatyczne (axe-core, Lighthouse, WAVE) znajdują **około 30–40%** problemów: brak `alt`, brak etykiet, niski kontrast, złe role i atrybuty ARIA, zduplikowane `id`, brak `lang`. Nie sprawdzą, czy:
- tekst alternatywny jest **sensowny** („obraz123.png” przejdzie),
- kolejność fokusu jest logiczna, a fokus wraca po zamknięciu modala,
- komunikaty są ogłaszane we właściwym momencie,
- obsługa klawiatury złożonych widżetów (tabela, Kanban, combobox) jest kompletna.

Dlatego audyt = **automat + klawiatura + czytnik ekranu + lista kontrolna** (np. według kryteriów WCAG AA).

#T CODE_JSX Test axe w Vitest (JSX)
`vitest-axe` (lub `jest-axe`) uruchamia axe-core na wyrenderowanym komponencie w jsdom.
```
// TicketForm.a11y.test.jsx
import { render } from '@testing-library/react';
import { axe } from 'vitest-axe';
import { expect, it } from 'vitest';
import { TicketForm } from './TicketForm';

it('formularz ticketu nie ma naruszeń dostępności', async () => {
  const { container } = render(<TicketForm onSubmit={() => {}} />);
  const results = await axe(container);
  expect(results.violations).toEqual([]);
});
```

#T CODE_TSX Test axe w Vitest (TSX)
W TSX możesz wypisać czytelny raport naruszeń — typ `AxeResults` daje dostęp do `id`, `help` i elementów.
```
// TicketForm.a11y.test.tsx
import { render } from '@testing-library/react';
import { axe } from 'vitest-axe';
import { expect, it } from 'vitest';

declare function TicketForm(props: { onSubmit: () => void }): React.JSX.Element;

it('formularz ticketu nie ma naruszeń dostępności', async () => {
  const { container } = render(<TicketForm onSubmit={() => {}} />);
  const results = await axe(container);
  const summary = results.violations.map((v) => `${v.id}: ${v.help} (${v.nodes.length})`);
  expect(summary).toEqual([]);
});
```

#T NOTE JSX ↔ TSX — raport zamiast „false is not true”
Test jest taki sam w obu wersjach; w TSX podpowiedzi typu `AxeResults` ułatwiają zbudowanie czytelnego komunikatu (identyfikator reguły, opis, liczba elementów), dzięki czemu w CI od razu widać, co poprawić. Pamiętaj o ograniczeniu: jsdom nie liczy stylów, więc **kontrast** sprawdzisz dopiero w prawdziwej przeglądarce (Playwright, Lighthouse).

#T CODE_BASIC Audyt w przeglądarce: Playwright + axe
`@axe-core/playwright` sprawdza całe ekrany w prawdziwej przeglądarce — z kontrastem i stylami.
```
// e2e/a11y.spec.ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

const screens = ['/tickets', '/tickets/42', '/tickets/new', '/login'];

for (const path of screens) {
  test(`brak naruszeń WCAG AA: ${path}`, async ({ page }) => {
    await page.goto(path);
    const results = await new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa', 'wcag21aa', 'wcag22aa']).analyze();
    expect(results.violations.map((v) => v.id)).toEqual([]);
  });
}
```

#T CODE_PRACTICAL Test klawiatury: fokus wraca po zamknięciu modala
Automat nie sprawdzi zarządzania fokusem — napisz to jako test E2E.
```
// e2e/keyboard.spec.ts
import { test, expect } from '@playwright/test';

test('modal przypisania: pułapka fokusu i powrót fokusu', async ({ page }) => {
  await page.goto('/tickets/42');
  const trigger = page.getByRole('button', { name: 'Przypisz' });
  await trigger.focus();
  await page.keyboard.press('Enter');

  const dialog = page.getByRole('dialog', { name: 'Przypisz ticket' });
  await expect(dialog).toBeVisible();
  await expect(dialog.getByRole('combobox', { name: 'Agent' })).toBeFocused();

  await page.keyboard.press('Escape');
  await expect(dialog).toBeHidden();
  await expect(trigger).toBeFocused();
});
```

#T STEP_BY_STEP Budujemy razem: audyt DevDesk
1. Uruchom Lighthouse (DevTools → Lighthouse → Accessibility) dla czterech głównych ekranów i zapisz wyniki oraz listę problemów.
2. Zainstaluj rozszerzenie axe DevTools i przeskanuj te same ekrany — porównaj z Lighthouse.
3. Przejdź każdy ekran klawiaturą według listy: kolejność fokusu, widoczność fokusu, Escape zamyka nakładki, fokus wraca, brak pułapek.
4. Przejdź ekran ticketu i formularz czytnikiem ekranu — zapisz problemy z nazwami, stanami i ogłoszeniami.
5. Popraw znalezione problemy; dla każdego dopisz w raporcie kryterium WCAG (np. 1.4.3 Kontrast, 2.4.7 Widoczny fokus, 4.1.2 Nazwa, rola, wartość).
6. Dodaj testy `vitest-axe` dla komponentów formularzy oraz `a11y.spec.ts` i `keyboard.spec.ts` w Playwright; uruchom je w CI (rozdział 21).
7. Przygotuj krótki raport: zakres, metoda, wynik, znane ograniczenia (np. wykresy — alternatywa tabelaryczna w rozdziale 20).

#T PITFALL Wynik 100 w Lighthouse jako dowód dostępności
Lighthouse z wynikiem 100 oznacza tylko brak problemów, które **potrafi wykryć** automat. Aplikacja z wynikiem 100 może być nieużywalna z klawiatury (np. przeciąganie bez alternatywy) albo mieć fokus znikający po każdej akcji. Wynik automatyczny traktuj jak testy jednostkowe — konieczne, ale niewystarczające; raport dostępności zawsze zawiera testy ręczne.

#T SUMMARY Kryterium akceptacji i podsumowanie
Audyt dostępności łączy narzędzia automatyczne (axe, Lighthouse — ok. 30–40% problemów), ręczne testy klawiaturą i czytnikiem ekranu oraz listę kontrolną WCAG AA. Efekt zabezpieczasz testami: `vitest-axe` dla komponentów (bez kontrastu w jsdom), `@axe-core/playwright` dla całych ekranów i testy E2E zarządzania fokusem. W TSX łatwiej zbudować czytelny raport naruszeń.

Kryterium akceptacji: masz raport dostępności czterech głównych ekranów DevDesk z poprawionymi problemami przypisanymi do kryteriów WCAG, testy axe komponentów i ekranów oraz test powrotu fokusu po zamknięciu modala — wszystkie przechodzą.
