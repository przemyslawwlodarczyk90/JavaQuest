W `src/components/` leży 140 plików — `TicketTable`, `LoginForm`, `KanbanCard`, `Button`, `useTicketFilters`, `api.ts`… Zmiana w module ticketów wymaga szukania plików w pięciu katalogach, `Button` importuje coś z `tickets`, a `tickets` z `auth` i z powrotem — import cykliczny wywala aplikację przy starcie. W tej lekcji uporządkujesz projekt według **funkcji** (feature-based), ustalisz warstwy i granice między modułami, dodasz aliasy importów i reguły lintera, które pilnują porządku za Ciebie.

#T DEFINITION Struktura według funkcji, a nie według typu pliku
Podział „według typu” (`components/`, `hooks/`, `api/`, `types/`) działa w małym projekcie. Gdy rośnie, wszystko, co dotyczy jednej funkcji, jest rozsiane po całym drzewie. Podział **według funkcji** grupuje razem to, co zmienia się razem:

src/
├── app/            ← start aplikacji: providery, router, globalne style, konfiguracja
├── features/       ← funkcje biznesowe, każda w swoim katalogu
│   ├── tickets/    ← komponenty, hooki, api, typy, testy ticketów
│   ├── board/      ← tablica Kanban
│   ├── auth/       ← logowanie, sesja, uprawnienia
│   └── dashboard/
├── shared/         ← kod bez wiedzy o domenie: ui (Button, Modal), lib (formatowanie dat), hooki ogólne
└── main.tsx

Wewnątrz funkcji możesz dalej dzielić na `components/`, `hooks/`, `api/`, `model/` — ale tylko wtedy, gdy plików jest dużo. Testy i style leżą **obok** pliku, którego dotyczą (`TicketTable.tsx`, `TicketTable.test.tsx`, `TicketTable.module.css`).

#T DEFINITION Warstwy i kierunek zależności
Najważniejsza zasada architektury: **zależności płyną w jedną stronę**.
- `app` może importować z `features` i `shared`,
- `features` mogą importować z `shared` i — przez publiczne API — z innych funkcji (lepiej: wcale),
- `shared` nie importuje niczego z `features` ani `app`.

Wewnątrz funkcji warstwy też mają kierunek: komponenty → hooki → api i model. Komponent nie woła `fetch` bezpośrednio; robi to warstwa `api`, z której korzysta hook (np. `useTickets` na TanStack Query). Model (typy, czyste funkcje jak `moveTicket`) nie zależy od Reacta — dzięki temu testujesz go bez renderowania.

Każda funkcja ma **publiczne API** — plik `index`, który eksportuje to, czego potrzebuje reszta aplikacji (strona, hook, typ). Wszystko inne jest szczegółem implementacji i może się zmieniać bez wpływu na inne moduły.

#T CODE_JSX Publiczne API funkcji tickets (JSX)
Reszta aplikacji importuje tylko z `@/features/tickets` — nie z głębi katalogu. Dzięki temu możesz przenieść albo przepisać `TicketTable` bez zmian w innych modułach.
```
// features/tickets/index.js
export { TicketsPage } from './pages/TicketsPage';
export { TicketDetailsPage } from './pages/TicketDetailsPage';
export { useTicket, useTickets } from './api/queries';
export { StatusBadge } from './components/StatusBadge';
// Nie eksportujemy: TicketTable, TicketRow, ticketsApi, filtrów — to szczegóły modułu.
```

#T CODE_TSX Publiczne API funkcji tickets (TSX)
W TSX publiczne API eksportuje też typy (`export type`), które inne moduły mogą potrzebować — np. `Ticket` dla tablicy Kanban.
```
// features/tickets/index.ts
export { TicketsPage } from './pages/TicketsPage';
export { TicketDetailsPage } from './pages/TicketDetailsPage';
export { useTicket, useTickets } from './api/queries';
export { StatusBadge } from './components/StatusBadge';
export type { Ticket, TicketStatus, TicketPriority } from './model/types';
// Nie eksportujemy: TicketTable, TicketRow, ticketsApi, filtrów — to szczegóły modułu.
```

#T NOTE JSX ↔ TSX — typy jako kontrakt między modułami
W TSX publiczne API modułu to nie tylko funkcje i komponenty, ale też **typy**: `features/board` importuje `type Ticket` z `@/features/tickets`, więc zmiana kształtu ticketu od razu pokazuje wszystkie miejsca do poprawy w innych modułach. `export type` i `import type` są usuwane przy kompilacji, więc nie tworzą zależności w czasie działania (ani importów cyklicznych). W JSX kontrakt między modułami opisujesz komentarzem JSDoc (`/** @typedef {import('./model/types').Ticket} Ticket */`) albo w ogóle — i rozjazd wychodzi dopiero w działaniu.

#T CODE_JSX Aliasy importów w Vite (JSX)
Zamiast `../../../shared/ui/Button` piszesz `@/shared/ui/Button`. Alias ustawiasz w Vite; w projekcie JS dodatkowo w `jsconfig.json`, żeby edytor rozumiał ścieżki.
```
// vite.config.js
import react from '@vitejs/plugin-react';
import { fileURLToPath, URL } from 'node:url';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) },
  },
});

// jsconfig.json (dla edytora):
// { "compilerOptions": { "baseUrl": ".", "paths": { "@/*": ["src/*"] } } }
```

#T CODE_TSX Aliasy importów w Vite (TSX)
W projekcie TS alias musi być w dwóch miejscach: w `tsconfig` (dla kompilatora i edytora) i w Vite (dla bundlera) — albo używasz wtyczki `vite-tsconfig-paths`, która czyta ścieżki z `tsconfig`.
```
// vite.config.ts
import react from '@vitejs/plugin-react';
import { fileURLToPath, URL } from 'node:url';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) },
  },
});

// tsconfig.app.json:
// { "compilerOptions": { "baseUrl": ".", "paths": { "@/*": ["src/*"] } } }
```

#T CODE_PRACTICAL Granice modułów pilnowane przez ESLint
Zasady architektury bez automatu łamią się po tygodniu. Reguła `no-restricted-imports` zabrania importów z głębi innych funkcji i importów z `features` w `shared`. (Rozbudowane projekty używają wtyczek `eslint-plugin-boundaries` albo narzędzi typu `dependency-cruiser`.)
```
// eslint.config.js
export default [
  // … konfiguracja bazowa, react-hooks, typescript-eslint
  {
    files: ['src/**/*.{js,jsx,ts,tsx}'],
    rules: {
      'no-restricted-imports': ['error', {
        patterns: [
          {
            group: ['@/features/*/*'],
            message: 'Importuj z publicznego API funkcji: @/features/<nazwa>, nie z jej wnętrza.',
          },
        ],
      }],
    },
  },
  {
    files: ['src/shared/**/*'],
    rules: {
      'no-restricted-imports': ['error', {
        patterns: [{ group: ['@/features/*', '@/app/*'], message: 'shared nie może zależeć od features ani app.' }],
      }],
    },
  },
];
```

#T WHEN_TO_USE Ile struktury na jakim etapie
- **Do ~20 komponentów** — płaska struktura według typu (`components/`, `hooks/`) jest w porządku; nie projektuj na zapas.
- **Kilka obszarów biznesowych, kilka osób** — `features/` + `shared/` + `app/`, publiczne API funkcji, aliasy.
- **Duży zespół, wiele funkcji** — dodatkowo reguły granic w lintcie, właściciele katalogów (`CODEOWNERS`), czasem podział na pakiety w monorepo (pnpm workspaces, Turborepo).

Unikaj „plików-beczek” (`index.ts`) **wewnątrz** funkcji i w `shared/ui` re-eksportujących wszystko ze wszystkiego — utrudniają tree shaking, spowalniają narzędzia i sprzyjają importom cyklicznym. Jeden `index` na granicy funkcji wystarczy.

#T STEP_BY_STEP Budujemy razem: przeprowadzka DevDesk
1. Utwórz katalogi `app/`, `features/`, `shared/`; przenieś providery i router do `app/`.
2. Przenieś generyczne komponenty (`Button`, `Badge`, `Modal`, `Toast`) do `shared/ui/`, a formatowanie dat i walut do `shared/lib/`.
3. Dla ticketów utwórz `features/tickets/` z podkatalogami `pages`, `components`, `hooks`, `api`, `model`; przenieś pliki razem z testami.
4. Napisz `features/tickets/index.ts` i zamień importy w innych modułach na `@/features/tickets`.
5. Powtórz dla `board`, `auth`, `dashboard`.
6. Dodaj alias `@` w Vite i `tsconfig` / `jsconfig`; zamień ścieżki `../../..`.
7. Dodaj reguły `no-restricted-imports`; napraw zgłoszone importy (często ujawniają ukryte zależności).
8. Uruchom testy, `tsc --noEmit` i build — przeprowadzka nie może zmienić zachowania aplikacji.

#T PITFALL Import cykliczny przez publiczne API
Gdy `features/tickets` importuje coś z `@/features/board`, a `board` z `@/features/tickets`, powstaje cykl. Objawy bywają dziwne: `undefined is not a function` przy starcie, komponent „nie istnieje” tylko w buildzie, HMR przeładowuje całą stronę. Rozwiązania: przenieś wspólny kod do `shared/` (jeśli nie ma wiedzy domenowej) albo do trzeciego modułu, z którego korzystają oba; importuj tylko typy (`import type` nie tworzy cyklu w czasie działania); odwróć zależność — `board` dostaje ticket przez props albo kontekst zamiast importować hooki ticketów. Narzędzia `madge --circular src` albo reguła `import/no-cycle` znajdą cykle automatycznie.

#T SUMMARY Kryterium akceptacji i podsumowanie
Rosnący projekt porządkujesz według funkcji: `app/` (start, providery, router), `features/<nazwa>/` (wszystko, co dotyczy jednej funkcji, z testami obok kodu) i `shared/` (kod bez wiedzy domenowej). Zależności płyną w jedną stronę, każda funkcja ma jedno publiczne API, aliasy `@/` skracają importy, a reguły ESLint pilnują granic. W TSX typy eksportowane przez publiczne API są kontraktem między modułami, a `import type` nie tworzy zależności w czasie działania.

Kryterium akceptacji: żaden plik spoza funkcji nie importuje z jej wnętrza (lint przechodzi z regułami granic), `shared/` nie zależy od `features/`, w projekcie nie ma importów cyklicznych (`madge --circular` zwraca pustą listę), a testy, sprawdzanie typów i build przechodzą bez zmian w działaniu aplikacji.
