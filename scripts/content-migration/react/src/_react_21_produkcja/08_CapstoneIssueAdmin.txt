#T INTRO Projekt końcowy: Issue Admin
Rozgrzewka: W jakiej kolejności migrujesz projekt z JS do TS? Dlaczego `any` „zaraża” kod? Czym różni się `@ts-expect-error` od `@ts-ignore`?

To ostatni duży projekt kursu. Przez 21 rozdziałów budowałeś DevDesk krok po kroku, z gotowym planem na każdą lekcję. Teraz budujesz **od zera** nową aplikację — **Issue Admin**, panel administracyjny zgłoszeń dla zespołu wsparcia — i sam podejmujesz decyzje: struktura, biblioteki, sposób zarządzania stanem, strategia testów, wdrożenie. Brief opisuje, **co** ma działać, a nie **jak**. Oprócz kodu oddajesz krótkie uzasadnienia decyzji (rekordy decyzji architektonicznych). Wybierz jedną wersję: JSX albo TSX — po całym kursie wiesz, co zyskujesz i co płacisz w każdej z nich.

#T DEFINITION Brief projektu
Issue Admin to aplikacja dla zespołu wsparcia, z backendem Spring Boot (albo MSW, jeśli backend nie jest częścią Twojego zadania). Funkcje:
1. **Logowanie** — formularz, sesja (ciasteczko `HttpOnly` albo token — uzasadnij), wylogowanie, chronione trasy; role `AGENT` i `ADMIN` (admin widzi dodatkowo zarządzanie użytkownikami).
2. **Lista zgłoszeń** — tabela z kolumnami: ID, tytuł, status, priorytet, przypisany, data utworzenia; **sortowanie** po kolumnach, **filtry** (status, priorytet, przypisany, wyszukiwanie tekstowe), **paginacja serwerowa**; filtry, sortowanie i strona zapisane w **adresie URL**.
3. **Szczegóły zgłoszenia** pod `/issues/:id` — dane, historia zmian, komentarze (dodawanie z aktualizacją optymistyczną), zmiana statusu i przypisania; 404 dla nieistniejącego ID.
4. **Formularz w modalu** — tworzenie i edycja zgłoszenia, walidacja schematem (wspólnym z warstwą API), błędy z serwera przy polach, ostrzeżenie przy zamykaniu z niezapisanymi zmianami.
5. **Akcje zbiorcze** — zaznaczenie wielu zgłoszeń i zmiana statusu/przypisania naraz.
6. **Dashboard** — liczby kluczowe i jeden wykres (trend albo podział według priorytetu), ładowany leniwie.
7. **Zarządzanie użytkownikami** (tylko `ADMIN`) — lista i zmiana roli.

Wymagania jakościowe: dostępność (klawiatura, czytnik ekranu, audyt axe bez naruszeń), obsługa stanów ładowania, błędu i pustych wyników na każdym ekranie, granice błędów, testy, CI, wdrożenie z podglądem dla pull requestów, monitoring błędów.

#T STEP_BY_STEP Kamienie milowe
1. **Szkielet** (dzień 1): projekt Vite, struktura `app/ features/ shared/`, aliasy, ESLint z regułami granic, Prettier, CI z lintem, typami (TSX) i buildem, wdrożenie „pustej” aplikacji z podglądem PR.
2. **Dane i API**: model, schematy Zod, klient API, MSW z handlerami (także błędy i opóźnienia), TanStack Query.
3. **Logowanie i trasy**: React Router z layoutem, chronione trasy, role, strona 404, granice błędów tras.
4. **Lista zgłoszeń**: tabela, sortowanie, filtry i paginacja w URL, stany ładowania/błędu/pusto, testy komponentów z MSW.
5. **Szczegóły i komentarze**: `/issues/:id`, mutacje, aktualizacja optymistyczna, 404.
6. **Formularz w modalu**: tworzenie i edycja, walidacja, błędy serwera, ostrzeżenie o niezapisanych zmianach, zarządzanie fokusem.
7. **Akcje zbiorcze, dashboard, użytkownicy**.
8. **Jakość**: testy E2E najważniejszych ścieżek (Playwright), audyt axe, pomiar wydajności (Profiler, Lighthouse), monitoring (Sentry), dokumentacja komponentów (Storybook dla `shared/ui` — opcjonalnie).
9. **Oddanie**: README z instrukcją uruchomienia, rekordy decyzji, link do produkcji i do raportu z testów.

#T DEFINITION Kryteria akceptacji
**Funkcjonalne**
- Wszystkie siedem funkcji z briefu działa na wdrożonej wersji.
- Skopiowanie adresu listy z filtrami i otwarcie go w nowej karcie odtwarza ten sam widok.
- Odświeżenie dowolnej trasy działa; nieistniejące zgłoszenie pokazuje 404, a błąd serwera — ekran z ponowieniem.
- Agent nie widzi zarządzania użytkownikami ani w menu, ani pod bezpośrednim adresem (a backend i tak odrzuca żądanie).

**Jakościowe**
- Lint i (w TSX) `tsc --noEmit` przechodzą w CI; testy jednostkowe i komponentów pokrywają logikę filtrów, formularza i mutacji; co najmniej trzy scenariusze E2E (logowanie, filtrowanie i przejście do szczegółów, utworzenie zgłoszenia).
- Audyt axe bez naruszeń na wszystkich ekranach; cała aplikacja obsługiwalna klawiaturą; modal więzi fokus i zwraca go po zamknięciu.
- Lighthouse (wersja produkcyjna): wydajność i dostępność co najmniej 90.
- Błędy z produkcji trafiają do monitoringu z mapami źródeł.
- W repozytorium nie ma sekretów; konfiguracja przez zmienne środowiskowe ze schematem.

**Dokumentacja**
- README: uruchomienie lokalne, testy, zmienne środowiskowe (`.env.example`), wdrożenie.
- Co najmniej pięć rekordów decyzji (ADR): wybór JSX/TSX, zarządzanie stanem serwera i UI, uwierzytelnianie, struktura projektu, strategia testów.

#T CODE_BASIC Szablon rekordu decyzji (ADR)
Krótki dokument w repozytorium (`docs/adr/0003-stan-serwera.md`) — jedna decyzja, jej kontekst i konsekwencje. Pisany wtedy, gdy decyzję podejmujesz, a nie na końcu projektu.
```
# 0003. Stan serwera w TanStack Query, stan UI lokalnie i w URL

Data: 2026-11-02
Status: przyjęta

## Kontekst
Lista zgłoszeń, szczegóły i komentarze pochodzą z API i są zmieniane przez wielu agentów.
Potrzebujemy cache, odświeżania w tle, aktualizacji optymistycznych i obsługi błędów.
Filtry i paginacja muszą dać się udostępnić linkiem.

## Rozważane opcje
1. Redux Toolkit + RTK Query — jeden magazyn na wszystko.
2. TanStack Query dla danych z API + useState/useReducer + parametry URL dla stanu UI.
3. Ręczny fetch w useEffect + Context.

## Decyzja
Opcja 2. Stan serwera to cache, nie stan aplikacji — TanStack Query rozwiązuje cache,
unieważnianie i mutacje. Filtry/sortowanie/strona są w URL (useSearchParams), stan
pojedynczych widoków (otwarty modal, zaznaczenie) lokalnie.

## Konsekwencje
+ mniej kodu niż w opcji 1, brak globalnego magazynu dla danych z API
+ linki do widoków listy działają od razu
- dwa mechanizmy do nauczenia dla nowych osób (Query + URL)
- gdyby pojawił się złożony stan UI współdzielony przez wiele ekranów, rozważymy Zustand (nowy ADR)
```

#T CODE_JSX Szkielet tras aplikacji (JSX)
Punkt startowy dla struktury tras: layout z chronionym obszarem, leniwie ładowane ekrany, granice błędów tras i strona 404. Reszta — w Twoich rękach.
```
// app/router.jsx
import { lazy } from 'react';
import { createBrowserRouter, Navigate } from 'react-router';
import { AppLayout } from './AppLayout';
import { RequireAuth } from '@/features/auth';
import { RouteError } from './RouteError';
import { NotFoundPage } from './NotFoundPage';

const IssuesPage = lazy(() => import('@/features/issues/pages/IssuesPage'));
const IssueDetailsPage = lazy(() => import('@/features/issues/pages/IssueDetailsPage'));
const DashboardPage = lazy(() => import('@/features/dashboard/pages/DashboardPage'));
const UsersPage = lazy(() => import('@/features/users/pages/UsersPage'));
const LoginPage = lazy(() => import('@/features/auth/pages/LoginPage'));

export const router = createBrowserRouter([
  { path: '/login', element: <LoginPage /> },
  {
    element: <RequireAuth><AppLayout /></RequireAuth>,
    errorElement: <RouteError />,
    children: [
      { index: true, element: <Navigate to="/issues" replace /> },
      { path: 'issues', element: <IssuesPage /> },
      { path: 'issues/:issueId', element: <IssueDetailsPage />, errorElement: <RouteError /> },
      { path: 'dashboard', element: <DashboardPage /> },
      { path: 'admin/users', element: <RequireAuth role="ADMIN"><UsersPage /></RequireAuth> },
    ],
  },
  { path: '*', element: <NotFoundPage /> },
]);
```

```
// app/router.tsx
import { lazy } from 'react';
import { createBrowserRouter, Navigate, type RouteObject } from 'react-router';
import { AppLayout } from './AppLayout';
import { RequireAuth } from '@/features/auth';

const LoginPage = lazy(() => import('@/features/auth/pages/LoginPage'));

const routes: RouteObject[] = [
  { path: '/login', element: <LoginPage /> },
  {
    element: <RequireAuth><AppLayout /></RequireAuth>,
    errorElement: <RouteError />,
    children: [
      { index: true, element: <Navigate to="/issues" replace /> },
      { path: 'issues', element: <IssuesPage /> },
      { path: 'issues/:issueId', element: <IssueDetailsPage />, errorElement: <RouteError /> },
      { path: 'dashboard', element: <DashboardPage /> },
      { path: 'admin/users', element: <RequireAuth role="ADMIN"><UsersPage /></RequireAuth> },
    ],
  },
  { path: '*', element: <NotFoundPage /> },
];

export const router = createBrowserRouter(routes);
```

#T NOTE JSX ↔ TSX — decyzja na projekt końcowy
Wybór wersji to pierwszy ADR. Argumenty za TSX w tym projekcie: model danych z API (Zod/OpenAPI daje typy z jednego źródła), wiele formularzy i mutacji, role i unie statusów, refaktoryzacje w trakcie pracy. Argumenty za JSX: szybszy start, mniej konfiguracji, mniejszy próg dla osób bez znajomości TS — kosztem większej liczby testów i walidacji w działaniu. Niezależnie od wyboru: walidacja danych z API schematem jest obowiązkowa, bo typy nie sprawdzają danych w czasie działania.

#T NOTE Wskazówka — kolejność, która oszczędza czas
Zacznij od pionowego „przekroju” jednej funkcji przez wszystkie warstwy (lista zgłoszeń: MSW → API → Query → tabela → test → wdrożenie), zanim zaczniesz kolejne. Problemy z konfiguracją (aliasy, MSW w testach, zmienne środowiskowe w CI) wyjdą od razu, na jednej funkcji, a nie w ostatnim tygodniu przy dziesięciu. Testy pisz razem z funkcją, nie na końcu — wtedy wiesz, że każdy kamień milowy jest naprawdę skończony.

#T PITFALL Typowe błędy w projekcie końcowym
- Stan filtrów w `useState` zamiast w URL — działa, dopóki ktoś nie wyśle linku albo nie odświeży strony.
- Dane z API skopiowane do stanu lokalnego „żeby móc je edytować” — dwa źródła prawdy, rozjazd po odświeżeniu cache.
- Ochrona ról tylko w interfejsie — backend musi odrzucać żądania niezależnie od tego, co pokazuje frontend.
- Wszystkie ekrany w jednej paczce — dashboard z biblioteką wykresów spowalnia logowanie.
- Brak stanów pustych i błędów („a co, jeśli lista jest pusta?”) — najczęstsza uwaga przy przeglądzie.
- Testy E2E dodane na końcu i niestabilne — zespół przestaje ufać CI, gdy najbardziej go potrzebuje.
- ADR-y pisane po fakcie, które opisują kod zamiast decyzji i odrzuconych alternatyw.
