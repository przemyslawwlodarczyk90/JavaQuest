#T INTRO Rozgrzewka i problem: 200 plików .jsx i decyzja „przechodzimy na TypeScript”
Rozgrzewka: Czym różni się strategia `NetworkFirst` od `CacheFirst`? Dlaczego `sw.js` nie może być cache'owany? Jak zakolejkować zapis wykonany offline?

Problem: przez cały kurs pisałeś każdą lekcję w dwóch wersjach. W prawdziwym życiu zwykle dostajesz **jedną** — i często jest to istniejący projekt w JavaScripcie, który zespół postanowił przenieść na TypeScript. Przepisanie wszystkiego naraz to tygodnie zamrożenia funkcji i ogromny pull request, którego nikt nie przejrzy. W tej lekcji przeprowadzisz migrację **stopniowo**: TS i JS obok siebie, typy najpierw tam, gdzie dają najwięcej (modele danych, API, współdzielone komponenty), plik po pliku, z działającą aplikacją po każdym kroku. To też podsumowanie całego toru dwutorowego: zobaczysz, które różnice JSX ↔ TSX z kursu mają największe znaczenie w praktyce.

#T DEFINITION Migracja stopniowa: allowJs i checkJs
TypeScript potrafi pracować z mieszanym projektem:
- **`allowJs: true`** — pliki `.js`/`.jsx` są częścią projektu TS: można je importować z `.ts`/`.tsx` i odwrotnie. Typy z plików JS są wnioskowane (często jako `any`).
- **`checkJs: true`** — TS sprawdza także pliki JS (na podstawie wnioskowania i komentarzy JSDoc). Przydatne jako etap pośredni; pojedynczy plik wyłączasz komentarzem `// @ts-nocheck`, włączasz w pliku `// @ts-check`.
- **`strict`** — zestaw najważniejszych sprawdzeń (`strictNullChecks`, `noImplicitAny`…). W migracji często zaczyna się od `strict: false` i włącza flagi stopniowo, albo od razu `strict: true` tylko dla nowych plików `.ts` (osobny `tsconfig` lub narzędzia typu `typescript-strict-plugin`).

Vite obsługuje `.ts` i `.tsx` bez konfiguracji — zmiana rozszerzenia pliku nie wymaga zmian w budowaniu. Sprawdzanie typów robi `tsc --noEmit` (lokalnie i w CI, lekcja 05).

#T DEFINITION Kolejność migracji: od danych do widoków
Najwięcej korzyści przy najmniejszym wysiłku daje migracja **od dołu**:
1. **Modele danych** — typy `Ticket`, `User`, statusy jako unie (rozdział 01). Wszystko inne z nich korzysta.
2. **Warstwa API** — funkcje pobierające dane z typem wyniku, najlepiej z walidacją Zod (`z.infer` daje typ ze schematu) albo typami generowanymi z OpenAPI (rozdział 11).
3. **Czyste funkcje i hooki** — sortowanie, filtrowanie, reducery (unie akcji), własne hooki.
4. **Współdzielone komponenty** (`shared/ui`) — typy props, `ComponentProps<'button'>`.
5. **Funkcje i strony** — plik po pliku, zaczynając od najczęściej zmienianych.

Każdy krok to osobny, mały pull request, po którym aplikacja działa i testy przechodzą. Zasada zespołu: **nowe pliki tylko w TS**, a plik JS, który i tak zmieniasz w zadaniu, przy okazji migrujesz.

#T CODE_JSX Etap pośredni: JSDoc w pliku .jsx (JSX)
Zanim zmienisz rozszerzenie, możesz dodać typy w komentarzach JSDoc i włączyć `// @ts-check` — edytor i `tsc` sprawdzą plik JS. To przydatne dla plików, których nie możesz od razu przenieść (np. konfiguracje narzędzi), i jako pierwszy krok w dużych modułach.
```
// @ts-check
// TicketRow.jsx
import { StatusBadge } from './StatusBadge';

/** @typedef {import('../model/types').Ticket} Ticket */

/**
 * Wiersz tabeli ticketów.
 * @param {{ ticket: Ticket, selected: boolean, onSelect: (id: number) => void }} props
 */
export function TicketRow({ ticket, selected, onSelect }) {
  return (
    <tr className={selected ? 'row row--selected' : 'row'} onClick={() => onSelect(ticket.id)}>
      <td>{ticket.id}</td>
      <td>{ticket.title}</td>
      <td><StatusBadge status={ticket.status} /></td>
      <td>{ticket.assignee ?? '—'}</td>
    </tr>
  );
}
```

#T CODE_TSX Po migracji: ten sam plik jako .tsx (TSX)
Zmiana rozszerzenia, typ props zamiast JSDoc — i kompilator od razu znajduje miejsca, które wcześniej działały „przypadkiem” (np. `assignee` może być `null`).
```
// TicketRow.tsx
import type { Ticket } from '../model/types';
import { StatusBadge } from './StatusBadge';

type TicketRowProps = {
  ticket: Ticket;
  selected: boolean;
  onSelect: (id: number) => void;
};

/** Wiersz tabeli ticketów. */
export function TicketRow({ ticket, selected, onSelect }: TicketRowProps) {
  return (
    <tr className={selected ? 'row row--selected' : 'row'} onClick={() => onSelect(ticket.id)}>
      <td>{ticket.id}</td>
      <td>{ticket.title}</td>
      <td><StatusBadge status={ticket.status} /></td>
      <td>{ticket.assignee ?? '—'}</td>
    </tr>
  );
}
```

#T NOTE JSX ↔ TSX — co z kursu przydaje się najbardziej
Z wszystkich różnic, które widziałeś w kursie, w migracjach najwięcej dają:
- **unie literałów** zamiast dowolnych tekstów (`status`, `variant`, typy akcji reducera) — literówki stają się błędami,
- **`strictNullChecks`** — kompilator pokazuje każde miejsce, gdzie `null` z API (np. `assignee`) mógłby wysypać render,
- **typy danych z jednego źródła** — schemat Zod (`z.infer`) albo OpenAPI, zamiast ręcznego opisywania odpowiedzi,
- **typy props** współdzielonych komponentów — dokumentacja i podpowiedzi dla całego zespołu,
- **generyczne hooki i funkcje** (`useLocalStorage<T>`, `move<T>`) — jedna implementacja, poprawne typy w każdym użyciu.

Najmniej dają adnotacje rzeczy oczywistych (`const count: number = 0`) — inferencja robi to sama.

#T CODE_PRACTICAL Najczęstsze problemy po zmianie rozszerzenia
Typowe błędy, które pojawiają się zaraz po zmianie `.jsx` na `.tsx`, i ich poprawne rozwiązania (zamiast `any`):
```
// migrationFixes.tsx
import { useRef, useState, type ChangeEvent } from 'react';

type Ticket = { id: number; title: string };

export function MigrationFixes({ onSave }: { onSave: (title: string) => void }) {
  // 1. useState([]) daje never[] — podaj typ elementów
  const [tickets, setTickets] = useState<Ticket[]>([]);

  // 2. useState(null) daje null — podaj unię
  const [selectedId, setSelectedId] = useState<number | null>(null);

  // 3. useRef(null) do elementu — podaj typ elementu i sprawdzaj null
  const inputRef = useRef<HTMLInputElement>(null);

  // 4. parametr zdarzenia bez typu (implicit any) — typ zdarzenia Reacta
  function handleChange(e: ChangeEvent<HTMLInputElement>) {
    setSelectedId(Number(e.target.value) || null);
  }

  // 5. dane z JSON.parse / fetch — unknown + walidacja, nie rzutowanie na ślepo
  function load(raw: string) {
    const parsed: unknown = JSON.parse(raw);
    if (Array.isArray(parsed)) setTickets(parsed.filter((t): t is Ticket => typeof t?.id === 'number'));
  }

  // 6. obiekt-słownik indeksowany tekstem — Record zamiast {}
  const labels: Record<string, string> = { OPEN: 'Otwarte', CLOSED: 'Zamknięte' };

  return (
    <div>
      <input ref={inputRef} onChange={handleChange} aria-label="ID" />
      <button type="button" onClick={() => inputRef.current?.focus()}>Fokus</button>
      <button type="button" onClick={() => load('[]')}>Wczytaj</button>
      <button type="button" onClick={() => onSave(labels.OPEN)}>Zapisz</button>
      <p>{tickets.length} / {selectedId ?? '—'}</p>
    </div>
  );
}
```

#T USAGE Jak nie utknąć w połowie
- **Mierz postęp**: liczba plików `.js/.jsx` vs `.ts/.tsx` w `src/` (prosty skrypt w CI) i liczba `any` / `@ts-ignore` — oba wskaźniki mają tylko maleć.
- **Zakazy w lintcie**: `@typescript-eslint/no-explicit-any` jako ostrzeżenie (błąd w nowych plikach), `@typescript-eslint/ban-ts-comment` z wymaganym opisem przy `@ts-expect-error`.
- **`@ts-expect-error` zamiast `@ts-ignore`** — gdy błąd zniknie, kompilator przypomni, by usunąć komentarz.
- **Biblioteki bez typów**: najpierw sprawdź pakiet `@types/nazwa`; jeśli go nie ma — minimalna deklaracja `declare module 'nazwa'` w `types/vendor.d.ts`, rozbudowywana w miarę potrzeby.
- **Nie zmieniaj logiki przy migracji** — pull request „TS” ma tylko dodawać typy i poprawiać realne błędy, które wskazał kompilator; refaktoryzacja to osobny PR. Dzięki temu przegląd jest szybki, a regresje łatwe do namierzenia.

#T STEP_BY_STEP Budujemy razem: migracja wersji JSX DevDesk
1. Dodaj `typescript`, `@types/react`, `@types/react-dom` i `tsconfig.json` z `allowJs: true`, `strict: true`; dodaj krok `tsc --noEmit` do CI.
2. Przenieś `features/tickets/model/types` do `.ts` — statusy i priorytety jako unie.
3. Warstwę API przenieś na Zod: schemat odpowiedzi, `z.infer` jako typ, walidacja w kliencie.
4. Przenieś czyste funkcje (`sorting`, `board.moveTicket`) i reducery (unie akcji) — testy powinny przejść bez zmian.
5. Przenieś `shared/ui` (`Button`, `Badge`, `Modal`) z typami props i JSDoc.
6. Funkcje i strony: plik po pliku; przy każdym błędzie kompilatora zdecyduj — prawdziwy błąd (popraw), brakujący typ (dopisz), ograniczenie biblioteki (`@ts-expect-error` z opisem).
7. Dodaj w CI raport: liczba plików JS i liczba `any` — i ustal cel na koniec kwartału.
8. Gdy w `src/` nie zostanie żaden `.js`/`.jsx`, wyłącz `allowJs`.

#T PITFALL any jako „tymczasowe” rozwiązanie
Najłatwiejszy sposób, by migracja „się skończyła”, to `any` wszędzie, gdzie kompilator protestuje — i wtedy masz projekt w TypeScripcie bez korzyści z TypeScriptu, za to z fałszywym poczuciem bezpieczeństwa. `any` wyłącza sprawdzanie nie tylko w miejscu użycia, ale **zaraża** wszystko, co z niego korzysta (`const x = data.items` z `any` też jest `any`). Gdy typ jest naprawdę nieznany, użyj `unknown` i zawęź go (sprawdzeniem albo schematem). Druga pułapka: rzutowanie `as Ticket` na dane z sieci — kompilator uwierzy, a w działaniu dane mogą wyglądać inaczej. Rzutowanie jest obietnicą, a nie sprawdzeniem.

#T SUMMARY Kryterium akceptacji i podsumowanie
Projekt JS przenosisz na TypeScript stopniowo: `allowJs` pozwala mieszać pliki, `checkJs` i JSDoc to opcjonalny etap pośredni, a `strict` obowiązuje od początku dla nowych plików. Kolejność: modele danych, API (Zod lub OpenAPI), czyste funkcje i hooki, współdzielone komponenty, potem funkcje i strony — małymi pull requestami, bez zmian logiki. Postęp mierzysz liczbą plików JS i `any`, linter pilnuje nowych `any`, a `@ts-expect-error` z opisem zastępuje `@ts-ignore`. Cały tor dwutorowy kursu pokazał, gdzie TS daje najwięcej: unie literałów, `null` z API, typy danych z jednego źródła, typy props i generyki.

Kryterium akceptacji: wersja JSX DevDesk przechodzi na TSX w serii małych pull requestów, z działającą aplikacją po każdym; `tsc --noEmit` w CI jest zielone przy `strict: true`; w kodzie nie ma `@ts-ignore`, a każde `@ts-expect-error` ma opis; liczba `any` jest raportowana i maleje; na końcu `allowJs` jest wyłączone.
