#T INTRO Rozgrzewka i problem: wdrożenie na własnym serwerze
Rozgrzewka: Dlaczego `index.html` nie może być cache'owany? Co robi fallback SPA? Jak aplikacja przeżywa usunięcie starych plików `assets/` po wdrożeniu?

Problem: firma nie korzysta z platform typu Vercel — wszystko działa na własnych serwerach w kontenerach, obok backendu Spring Boot z rozdziału 11. Administrator prosi o obraz Dockera z frontendem, który da się uruchomić jednym poleceniem i skonfigurować zmiennymi środowiskowymi. Drugi zespół woli prostszy wariant: jeden plik JAR, w którym Spring Boot serwuje i API, i frontend. W tej lekcji przygotujesz oba: wieloetapowy obraz Dockera z Nginx (fallback SPA, cache, kompresja, proxy do API) oraz frontend wbudowany w aplikację Spring Boot.

#T DEFINITION Wieloetapowy obraz Dockera
Do zbudowania frontendu potrzebujesz Node i `node_modules` (setki MB), do serwowania — tylko statycznych plików i lekkiego serwera. **Budowanie wieloetapowe** (multi-stage) rozdziela te kroki w jednym `Dockerfile`:
1. **etap build** — obraz `node`, kopiowanie `package.json` i `package-lock.json`, `npm ci`, kopiowanie źródeł, `npm run build`,
2. **etap runtime** — obraz `nginx:alpine` (kilkadziesiąt MB), kopiowanie **tylko** `dist/` z poprzedniego etapu i konfiguracji Nginx.

Końcowy obraz nie zawiera Node, kodu źródłowego ani zależności deweloperskich. Kolejność kroków ma znaczenie dla cache warstw: `package*.json` i `npm ci` przed skopiowaniem kodu sprawiają, że zmiana w komponencie nie powoduje ponownej instalacji zależności.

#T CODE_BASIC Dockerfile frontendu
```
# Dockerfile
# --- etap 1: budowanie ---
FROM node:22-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
ARG VITE_APP_VERSION=dev
ENV VITE_APP_VERSION=$VITE_APP_VERSION
RUN npm run build

# --- etap 2: serwowanie ---
FROM nginx:1.27-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
# Szablon konfiguracji czasu działania (lekcja 02): config.json generowany ze zmiennych kontenera przy starcie
COPY docker/config.template.json /etc/nginx/templates/config.json.template
EXPOSE 80
HEALTHCHECK CMD wget -qO- http://localhost/healthz || exit 1

# .dockerignore (obok Dockerfile): node_modules, dist, .git, .env*.local, coverage
```

#T CODE_BASIC Konfiguracja Nginx dla SPA
```
# nginx.conf
server {
  listen 80;
  root /usr/share/nginx/html;
  index index.html;

  gzip on;
  gzip_types text/css application/javascript application/json image/svg+xml;
  gzip_min_length 1024;

  # Pliki z hashem w nazwie — cache na rok
  location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
    try_files $uri =404;
  }

  # API przekazywane do backendu Spring Boot (nazwa usługi z docker compose)
  location /api/ {
    proxy_pass http://backend:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }

  location = /healthz {
    access_log off;
    return 200 "ok";
  }

  # Fallback SPA: istniejący plik albo index.html — bez cache
  location / {
    add_header Cache-Control "no-cache";
    add_header X-Content-Type-Options "nosniff";
    add_header Referrer-Policy "strict-origin-when-cross-origin";
    try_files $uri $uri/ /index.html;
  }
}
```

#T DEFINITION Dlaczego proxy, a nie CORS
Gdy Nginx serwuje frontend i przekazuje `/api/` do backendu, przeglądarka widzi **jedno źródło** (ten sam schemat, host i port) — nie ma żądań cross-origin, więc nie trzeba konfigurować CORS, a ciasteczka sesji (`HttpOnly`, `SameSite=Lax`, rozdział 11) działają bez dodatkowych ustawień. To ten sam układ, który w trybie deweloperskim daje proxy Vite. Nagłówki `X-Forwarded-*` przekazują backendowi prawdziwy adres i protokół klienta — Spring Boot czyta je po ustawieniu `server.forward-headers-strategy=framework`.

#T CODE_JSX Odczyt konfiguracji czasu działania (JSX)
Nginx przy starcie kontenera zamienia `${API_URL}` w szablonie na wartość zmiennej (mechanizm `envsubst` w oficjalnym obrazie). Aplikacja pobiera `config.json` przed renderem — jeden obraz działa w każdym środowisku.
```
// main.jsx
import { createRoot } from 'react-dom/client';
import { App } from './app/App';
import { setRuntimeConfig } from './shared/config';

async function start() {
  const res = await fetch('/config.json', { cache: 'no-store' });
  const runtime = res.ok ? await res.json() : {};
  setRuntimeConfig(runtime); // walidacja schematem jak w lekcji 02

  createRoot(document.getElementById('root')).render(<App />);
}

start();

// docker/config.template.json:
// { "apiUrl": "${API_URL}", "sentryDsn": "${SENTRY_DSN}" }
```

#T CODE_TSX Odczyt konfiguracji czasu działania (TSX)
```
// main.tsx
import { createRoot } from 'react-dom/client';
import { App } from './app/App';
import { setRuntimeConfig } from './shared/config';

async function start(): Promise<void> {
  const res = await fetch('/config.json', { cache: 'no-store' });
  const runtime: unknown = res.ok ? await res.json() : {};
  setRuntimeConfig(runtime); // walidacja schematem jak w lekcji 02 — stąd unknown, a nie rzutowanie

  createRoot(document.getElementById('root')!).render(<App />);
}

void start();

// docker/config.template.json:
// { "apiUrl": "${API_URL}", "sentryDsn": "${SENTRY_DSN}" }
```

#T NOTE JSX ↔ TSX — dane z zewnątrz jako unknown
W TSX wynik `res.json()` przypisujesz do `unknown`, a nie rzutujesz na `RuntimeConfig` — plik generowany przez serwer może być pusty, nieaktualny albo mieć literówkę w nazwie zmiennej, i tylko walidacja schematem to wychwyci. `void start()` sygnalizuje linterowi (`no-floating-promises`), że świadomie nie czekasz na Promise. W JSX kod jest identyczny, ale nic nie zmusza do walidacji — tym bardziej trzymaj ją w `setRuntimeConfig`.

#T DEFINITION Wariant drugi: frontend wewnątrz aplikacji Spring Boot
Spring Boot serwuje automatycznie wszystko, co leży w `src/main/resources/static/` (w JAR: `classpath:/static/`). Jeśli skopiujesz tam zawartość `dist/`, jeden plik JAR zawiera API i frontend:
- **budowanie**: wtyczka Maven `frontend-maven-plugin` instaluje Node, uruchamia `npm ci` i `npm run build` w fazie `generate-resources`, a `maven-resources-plugin` kopiuje `dist/` do `target/classes/static/` — `mvn package` daje kompletny JAR,
- **fallback SPA**: Spring zwróci 404 dla `/tickets/42`, bo takiego pliku nie ma — potrzebny jest resolver, który dla nieistniejących ścieżek (poza `/api/`) zwraca `index.html`,
- **cache**: `spring.web.resources.cache.cachecontrol.max-age` dla zasobów oraz osobna obsługa `index.html` (bez cache).

Zalety: jedno wdrożenie, jedno źródło, zero CORS. Wady: każda zmiana frontendu wymaga zbudowania i wdrożenia backendu, a frontend nie może być serwowany z CDN niezależnie.

#T CODE_PRACTICAL Fallback SPA w Spring Boot
Resolver zasobów zwraca istniejący plik, a dla pozostałych ścieżek — `index.html`. Ścieżki `api/` są wyłączone, żeby brakujący endpoint dawał prawdziwe 404, a nie stronę aplikacji.
```
// SpaConfig.java (pakiet config; klasy z org.springframework.web.servlet.config.annotation, .resource, .core.io, .http)

@Configuration
public class SpaConfig implements WebMvcConfigurer {

    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        registry.addResourceHandler("/assets/**")
                .addResourceLocations("classpath:/static/assets/")
                .setCacheControl(CacheControl.maxAge(Duration.ofDays(365)).cachePublic().immutable());

        registry.addResourceHandler("/**")
                .addResourceLocations("classpath:/static/")
                .setCacheControl(CacheControl.noCache())
                .resourceChain(true)
                .addResolver(new PathResourceResolver() {
                    @Override
                    protected Resource getResource(String resourcePath, Resource location) throws IOException {
                        Resource requested = location.createRelative(resourcePath);
                        if (requested.exists() && requested.isReadable()) return requested;
                        if (resourcePath.startsWith("api/")) return null; // brakujący endpoint = prawdziwe 404
                        return new ClassPathResource("/static/index.html");
                    }
                });
    }
}
```

#T WHEN_TO_USE Który wariant wybrać
- **Platforma statyczna (Cloudflare, Vercel)** — najmniej pracy, CDN na całym świecie, podglądy dla pull requestów; frontend i backend wdrażane niezależnie (wymaga CORS albo proxy po stronie platformy).
- **Kontener Nginx** — własna infrastruktura (Kubernetes, serwery firmy), pełna kontrola nad nagłówkami i proxy, niezależne wdrażanie frontendu i backendu, jeden obraz dla wszystkich środowisk z konfiguracją czasu działania.
- **Frontend w JAR Spring Boot** — mały zespół, jedna aplikacja, proste wdrożenie jednego artefaktu; akceptujesz wspólny cykl wydań frontendu i backendu.

#T STEP_BY_STEP Budujemy razem: DevDesk w kontenerach
1. Dodaj `.dockerignore` i wieloetapowy `Dockerfile`; zbuduj obraz i sprawdź jego rozmiar (`docker images`) — powinien mieć kilkadziesiąt MB.
2. Dodaj `nginx.conf` z fallbackiem, cache, kompresją, `/healthz` i proxy `/api/`.
3. Uruchom `docker compose up` z frontendem, backendem Spring Boot i bazą; zaloguj się i sprawdź, że ciasteczko sesji działa bez CORS.
4. Odśwież `/tickets/42` i sprawdź nagłówki `assets/*` oraz `index.html` w DevTools.
5. Dodaj szablon `config.json` i odczyt w `main` — uruchom ten sam obraz z innym `API_URL` i sprawdź, że aplikacja go używa.
6. Wariant drugi: skonfiguruj `frontend-maven-plugin` w backendzie, dodaj `SpaConfig` i zbuduj jeden JAR (`mvn package`); uruchom `java -jar` i przetestuj odświeżanie tras i brakujący endpoint `/api/nie-ma`.

#T PITFALL try_files kierujące wszystko do index.html
Konfiguracja `location / { try_files $uri /index.html; }` **bez** osobnych bloków dla `/assets/` i `/api/` sprawia, że brakujący plik JS (np. po wdrożeniu) i nieistniejący endpoint API dostają w odpowiedzi `index.html` ze statusem 200. Objawy: „Unexpected token '<'” w konsoli, klient API próbuje parsować HTML jako JSON, monitoring nie widzi błędów 404. Pliki z `assets/` mają zwracać prawdziwe 404 (`try_files $uri =404`), a `/api/` ma trafiać do backendu. Druga pułapka: `add_header` w zagnieżdżonym bloku `location` w Nginx **zastępuje** nagłówki z bloku nadrzędnego — nagłówki bezpieczeństwa powtarzaj w każdym bloku albo dołączaj wspólnym plikiem (`include`).

#T SUMMARY Kryterium akceptacji i podsumowanie
Wieloetapowy `Dockerfile` buduje frontend w obrazie Node, a serwuje go z lekkiego obrazu Nginx zawierającego tylko `dist/`. Nginx obsługuje fallback SPA (`try_files … /index.html`), cache (`assets/` na rok, `index.html` bez cache), kompresję i proxy `/api/` do backendu — jedno źródło eliminuje CORS. Konfiguracja czasu działania (`config.json` z szablonu i zmiennych kontenera) pozwala używać jednego obrazu w wielu środowiskach. Alternatywnie frontend wbudowujesz w JAR Spring Boot (`static/`) z resolverem zwracającym `index.html` dla tras aplikacji.

Kryterium akceptacji: obraz frontendu ma kilkadziesiąt MB i nie zawiera kodu źródłowego; `docker compose up` uruchamia działający DevDesk z logowaniem; odświeżenie tras działa, a brakujący plik z `assets/` i nieistniejący endpoint API zwracają 404; ten sam obraz łączy się z różnymi API zależnie od zmiennej środowiskowej; wariant JAR serwuje aplikację i API z jednego procesu.
