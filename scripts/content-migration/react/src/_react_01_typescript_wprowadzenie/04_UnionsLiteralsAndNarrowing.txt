#T INTRO Unie: najczęściej używana „supermoc” TypeScriptu w React
Ticket ma jeden z trzech statusów. Odpowiedź z API to „ładowanie”, „sukces z danymi” albo „błąd z komunikatem”. Przycisk ma wariant „primary”, „secondary” albo „danger”. Wszystkie te sytuacje opisuje **unia** — typ „jedno z kilku”. W tej lekcji nauczysz się unie tworzyć i — co ważniejsze — bezpiecznie z nich korzystać.

#T DEFINITION Unia typów i unia literałów
Unia zapisywana pionową kreską oznacza „wartość jest jednym z tych typów”:
- `string | number` — tekst albo liczba,
- `string | null` — tekst albo brak,
- `'OPEN' | 'IN_PROGRESS' | 'CLOSED'` — **unia literałów**: dokładnie jedna z trzech wartości tekstowych.

Unie literałów zastępują w TS „magiczne stringi”. Edytor podpowiada dozwolone wartości, a literówka `'CLOESD'` jest błędem kompilacji.

#T CODE_JSX Wariant przycisku w JavaScripcie
Każdy tekst jest dozwolony. Literówka w wariancie da przycisk bez stylu.
```
// Button.jsx
export function Button({ variant, children }) {
  return <button className={`btn btn--${variant}`}>{children}</button>;
}

export const save = <Button variant="primay">Zapisz</Button>; // literówka, brak błędu
```

#T CODE_TSX Wariant przycisku z unią literałów
```
// Button.tsx
import type { ReactNode } from 'react';

type ButtonProps = {
  variant: 'primary' | 'secondary' | 'danger';
  children: ReactNode;
};

export function Button({ variant, children }: ButtonProps) {
  return <button className={`btn btn--${variant}`}>{children}</button>;
}

// @ts-expect-error — 'primay' nie należy do unii
export const save = <Button variant="primay">Zapisz</Button>;
```

#T NOTE JSX ↔ TSX — co zastępuje unię w JavaScripcie
W JSX możesz udokumentować dozwolone wartości komentarzem albo sprawdzać je w czasie działania (np. `if (!['primary','secondary','danger'].includes(variant)) console.warn(...)`), ewentualnie biblioteką PropTypes. Wszystko to działa dopiero po uruchomieniu. Unia w TSX daje dwie rzeczy jednocześnie: podpowiedzi w edytorze przy wpisywaniu `variant="` i błąd kompilacji przy literówce.

#T DEFINITION Zawężanie typów (narrowing)
Gdy zmienna ma typ unii, TypeScript pozwala użyć tylko tego, co jest wspólne dla wszystkich jej członów. Żeby użyć czegoś specyficznego, trzeba **zawęzić** typ — sprawdzić, który przypadek zachodzi. TypeScript rozumie zwykłe warunki JavaScriptu:
- `typeof x === 'string'`,
- `x === null`, `x !== undefined`, `if (x)`,
- `'pole' in obiekt`,
- porównanie pola-dyskryminatora: `state.status === 'error'`,
- `Array.isArray(x)`.

Wewnątrz gałęzi `if` typ jest zawężony, a po wczesnym `return` — zawężony w dalszej części funkcji.

#T CODE_BASIC Zawężanie null
```
import type { Ticket } from '../types';

export function assigneeLabel(ticket: Ticket): string {
  // ticket.assignee.toUpperCase() — błąd: assignee może być null
  if (ticket.assignee === null) {
    return 'Nieprzypisany';
  }
  return ticket.assignee.toUpperCase(); // tu assignee: string
}
```

#T DEFINITION Unia z dyskryminatorem
Najważniejszy wzorzec w całym kursie. Każdy wariant unii ma wspólne pole o stałej wartości (dyskryminator, zwykle `status` lub `type`), a pozostałe pola zależą od wariantu. Po sprawdzeniu dyskryminatora TypeScript wie, które pola są dostępne. Tak opiszemy stan ładowania danych z API (rozdział 10) i akcje reducera (rozdział 06).

#T CODE_JSX Stan ładowania w JavaScripcie
Nic nie chroni przed odczytem `data` w stanie błędu albo `error` w stanie sukcesu.
```
// TicketsStatus.jsx
export function TicketsStatus({ state }) {
  if (state.status === 'loading') return <p>Ładowanie…</p>;
  if (state.status === 'error') return <p>Błąd: {state.error}</p>;
  return <p>Pobrano {state.data.length} ticketów</p>;
}
```

#T CODE_TSX Stan ładowania jako unia z dyskryminatorem
W gałęzi `'error'` dostępne jest tylko `error`, w `'success'` — tylko `data`. Odczyt `state.data` w stanie błędu jest błędem kompilacji.
```
// TicketsStatus.tsx
import type { Ticket } from '../types';

export type TicketsState =
  | { status: 'loading' }
  | { status: 'error'; error: string }
  | { status: 'success'; data: Ticket[] };

export function TicketsStatus({ state }: { state: TicketsState }) {
  if (state.status === 'loading') return <p>Ładowanie…</p>;
  if (state.status === 'error') return <p>Błąd: {state.error}</p>;
  return <p>Pobrano {state.data.length} ticketów</p>;
}
```

#T DEFINITION Wyczerpujący switch i never
Gdy obsługujesz unię w `switch`, możesz poprosić TypeScript o sprawdzenie, czy obsłużyłeś wszystkie przypadki. W gałęzi `default` przypisujesz wartość do zmiennej typu `never` — jeśli jakiś przypadek pominąłeś, wartość nie jest `never` i pojawia się błąd. Po dodaniu nowego statusu kompilator wskaże każdy `switch`, który trzeba uzupełnić.

#T CODE_PRACTICAL Kolor priorytetu z kontrolą kompletności
```
import type { TicketPriority } from '../types';

export function priorityColor(p: TicketPriority): string {
  switch (p) {
    case 'LOW': return 'gray';
    case 'MEDIUM': return 'blue';
    case 'HIGH': return 'orange';
    case 'CRITICAL': return 'red';
    default: {
      const unreachable: never = p; // błąd, jeśli któryś priorytet pominięto
      return unreachable;
    }
  }
}
```

#T DEFINITION Optional chaining i ?? z typami
Znane z toru JavaScript `?.` i `??` współpracują z typami: `user?.name` ma typ `string | undefined`, a `user?.name ?? 'Gość'` — już `string`. TypeScript rozumie, że `??` usuwa `null` i `undefined` z typu.

#T STEP_BY_STEP Zaprojektuj typ wyniku zapisu formularza
1. W `types.ts` utwórz typ `SaveResult` jako unię z dyskryminatorem `status`.
2. Wariant `'idle'` — bez dodatkowych pól (nic jeszcze nie wysłano).
3. Wariant `'saving'` — bez dodatkowych pól.
4. Wariant `'saved'` — z polem `ticketId: number`.
5. Wariant `'failed'` — z polem `message: string`.
6. Napisz funkcję `saveMessage(r: SaveResult): string` z `switch` i kontrolą `never`.
7. Dodaj na próbę piąty wariant `'conflict'` i zobacz, że kompilator wskazuje `switch` do uzupełnienia.

#T PITFALL Unia „worek opcjonalnych pól”
Typ `{ loading: boolean; error?: string; data?: Ticket[] }` dopuszcza stany bez sensu: `loading: true` razem z `data` i `error` naraz. Każde użycie wymaga sprawdzania trzech pól. Unia z dyskryminatorem opisuje tylko stany, które naprawdę mogą wystąpić — „niemożliwe stany są niemożliwe do zapisania”.

#T CODE_WRONG Stan z opcjonalnymi polami
```
type State = { loading: boolean; error?: string; data?: string[] };
const s: State = { loading: true, error: 'Błąd', data: ['a'] }; // poprawne typowo, bez sensu logicznie
```

#T CODE_RIGHT Stan jako unia z dyskryminatorem
```
type State =
  | { status: 'loading' }
  | { status: 'error'; error: string }
  | { status: 'success'; data: string[] };

const s: State = { status: 'success', data: ['a'] };
```

#T SUMMARY Podsumowanie
Unia (`A | B`) to „jedno z kilku”, unia literałów (`'OPEN' | 'CLOSED'`) zastępuje magiczne stringi. Żeby użyć specyficznych właściwości, zawężasz typ zwykłymi warunkami (`typeof`, `=== null`, `in`, porównanie dyskryminatora). Unia z dyskryminatorem opisuje stany typu ładowanie/błąd/sukces bez niemożliwych kombinacji, a `never` w `default` pilnuje obsłużenia wszystkich przypadków. Kryterium akceptacji: masz typ `SaveResult` i funkcję `saveMessage`, a dodanie nowego wariantu powoduje błąd kompilacji w `switch`.
