#T INTRO TypeScript w sześciu lekcjach — tyle, ile potrzeba do Reacta
Ten rozdział nie jest pełnym kursem TypeScriptu. Jego cel jest konkretny: od rozdziału 02 każdy przykład dostajesz w wersji `.jsx` i `.tsx`, więc musisz rozumieć, co oznaczają dopisane w TSX fragmenty — `: string`, `type Props = {...}`, `'OPEN' | 'CLOSED'`, `<T>`, `?`. Po tych sześciu lekcjach przeczytasz każdy komponent TSX z kursu i będziesz wiedział, dlaczego typ jest zapisany tak, a nie inaczej.

#T DEFINITION Czym jest TypeScript
TypeScript (TS) to JavaScript z dodanymi typami. Każdy poprawny kod JavaScript jest poprawnym kodem TypeScript — TS niczego nie zabiera, tylko dodaje możliwość opisania, jakiego rodzaju wartości trzyma zmienna, przyjmuje funkcja i ma obiekt.

Kompilator TypeScript (`tsc`) robi dwie rzeczy:
1. **sprawdza typy** — zgłasza błąd, gdy np. przekazujesz liczbę tam, gdzie oczekiwany jest tekst,
2. **usuwa typy** — wynikiem jest zwykły JavaScript, który uruchamia przeglądarka.

Czym TS NIE jest: nie jest osobnym językiem uruchamianym w przeglądarce i nie sprawdza danych w czasie działania programu. Typy znikają po kompilacji.

#T ANALOGY Formularz z polami opisanymi i bez opisów
JavaScript to formularz z pustymi kratkami bez podpisów — możesz wpisać w kratkę „wiek” słowo „niebieski” i dowiesz się o problemie dopiero, gdy ktoś spróbuje policzyć średnią wieku.

TypeScript to formularz z podpisami i maskami pól: w kratkę „wiek” da się wpisać tylko liczbę, a pole „e-mail” jest obowiązkowe. Błąd widzisz w chwili wypełniania, a nie tydzień później.

#T CODE_JSX Błąd, który JavaScript pokaże dopiero w przeglądarce
Literówka w nazwie pola i zły typ argumentu. Kod uruchomi się bez błędu, ale wyświetli `undefined` i zwróci zły wynik.
```
// tickets.js
export function formatTicket(ticket) {
  return `#${ticket.id} ${ticket.titel}`; // literówka: titel zamiast title
}

export function daysOpen(createdAt) {
  const ms = Date.now() - new Date(createdAt).getTime();
  return Math.floor(ms / 86_400_000);
}

daysOpen(42); // przekazujemy ID zamiast daty — wynik jest bez sensu, ale bez błędu
```

#T CODE_TSX Ten sam kod w TypeScripcie
Oba błędy zostaną podkreślone w edytorze, zanim w ogóle uruchomisz aplikację.
```
// tickets.ts
type Ticket = { id: number; title: string; createdAt: string };

export function formatTicket(ticket: Ticket): string {
  return `#${ticket.id} ${ticket.title}`; // ticket.titel — błąd: brak takiej właściwości
}

export function daysOpen(createdAt: string): number {
  const ms = Date.now() - new Date(createdAt).getTime();
  return Math.floor(ms / 86_400_000);
}

// @ts-expect-error — liczba zamiast tekstu: TypeScript zgłasza błąd
daysOpen(42);
```

#T NOTE JSX ↔ TSX — co dopisaliśmy
- `type Ticket = {...}` — opis kształtu obiektu,
- `(ticket: Ticket)` i `(createdAt: string)` — typy parametrów,
- `: string` i `: number` po nawiasie — typ zwracanej wartości (opcjonalny, TS sam by go wywnioskował).

Logika funkcji jest identyczna. Typy to wyłącznie dodatkowy opis — po kompilacji plik `.ts` wygląda tak jak `.js`. Komentarz `@ts-expect-error` mówi kompilatorowi „w następnej linii spodziewam się błędu” — używamy go w kursie, żeby pokazać błąd bez psucia kompilacji przykładu.

#T VISUAL_EXAMPLE Kiedy wykrywasz błąd
JavaScript:   piszesz kod → zapisujesz → uruchamiasz → klikasz → widzisz „undefined” → szukasz przyczyny
TypeScript:   piszesz kod → edytor podkreśla błąd na czerwono → poprawiasz od razu

Im później wykryty błąd, tym droższy. Najdroższy jest ten zgłoszony przez użytkownika.

#T STEP_BY_STEP Wypróbuj TypeScript bez instalacji
1. Otwórz stronę typescriptlang.org/play (TS Playground).
2. Wklej wersję JavaScript funkcji `formatTicket` z literówką `titel`.
3. Dodaj nad nią `type Ticket = { id: number; title: string; createdAt: string };` i typ parametru `(ticket: Ticket)`.
4. Zobacz czerwone podkreślenie pod `titel` i najedź na nie myszą — przeczytaj komunikat.
5. W zakładce „.JS” po prawej zobacz wynik kompilacji: typy zniknęły.
6. Najedź myszą na zmienną bez typu, np. `const n = 5` — Playground pokaże, że TS wie, że to `number`.

#T USAGE Gdzie TypeScript daje najwięcej w React
- **Props komponentów** — edytor podpowiada, jakie props przyjmuje komponent, i zgłasza brakujące.
- **Zdarzenia** — wiesz, że `e.target.value` w polu tekstowym to `string`, a nie liczba.
- **Dane z API** — opisujesz kształt odpowiedzi raz i wszędzie masz podpowiedzi pól.
- **Refaktoryzacja** — zmieniasz nazwę pola `assignee` na `owner` i kompilator pokazuje wszystkie miejsca do poprawy.
- **Praca w zespole** — typy są dokumentacją, która nie może się zdezaktualizować, bo kompilator jej pilnuje.

#T PITFALL TypeScript nie sprawdza danych w czasie działania
Typ `Ticket` mówi kompilatorowi, czego się spodziewasz. Jeśli serwer zwróci `{ id: "42" }` (tekst zamiast liczby), TypeScript tego nie zauważy — typy już nie istnieją w przeglądarce. Dane z zewnątrz (API, localStorage, formularze) trzeba sprawdzać w czasie działania, np. biblioteką Zod (rozdział 05).

#T WHEN_TO_USE Kiedy TS pomaga, a kiedy przeszkadza
Pomaga: w projektach rozwijanych dłużej niż kilka dni, w zespołach, w kodzie z dużą liczbą obiektów danych i komponentów z wieloma props, przy integracji z API.

Przeszkadza: w szybkim prototypie na godzinę, przy nauce zupełnych podstaw (dlatego kurs opiera się na JavaScripcie, a TS idzie obok), gdy zespół zaczyna pisać skomplikowane typy „dla sportu” zamiast prostych opisów danych. Zasada: typy mają być proste i opisywać dane, a nie popisywać się możliwościami systemu typów.

#T SUMMARY Podsumowanie
TypeScript to JavaScript z typami. Kompilator sprawdza typy i usuwa je — w przeglądarce działa zwykły JavaScript. TS wyłapuje literówki w nazwach pól i złe argumenty już w edytorze, ale nie sprawdza danych z zewnątrz w czasie działania. Kryterium akceptacji: w TS Playground dodałeś typy do funkcji `formatTicket` i zobaczyłeś, jak edytor zgłasza literówkę oraz jak wygląda kod po kompilacji.
