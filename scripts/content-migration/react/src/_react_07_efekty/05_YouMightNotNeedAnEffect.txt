#T INTRO Rozgrzewka i problem: efekty, które nic nie synchronizują
Rozgrzewka: Kiedy React wywołuje funkcję sprzątającą? Dlaczego StrictMode montuje komponent dwa razy? Jak usunąć nasłuchiwanie zdarzenia, żeby naprawdę zostało usunięte?

Problem: przegląd kodu DevDesk pokazał dziewięć `useEffect`. Tylko trzy z nich rozmawiają z czymś poza Reactem. Pozostałe sześć kopiuje dane między stanami, reaguje na kliknięcia przez obserwowanie stanu albo resetuje formularze. Każdy z nich dodaje render, opóźnia aktualizację ekranu i jest potencjalnym źródłem błędu. Ta lekcja to praktyczny przegląd antywzorców ze strony dokumentacji „You Might Not Need an Effect” — i sposobów ich usunięcia.

#T DEFINITION Dwa pytania przed napisaniem efektu
1. **Czy synchronizuję się z systemem zewnętrznym?** (DOM poza Reactem, sieć, przeglądarka, biblioteka spoza Reacta). Jeśli nie — to nie jest zadanie dla efektu.
2. **Czy kod ma się wykonać, bo komponent został wyświetlony, czy dlatego, że użytkownik coś zrobił?** Jeśli dlatego, że użytkownik coś zrobił (kliknął, wysłał, wybrał) — kod należy do handlera tego zdarzenia.

#T API_REFERENCE Antywzorce i ich zamienniki
1. **Dane wyliczane w efekcie** (`useEffect(() => setFiltered(...), [items, query])`) → oblicz w renderze; kosztowne obliczenia → `useMemo` po pomiarze.
2. **Reset całego stanu przy zmianie props** (`useEffect(() => setComment(''), [ticketId])`) → `key={ticketId}` na komponencie.
3. **Dostosowanie części stanu przy zmianie props** → najlepiej przeprojektuj stan (przechowuj ID, licz resztę); ostatecznie aktualizacja w trakcie renderu z porównaniem poprzedniej wartości.
4. **Logika zdarzenia w efekcie** (efekt obserwujący `submitted === true`, by wysłać dane) → kod w handlerze `onSubmit`.
5. **Łańcuch efektów** (efekt A ustawia stan, który wyzwala efekt B, który ustawia stan…) → wylicz wszystko w jednym handlerze lub w renderze.
6. **Powiadamianie rodzica o zmianie stanu** (`useEffect(() => onChange(value), [value])`) → wywołaj `onChange` w tym samym handlerze, który zmienia stan — albo podnieś stan do rodzica.
7. **Przekazywanie danych w górę** (dziecko pobiera dane i efektem wysyła je rodzicowi) → niech rodzic pobierze dane i przekaże je w dół.
8. **Inicjalizacja aplikacji raz** (efekt w `App` z `[]`) → kod na poziomie modułu albo w `main.jsx` przed renderem, ewentualnie flaga modułowa.

#T CODE_WRONG Łańcuch efektów w formularzu edycji
Trzy efekty, trzy dodatkowe rendery, a zapis wykonuje się także wtedy, gdy `saved` zmieni się z innego powodu.
```
const [ticket, setTicket] = useState(initial);
const [isDirty, setIsDirty] = useState(false);
const [saved, setSaved] = useState(false);

useEffect(() => {
  setIsDirty(ticket.title !== initial.title);
}, [ticket, initial]);

useEffect(() => {
  if (saved) onSave(ticket);
}, [saved]);

useEffect(() => {
  if (saved) setSaved(false);
}, [saved]);
```

#T CODE_RIGHT Wartość wyliczana i logika w handlerze
```
const [ticket, setTicket] = useState(initial);
const isDirty = ticket.title !== initial.title; // wyliczane

function handleSave() {
  onSave(ticket); // skutek kliknięcia — w handlerze
}
```

#T CODE_JSX Powiadamianie rodzica: efekt kontra handler (JSX)
Wersja z efektem renderuje dziecko, potem efekt wywołuje rodzica, rodzic się renderuje — dwa przebiegi. Wersja z handlerem: React grupuje obie aktualizacje w jeden render.
```
// Toggle.jsx
import { useState } from 'react';

// ŹLE: onChange w efekcie
// useEffect(() => { onChange(on); }, [on, onChange]);

export function Toggle({ onChange }) {
  const [on, setOn] = useState(false);

  function handleClick() {
    const next = !on;
    setOn(next);
    onChange(next); // DOBRZE: w tym samym zdarzeniu
  }

  return <button type="button" aria-pressed={on} onClick={handleClick}>{on ? 'Wł.' : 'Wył.'}</button>;
}
```

#T CODE_TSX Powiadamianie rodzica: efekt kontra handler (TSX)
Jeszcze lepiej: jeśli rodzic i tak przechowuje wartość, komponent może być w pełni kontrolowany i w ogóle nie mieć stanu.
```
// Toggle.tsx
type ToggleProps = { value: boolean; onChange: (next: boolean) => void };

export function Toggle({ value, onChange }: ToggleProps) {
  return (
    <button type="button" aria-pressed={value} onClick={() => onChange(!value)}>
      {value ? 'Wł.' : 'Wył.'}
    </button>
  );
}
```

#T NOTE JSX ↔ TSX — kompilator nie odróżni dobrego efektu od złego
Wszystkie antywzorce z tej lekcji kompilują się w TSX bez ostrzeżeń — to problemy projektowe, nie typów. Pośrednio TypeScript pomaga jednak przy refaktoryzacji: gdy usuwasz stan `filteredTickets` i zastępujesz go wartością wyliczaną, kompilator wskaże wszystkie miejsca, które wywoływały `setFilteredTickets`. W JSX zostają one jako błędy „setFilteredTickets is not defined” w czasie działania. Wykrywaniu części antywzorców pomaga nowsza reguła ESLint `react-hooks/set-state-in-effect` (w konfiguracjach zgodnych z React Compiler) — ostrzega przed synchronicznym `setState` w efekcie.

#T CODE_BASIC Dostosowanie stanu przy zmianie props bez efektu
Rzadki przypadek, gdy reset przez `key` nie pasuje (chcesz zachować część stanu). React pozwala ustawić stan w trakcie renderu, jeśli warunek zapobiega pętli — przerwie bieżący render i powtórzy go z nowym stanem, zanim cokolwiek trafi na ekran.
```
import { useState } from 'react';
import type { Ticket } from '../types';

export function TicketList({ tickets }: { tickets: readonly Ticket[] }) {
  const [selectedId, setSelectedId] = useState<number | null>(null);
  const [prevTickets, setPrevTickets] = useState(tickets);

  if (tickets !== prevTickets) {
    setPrevTickets(tickets);
    if (selectedId !== null && !tickets.some((t) => t.id === selectedId)) setSelectedId(null);
  }

  return <ul>{tickets.map((t) => <li key={t.id} onClick={() => setSelectedId(t.id)}>{t.title}</li>)}</ul>;
}
```

#T CODE_PRACTICAL Jeszcze prościej: wylicz, zamiast dostosowywać
Ten sam efekt bez dodatkowego stanu: zaznaczenie, którego nie ma na liście, traktujesz jak brak zaznaczenia.
```
import { useState } from 'react';
import type { Ticket } from '../types';

export function TicketList({ tickets }: { tickets: readonly Ticket[] }) {
  const [selectedId, setSelectedId] = useState<number | null>(null);
  const selected = tickets.find((t) => t.id === selectedId) ?? null; // nieistniejące ID → null

  return (
    <>
      <ul>{tickets.map((t) => <li key={t.id} onClick={() => setSelectedId(t.id)}>{t.title}</li>)}</ul>
      <p>{selected ? `Wybrano #${selected.id}` : 'Nic nie wybrano'}</p>
    </>
  );
}
```

#T PITFALL „Efekt na wszelki wypadek”
Częsty odruch po naprawie błędu: „dodam efekt, który pilnuje, żeby X było zgodne z Y”. Taki efekt maskuje przyczynę (zduplikowany stan albo logikę w złym miejscu) i zostawia okno czasowe, w którym X i Y się różnią — użytkownik widzi przez chwilę błędne dane. Napraw przyczynę: jedno źródło prawdy i dane wyliczane.

#T SUMMARY Kryterium akceptacji i podsumowanie
Efekt jest potrzebny tylko do synchronizacji z systemem zewnętrznym. Dane wyliczane liczysz w renderze, stan resetujesz przez `key`, skutki działań użytkownika wykonujesz w handlerach, rodzica powiadamiasz w tym samym zdarzeniu (albo podnosisz stan), a łańcuchy efektów zastępujesz jednym handlerem. W rzadkich przypadkach stan można dostosować podczas renderu z warunkiem, ale zwykle lepiej go przeprojektować. TypeScript nie wykrywa tych problemów — pomaga przy refaktoryzacji.

Kryterium akceptacji: w DevDesk zostały wyłącznie efekty synchronizujące z systemem zewnętrznym (każdy z komentarzem), aplikacja działa jak przed audytem, a liczba renderów przy typowych akcjach spadła.
