#T INTRO Rozgrzewka i problem: kiedy właściwie „dzieje się” komponent?
Rozgrzewka: Czym różni się własny hook od zwykłej funkcji? Czy dwa komponenty wywołujące ten sam hook współdzielą stan? Dlaczego reducer nie może wywoływać `fetch`?

Problem: DevDesk musi wkrótce rozmawiać ze światem poza Reactem: zapisywać motyw w localStorage, zmieniać tytuł karty przeglądarki („(3) DevDesk” przy nowych ticketach), nasłuchiwać skrótów klawiszowych na całym oknie, pobierać dane z API. Żeby robić to poprawnie, musisz wiedzieć, w jakiej kolejności React wywołuje Twój kod. Ta lekcja buduje model mentalny, a kolejne — narzędzia.

#T DEFINITION Trzy momenty życia komponentu
1. **Montowanie (mount)** — komponent pojawia się na ekranie po raz pierwszy: React wywołuje funkcję komponentu, tworzy elementy DOM i wstawia je do strony.
2. **Aktualizacja (update)** — zmienia się stan komponentu, jego props albo kontekst: React wywołuje funkcję ponownie i nanosi różnice na DOM.
3. **Odmontowanie (unmount)** — komponent znika z drzewa (warunek stał się fałszywy, zmienił się `key`, rodzic zniknął): React usuwa jego DOM i stan.

Każda aktualizacja składa się z dwóch faz: **render** (wywołanie funkcji komponentu — obliczenie JSX, musi być czyste) i **commit** (naniesienie zmian na DOM). Efekty (`useEffect`) uruchamiają się **po** commicie, gdy ekran jest już zaktualizowany.

#T VISUAL_EXAMPLE Kolejność zdarzeń
montowanie:   render App → render TicketList → commit (DOM gotowy) → efekty TicketList → efekty App
aktualizacja: setState → render komponentu → commit → sprzątanie poprzednich efektów (jeśli zależności się zmieniły) → nowe efekty
odmontowanie: commit (DOM usunięty) → sprzątanie efektów komponentu

Efekty dzieci uruchamiają się przed efektami rodziców (od dołu drzewa w górę).

#T CODE_JSX Obserwacja kolejności (JSX)
Wklej, otwórz konsolę i przełączaj panel. W trybie deweloperskim ze StrictMode zobaczysz dodatkowe wywołania — to zamierzone (lekcja 4).
```
// LifecycleDemo.jsx
import { useEffect, useState } from 'react';

function Panel({ title }) {
  console.log('render Panel', title);

  useEffect(() => {
    console.log('efekt Panel: zamontowany lub zmieniony tytuł', title);
    return () => console.log('sprzątanie Panel', title);
  }, [title]);

  return <h3>{title}</h3>;
}

export function LifecycleDemo() {
  const [visible, setVisible] = useState(true);
  const [title, setTitle] = useState('Szczegóły');

  return (
    <div>
      <button onClick={() => setVisible((v) => !v)}>{visible ? 'Ukryj' : 'Pokaż'} panel</button>
      <button onClick={() => setTitle((t) => (t === 'Szczegóły' ? 'Historia' : 'Szczegóły'))}>Zmień tytuł</button>
      {visible && <Panel title={title} />}
    </div>
  );
}
```

#T CODE_TSX Obserwacja kolejności (TSX)
Kod identyczny poza typem props. Funkcja zwracana z efektu (sprzątanie) ma typ `() => void` — TypeScript pilnuje, żeby efekt zwracał funkcję albo nic.
```
// LifecycleDemo.tsx
import { useEffect, useState } from 'react';

function Panel({ title }: { title: string }) {
  console.log('render Panel', title);

  useEffect(() => {
    console.log('efekt Panel: zamontowany lub zmieniony tytuł', title);
    return () => console.log('sprzątanie Panel', title);
  }, [title]);

  return <h3>{title}</h3>;
}

export function LifecycleDemo() {
  const [visible, setVisible] = useState(true);
  const [title, setTitle] = useState('Szczegóły');

  return (
    <div>
      <button onClick={() => setVisible((v) => !v)}>{visible ? 'Ukryj' : 'Pokaż'} panel</button>
      <button onClick={() => setTitle((t) => (t === 'Szczegóły' ? 'Historia' : 'Szczegóły'))}>Zmień tytuł</button>
      {visible && <Panel title={title} />}
    </div>
  );
}
```

#T NOTE JSX ↔ TSX — co zwraca efekt
W TSX typ `useEffect` dopuszcza tylko dwie wartości zwracane: nic (`undefined`) albo funkcję sprzątającą. Najczęstszy błąd, który to wyłapuje: `useEffect(async () => {...})` — funkcja `async` zwraca `Promise`, a nie funkcję sprzątającą, więc TypeScript zgłosi błąd typu. W JSX ten sam kod się wykona, React wypisze ostrzeżenie w konsoli, a sprzątanie nie zadziała. Poprawny zapis asynchronicznego efektu poznasz w rozdziale o API.

#T DEFINITION Zmiana myślenia: synchronizacja zamiast cyklu życia
W komponentach klasowych myślało się „przy montowaniu zrób X, przy aktualizacji Y, przy odmontowaniu Z”. W komponentach funkcyjnych lepszy model to **synchronizacja**: efekt opisuje, jak utrzymać zgodność systemu zewnętrznego z aktualnymi props i stanem — „tytuł karty przeglądarki ma odpowiadać liczbie nowych ticketów”. React sam uruchomi synchronizację, gdy dane się zmienią, i posprząta po starej wersji. Nie musisz myśleć, czy to montowanie, czy aktualizacja.

#T CODE_BASIC Synchronizacja tytułu karty
Efekt mówi: „`document.title` ma odpowiadać `newCount`”. Uruchamia się po montowaniu i po każdej zmianie `newCount`.
```
import { useEffect } from 'react';

export function useDocumentTitle(newCount: number) {
  useEffect(() => {
    document.title = newCount > 0 ? `(${newCount}) DevDesk` : 'DevDesk';
  }, [newCount]);
}
```

#T CODE_PRACTICAL Co należy do renderu, a co do efektu
```
import { useEffect, useState } from 'react';
import type { Ticket } from '../types';

export function TicketCounter({ tickets }: { tickets: readonly Ticket[] }) {
  // RENDER: obliczenia z props i stanu — czyste
  const openCount = tickets.filter((t) => t.status === 'OPEN').length;
  const [highlight, setHighlight] = useState(false);

  // EFEKT: synchronizacja z czymś poza Reactem (tytuł karty przeglądarki)
  useEffect(() => {
    document.title = `DevDesk — ${openCount} otwartych`;
  }, [openCount]);

  // HANDLER: reakcja na konkretne działanie użytkownika
  function handleClick() {
    setHighlight((h) => !h);
  }

  return <button type="button" onClick={handleClick} className={highlight ? 'hl' : ''}>Otwarte: {openCount}</button>;
}
```

#T API_REFERENCE Gdzie umieścić kod — ściąga
- **Obliczenie z props/stanu** (filtrowanie, liczniki, formatowanie) → ciało komponentu, podczas renderu.
- **Reakcja na działanie użytkownika** (kliknięcie, wysłanie formularza) → handler zdarzenia.
- **Synchronizacja z systemem zewnętrznym** (DOM poza Reactem, localStorage, tytuł strony, subskrypcja, timer, połączenie sieciowe, biblioteka spoza Reacta) → `useEffect`.
- **Odczyt danych z serwera** → efekt lub (lepiej) biblioteka danych (rozdział 10) albo framework.
- **Pomiar DOM przed malowaniem** → `useLayoutEffect` (lekcja 6).

#T PITFALL Efekt jako „po renderze zrób coś z danymi”
Najczęstszy błąd: traktowanie efektu jak miejsca na dowolny kod „po renderze” — przeliczanie danych, kopiowanie props do stanu, reagowanie na kliknięcie przez obserwowanie zmiany stanu. Każdy taki efekt dodaje dodatkowy render i ryzyko rozjazdu danych. Efekt jest **furtką ewakuacyjną** z Reacta — do synchronizacji z czymś, czym React nie zarządza.

#T SUMMARY Kryterium akceptacji i podsumowanie
Komponent jest montowany, aktualizowany i odmontowywany; każda aktualizacja to faza render (czyste obliczenie) i commit (zmiany w DOM). Efekty uruchamiają się po commicie, od dzieci do rodziców, a przed ponownym uruchomieniem React sprząta poprzednią wersję. Myśl o efektach jako o synchronizacji z systemem zewnętrznym, nie o „cyklu życia”. W TSX efekt może zwrócić tylko funkcję sprzątającą albo nic.

Kryterium akceptacji: potrafisz przewidzieć kolejność logów z `LifecycleDemo` dla trzech scenariuszy, a tytuł karty przeglądarki w DevDesk pokazuje aktualną liczbę otwartych ticketów.
