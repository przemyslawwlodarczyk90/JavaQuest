#T INTRO Rozgrzewka i problem: filtrowanie, które się rozjeżdża
Rozgrzewka: Co sprawia, że input jest kontrolowany? Dlaczego `value={ticket?.title}` może wywołać ostrzeżenie? Gdzie powinien żyć stan `query`?

Problem: wyszukiwarka ma filtrować tabelę, a obok pojawia się filtr statusu. Pierwszy odruch: dodać stan `filteredTickets` i aktualizować go przy każdej zmianie `query`, `status` i `tickets`. Po tygodniu ktoś zamyka ticket, a przefiltrowana lista pokazuje go nadal jako otwarty — bo zapomniano zaktualizować `filteredTickets` w `closeTicket`. Ta lekcja uczy najważniejszej zasady projektowania stanu: **dane, które da się wyliczyć, nie są stanem**.

#T DEFINITION Minimalny stan i dane wyliczane
Stan to minimalny zestaw danych, z którego da się odtworzyć cały interfejs. Wszystko, co można policzyć z istniejącego stanu i props, liczysz **podczas renderowania** — zwykłym kodem w ciele komponentu.

W DevDesk:
- stan: `tickets`, `query`, `statusFilter`, `selectedId`,
- wyliczane: `filteredTickets`, `openCount`, `selectedTicket`, „Znaleziono N wyników”.

Test na stan (z „Thinking in React”): Czy wartość zmienia się w czasie? Czy przychodzi z props? Czy da się ją wyliczyć z innego stanu lub props? Jeśli da się wyliczyć — to nie jest stan.

#T ANALOGY Arkusz kalkulacyjny
W arkuszu wpisujesz tylko dane źródłowe (ceny, ilości), a kolumna „Razem” to formuła. Nie przepisujesz ręcznie sumy po każdej zmianie ceny — formuła liczy się sama. Dane wyliczane w React to formuły: zmienisz stan, a wynik przelicza się przy renderze.

#T CODE_JSX Filtrowanie po tekście i statusie (JSX)
```
// Main.jsx
import { useState } from 'react';
import { tickets as initialTickets } from '../data/tickets';
import { SearchInput } from './SearchInput';
import { TicketTable } from './TicketTable';

function matchesQuery(ticket, query) {
  const q = query.trim().toLowerCase();
  if (!q) return true;
  return (
    ticket.title.toLowerCase().includes(q) ||
    ticket.tags.some((tag) => tag.includes(q)) ||
    (ticket.assignee ?? '').includes(q)
  );
}

export function Main() {
  const [tickets, setTickets] = useState(initialTickets);
  const [query, setQuery] = useState('');
  const [statusFilter, setStatusFilter] = useState('ALL');

  // dane wyliczane — liczone przy każdym renderze, zawsze aktualne
  const filteredTickets = tickets.filter(
    (t) => (statusFilter === 'ALL' || t.status === statusFilter) && matchesQuery(t, query),
  );

  return (
    <main className="app-main">
      <SearchInput value={query} onChange={setQuery} />
      <select aria-label="Status" value={statusFilter} onChange={(e) => setStatusFilter(e.target.value)}>
        <option value="ALL">Wszystkie</option>
        <option value="OPEN">Otwarte</option>
        <option value="IN_PROGRESS">W toku</option>
        <option value="CLOSED">Zamknięte</option>
      </select>
      <p>Znaleziono: {filteredTickets.length} z {tickets.length}</p>
      <TicketTable tickets={filteredTickets} />
    </main>
  );
}
```

#T CODE_TSX Filtrowanie po tekście i statusie (TSX)
Filtr statusu to unia `TicketStatus | 'ALL'`. Wartość z `<select>` jest tekstem, więc przy zapisie trzeba ją rzutować na typ filtra — bezpieczne, bo opcje są pod kontrolą komponentu.
```
// Main.tsx
import { useState } from 'react';
import { tickets as initialTickets } from '../data/tickets';
import type { Ticket, TicketStatus } from '../types';
import { SearchInput } from './SearchInput';
import { TicketTable } from './TicketTable';

type StatusFilter = TicketStatus | 'ALL';

function matchesQuery(ticket: Ticket, query: string): boolean {
  const q = query.trim().toLowerCase();
  if (!q) return true;
  return (
    ticket.title.toLowerCase().includes(q) ||
    ticket.tags.some((tag) => tag.includes(q)) ||
    (ticket.assignee ?? '').includes(q)
  );
}

export function Main() {
  const [tickets, setTickets] = useState(initialTickets);
  const [query, setQuery] = useState('');
  const [statusFilter, setStatusFilter] = useState<StatusFilter>('ALL');

  const filteredTickets = tickets.filter(
    (t) => (statusFilter === 'ALL' || t.status === statusFilter) && matchesQuery(t, query),
  );

  return (
    <main className="app-main">
      <SearchInput value={query} onChange={setQuery} />
      <select
        aria-label="Status"
        value={statusFilter}
        onChange={(e) => setStatusFilter(e.target.value as StatusFilter)}
      >
        <option value="ALL">Wszystkie</option>
        <option value="OPEN">Otwarte</option>
        <option value="IN_PROGRESS">W toku</option>
        <option value="CLOSED">Zamknięte</option>
      </select>
      <p>Znaleziono: {filteredTickets.length} z {tickets.length}</p>
      <TicketTable tickets={filteredTickets} />
    </main>
  );
}
```

#T NOTE JSX ↔ TSX — wartość z select
`e.target.value` z `<select>` ma w TSX typ `string`, a stan ma typ `StatusFilter`. Rzutowanie `as StatusFilter` mówi kompilatorowi „ufam, że to jedna z wartości” — jest akceptowalne, bo opcje generujesz sam. Lepiej jeszcze generować opcje z tablicy `as const` (typ i lista z jednego źródła), wtedy nie da się dodać opcji spoza typu. Warto też zauważyć, że `matchesQuery` ma w TSX typ wyniku `boolean` i typ `ticket`, a w JSX literówka `ticket.titel` dałaby wyjątek przy pierwszym wpisanym znaku.

#T CODE_WRONG Wyliczalne dane jako osobny stan
Trzeba pamiętać o aktualizacji `filteredTickets` w każdym miejscu, które zmienia `tickets`, `query` lub `status`. Do tego pierwszy render pokazuje listę sprzed filtrowania.
```
const [tickets, setTickets] = useState(initialTickets);
const [query, setQuery] = useState('');
const [filteredTickets, setFilteredTickets] = useState(initialTickets);

useEffect(() => {
  setFilteredTickets(tickets.filter((t) => t.title.includes(query)));
}, [tickets, query]);
```

#T CODE_RIGHT Wyliczenie podczas renderu
Jedna linia, zawsze aktualna, bez dodatkowego renderu.
```
const [tickets, setTickets] = useState(initialTickets);
const [query, setQuery] = useState('');

const filteredTickets = tickets.filter((t) => t.title.includes(query));
```

#T DEFINITION A co z wydajnością?
Filtrowanie kilkuset czy kilku tysięcy elementów przy każdym renderze trwa ułamki milisekundy — to nie jest problem. Jeśli pomiar (rozdział 16) pokaże, że obliczenie jest naprawdę kosztowne, owijasz je w `useMemo`, które zapamiętuje wynik do zmiany zależności. Nigdy nie zaczynasz od `useEffect` + drugi stan: to i tak liczy wszystko, a do tego dodaje render i ryzyko rozjazdu.

#T CODE_PRACTICAL Opcje filtra z jednego źródła
```
import type { TicketStatus } from '../types';

export const STATUS_OPTIONS = [
  { value: 'ALL', label: 'Wszystkie' },
  { value: 'OPEN', label: 'Otwarte' },
  { value: 'IN_PROGRESS', label: 'W toku' },
  { value: 'CLOSED', label: 'Zamknięte' },
] as const satisfies readonly { value: TicketStatus | 'ALL'; label: string }[];

export type StatusFilter = (typeof STATUS_OPTIONS)[number]['value'];

export function StatusSelect({ value, onChange }: { value: StatusFilter; onChange: (v: StatusFilter) => void }) {
  return (
    <select aria-label="Status" value={value} onChange={(e) => onChange(e.target.value as StatusFilter)}>
      {STATUS_OPTIONS.map((o) => <option key={o.value} value={o.value}>{o.label}</option>)}
    </select>
  );
}
```

#T STEP_BY_STEP Budujemy razem: działające filtry DevDesk
1. W `Main` dodaj stan `statusFilter` (start `'ALL'`) i komponent `StatusSelect` w pasku narzędzi.
2. Napisz `matchesQuery` poza komponentem (nie zależy od stanu, tylko od argumentów).
3. Wylicz `filteredTickets` w ciele komponentu i przekaż do tabeli.
4. Dodaj tekst „Znaleziono: N z M” oraz pusty stan tabeli „Brak ticketów pasujących do filtrów” z przyciskiem „Wyczyść filtry” (ustawia `query` na `''` i status na `'ALL'`).
5. Zamknij ticket przy aktywnym filtrze „Otwarte” — powinien zniknąć z listy natychmiast, bez dodatkowego kodu.
6. Policz liczniki statystyk (`openCount`, `urgentCount`) z `tickets` w stanie — zamknięcie ticketu zmniejsza licznik „Otwarte”.
7. Sprawdź w kodzie, że nigdzie nie ma `useEffect` liczącego dane.

#T WHEN_TO_USE Stan czy wartość wyliczana — ściąga
- Wpisywany tekst, wybrany filtr, numer strony, zaznaczony wiersz → **stan** (zmieniają się przez działania użytkownika).
- Lista po filtrze, liczniki, sumy, wybrany obiekt z listy po ID, „czy formularz jest poprawny” → **wyliczane**.
- Dane, które przyszły z props → **ani jedno, ani drugie** — używasz ich bezpośrednio, nie kopiujesz do stanu.

#T SUMMARY Kryterium akceptacji i podsumowanie
Stan to minimum danych potrzebnych do odtworzenia UI; wszystko, co da się policzyć ze stanu i props, liczysz podczas renderowania. Dane wyliczane są zawsze aktualne i nie wymagają synchronizacji. `useEffect` + drugi stan do obliczeń to antywzorzec. W TSX filtr statusu jako unia `TicketStatus | 'ALL'`, a opcje najlepiej generować z tablicy `as const`.

Kryterium akceptacji: wyszukiwarka i filtr statusu działają razem, licznik „Znaleziono N z M” jest zawsze poprawny, zamknięcie ticketu przy filtrze „Otwarte” natychmiast usuwa go z listy, a w kodzie nie ma stanu `filteredTickets` ani efektu liczącego dane.
