#T INTRO Rozgrzewka i problem: zamknięcie ticketu nie odświeża tabeli
Rozgrzewka: Dlaczego trzy razy `setCount(count + 1)` dodaje tylko 1? Czym jest batching? Kiedy użyć formy funkcyjnej settera?

Problem: lista ticketów trafia do stanu, a przycisk „Zamknij” robi `ticket.status = 'CLOSED'; setTickets(tickets);`. Status w danych się zmienia, ale tabela na ekranie — nie. React porównuje stan **referencją**: dostał tę samą tablicę, więc uznał, że nic się nie zmieniło. W tej lekcji nauczysz się aktualizować obiekty i tablice niemutowalnie.

#T DEFINITION Niemutowalne aktualizacje
Obiektów i tablic w stanie nie zmieniasz w miejscu. Zawsze tworzysz **nową** kopię z naniesioną zmianą i przekazujesz ją do settera. React porównuje starą i nową wartość przez `Object.is` — nowa referencja oznacza zmianę i render. Dodatkowa korzyść: stara wersja pozostaje nienaruszona, co ułatwia cofanie zmian, porównywanie i debugowanie.

#T API_REFERENCE Ściąga operacji niemutowalnych
Obiekty:
- zmiana pola: `{ ...ticket, status: 'CLOSED' }`,
- usunięcie pola: `const { assignee, ...rest } = ticket;`,
- zagnieżdżony obiekt: `{ ...user, address: { ...user.address, city: 'Gdańsk' } }`.

Tablice:
- dodanie na końcu: `[...tickets, newTicket]`; na początku: `[newTicket, ...tickets]`,
- usunięcie: `tickets.filter((t) => t.id !== id)`,
- zmiana elementu: `tickets.map((t) => (t.id === id ? { ...t, status: 'CLOSED' } : t))`,
- wstawienie w środek: `tickets.toSpliced(index, 0, newTicket)`,
- zamiana elementu pod indeksem: `tickets.with(index, updated)`,
- sortowanie: `tickets.toSorted(compare)`; odwrócenie: `tickets.toReversed()`.

Mutujące metody, których NIE używasz na stanie: `push`, `pop`, `shift`, `unshift`, `splice`, `sort`, `reverse`, przypisanie `arr[i] = x`, `obj.pole = x`.

#T CODE_JSX Tickety w stanie z zamykaniem i usuwaniem (JSX)
```
// Main.jsx
import { useState } from 'react';
import { tickets as initialTickets } from '../data/tickets';
import { TicketTable } from './TicketTable';

export function Main() {
  const [tickets, setTickets] = useState(initialTickets);

  function closeTicket(id) {
    setTickets((prev) => prev.map((t) => (t.id === id ? { ...t, status: 'CLOSED' } : t)));
  }

  function deleteTicket(id) {
    setTickets((prev) => prev.filter((t) => t.id !== id));
  }

  return <TicketTable tickets={tickets} onClose={closeTicket} onDelete={deleteTicket} />;
}
```

#T CODE_TSX Tickety w stanie z zamykaniem i usuwaniem (TSX)
Stan wnioskuje typ `Ticket[]` z wartości startowej. W `map` TypeScript sprawdza, że `{ ...t, status: 'CLOSED' }` jest poprawnym `Ticket` — `status: 'DONE'` byłoby błędem.
```
// Main.tsx
import { useState } from 'react';
import { tickets as initialTickets } from '../data/tickets';
import { TicketTable } from './TicketTable';

export function Main() {
  const [tickets, setTickets] = useState(initialTickets);

  function closeTicket(id: number) {
    setTickets((prev) => prev.map((t) => (t.id === id ? { ...t, status: 'CLOSED' } : t)));
  }

  function deleteTicket(id: number) {
    setTickets((prev) => prev.filter((t) => t.id !== id));
  }

  return <TicketTable tickets={tickets} onClose={closeTicket} onDelete={deleteTicket} />;
}
```

#T NOTE JSX ↔ TSX — kontrola kształtu przy spread
Spread nie zabezpiecza przed literówkami w JS: `{ ...t, stauts: 'CLOSED' }` doda nowe pole `stauts` i nic nie zmieni. W TSX zwracana z `map` wartość musi pasować do `Ticket`, więc literówka w nazwie pola albo zła wartość statusu są błędami kompilacji. TypeScript pomaga też w odwrotnym kierunku: z typem `readonly Ticket[]` w props dziecko nie może wywołać mutującego `push` ani `sort` na otrzymanej tablicy.

#T CODE_WRONG Mutacja stanu
React dostaje tę samą referencję i pomija render. Do tego zmieniłeś obiekt, który mogą widzieć inne komponenty.
```
function closeTicket(id) {
  const ticket = tickets.find((t) => t.id === id);
  ticket.status = 'CLOSED';
  setTickets(tickets);
}
```

#T CODE_RIGHT Nowa tablica z nowym obiektem
```
function closeTicket(id) {
  setTickets((prev) => prev.map((t) => (t.id === id ? { ...t, status: 'CLOSED' } : t)));
}
```

#T DEFINITION Immer: wygodne aktualizacje głęboko zagnieżdżonych danych
Gdy dane są głęboko zagnieżdżone (ticket → komentarze → reakcje), spread na trzech poziomach jest długi i podatny na błędy. Biblioteka **Immer** pozwala pisać kod „mutujący” na szkicu (draft), a sama tworzy nową, niemutowalną wersję. Hook `useImmer` z paczki `use-immer` działa jak `useState`, ale setter przyjmuje funkcję modyfikującą szkic.

#T CODE_BASIC Spread na kilku poziomach
```
import type { Ticket } from '../types';

type Comment = { id: number; text: string; likes: number };
type TicketWithComments = Ticket & { comments: Comment[] };

export function likeComment(ticket: TicketWithComments, commentId: number): TicketWithComments {
  return {
    ...ticket,
    comments: ticket.comments.map((c) => (c.id === commentId ? { ...c, likes: c.likes + 1 } : c)),
  };
}
```

#T CODE_PRACTICAL To samo z Immer
`produce` przekazuje szkic, który możesz „mutować”. Wynikiem jest nowy obiekt; oryginał pozostaje bez zmian. W komponencie: `const [ticket, updateTicket] = useImmer(initial)` i `updateTicket((draft) => { ... })`.
```
import { produce } from 'immer';
import type { Ticket } from '../types';

type Comment = { id: number; text: string; likes: number };
type TicketWithComments = Ticket & { comments: Comment[] };

export function likeComment(ticket: TicketWithComments, commentId: number): TicketWithComments {
  return produce(ticket, (draft) => {
    const comment = draft.comments.find((c) => c.id === commentId);
    if (comment) comment.likes += 1;
  });
}
```

#T STEP_BY_STEP Budujemy razem: tickety jako stan
1. W `Main` przenieś tickety do stanu: `useState(initialTickets)`.
2. Zaimplementuj `closeTicket` przez `map` i podepnij pod przycisk „Zamknij” w wierszu.
3. Dodaj przycisk „Usuń” w wierszu i `deleteTicket` przez `filter`; po usunięciu wybranego ticketu karta szczegółów powinna pokazać „Wybierz ticket z listy” (wynika to samo z `find`).
4. Dodaj w karcie przycisk „Przypisz do mnie”, który ustawia `assignee: 'anna'` dla wybranego ticketu.
5. Dodaj przycisk „+ Szybki ticket”, który dopisuje na początek listy ticket z tytułem „Nowy ticket”, ID `Math.max(...ids) + 1` i datą `new Date().toISOString()` (ID i datę wyliczasz w handlerze, nie w renderze).
6. W React DevTools sprawdź, że po każdej akcji stan `tickets` to nowa tablica, a dane w `data/tickets` pozostały nienaruszone (przeładuj stronę — wracają pierwotne tickety).

#T PITFALL Płytka kopia przy zagnieżdżeniu
`const copy = { ...ticket }; copy.tags.push('pilne');` — spread kopiuje tylko pierwszy poziom. `copy.tags` to ta sama tablica co `ticket.tags`, więc zmieniłeś oryginał. Każdy zmieniany poziom musi zostać skopiowany: `{ ...ticket, tags: [...ticket.tags, 'pilne'] }`.

#T WHEN_TO_USE Spread czy Immer
Spread i metody `map`/`filter` wystarczą dla płaskich danych i jednego, dwóch poziomów zagnieżdżenia — to większość przypadków w aplikacjach. Immer warto dodać, gdy aktualizacje sięgają trzech i więcej poziomów albo modyfikujesz wiele pól naraz w złożonym obiekcie. Redux Toolkit (rozdział 13) używa Immera wewnętrznie.

#T SUMMARY Kryterium akceptacji i podsumowanie
Obiekty i tablice w stanie aktualizujesz, tworząc nowe kopie: spread dla obiektów, `map`/`filter`/`toSorted`/`toSpliced`/`with` dla tablic. Mutacja (`push`, `sort`, `obj.x = ...`) daje tę samą referencję i React pomija render. Przy głębokim zagnieżdżeniu pomaga Immer. W TSX spread jest sprawdzany względem typu, więc literówki w polach są błędami.

Kryterium akceptacji: tickety są w stanie; „Zamknij”, „Usuń”, „Przypisz do mnie” i „+ Szybki ticket” natychmiast zmieniają tabelę i kartę szczegółów, a żadna operacja nie mutuje istniejących obiektów.
