#T INTRO Rozgrzewka i problem: każda zmiana to strach przed regresją
Rozgrzewka: Co trzymasz w magazynie stanu, a czego nie? Dlaczego sumy koszyka liczy czysta funkcja? Czym różni się RTK Query od TanStack Query?

Problem: DevDesk ma już kilkadziesiąt komponentów, routing, zapytania, mutacje i magazyny stanu. Każda zmiana — przeniesienie filtra do adresu, nowy reducer, inna biblioteka formularzy — wymaga ręcznego przeklikania aplikacji, i zawsze coś umyka. Zanim napiszesz pierwszy test, potrzebujesz **strategii**: co testować, na jakim poziomie i jak, żeby testy dawały pewność, a nie przeszkadzały w zmianach.

#T DEFINITION Poziomy testów frontendu
- **Testy statyczne** — TypeScript i ESLint: łapią literówki, złe typy, łamanie zasad hooków, zanim kod się uruchomi. Najtańsze.
- **Testy jednostkowe** — czyste funkcje i logika bez interfejsu: `computeTotals`, `paginate`, reducer, parsowanie adresu. Szybkie (milisekundy), precyzyjne.
- **Testy komponentów / integracyjne** — renderują komponent (lub ekran) w symulowanym DOM (jsdom), klikają jak użytkownik i sprawdzają, co widać na ekranie; sieć przez MSW. Główna siła testów React.
- **Testy end-to-end (E2E)** — prawdziwa przeglądarka i (często) prawdziwy backend: pełna ścieżka „zaloguj → utwórz ticket → zobacz go na liście”. Najwolniejsze i najbardziej kruche, ale sprawdzają całość.

#T VISUAL_EXAMPLE Trofeum testów (Testing Trophy)
            ▲   E2E (Playwright) — kilka kluczowych ścieżek
           ███
         ███████   Integracyjne (Testing Library + MSW) — najwięcej pewności za rozsądną cenę
       ███████████
         ███████   Jednostkowe (Vitest) — logika, funkcje, reducery
          █████
       ═════════════  Statyczne (TypeScript, ESLint) — podstawa, zawsze włączone

Model popularyzowany przez autora Testing Library: najwięcej wysiłku inwestuj w testy integracyjne komponentów, bo najlepiej odpowiadają temu, jak użytkownik korzysta z aplikacji.

#T DEFINITION Testuj zachowanie, nie implementację
Główna zasada Testing Library: „Im bardziej testy przypominają sposób używania aplikacji, tym więcej pewności dają”. Test powinien:
- szukać elementów tak, jak użytkownik (po roli, etykiecie, tekście), a nie po klasach CSS czy nazwach komponentów,
- wykonywać działania użytkownika (kliknięcie, wpisanie tekstu), a nie wywoływać funkcje komponentu,
- sprawdzać efekt widoczny dla użytkownika (tekst na ekranie, wysłane żądanie), a nie wewnętrzny stan.

Taki test **przetrwa refaktoryzację** (zamiana `useState` na reducer, CSS Modules na Tailwind, kontekst na Zustand) i zawiedzie tylko wtedy, gdy zepsuje się coś, co widzi użytkownik.

#T CODE_JSX Test implementacji kontra test zachowania (JSX)
Pierwszy test „zna” wnętrze komponentu i pęknie przy każdej refaktoryzacji. Drugi opisuje to, co robi użytkownik.
```
// Counter.test.jsx — porównanie podejść
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { expect, test } from 'vitest';
import { WatchToggle } from './WatchToggle';

// ŹLE (koncepcyjnie): sprawdzanie klasy CSS i struktury
test('ma klasę active po kliknięciu', async () => {
  const { container } = render(<WatchToggle />);
  await userEvent.click(container.querySelector('.watch-btn'));
  expect(container.querySelector('.watch-btn--active')).not.toBeNull();
});

// DOBRZE: zachowanie widoczne dla użytkownika
test('użytkownik może zacząć obserwować ticket', async () => {
  render(<WatchToggle />);
  await userEvent.click(screen.getByRole('button', { name: /obserwuj/i }));
  expect(screen.getByRole('button', { name: /obserwujesz/i })).toBeInTheDocument();
});
```

#T CODE_TSX Test implementacji kontra test zachowania (TSX)
W TSX test wygląda tak samo; różnica: `container.querySelector` zwraca `Element | null`, więc wersja „implementacyjna” wymaga dodatkowych sprawdzeń — kolejny sygnał, że to zła droga.
```
// WatchToggle.test.tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { expect, test } from 'vitest';
import { WatchToggle } from './WatchToggle';

test('użytkownik może zacząć obserwować ticket', async () => {
  const user = userEvent.setup();
  render(<WatchToggle />);
  await user.click(screen.getByRole('button', { name: /obserwuj/i }));
  expect(screen.getByRole('button', { name: /obserwujesz/i })).toBeInTheDocument();
});
```

#T NOTE JSX ↔ TSX — testy też są kodem
Testy możesz pisać w `.test.jsx` lub `.test.tsx` niezależnie od języka aplikacji, ale zwykle trzyma się jednego. W TSX testy dostają typy komponentów: renderując `<TicketRow />` bez wymaganych props, dostaniesz błąd kompilacji testu — co łapie część pomyłek zanim test się uruchomi. Typy NIE zastępują testów: TypeScript nie sprawdzi, że kliknięcie „Zamknij” naprawdę zamyka ticket, a test nie sprawdzi wszystkich kombinacji typów. To dwa uzupełniające się poziomy trofeum.

#T API_REFERENCE Co testować w DevDesk — lista kontrolna
Na pewno:
- czyste funkcje z logiką biznesową (sumy, filtry, sortowanie, paginacja, parsowanie adresu, walidacja),
- reducery i magazyny stanu (przejścia stanów, akcje zbiorcze, cofanie),
- kluczowe komponenty w działaniu: formularz z walidacją, tabela z filtrami, modal z fokusem, przepływ „usuń z cofnięciem”,
- stany asynchroniczne: ładowanie, błąd z ponowieniem, pusty wynik (przez MSW),
- 3–5 ścieżek E2E: logowanie, tworzenie ticketu, edycja, wyszukiwanie z filtrem w adresie.

Raczej nie:
- szczegóły bibliotek (że `useState` działa, że React Router zmienia adres),
- style i dokładny układ (to zadanie testów wizualnych, lekcja 8),
- każdy wariant prezentacyjnego komponentu bez logiki,
- „pokrycie 100%” jako cel sam w sobie.

#T STEP_BY_STEP Budujemy razem: plan testów DevDesk
1. Wypisz 10 najważniejszych zachowań DevDesk z punktu widzenia użytkownika (np. „po wpisaniu tekstu tabela pokazuje pasujące tickety”, „po błędzie serwera mogę spróbować ponownie”).
2. Każdemu zachowaniu przypisz poziom testu: jednostkowy, integracyjny czy E2E — i uzasadnij w jednym zdaniu.
3. Wypisz funkcje czyste, które już masz (`computeTotals`, `paginate`, `sortTickets`, `parseCatalogParams`, reducery) — to kandydaci na pierwsze, najprostsze testy.
4. Zaplanuj miejsce: testy obok kodu (`TicketRow.test.tsx` przy `TicketRow.tsx`), E2E w osobnym katalogu `e2e/`.
5. Ustal regułę zespołu: każdy naprawiony błąd dostaje test, który by go wykrył.
6. W następnych lekcjach zrealizujesz plan poziom po poziomie.

#T PITFALL Testy, które sprawdzają mocki
Test, w którym wszystko jest zamockowane (`vi.mock` na komponentach-dzieciach, hookach, kliencie API), często sprawdza tylko, czy mocki zostały wywołane — przejdzie także wtedy, gdy aplikacja jest zepsuta. Mockuj na granicy systemu (sieć przez MSW, czas przez fałszywe zegary), a resztę renderuj prawdziwą.

#T SUMMARY Kryterium akceptacji i podsumowanie
Testy frontendu mają poziomy: statyczne (TS, ESLint), jednostkowe (logika), integracyjne (komponenty w jsdom z MSW) i E2E (prawdziwa przeglądarka). Najwięcej pewności za rozsądną cenę dają testy integracyjne. Testuj zachowanie widoczne dla użytkownika (role, etykiety, teksty, działania), a nie implementację (klasy, stan wewnętrzny) — wtedy testy przetrwają refaktoryzację. Mockuj na granicy systemu. Typy i testy uzupełniają się.

Kryterium akceptacji: masz spisany plan testów DevDesk — 10 zachowań z przypisanym poziomem testu i uzasadnieniem, listę funkcji czystych do testów jednostkowych oraz regułę „każdy błąd dostaje test”.
