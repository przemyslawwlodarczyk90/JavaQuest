#T INTRO Rozgrzewka i problem: logika schowana w hookach
Rozgrzewka: Czym różni się `user.click` od `fireEvent.click`? Po co `await` przed każdym wywołaniem user-event? Jak sprawdzić w teście, że fokus wrócił na przycisk?

Problem: duża część logiki DevDesk żyje we własnych hookach i kontekstach: `useTicketFilters`, `useControllableState`, `useSelection`, `useCombobox`, `PrefsProvider`, magazyn Zustand koszyka. Testowanie ich wyłącznie przez pełne ekrany jest wolne i trudno w nim trafić w przypadki brzegowe (np. zmiana trybu kontrolowanego). Testing Library ma `renderHook` do testowania hooków w izolacji, a konteksty i magazyny testujesz przez wrapper lub bezpośrednio.

#T DEFINITION renderHook
`renderHook(() => useMyHook(args), { wrapper, initialProps })` renderuje mały, niewidoczny komponent wywołujący hook i zwraca:
- `result.current` — aktualna wartość zwrócona przez hook (odczytuj zawsze przez `result.current`, bo zmienia się po renderach),
- `rerender(noweProps)` — ponowny render z innymi argumentami,
- `unmount()` — odmontowanie (sprawdzenie sprzątania efektów).

Zmiany stanu wywołane z testu (np. `result.current.toggle()`) opakowujesz w `act(() => ...)`, żeby React przetworzył aktualizację przed asercją.

#T CODE_JSX Test hooka zaznaczania (JSX)
```
// useSelection.test.js
import { act, renderHook } from '@testing-library/react';
import { expect, test } from 'vitest';
import { useSelection } from './useSelection';

test('toggle dodaje i usuwa ID, setAll zaznacza wiele naraz', () => {
  const { result } = renderHook(() => useSelection());

  act(() => result.current.toggle(1));
  act(() => result.current.toggle(2));
  expect([...result.current.selectedIds]).toEqual([1, 2]);

  act(() => result.current.toggle(1));
  expect([...result.current.selectedIds]).toEqual([2]);

  act(() => result.current.setAll([3, 4], true));
  expect(result.current.selectedIds.size).toBe(3);

  act(() => result.current.clear());
  expect(result.current.selectedIds.size).toBe(0);
});
```

#T CODE_TSX Test hooka z argumentami i rerender (TSX)
`initialProps` z typem pozwala testować reakcję hooka na zmianę argumentów — tu tryb kontrolowany `useControllableState`.
```
// useControllableState.test.ts
import { act, renderHook } from '@testing-library/react';
import { expect, test, vi } from 'vitest';
import { useControllableState } from './useControllableState';

test('w trybie kontrolowanym zwraca value z props i tylko woła onChange', () => {
  const onChange = vi.fn<(v: string[]) => void>();
  const { result, rerender } = renderHook(
    ({ value }: { value: string[] }) => useControllableState({ value, defaultValue: [], onChange }),
    { initialProps: { value: ['api'] } },
  );

  act(() => result.current[1](['api', 'ui']));
  expect(onChange).toHaveBeenCalledWith(['api', 'ui']);
  expect(result.current[0]).toEqual(['api']); // rodzic jeszcze nie zmienił value

  rerender({ value: ['api', 'ui'] });
  expect(result.current[0]).toEqual(['api', 'ui']);
});

test('w trybie niekontrolowanym trzyma własny stan', () => {
  const { result } = renderHook(() => useControllableState<string[]>({ defaultValue: ['ui'] }));
  act(() => result.current[1]((prev: string[]) => [...prev, 'auth']));
  expect(result.current[0]).toEqual(['ui', 'auth']);
});
```

#T NOTE JSX ↔ TSX — typy w renderHook
W TSX typ `initialProps` (`{ value: string[] }`) przenosi się na `rerender` — `rerender({ value: 'api' })` (tekst zamiast tablicy) jest błędem. `result.current` ma typ zwracany przez hook, więc `result.current[1]` to setter przyjmujący `string[] | ((prev) => string[])`. W JSX te same testy działają, ale pomyłka w danych testowych da mylący wynik zamiast błędu kompilacji. Sam test jest identyczny w obu wersjach — dobrze napisany hook testuje się tak samo niezależnie od języka.

#T DEFINITION Testowanie kontekstów i providerów
Hook kontekstu (`usePrefs`, `useAuth`, `useToast`) testujesz przez `renderHook` z opcją `wrapper` — komponentem renderującym provider. Testuj dwie rzeczy: zachowanie wewnątrz providera (zmiany wartości) i błąd poza providerem (czytelny komunikat). Dla błędu poza providerem `renderHook` rzuci wyjątek — sprawdzasz go `expect(() => renderHook(...)).toThrow(...)`, a hałaśliwy log błędu Reacta wyciszasz szpiegiem na `console.error`.

#T CODE_BASIC Test providera preferencji
```
import { act, renderHook } from '@testing-library/react';
import type { ReactNode } from 'react';
import { expect, test, vi } from 'vitest';
import { PrefsProvider, usePrefs } from './PrefsContext';

const wrapper = ({ children }: { children: ReactNode }) => <PrefsProvider>{children}</PrefsProvider>;

test('updatePrefs zmienia tylko podane pola', () => {
  const { result } = renderHook(() => usePrefs(), { wrapper });
  act(() => result.current.updatePrefs({ density: 'compact' }));
  expect(result.current.prefs.density).toBe('compact');
  expect(result.current.prefs.dateFormat).toBe('relative');
});

test('usePrefs poza providerem rzuca czytelny błąd', () => {
  const spy = vi.spyOn(console, 'error').mockImplementation(() => {});
  expect(() => renderHook(() => usePrefs())).toThrow(/wewnątrz <PrefsProvider>/);
  spy.mockRestore();
});
```

#T CODE_PRACTICAL Test magazynu Zustand bez Reacta
Magazyn Zustand to też obiekt z `getState`/`setState` — logikę akcji testujesz bez renderowania. Przed każdym testem przywracasz stan początkowy, bo magazyn jest globalny dla modułu.
```
import { beforeEach, expect, test } from 'vitest';
import { useQuickCart } from './quickCartStore';

const initial = useQuickCart.getState();

beforeEach(() => {
  useQuickCart.setState(initial, true); // true = zastąp cały stan
});

test('add nie dubluje ticketu, setNote zmienia notatkę', () => {
  const { add, setNote } = useQuickCart.getState();
  add(42);
  add(42);
  setNote(42, 'oddzwonić');
  expect(useQuickCart.getState().items).toEqual([expect.objectContaining({ ticketId: 42, note: 'oddzwonić' })]);
});
```

#T STEP_BY_STEP Budujemy razem: testy logiki DevDesk
1. Napisz testy `renderHook` dla `useSelection`, `useControllableState` (oba tryby i zmiana `value`), `useToggle` i `useTicketFilters` (reset strony przy zmianie filtra).
2. Przetestuj `useCombobox`: filtrowanie po wpisaniu, zmiana aktywnej pozycji, wybór — przez prop gettery wywołane na małym komponencie testowym albo przez `renderHook` i wywołanie handlerów z `getInputProps()`.
3. Przetestuj `PrefsProvider` (zmiana pól, błąd poza providerem) i `AuthProvider` z MSW dla `/api/auth/refresh` (wyprzedzenie następnej lekcji).
4. Przetestuj magazyn Zustand koszyka bez Reacta: akcje, ograniczenie ilości, migracja `persist` (wywołaj funkcję `migrate` bezpośrednio).
5. Sprawdź sprzątanie: `unmount()` hooka z interwałem (`useSecondsSince`) przy fałszywych zegarach — po odmontowaniu stan się nie zmienia, a `vi.getTimerCount()` zwraca 0.
6. Uzupełnij `renderWithProviders` o wszystkie providery DevDesk i użyj tego samego zestawu jako `wrapper` w `renderHook`.

#T PITFALL Testowanie hooka zamiast zachowania ekranu
`renderHook` jest świetny dla hooków wielokrotnego użytku z logiką (biblioteka zespołu, `useControllableState`). Testowanie przez `renderHook` każdego hooka „ekranowego” (np. `useTicketsPageState` używanego w jednym miejscu) wiąże testy z implementacją: po przeniesieniu logiki z hooka do komponentu testy trzeba przepisać, choć zachowanie się nie zmieniło. Dla logiki jednego ekranu lepszy jest test komponentu.

#T SUMMARY Kryterium akceptacji i podsumowanie
`renderHook(() => useHook(...), { wrapper, initialProps })` testuje hooki w izolacji: wartość w `result.current`, zmiany w `act`, nowe argumenty przez `rerender`, sprzątanie przez `unmount`. Konteksty testujesz z `wrapper` (zachowanie wewnątrz i błąd poza providerem), magazyny Zustand — bez Reacta przez `getState`/`setState` z przywracaniem stanu przed testem. `renderHook` stosuj dla hooków wielokrotnego użytku, a logikę pojedynczych ekranów testuj przez komponenty. W TSX `initialProps` i `result.current` mają typy hooka.

Kryterium akceptacji: hooki `useSelection`, `useControllableState`, `useTicketFilters`, `useCombobox`, provider preferencji i magazyn koszyka mają testy, a test hooka z interwałem potwierdza sprzątanie po odmontowaniu.
