#T INTRO Rozgrzewka i problem: test, który nie klika
Rozgrzewka: W jakiej kolejności wybierasz zapytania Testing Library? Kiedy używasz `queryBy`, a kiedy `findBy`? Po co fabryka danych testowych?

Problem: testy z poprzedniej lekcji sprawdzają, co komponent renderuje. Najważniejsze błędy DevDesk są jednak w **interakcjach**: formularz pozwala wysłać za krótki tytuł, Escape nie zamyka modala, fokus nie wraca na przycisk, strzałki nie przełączają zakładek. Do symulowania działań użytkownika służy **user-event** — biblioteka, która odtwarza pełną sekwencję zdarzeń przeglądarki (fokus, klawisze, wpisywanie znak po znaku, kliknięcie z najechaniem), a nie pojedyncze sztuczne zdarzenie.

#T DEFINITION user-event a fireEvent
`fireEvent.click(el)` wysyła jedno zdarzenie `click`. Prawdziwe kliknięcie to sekwencja: `pointerover`, `pointerenter`, `mouseover`, `pointerdown`, `mousedown`, fokus, `pointerup`, `mouseup`, `click` — i nie wydarzy się, jeśli element jest wyłączony albo zasłonięty przez `pointer-events: none`. `user.type(pole, 'abc')` wpisuje znak po znaku, wywołując `keydown`, `keypress`, `input`, `keyup` dla każdego — tak jak klawiatura. Dlatego testy z user-event łapią błędy, których `fireEvent` nie złapie (np. handler podpięty pod `onKeyDown` zamiast `onChange`).

Wzorzec: `const user = userEvent.setup()` na początku testu, a potem `await user.click(...)`, `await user.type(...)`, `await user.keyboard('{Escape}')`, `await user.tab()`, `await user.selectOptions(...)`, `await user.clear(...)`, `await user.upload(...)`. Wszystkie metody są asynchroniczne — zawsze `await`.

#T CODE_JSX Test formularza z walidacją (JSX)
```
// NewTicketForm.test.jsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { describe, expect, test, vi } from 'vitest';
import { NewTicketForm } from './NewTicketForm';

describe('NewTicketForm', () => {
  test('nie wysyła formularza z za krótkim tytułem i pokazuje komunikat przy polu', async () => {
    const user = userEvent.setup();
    const onCreate = vi.fn();
    render(<NewTicketForm onCreate={onCreate} />);

    await user.type(screen.getByLabelText('Tytuł'), 'abc');
    await user.click(screen.getByRole('button', { name: 'Utwórz' }));

    expect(onCreate).not.toHaveBeenCalled();
    const title = screen.getByLabelText('Tytuł');
    expect(title).toHaveAttribute('aria-invalid', 'true');
    expect(title).toHaveAccessibleDescription(/co najmniej 5 znaków/i);
    expect(title).toHaveFocus();
  });

  test('wysyła poprawne dane i czyści formularz', async () => {
    const user = userEvent.setup();
    const onCreate = vi.fn();
    render(<NewTicketForm onCreate={onCreate} />);

    await user.type(screen.getByLabelText('Tytuł'), 'Błąd eksportu CSV');
    await user.selectOptions(screen.getByLabelText('Priorytet'), 'HIGH');
    await user.click(screen.getByRole('button', { name: 'Utwórz' }));

    expect(onCreate).toHaveBeenCalledWith(expect.objectContaining({ title: 'Błąd eksportu CSV', priority: 'HIGH' }));
    expect(screen.getByLabelText('Tytuł')).toHaveValue('');
  });
});
```

#T CODE_TSX Test formularza z walidacją (TSX)
`vi.fn<(values: FormValues) => void>()` daje szpiega z typem — `toHaveBeenCalledWith` sprawdza zgodność argumentu z typem funkcji.
```
// NewTicketForm.test.tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { describe, expect, test, vi } from 'vitest';

type FormValues = { title: string; priority: 'LOW' | 'MEDIUM' | 'HIGH' | 'CRITICAL' };
declare function NewTicketForm(props: { onCreate: (values: FormValues) => void }): React.JSX.Element;

describe('NewTicketForm', () => {
  test('wysyła poprawne dane i czyści formularz', async () => {
    const user = userEvent.setup();
    const onCreate = vi.fn<(values: FormValues) => void>();
    render(<NewTicketForm onCreate={onCreate} />);

    await user.type(screen.getByLabelText('Tytuł'), 'Błąd eksportu CSV');
    await user.selectOptions(screen.getByLabelText('Priorytet'), 'HIGH');
    await user.click(screen.getByRole('button', { name: 'Utwórz' }));

    expect(onCreate).toHaveBeenCalledWith(expect.objectContaining({ title: 'Błąd eksportu CSV', priority: 'HIGH' }));
    expect(screen.getByLabelText('Tytuł')).toHaveValue('');
  });
});
```

#T NOTE JSX ↔ TSX — typowany szpieg
`vi.fn()` bez typu w TSX przyjmuje dowolne argumenty, więc test nie zauważy, że komponent wywołuje `onCreate` z innym kształtem danych niż deklaruje. `vi.fn<(values: FormValues) => void>()` łączy szpiega z typem props komponentu — przekazanie go jako `onCreate` jest sprawdzane, a `expect(onCreate).toHaveBeenCalledWith(...)` podpowiada pola. W JSX szpieg zawsze przyjmie wszystko. W obu wersjach najważniejsze asercje są o tym, co widzi użytkownik: komunikat, fokus, wyczyszczone pole.

#T DEFINITION Asercje dostępności w testach interakcji
`jest-dom` ma dopasowania, które przy okazji testują dostępność:
- `toHaveFocus()` — element ma fokus (np. po otwarciu modala, po błędzie walidacji),
- `toHaveAccessibleName('…')` i `toHaveAccessibleDescription('…')` — nazwa i opis widziane przez czytnik ekranu (opis z `aria-describedby`),
- `toHaveAttribute('aria-expanded', 'true')`, `toBeChecked()`, `toBeDisabled()`, `toHaveValue(...)`,
- `toBeVisible()` — element jest widoczny (nie `hidden`, nie `display: none`).

Dzięki nim testy interakcji sprawdzają też pracę z klawiaturą i czytnikiem ekranu, które łatwo zepsuć przy refaktoryzacji.

#T CODE_BASIC Test klawiatury: zakładki i modal
```
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { expect, test } from 'vitest';

declare function TicketSections(): React.JSX.Element;
declare function NewTicketDialogDemo(): React.JSX.Element;

test('strzałki przełączają zakładki, a fokus idzie za aktywną zakładką', async () => {
  const user = userEvent.setup();
  render(<TicketSections />);

  await user.tab(); // fokus na aktywnej zakładce
  expect(screen.getByRole('tab', { name: /Szczegóły/ })).toHaveFocus();

  await user.keyboard('{ArrowRight}');
  const activity = screen.getByRole('tab', { name: /Aktywność/ });
  expect(activity).toHaveFocus();
  expect(activity).toHaveAttribute('aria-selected', 'true');
  expect(screen.getByRole('tabpanel')).toHaveAccessibleName(/Aktywność/);
});

test('Escape zamyka modal, a fokus wraca na przycisk otwierający', async () => {
  const user = userEvent.setup();
  render(<NewTicketDialogDemo />);

  const opener = screen.getByRole('button', { name: '+ Nowy ticket' });
  await user.click(opener);
  expect(screen.getByRole('dialog', { name: 'Nowy ticket' })).toBeInTheDocument();
  expect(screen.getByLabelText('Tytuł')).toHaveFocus();

  await user.keyboard('{Escape}');
  expect(screen.queryByRole('dialog')).not.toBeInTheDocument();
  expect(opener).toHaveFocus();
});
```

#T CODE_PRACTICAL Fałszywy czas z user-event: toast z cofnięciem
Przy fałszywych zegarach user-event musi wiedzieć, jak „przesuwać czas” — opcja `advanceTimers`.
```
import { act, render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { afterEach, expect, test, vi } from 'vitest';

declare function TicketListWithUndo(props: { onDeleteOnServer: (id: number) => void }): React.JSX.Element;

afterEach(() => vi.useRealTimers());

test('usunięcie można cofnąć w ciągu 5 sekund, potem staje się ostateczne', async () => {
  vi.useFakeTimers();
  const user = userEvent.setup({ advanceTimers: vi.advanceTimersByTime });
  const onDeleteOnServer = vi.fn();
  render(<TicketListWithUndo onDeleteOnServer={onDeleteOnServer} />);

  await user.click(screen.getAllByRole('button', { name: 'Usuń' })[0]);
  expect(screen.getByRole('status')).toHaveTextContent(/Usunięto ticket/);

  await user.click(screen.getByRole('button', { name: 'Cofnij' }));
  act(() => { vi.advanceTimersByTime(6000); });
  expect(onDeleteOnServer).not.toHaveBeenCalled();
});
```

#T STEP_BY_STEP Budujemy razem: testy interakcji DevDesk
1. Napisz testy formularza nowego ticketu: błędna walidacja (komunikat, `aria-invalid`, fokus), poprawne wysłanie (dane w callbacku, wyczyszczony formularz), reguła zależna (CRITICAL bez opisu).
2. Napisz test zakładek (strzałki, Home, End, `aria-selected`) i modala (otwarcie, fokus w polu, Tab nie wychodzi poza modal, Escape, powrót fokusu).
3. Napisz test „usuń z cofnięciem” z fałszywym czasem: cofnięcie przywraca wiersz; brak cofnięcia po 5 s wywołuje usunięcie na serwerze.
4. Napisz test wyszukiwarki z opóźnieniem: wpisanie tekstu i przesunięcie czasu o 300 ms filtruje listę (komponent z danymi lokalnymi).
5. Celowo zepsuj obsługę Escape w modalu — test powinien to wykryć z czytelnym komunikatem.
6. Przejrzyj testy: żaden nie wywołuje handlerów komponentu bezpośrednio ani nie sprawdza stanu wewnętrznego.

#T PITFALL Brak await przy user-event
`user.click(button)` bez `await` zwraca obietnicę, a test idzie dalej, zanim kliknięcie się wykona — asercja sprawdza stan sprzed kliknięcia i albo test przechodzi przypadkiem, albo pada losowo. Każde wywołanie user-event poprzedzaj `await` (ESLint z wtyczką `eslint-plugin-testing-library` ma regułę, która tego pilnuje).

#T SUMMARY Kryterium akceptacji i podsumowanie
user-event odtwarza pełne sekwencje zdarzeń przeglądarki (wskaźnik, fokus, klawisze znak po znaku), więc testy łapią błędy, których nie wykryje pojedynczy `fireEvent`. Wzorzec: `const user = userEvent.setup()`, potem `await user.click/type/keyboard/tab/selectOptions`. Asercje `toHaveFocus`, `toHaveAccessibleName`/`Description`, `toHaveAttribute('aria-…')` sprawdzają też dostępność. Przy fałszywych zegarach podaj `advanceTimers`. W TSX typowany szpieg `vi.fn<typ>()` łączy test z kontraktem props.

Kryterium akceptacji: formularz nowego ticketu, zakładki, modal (z fokusem i Escape) i usuwanie z cofnięciem mają testy interakcji z user-event, a celowe zepsucie obsługi klawiatury lub walidacji powoduje niezaliczony test.
