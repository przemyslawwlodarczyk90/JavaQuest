#T INTRO Trening: hooki React 19
React 19 dodał zestaw narzędzi do pracy z operacjami asynchronicznymi bez ręcznego żonglowania flagami `isLoading`, `error` i `try/finally`: `use` (odczyt Promise i kontekstu), `useActionState` (stan wyniku akcji), `useFormStatus` (stan wysyłania formularza nadrzędnego), `useOptimistic` (natychmiastowy podgląd zmiany) i asynchroniczne `startTransition` (stan oczekiwania dla dowolnej akcji). Ten trening to dwanaście zadań, które utrwalają każdy z nich osobno, a na końcu łączą je w jeden formularz.

Wszystkie zadania korzystają z udawanego API — funkcji zwracających Promise z opóźnieniem. Przygotuj je raz w pliku `fakeApi`:
- `wait(ms)` — Promise rozwiązywany po `ms`,
- `fetchUser(id)` — po 600 ms zwraca `{ id, name }`, dla `id === 0` odrzuca błędem,
- `saveName(name)` — po 800 ms zwraca zapisane imię, dla imienia „błąd” odrzuca.

#T CODE_JSX Udawane API do treningu (JSX)
```
// fakeApi.js
export const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

export async function fetchUser(id) {
  await wait(600);
  if (id === 0) throw new Error('Nie znaleziono użytkownika');
  return { id, name: ['Ala', 'Bob', 'Celina'][id % 3] };
}

export async function saveName(name) {
  await wait(800);
  if (name.trim().toLowerCase() === 'błąd') throw new Error('Serwer odrzucił imię');
  return name.trim();
}
```

#T STEP_BY_STEP Zadanie 1 — use(Context) warunkowo
`use` jako jedyny hook może być wywołany w warunku lub pętli. Wykorzystaj to do odczytu kontekstu tylko wtedy, gdy jest potrzebny.

Wymagania:
1. `CurrencyContext` z wartością `'PLN'` albo `'EUR'` i przełącznikiem w `App`.
2. Komponent `Price({ amount, show })`: gdy `show` jest fałszem — zwraca `null` **przed** odczytem kontekstu; w przeciwnym razie `use(CurrencyContext)` i formatowanie `Intl.NumberFormat`.
3. Lista trzech cen, z których jedna ma `show={false}`.

Sprawdź się: ten sam kod z `useContext` po wczesnym `return` złamałby zasady hooków — z `use` jest poprawny.

#T CODE_JSX Rozwiązanie 1 (JSX)
```
// Price.jsx
import { createContext, use, useState } from 'react';

const CurrencyContext = createContext('PLN');

function Price({ amount, show }) {
  if (!show) return null;
  const currency = use(CurrencyContext); // dozwolone po wczesnym return
  return <span>{new Intl.NumberFormat('pl-PL', { style: 'currency', currency }).format(amount)}</span>;
}

export function App() {
  const [currency, setCurrency] = useState('PLN');
  return (
    <CurrencyContext value={currency}>
      <button type="button" onClick={() => setCurrency((c) => (c === 'PLN' ? 'EUR' : 'PLN'))}>Waluta: {currency}</button>
      <ul>
        <li><Price amount={120} show /></li>
        <li><Price amount={45.5} show={false} /></li>
        <li><Price amount={9.99} show /></li>
      </ul>
    </CurrencyContext>
  );
}
```

#T STEP_BY_STEP Zadanie 2 — use(promise) i Suspense
Wyświetl profil użytkownika pobierany przez `fetchUser`, z ekranem ładowania z `Suspense`.

Wymagania:
1. Promise tworzy **rodzic** w handlerze (albo przy inicjalizacji stanu) i przekazuje w props — nie komponent czytający.
2. `UserCard({ userPromise })` odczytuje dane przez `use(userPromise)` — bez `useEffect` i bez stanu ładowania.
3. `Suspense fallback={<p>Ładowanie…</p>}` wokół `UserCard`.
4. Przyciski „Użytkownik 1 / 2 / 3” tworzą nowy Promise i zapisują go w stanie rodzica.

Sprawdź się: przełączenie użytkownika pokazuje fallback, a potem nowe dane; w komponencie `UserCard` nie ma ani jednego `useState`.

#T CODE_JSX Rozwiązanie 2 (JSX)
```
// UserProfile.jsx
import { Suspense, use, useState } from 'react';
import { fetchUser } from './fakeApi';

function UserCard({ userPromise }) {
  const user = use(userPromise);
  return <h2>{user.name} (#{user.id})</h2>;
}

export function UserProfile() {
  const [userPromise, setUserPromise] = useState(() => fetchUser(1));

  return (
    <section>
      {[1, 2, 3].map((id) => (
        <button key={id} type="button" onClick={() => setUserPromise(fetchUser(id))}>Użytkownik {id}</button>
      ))}
      <Suspense fallback={<p>Ładowanie…</p>}>
        <UserCard userPromise={userPromise} />
      </Suspense>
    </section>
  );
}
```

#T CODE_BASIC Zadanie 3 — przewidź wynik: gdzie powstaje Promise
Co zobaczy użytkownik w każdym wariancie? Który działa poprawnie?
```
// @check-skip
// A
function UserCard({ id }) {
  const user = use(fetchUser(id));
  return <h2>{user.name}</h2>;
}

// B
function UserCard({ id }) {
  try {
    const user = use(fetchUser(id));
    return <h2>{user.name}</h2>;
  } catch {
    return <p>Błąd</p>;
  }
}

// C
const cache = new Map();
function getUser(id) {
  if (!cache.has(id)) cache.set(id, fetchUser(id));
  return cache.get(id);
}
function UserCard({ id }) {
  const user = use(getUser(id));
  return <h2>{user.name}</h2>;
}
```

#T NOTE Odpowiedź do zadania 3
- **A** — wieczne „Ładowanie…” (i ostrzeżenie w konsoli o Promise niezapamiętanym między renderami). Każdy render tworzy **nowy** Promise; gdy poprzedni się rozwiąże, React renderuje ponownie, `use` dostaje kolejny nowy Promise i znowu zawiesza komponent. Promise musi przetrwać między renderami.
- **B** — błąd w użyciu: `use` nie wolno owijać w `try/catch`. Zawieszenie działa przez wyjątek specjalnego rodzaju; złapanie go psuje mechanizm (React zgłosi błąd). Odrzucony Promise obsługujesz granicą błędu (zadanie 4).
- **C** — działa: Promise dla danego `id` jest tworzony raz i trzymany w pamięci podręcznej poza komponentem. To uproszczona wersja tego, co robią biblioteki (TanStack Query, frameworki z RSC). Brakuje tu unieważniania pamięci i obsługi błędów — dlatego w aplikacji używasz biblioteki.

#T STEP_BY_STEP Zadanie 4 — odrzucony Promise i granica błędu
Rozbuduj zadanie 2: przycisk „Użytkownik 0” wywołuje `fetchUser(0)`, który odrzuca Promise.

Wymagania:
1. Owiń `Suspense` w `ErrorBoundary` z pakietu `react-error-boundary`.
2. `FallbackComponent` pokazuje komunikat błędu i przycisk „Spróbuj ponownie”, który wywołuje `resetErrorBoundary`.
3. `onReset` granicy ustawia w rodzicu nowy, poprawny Promise (np. użytkownik 1).
4. Kolejność: `ErrorBoundary` na zewnątrz, `Suspense` w środku.

Sprawdź się: po błędzie i kliknięciu „Spróbuj ponownie” widać „Ładowanie…”, a potem użytkownika 1.

#T CODE_JSX Rozwiązanie 4 (JSX)
```
// UserProfileWithErrors.jsx
import { Suspense, use, useState } from 'react';
import { ErrorBoundary } from 'react-error-boundary';
import { fetchUser } from './fakeApi';

function UserCard({ userPromise }) {
  const user = use(userPromise);
  return <h2>{user.name}</h2>;
}

function ErrorFallback({ error, resetErrorBoundary }) {
  return (
    <div role="alert">
      <p>Nie udało się pobrać użytkownika: {error.message}</p>
      <button type="button" onClick={resetErrorBoundary}>Spróbuj ponownie</button>
    </div>
  );
}

export function UserProfileWithErrors() {
  const [userPromise, setUserPromise] = useState(() => fetchUser(1));

  return (
    <section>
      {[0, 1, 2].map((id) => (
        <button key={id} type="button" onClick={() => setUserPromise(fetchUser(id))}>Użytkownik {id}</button>
      ))}
      <ErrorBoundary FallbackComponent={ErrorFallback} onReset={() => setUserPromise(fetchUser(1))} resetKeys={[userPromise]}>
        <Suspense fallback={<p>Ładowanie…</p>}>
          <UserCard userPromise={userPromise} />
        </Suspense>
      </ErrorBoundary>
    </section>
  );
}
```

  );
}

        <button key={id} type="button" onClick={() => setUserPromise(fetchUser(id))}>Użytkownik {id}</button>
      ))}
      <ErrorBoundary FallbackComponent={ErrorFallback} onReset={() => setUserPromise(fetchUser(1))} resetKeys={[userPromise]}>

#T NOTE resetKeys: wyjście z błędu przez zmianę danych
`resetKeys={[userPromise]}` sprawia, że granica błędu sama się resetuje, gdy zmieni się Promise — kliknięcie innego użytkownika po błędzie od razu próbuje go załadować, bez przycisku „Spróbuj ponownie”. Bez `resetKeys` granica zostałaby w stanie błędu do ręcznego resetu, nawet gdy dane już są poprawne.

#T STEP_BY_STEP Zadanie 5 — useActionState: pierwszy formularz z akcją
Formularz zmiany imienia oparty na akcji zamiast `onSubmit`.

Wymagania:
1. `const [state, formAction, isPending] = useActionState(updateName, { name: 'Ala', error: null })`.
2. Funkcja akcji `updateName(prevState, formData)` jest `async`: czyta `formData.get('name')`, woła `saveName`, zwraca nowy stan; przy błędzie zwraca `{ ...prevState, error: komunikat }`.
3. `<form action={formAction}>` z polem `name` (niekontrolowane, `defaultValue={state.name}`) i przyciskiem.
4. Pod formularzem: „Obecne imię: …”, komunikat błędu w `role="alert"`, przycisk wyłączony przy `isPending`.

Sprawdź się: wpisanie „błąd” pokazuje komunikat i zostawia stare imię; w komponencie nie ma `useState` ani `try/finally` ustawiającego flagę ładowania.

#T CODE_JSX Rozwiązanie 5 (JSX)
```
// NameForm.jsx
import { useActionState } from 'react';
import { saveName } from './fakeApi';

async function updateName(prevState, formData) {
  try {
    const name = await saveName(String(formData.get('name') ?? ''));
    return { name, error: null };
  } catch (err) {
    return { ...prevState, error: err.message };
  }
}

export function NameForm() {
  const [state, formAction, isPending] = useActionState(updateName, { name: 'Ala', error: null });

  return (
    <form action={formAction}>
      <label>Imię <input name="name" defaultValue={state.name} /></label>
      <button type="submit" disabled={isPending}>{isPending ? 'Zapisywanie…' : 'Zapisz'}</button>
      <p>Obecne imię: {state.name}</p>
      {state.error && <p role="alert">{state.error}</p>}
    </form>
  );
}
```

#T NOTE Formularz z akcją resetuje pola
Po zakończeniu akcji przekazanej do `<form action>` React **resetuje** formularz (jak natywny formularz po wysłaniu) — niekontrolowane pola wracają do `defaultValue`. Dlatego `defaultValue={state.name}` pokazuje po zapisie nowe imię, a po błędzie — stare. Jeśli po błędzie chcesz zachować to, co wpisał użytkownik, zwróć wpisane wartości w stanie akcji (zadanie 6).

#T STEP_BY_STEP Zadanie 6 — błędy walidacji zwracane z akcji
Formularz rejestracji na wydarzenie: e-mail i liczba miejsc. Walidacja dzieje się w akcji (tak jak na serwerze), a błędy wracają w stanie.

Wymagania:
1. Stan akcji: `{ values: { email, seats }, errors: {}, success: false }`.
2. Akcja waliduje: e-mail z `@`, miejsca 1–5. Przy błędach zwraca **wpisane wartości** i obiekt błędów — bez wywołania zapisu.
3. Pola mają `defaultValue` z `state.values` i `key` zależny od wersji stanu (np. `key={state.version}`), żeby po zwróceniu wartości pole pokazało to, co wpisał użytkownik.
4. Przy sukcesie: komunikat „Zapisano na wydarzenie” i czysty formularz.
5. Błąd przy polu: `aria-invalid` + `aria-describedby`.

Sprawdź się: po błędzie w e-mailu wpisana liczba miejsc nie znika.

#T CODE_JSX Rozwiązanie 6 (JSX)
```
// EventSignup.jsx
import { useActionState } from 'react';
import { wait } from './fakeApi';

const EMPTY = { values: { email: '', seats: '1' }, errors: {}, success: false, version: 0 };

async function signup(prev, formData) {
  const values = { email: String(formData.get('email') ?? ''), seats: String(formData.get('seats') ?? '') };
  const errors = {};
  if (!values.email.includes('@')) errors.email = 'Podaj poprawny e-mail';
  const seats = Number(values.seats);
  if (!Number.isInteger(seats) || seats < 1 || seats > 5) errors.seats = 'Od 1 do 5 miejsc';

  if (Object.keys(errors).length > 0) return { values, errors, success: false, version: prev.version + 1 };
  await wait(600);
  return { ...EMPTY, success: true, version: prev.version + 1 };
}

export function EventSignup() {
  const [state, formAction, isPending] = useActionState(signup, EMPTY);

  return (
    <form action={formAction} noValidate>
      <label>
        E-mail
        <input key={`email-${state.version}`} name="email" defaultValue={state.values.email}
          aria-invalid={Boolean(state.errors.email)} aria-describedby={state.errors.email ? 'email-error' : undefined} />
      </label>
      {state.errors.email && <p id="email-error" className="error">{state.errors.email}</p>}
      <label>
        Miejsca
        <input key={`seats-${state.version}`} name="seats" type="number" defaultValue={state.values.seats}
          aria-invalid={Boolean(state.errors.seats)} aria-describedby={state.errors.seats ? 'seats-error' : undefined} />
      </label>
      {state.errors.seats && <p id="seats-error" className="error">{state.errors.seats}</p>}
      <button type="submit" disabled={isPending}>Zapisz się</button>
      {state.success && <p role="status">Zapisano na wydarzenie</p>}
    </form>
  );
}
```

#T STEP_BY_STEP Zadanie 7 — useFormStatus: przycisk, który wie, że formularz się wysyła
Wydziel przycisk wysyłania do komponentu wielokrotnego użytku.

Wymagania:
1. `SubmitButton({ children, pendingText })` używa `useFormStatus()` i pokazuje `pendingText` oraz `disabled` podczas wysyłania.
2. Podczas wysyłania pokazuje też, **co** jest wysyłane: `data.get('name')` z obiektu `useFormStatus`.
3. Użyj go w formularzu z zadania 5 zamiast zwykłego przycisku — bez przekazywania `isPending` w props.
4. Przeczytaj przewidź-wynik poniżej rozwiązania.

Sprawdź się: ten sam `SubmitButton` działa w dwóch różnych formularzach na stronie i każdy pokazuje własny stan.

#T CODE_JSX Rozwiązanie 7 (JSX)
```
// SubmitButton.jsx
import { useFormStatus } from 'react-dom';

export function SubmitButton({ children, pendingText = 'Wysyłanie…' }) {
  const { pending, data } = useFormStatus();
  const sending = data?.get('name');

  return (
    <button type="submit" disabled={pending}>
      {pending ? `${pendingText}${sending ? ` (${sending})` : ''}` : children}
    </button>
  );
}
```

  const [error, setError] = useState(null);

#T NOTE Aktualizacje po await w przejściu
Wszystko, co wywołasz synchronicznie wewnątrz funkcji przekazanej do `startTransition`, jest oznaczane jako przejście. Ale po `await` kod wykonuje się już w innym zadaniu — React (w obecnej wersji) nie wie, że to wciąż to samo przejście, więc aktualizacje stanu po `await` owijasz w kolejne `startTransition`. Bez tego zadziałają jako zwykłe, pilne aktualizacje: zwykle działa to poprawnie, ale stan może pokazać się przed zakończeniem `isPending` albo przerwać inne przejście. W akcjach formularzy i `useActionState` React robi to za ciebie.

#T NOTE JSX ↔ TSX — typy w hookach React 19
- `use(promise)` przenosi typ z `Promise<T>` na wynik — typuj funkcje API, a komponenty dostaną typy za darmo.
- `useActionState(action, initial)` wnioskuje typ stanu z akcji; akcja ma sygnaturę `(prev: State, formData: FormData) => State | Promise<State>`.
- `useOptimistic(state, updateFn)` — typuj parametry `updateFn`, żeby `addOptimistic` przyjmował właściwy typ wartości.
- `useFormStatus().data` to `FormData | null`, a `FormData.get` zwraca `FormDataEntryValue | null` (tekst albo plik) — sprawdzasz `typeof … === 'string'`.

W JSX te same hooki działają identycznie, ale literówka w nazwie pola formularza (`formData.get('txt')`) da po cichu `null`.

#T SUMMARY Podsumowanie treningu
Przećwiczyłeś wszystkie hooki React 19 do pracy asynchronicznej: `use` z kontekstem (warunkowo) i z Promise (tworzonym poza komponentem czytającym, z `Suspense` i granicą błędu), `useActionState` ze stanem wyniku i błędami walidacji zwracanymi z akcji, `useFormStatus` w komponencie wewnątrz formularza, `useOptimistic` z automatycznym wycofaniem przy błędzie oraz `useTransition` z funkcją asynchroniczną i zagnieżdżonym `startTransition` po `await`. Wiesz też, czego te hooki nie zastępują: pamięci podręcznej stanu serwera (TanStack Query) i zwykłego `useState` dla lokalnych interakcji.

Kryterium zaliczenia: poprawne odpowiedzi do zadań 3, 7 (przewidź wynik) i 11; w zadaniach 5–12 żaden komponent nie ma ręcznej flagi `isLoading` ani kodu wycofującego zmianę optymistyczną.
