#T INTRO NIO.2: Path i Files — ściąga egzaminacyjna
API NIO.2 (`java.nio.file`) to nowoczesny sposób pracy z plikami. Egzamin zadaje dużo pytań o **operacje na ścieżkach** (które nie dotykają dysku) i o **metody klasy `Files`** — ich wartości zwracane, opcje i wyjątki.

#T DEFINITION Tworzenie ścieżek
```
Path p1 = Path.of("dane", "plik.txt");      // Java 11
Path p2 = Paths.get("dane/plik.txt");       // starszy sposób
Path p3 = Path.of("/home/ola");             // ścieżka bezwzględna (Unix)
File f = p1.toFile();  Path back = f.toPath();
```
Path jest **niemutowalna** — metody zwracają nowe obiekty. Utworzenie obiektu `Path` nie sprawdza, czy plik istnieje.

#T NOTE Operacje na ścieżkach (bez dostępu do dysku)
```
Path p = Path.of("a/b/c.txt");
p.getFileName()    -> c.txt          p.getNameCount() -> 3
p.getName(0)       -> a              p.getParent()    -> a/b
p.subpath(1, 3)    -> b/c.txt        p.getRoot()      -> null (ścieżka względna)
p.resolve("d")     -> a/b/c.txt/d    p.resolveSibling("x") -> a/b/x
Path.of("a/./b/../c").normalize()   -> a/c
Path.of("a/b").relativize(Path.of("a/c/d")) -> ../c/d
```
- `resolve` z argumentem **bezwzględnym** zwraca sam argument.
- `relativize` wymaga, by obie ścieżki były względne albo obie bezwzględne (inaczej `IllegalArgumentException`).
- `startsWith`/`endsWith` porównują **całe elementy** ścieżki, a nie znaki: `Path.of("abc").startsWith("ab")` to `false`.
- Indeksy w `getName` i `subpath` liczone od 0, nie obejmują korzenia.
- `toAbsolutePath()` nie sprawdza istnienia; `toRealPath()` sprawdza i rzuca `NoSuchFileException`.

#T NOTE Metody Files
```
exists / notExists / isDirectory / isRegularFile / isSameFile / size
createFile          -> FileAlreadyExistsException, gdy istnieje
createDirectory     -> wyjątek, gdy rodzic nie istnieje lub katalog już jest
createDirectories   -> tworzy całą ścieżkę, nie rzuca, gdy istnieje
delete              -> NoSuchFileException / DirectoryNotEmptyException
deleteIfExists      -> zwraca boolean
copy / move         -> FileAlreadyExistsException bez REPLACE_EXISTING
readString / writeString / readAllLines / write(path, lines, opcje)
lines / list / walk(start, głębokość) / find  -> Stream - zamykać!
newBufferedReader / newBufferedWriter
readAttributes(path, BasicFileAttributes.class) / getLastModifiedTime
```
Opcje zapisu (`StandardOpenOption`): `CREATE`, `CREATE_NEW`, `APPEND`, `TRUNCATE_EXISTING`, `WRITE`. Domyślnie `writeString`/`write` tworzą plik i nadpisują go.

#T PITFALL Pułapki
- `Files.list` przegląda tylko jeden poziom, `Files.walk` — rekurencyjnie (domyślnie bez limitu głębokości, z katalogiem startowym w wyniku).
- `Files.delete` na niepustym katalogu rzuca `DirectoryNotEmptyException`.
- `Files.move` w obrębie tego samego katalogu to zmiana nazwy.
- Strumienie z `lines`, `list`, `walk`, `find` trzymają otwarte zasoby — należy używać try-with-resources.
- `Path.of("x").equals(Path.of("./x"))` to `false` — `equals` porównuje zapis, a nie plik na dysku (do tego służy `isSameFile`).

#T SUMMARY Podsumowanie
Rozróżniaj operacje czysto „tekstowe” na ścieżkach (`resolve`, `relativize`, `normalize`, `subpath`) od metod `Files`, które dotykają dysku i rzucają `IOException`. Pamiętaj o wyjątkach przy istniejących plikach i niepustych katalogach oraz o zamykaniu strumieni.

#EX
P: Jak utworzyć obiekt Path?
H: Metody fabryczne.
S: Path.of("a", "b", "c.txt") (od Javy 11), Paths.get(...) (starszy odpowiednik), FileSystems.getDefault().getPath(...) albo file.toPath() z obiektu java.io.File. Path to interfejs, więc nie tworzy się go przez new. Utworzenie ścieżki nie sprawdza, czy plik istnieje.

#EX
P: Które operacje na Path nie dotykają dysku?
H: Przekształcenia samej ścieżki.
S: getFileName(), getParent(), getRoot(), getNameCount(), getName(i), subpath(), resolve(), relativize(), normalize(), isAbsolute() i toAbsolutePath() działają wyłącznie na tekście ścieżki. Dysk odpytuje m.in. toRealPath() (rozwiązuje dowiązania i rzuca wyjątek, gdy plik nie istnieje) oraz metody klasy Files.

#EX
P: Jak działa resolve() i co się dzieje przy ścieżce bezwzględnej jako argumencie?
H: Doklejanie.
S: a.resolve(b) dokleja ścieżkę b do a. Jeśli b jest bezwzględna, wynikiem jest po prostu b. resolveSibling(b) rozwiązuje względem rodzica a. resolve nie usuwa elementów . ani .. — do tego służy normalize().

#EX
P: Jak działa relativize()?
H: Droga od jednej ścieżki do drugiej.
S: a.relativize(b) zwraca ścieżkę względną, która prowadzi z a do b, np. z /x/y do /x/z/p.txt wynik to ../z/p.txt. Obie ścieżki muszą być tego samego rodzaju — obie względne albo obie bezwzględne; mieszanie rzuca IllegalArgumentException.

#EX
P: Czym różnią się Files.delete() i Files.deleteIfExists()?
H: Brak pliku i niepusty katalog.
S: Files.delete() rzuca NoSuchFileException, gdy plik nie istnieje. deleteIfExists() zwraca wtedy false. Obie rzucają DirectoryNotEmptyException przy próbie usunięcia niepustego katalogu — trzeba najpierw usunąć zawartość, np. przechodząc drzewo przez Files.walk w odwrotnej kolejności.

#EX
P: Jak zachowuje się Files.copy() i Files.move(), gdy plik docelowy istnieje?
H: Opcje kopiowania.
S: Domyślnie obie rzucają FileAlreadyExistsException. Opcja StandardCopyOption.REPLACE_EXISTING pozwala nadpisać cel, COPY_ATTRIBUTES kopiuje atrybuty, a ATOMIC_MOVE wymusza atomowe przeniesienie. Kopiowanie katalogu kopiuje tylko sam katalog, bez zawartości. createDirectory też rzuca wyjątek, gdy katalog istnieje, a createDirectories — nie.

#EX
P: Czym różnią się Files.readAllLines() i Files.lines()?
H: Pamięć i zamykanie.
S: readAllLines() wczytuje cały plik do List<String> naraz, co przy dużych plikach zużywa dużo pamięci. lines() zwraca leniwy Stream<String>, który czyta plik w miarę potrzeby, ale trzyma otwarty plik — trzeba go zamknąć, najlepiej w try-with-resources. Podobnie Files.list(), walk() i find().

#EX
P: Czym różnią się Files.list(), Files.walk() i Files.find()?
H: Głębokość i filtrowanie.
S: list() zwraca tylko bezpośrednią zawartość katalogu (bez rekurencji). walk() przechodzi drzewo w głąb, opcjonalnie z limitem głębokości, i domyślnie nie podąża za dowiązaniami symbolicznymi (chyba że z FileVisitOption.FOLLOW_LINKS). find() działa jak walk, ale przyjmuje limit głębokości i predykat (ścieżka, atrybuty) do filtrowania. Wszystkie zwracają Stream<Path> do zamknięcia.
