#T INTRO Synchronizacja i Concurrency API — ściąga egzaminacyjna
Gdy kilka wątków współdzieli dane, potrzebna jest synchronizacja. Egzamin sprawdza znajomość `synchronized`, blokad z `java.util.concurrent.locks`, klas atomowych, kolekcji współbieżnych i narzędzi koordynacji (`CountDownLatch`, `CyclicBarrier`, `Semaphore`) oraz pojęć: wyścig, zakleszczenie, zagłodzenie, livelock.

#T DEFINITION synchronized
```
synchronized void inc() { count++; }          // monitor: this
static synchronized void sinc() { total++; }  // monitor: obiekt Klasa.class
void m() {
    synchronized (lock) { ... }               // monitor: dowolny obiekt
}
```
- W danej chwili tylko jeden wątek może trzymać monitor danego obiektu.
- Blokady są **wielowejściowe** (reentrant): wątek trzymający monitor może ponownie wejść do bloku na tym samym obiekcie.
- Metody statyczna i instancyjna `synchronized` używają **różnych** monitorów, więc nie wykluczają się nawzajem.

#T NOTE Lock, ReentrantLock, ReadWriteLock
- `lock()` / `unlock()` — `unlock` zawsze w `finally`. `unlock` bez posiadania blokady → `IllegalMonitorStateException`.
- `tryLock()` zwraca `boolean` od razu; `tryLock(czas, jednostka)` czeka najwyżej podany czas.
- Blokadę trzeba zwolnić tyle razy, ile razy ją założono.
- `new ReentrantLock(true)` — tryb sprawiedliwy (fair).
- `ReentrantReadWriteLock`: wiele wątków czyta równocześnie, zapis jest wyłączny.

#T NOTE Klasy atomowe i kolekcje współbieżne
- `AtomicInteger`: `incrementAndGet` (zwraca nową), `getAndIncrement` (zwraca starą), `addAndGet`, `compareAndSet(oczekiwana, nowa)`, `updateAndGet(f)`, `accumulateAndGet(x, f)`.
- `ConcurrentHashMap` — bezpieczna, **bez kluczy i wartości `null`**; `merge`/`compute` są atomowe.
- `CopyOnWriteArrayList` — każda modyfikacja kopiuje tablicę; iterator widzi migawkę i nigdy nie rzuca `ConcurrentModificationException`.
- `BlockingQueue` (`ArrayBlockingQueue`, `LinkedBlockingQueue`): `put`/`take` blokują; `offer`/`poll` z limitem czasu.
- `Collections.synchronizedList(...)` — każda metoda synchronizowana, ale **iterację** trzeba objąć `synchronized(list)`.

#T NOTE Narzędzia koordynacji
- `CountDownLatch(n)`: `countDown()` zmniejsza licznik, `await()` czeka na zero; nie da się go zresetować.
- `CyclicBarrier(n, akcja)`: n wątków czeka na siebie w `await()`, potem (opcjonalnie) wykonuje się akcja; bariera jest wielokrotnego użytku.
- `Semaphore(n)`: `acquire()` / `release()` ogranicza liczbę równoczesnych wątków.

#T PITFALL Problemy współbieżności
- **Wyścig (race condition)** — wynik zależy od przeplotu wątków (np. `count++` bez synchronizacji).
- **Zakleszczenie (deadlock)** — wątki czekają nawzajem na blokady trzymane przez siebie (np. różna kolejność zakładania blokad).
- **Zagłodzenie (starvation)** — wątek nigdy nie dostaje dostępu do zasobu.
- **Livelock** — wątki są aktywne, ale ciągle ustępują sobie i nie robią postępu.
- `volatile` daje widoczność, ale nie atomowość operacji złożonych.

#T SUMMARY Podsumowanie
Do prostych liczników używaj klas atomowych, do sekcji krytycznych `synchronized` lub `Lock` (z `unlock` w `finally`), do współdzielonych kolekcji — kolekcji współbieżnych. Pamiętaj, który monitor blokuje metoda statyczna, a który instancyjna.

#Q
Q: Jaki jest poprawny wzorzec użycia Lock?
```
Lock lock = new ReentrantLock();
```
+ lock.lock(); try { /* sekcja krytyczna */ } finally { lock.unlock(); }
- try { lock.lock(); /* sekcja */ } catch (Exception e) { lock.unlock(); }
- lock.lock(); /* sekcja */ lock.unlock();
- synchronized (lock) { lock.unlock(); }
E: unlock w finally gwarantuje zwolnienie blokady także przy wyjątku. lock() wywołuje się przed try, by nie zwalniać blokady, której nie udało się założyć.

Q: Co oznacza zakleszczenie (deadlock)?
+ Dwa lub więcej wątków czeka w nieskończoność na zasoby trzymane przez siebie nawzajem
- Wątek nigdy nie dostaje dostępu do zasobu, bo inne go wyprzedzają

- Wynik zależy od kolejności wykonania wątków
E: Pozostałe opisy to zagłodzenie (starvation), livelock i wyścig (race condition).

#EX
P: Na jakim obiekcie blokuje się metoda synchronized?
H: Metoda instancyjna a statyczna.
S: Metoda instancyjna synchronized blokuje monitor obiektu this, a statyczna — obiekt Class danej klasy. Blok synchronized(obj) blokuje wskazany obiekt. Dwa wątki wykluczają się tylko wtedy, gdy synchronizują się na tym samym obiekcie. Monitor jest wielowejściowy (reentrant).

#EX
P: Jakie przewagi ma ReentrantLock nad synchronized?
H: tryLock, przerywalność, uczciwość.
S: ReentrantLock udostępnia tryLock() (próba bez czekania) i tryLock(czas), lockInterruptibly() (czekanie przerywalne), tryb fair, wiele warunków przez newCondition(). Wymaga jednak ręcznego zwolnienia — unlock() zawsze w bloku finally. Wywołanie unlock() przez wątek, który nie trzyma blokady, rzuca IllegalMonitorStateException.

#EX
P: Do czego służy ReadWriteLock?
H: Wielu czytelników, jeden pisarz.
S: ReentrantReadWriteLock ma dwie blokady: readLock(), który może trzymać wiele wątków jednocześnie, oraz writeLock(), który jest wyłączny i wyklucza też czytelników. Opłaca się, gdy odczytów jest znacznie więcej niż zapisów.

#EX
P: Dlaczego count++ nie jest bezpieczne wątkowo i jak to naprawić?
H: Odczyt, modyfikacja, zapis.
S: count++ to trzy operacje: odczyt, zwiększenie i zapis — dwa wątki mogą odczytać tę samą wartość i jedna aktualizacja zginie. volatile tego nie naprawia, bo gwarantuje tylko widoczność, a nie atomowość. Rozwiązania to AtomicInteger.incrementAndGet(), LongAdder, synchronized albo Lock.

#EX
P: Czym różnią się kolekcje współbieżne od kolekcji opakowanych przez Collections.synchronizedXxx?
H: Blokowanie całości i iteracja.
S: Opakowania synchronizedList/Map blokują całą kolekcję przy każdej operacji, a iterację trzeba ręcznie synchronizować — inaczej grozi ConcurrentModificationException. Kolekcje z java.util.concurrent (ConcurrentHashMap, CopyOnWriteArrayList, ConcurrentLinkedQueue, BlockingQueue) mają drobniejsze blokowanie lub algorytmy bez blokad, a ich iteratory nie rzucają ConcurrentModificationException. ConcurrentHashMap nie przyjmuje null jako klucza ani wartości.

#EX
P: Kiedy warto użyć CopyOnWriteArrayList?
H: Proporcja odczytów do zapisów.
S: Każda modyfikacja tworzy nową kopię tablicy, więc odczyty i iteracja są szybkie i bezpieczne bez blokowania, a iterator widzi migawkę z chwili utworzenia. Opłaca się przy rzadkich zapisach i częstych odczytach, np. lista słuchaczy zdarzeń; przy częstych zapisach jest bardzo kosztowna.

#EX
P: Do czego służą CountDownLatch, CyclicBarrier i Semaphore?
H: Odliczanie, punkt spotkania, liczba zezwoleń.
S: CountDownLatch pozwala czekać (await) aż licznik spadnie do zera przez countDown() — jest jednorazowy. CyclicBarrier zatrzymuje określoną liczbę wątków, aż wszystkie dojdą do bariery, po czym może być użyty ponownie i opcjonalnie uruchamia akcję. Semaphore ogranicza liczbę wątków mających jednocześnie dostęp do zasobu przez acquire() i release().

#EX
P: Czym są zakleszczenie, zagłodzenie i livelock?
H: Czekanie w kółko, brak dostępu, ruch bez postępu.
S: Zakleszczenie (deadlock) — wątki czekają na siebie nawzajem, bo każdy trzyma blokadę potrzebną drugiemu; zapobiega mu stała kolejność zakładania blokad lub tryLock z limitem. Zagłodzenie (starvation) — wątek nigdy nie dostaje dostępu do zasobu, bo inne go ciągle zajmują. Livelock — wątki są aktywne i reagują na siebie, ale żaden nie robi postępu. Wyścig (race condition) to błędny wynik zależny od przeplotu wątków.
