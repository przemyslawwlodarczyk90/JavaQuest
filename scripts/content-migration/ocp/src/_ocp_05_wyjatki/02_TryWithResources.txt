#T INTRO try-with-resources — ściąga egzaminacyjna
Konstrukcja try-with-resources automatycznie zamyka zasoby. Egzamin pyta o **kolejność**: zamykania zasobów, wykonania `catch` i `finally`, a także o **wyjątki stłumione** (suppressed) i o to, jakie zmienne wolno umieścić w nawiasie.

#T DEFINITION Składnia i kolejność
```
try (var a = new Res("A"); var b = new Res("B")) {
    // ciało
} catch (Exception e) {
    // po zamknięciu zasobów
} finally {
    // na samym końcu
}
```
Kolejność:
1. Zasoby otwierane są od lewej do prawej.
2. Wykonuje się ciało `try`.
3. Zasoby zamykane są **w odwrotnej kolejności** (B, potem A) — także gdy ciało rzuci wyjątek.
4. Dopiero potem `catch` (jeśli był wyjątek), na końcu `finally`.

#T NOTE Wymagania wobec zasobów
- Typ musi implementować `AutoCloseable` (lub `Closeable`, który go rozszerza).
- `AutoCloseable.close()` deklaruje `throws Exception`, `Closeable.close()` — `throws IOException`. Jeśli metoda `close()` danego typu deklaruje wyjątek kontrolowany, trzeba go obsłużyć.
- Zasób zadeklarowany w nawiasie jest niejawnie `final` i widoczny tylko w bloku `try`.
- Od Javy 9 można użyć istniejącej zmiennej **final lub efektywnie finalnej**: `try (in) { ... }`.
- try-with-resources nie wymaga `catch` ani `finally`.
- Zasób równy `null` nie jest zamykany (brak wyjątku).

#T NOTE Wyjątki stłumione
- Jeśli ciało rzuci wyjątek, a `close()` też rzuci wyjątek, to **główny** jest ten z ciała, a wyjątek z `close()` zostaje do niego dodany jako stłumiony (`getSuppressed()`).
- Jeśli ciało zakończy się normalnie, a `close()` rzuci wyjątek, to ten wyjątek jest główny.
- Jeśli kilka `close()` rzuci wyjątki, pierwszy staje się główny (gdy ciało było poprawne), a kolejne — stłumionymi.

#T PITFALL Pułapki
- Wyjątek w konstruktorze drugiego zasobu: pierwszy zasób (już otwarty) zostanie zamknięty, drugi nie istnieje.
- Zmienna zasobu nie jest widoczna w `catch` ani `finally`.
- `try (String s = "x")` się nie kompiluje — `String` nie jest `AutoCloseable`.
- Zmiana wartości zmiennej przed `try (zmienna)` sprawia, że nie jest efektywnie finalna.

#T SUMMARY Podsumowanie
Zasoby: otwierane od lewej, zamykane od prawej, zamknięte przed `catch` i `finally`. Wyjątek z ciała wygrywa, a wyjątki z `close()` są wtedy stłumione.

+ Zasoby są zamykane przed wykonaniem bloku catch
- Zasoby są zamykane po wykonaniu bloku finally
- Zasoby są zamykane w kolejności deklaracji
- Blok try-with-resources musi mieć catch lub finally
E: Kolejność to: ciało, zamknięcie zasobów (od ostatniego), catch, finally. catch i finally są opcjonalne.

#EX
P: Jakie obiekty można zadeklarować w try-with-resources?
H: Interfejs, który musi implementować zasób.
S: Tylko obiekty implementujące AutoCloseable (lub jego podinterfejs Closeable). Zasoby deklaruje się w nawiasie po try, oddzielając średnikami. Od Javy 9 można też podać istniejącą zmienną, jeśli jest final lub effectively final.

#EX
P: W jakiej kolejności zamykane są zasoby i kiedy następuje to względem catch i finally?
H: Odwrotna kolejność, zanim wykona się catch.
S: Zasoby są zamykane w kolejności odwrotnej do deklaracji, zaraz po zakończeniu bloku try — przed wykonaniem bloków catch i finally. Dlatego w catch i finally zasoby są już zamknięte.

#EX
P: Czym są wyjątki stłumione (suppressed)?
H: Wyjątek z close i wyjątek z try.
S: Gdy blok try rzuci wyjątek, a zamknięcie zasobu też rzuci wyjątek, ten drugi nie zastępuje pierwszego, tylko jest do niego dołączany jako stłumiony. Główny wyjątek trafia do catch, a stłumione odczytuje się przez getSuppressed(). Gdy try zakończy się normalnie, wyjątek z close staje się wyjątkiem głównym.

#EX
P: Czym różnią się AutoCloseable i Closeable?
H: Wyjątki w close i idempotentność.
S: AutoCloseable.close() deklaruje throws Exception. Closeable (z java.io) rozszerza AutoCloseable, a jego close() deklaruje tylko IOException i według kontraktu powinien być idempotentny — wielokrotne wywołanie nie zmienia skutku. Przy własnych zasobach warto zawęzić deklarowane wyjątki, aby użytkownik nie musiał łapać Exception.

#EX
P: Czy zmienna zasobu w try-with-resources może zostać ponownie przypisana?
H: Niejawny modyfikator.
S: Nie — zasoby zadeklarowane w nagłówku try są niejawnie final. Próba przypisania im innej wartości w bloku try to błąd kompilacji. Zasób jest też widoczny tylko w bloku try, a nie w catch ani finally.

#EX
P: Co się dzieje, gdy zasób ma wartość null?
H: Wywołanie close.
S: Jeśli zasób zainicjalizuje się wartością null, try-with-resources nie wywoła na nim close i nie rzuci NullPointerException przy zamykaniu. Wyjątek pojawi się dopiero, gdy kod w bloku try spróbuje użyć tego zasobu.

#EX
P: Czy try-with-resources wymaga catch lub finally?
H: Porównaj ze zwykłym try.
S: Nie — sam try z zasobami jest kompletną instrukcją, bo zamykanie zasobów pełni rolę finally. Zwykłe try bez zasobów musi mieć co najmniej jeden catch albo finally. Wyjątki kontrolowane z close nadal trzeba obsłużyć albo zadeklarować.

#EX
P: Dlaczego try-with-resources jest lepsze od ręcznego zamykania w finally?
H: Wyjątki z close, kilka zasobów, czytelność.
S: Ręczne zamykanie w finally wymaga sprawdzania null, zagnieżdżonych try przy kilku zasobach i łatwo przez nie zgubić pierwotny wyjątek, gdy close również rzuci. try-with-resources zamyka wszystko automatycznie w poprawnej kolejności i zachowuje oba wyjątki dzięki mechanizmowi suppressed.
