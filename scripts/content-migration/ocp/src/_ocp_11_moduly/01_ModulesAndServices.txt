#T INTRO Moduły (JPMS) i wdrażanie — ściąga egzaminacyjna
System modułów (Java Platform Module System, Java 9) pozwala jawnie określić, od czego zależy kod i co udostępnia innym. Egzamin pyta o dyrektywy `module-info.java`, rodzaje modułów (nazwane, automatyczne, nienazwany), polecenia `javac`, `java`, `jar`, `jdeps`, `jlink`, usługi (`ServiceLoader`) i strategie migracji.

#T DEFINITION Dyrektywy module-info.java
```
module pl.sklep.zamowienia {
    requires pl.sklep.model;                 // zależność
    requires transitive pl.sklep.wspolne;    // zależność przekazywana dalej
    requires static pl.sklep.adnotacje;      // wymagana tylko przy kompilacji
    exports pl.sklep.zamowienia.api;         // publiczne typy pakietu dostępne dla wszystkich
    exports pl.sklep.zamowienia.spi to pl.sklep.raporty;  // tylko dla wskazanego modułu
    opens pl.sklep.zamowienia.encje;         // dostęp przez refleksję (w czasie działania)
    opens pl.sklep.zamowienia.dto to com.fasterxml.jackson.databind;
    uses pl.sklep.platnosci.Platnosc;        // moduł korzysta z usługi
    provides pl.sklep.platnosci.Platnosc with pl.sklep.zamowienia.Karta;  // implementacja usługi
}
```
- Plik `module-info.java` leży w katalogu głównym źródeł modułu (obok najwyższego pakietu).
- Moduł `java.base` jest wymagany niejawnie.
- `open module nazwa { ... }` otwiera wszystkie pakiety do refleksji (wtedy dyrektywy `opens` w środku są niedozwolone).
- `exports` dotyczy pakietów, a nie klas; nie obejmuje podpakietów.

#T NOTE Rodzaje modułów
- **Nazwany** — ma `module-info.class`, leży na ścieżce modułów (module path).
- **Automatyczny** — zwykły JAR na ścieżce modułów; nazwa z `Automatic-Module-Name` w manifeście albo z nazwy pliku (bez wersji, myślniki → kropki). Eksportuje i otwiera wszystkie pakiety oraz czyta wszystkie inne moduły.
- **Nienazwany** — wszystko na ścieżce klas (classpath). Czyta wszystkie moduły, ale moduły nazwane **nie mogą** wymagać modułu nienazwanego.
- Zakazane: cykliczne zależności `requires` oraz ten sam pakiet w dwóch modułach (split package).

#T NOTE Polecenia
Najważniejsze polecenia JDK związane z modułami i ich skróty:
```
javac -d out --module-path libs  src/...java      (-p = --module-path)
java --module-path out --module pl.app/pl.app.Main  (-m = --module)
java --list-modules
java --describe-module pl.app   (-d)
java --show-module-resolution ...
jar --create --file app.jar --main-class pl.app.Main -C out .
jar --describe-module --file app.jar   (-d)
jdeps --module-path libs app.jar        analiza zależności
jdeps --jdk-internals app.jar           użycie wewnętrznych API JDK
jlink --module-path ... --add-modules pl.app --output obraz   własne, okrojone środowisko
jmod   tworzenie plików .jmod
```

#T NOTE Usługi i migracja
- Usługę tworzą: interfejs (moduł API), dostawca (`provides … with …`) i konsument (`uses …` + `ServiceLoader.load(Interfejs.class)`).
- Dostawca w module musi mieć publiczny konstruktor bezargumentowy albo publiczną statyczną metodę `provider()`.
- `ServiceLoader` jest leniwy; `stream()` daje `ServiceLoader.Provider` z metodami `type()` i `get()`.
- Migracja **od dołu** (bottom-up): najpierw moduły bez zależności (najniższe), reszta tymczasowo w nienazwanym.
- Migracja **od góry** (top-down): wszystkie JAR-y na ścieżkę modułów jako automatyczne, potem stopniowo zamiana najwyższych na nazwane.

#T PITFALL Pułapki
- `requires` przyjmuje nazwę **modułu**, `exports` — nazwę **pakietu**.
- `requires transitive` sprawia, że moduł zależny od nas automatycznie czyta także przekazany moduł.
- Typy z pakietu niewyeksportowanego są niedostępne nawet, gdy są `public`.
- `exports` daje dostęp w czasie kompilacji i działania do typów publicznych; `opens` — tylko refleksję w czasie działania (także do składowych prywatnych).
- Nazwy modułów są w formie odwróconej domeny (`pl.firma.modul`) i nie mogą zawierać myślników.

#T SUMMARY Podsumowanie
`requires` (moduł) / `exports` (pakiet) / `opens` (refleksja) / `uses` i `provides … with` (usługi). Moduły nazwane nie widzą nienazwanego; automatyczne powstają z JAR-ów na ścieżce modułów. Zapamiętaj skróty `-p`, `-m`, `-d` i przeznaczenie `jdeps` oraz `jlink`.

#Q
Q: Jak nazywa się plik deskryptora modułu?
+ module-info.java
- module.xml
- MANIFEST.MF
- module-descriptor.java
E: Deskryptor modułu to plik module-info.java, kompilowany do module-info.class.

#Q
Q: Gdzie powinien znajdować się plik module-info.java?
+ W katalogu głównym źródeł modułu, obok katalogu najwyższego pakietu
- W katalogu META-INF
- W każdym pakiecie modułu
- W katalogu zasobów resources
E: Deskryptor jest jeden na moduł i leży w korzeniu źródeł (np. src/pl.app/module-info.java).

#Q
Q: Która dyrektywa udostępnia publiczne typy pakietu innym modułom?
+ exports
- requires
- opens
- provides
E: exports udostępnia pakiet w czasie kompilacji i działania. requires deklaruje zależność, opens daje dostęp przez refleksję, provides rejestruje implementację usługi.

#Q
Q: Która deklaracja jest poprawna w module-info.java?
+ requires java.sql;
- requires java.sql.*;
- exports java.sql;
- import java.sql;
E: requires przyjmuje nazwę modułu (bez gwiazdki). exports dotyczy własnych pakietów modułu, a import nie występuje w deskryptorze.

#Q
Q: Który zapis jest poprawny?
+ exports pl.app.api to pl.raporty, pl.audyt;
- exports pl.app.api to *;
- exports pl.app.api.*;
- exports module pl.app.api;
E: Kwalifikowany eksport wymienia moduły odbiorców po słowie to, oddzielone przecinkami.

#Q
Q: Moduł A ma requires transitive B, a moduł C ma requires A. Co jest prawdą?
+ C może używać wyeksportowanych pakietów B bez własnej dyrektywy requires B
- C musi dodać requires B, aby używać pakietów B
- B może używać pakietów C
- Powstaje zależność cykliczna
E: requires transitive przekazuje czytelność modułu B wszystkim modułom zależnym od A.

#Q
Q: Do czego służy requires static?
+ Do zależności wymaganej przy kompilacji, a opcjonalnej w czasie działania
- Do zależności od klas statycznych
- Do wymagania modułu tylko w czasie działania
- Do importu statycznego z innego modułu
E: requires static oznacza zależność kompilacyjną; moduł nie musi być obecny w czasie działania.

#Q
Q: Czym różni się opens od exports?
+ opens daje dostęp przez refleksję w czasie działania (także do składowych prywatnych), ale nie w czasie kompilacji
- opens działa tylko w czasie kompilacji
- opens dotyczy modułów, a exports pakietów
- Nie ma różnicy
E: Biblioteki takie jak Hibernate czy Jackson potrzebują opens, by odczytywać pola przez refleksję. exports udostępnia publiczne typy do zwykłego użycia w kodzie.

#Q
Q: Co oznacza zapis open module pl.app { requires java.sql; }?
+ Wszystkie pakiety modułu są otwarte do refleksji w czasie działania
- Wszystkie pakiety są wyeksportowane
- Moduł może być wymagany przez moduły nienazwane
- Moduł nie ma zależności
E: open module otwiera wszystkie pakiety do głębokiej refleksji, ale ich nie eksportuje.

#Q
Q: Która deklaracja się NIE skompiluje?
+ open module pl.app { opens pl.app.model; }
- open module pl.app { exports pl.app.api; }
- module pl.app { opens pl.app.model; }
- module pl.app { opens pl.app.model to pl.orm; }
E: W module otwartym dyrektywy opens są niedozwolone, bo wszystkie pakiety i tak są otwarte.

#Q
Q: Który moduł jest wymagany niejawnie przez każdy moduł?
+ java.base
- java.se
- java.lang
- java.desktop
E: java.base (z pakietami java.lang, java.util, java.io itd.) nie musi być deklarowany. java.lang to pakiet, a nie moduł.

#Q
Q: Która dyrektywa deklaruje, że moduł korzysta z usługi?

- consumes pl.platnosci.Platnosc;
E: Konsument deklaruje uses z nazwą interfejsu usługi, a dostawca — provides … with ….

#Q
Q: Który zapis poprawnie rejestruje implementację usługi?
+ provides pl.platnosci.Platnosc with pl.karta.PlatnoscKarta;
- provides pl.karta.PlatnoscKarta with pl.platnosci.Platnosc;

E: Najpierw interfejs usługi, po słowie with — klasa implementująca.

#Q
Q: Jakie warunki musi spełniać klasa dostawcy usługi w module nazwanym?
+ Mieć publiczny konstruktor bezargumentowy albo publiczną statyczną metodę provider()
- Być w pakiecie wyeksportowanym
- Mieć adnotację @Service
- Być klasą finalną
E: ServiceLoader tworzy dostawcę przez metodę provider() albo konstruktor bezargumentowy. Pakiet dostawcy nie musi być eksportowany.

#Q
Q: Który kod poprawnie pobiera wszystkie implementacje usługi Platnosc?
+ ServiceLoader.load(Platnosc.class)
- new ServiceLoader<Platnosc>()
- ServiceLoader.get(Platnosc.class)
- Class.forName("Platnosc").getServices()
E: ServiceLoader.load(Klasa.class) zwraca ServiceLoader, po którym można iterować lub wywołać stream().

#Q
Q: Co zwraca ServiceLoader.load(Platnosc.class).stream()?
+ Stream<ServiceLoader.Provider<Platnosc>>
- Stream<Platnosc>
- List<Platnosc>
- Optional<Platnosc>
E: stream() daje obiekty Provider z metodami type() (bez tworzenia instancji) i get() (tworzy instancję).

#Q
Q: Co wypisze kod?
```
ServiceLoader<Runnable> loader = ServiceLoader.load(Runnable.class);
System.out.println(loader.findFirst().isPresent() + " " + loader.stream().count());
```
+ false 0
- true 1
- Wyjątek ServiceConfigurationError
- Błąd kompilacji
X: out
E: Bez zarejestrowanych dostawców ServiceLoader nie znajduje implementacji — findFirst zwraca pusty Optional (bez wyjątku).

#Q
Q: Które stwierdzenie o module automatycznym jest prawdziwe?
+ Eksportuje i otwiera wszystkie swoje pakiety
- Nie może być wymagany przez moduły nazwane
- Musi mieć plik module-info.class
- Czyta tylko java.base
E: Moduł automatyczny eksportuje wszystko, czyta wszystkie moduły (także nienazwany) i może być wymagany przez moduły nazwane.

#Q
Q: Które stwierdzenie o module nienazwanym (unnamed module) jest prawdziwe?
+ Moduły nazwane nie mogą go wymagać przez requires
- Zawiera JAR-y ze ścieżki modułów
- Eksportuje tylko wybrane pakiety
- Istnieje osobny moduł nienazwany dla każdego JAR-a
E: Kod na ścieżce klas trafia do jednego modułu nienazwanego, który czyta wszystkie moduły, ale sam nie ma nazwy, więc nie można go wymagać.

#Q
Q: Gdzie musi znajdować się JAR, aby stał się modułem automatycznym?
+ Na ścieżce modułów (--module-path), bez module-info.class
- Na ścieżce klas (--class-path)
- W katalogu lib JDK
- W dowolnym miejscu z wpisem w manifeście Main-Class
E: Zwykły JAR na ścieżce klas trafia do modułu nienazwanego, a na ścieżce modułów staje się modułem automatycznym.

#Q
Q: Moduł A wymaga modułu B, a moduł B wymaga modułu A. Co się stanie?
+ Błąd kompilacji — cykliczne zależności między modułami są zabronione
- Działa poprawnie
- Działa tylko z requires transitive
- Błąd dopiero w czasie działania
E: Graf zależności modułów musi być acykliczny.

#Q
Q: Dwa moduły zawierają pakiet pl.wspolne. Co się stanie, gdy oba trafią na ścieżkę modułów aplikacji?
+ Błąd — ten sam pakiet nie może być w dwóch modułach (split package)
- Klasy zostaną połączone
- Użyty zostanie pakiet z pierwszego modułu
- Działa, jeśli tylko jeden z nich eksportuje pakiet
E: Każdy pakiet może należeć tylko do jednego modułu czytanego przez dany moduł.

#Q
Q: Na czym polega migracja od dołu (bottom-up)?
+ Najpierw zamienia się na moduły biblioteki bez zależności, a pozostały kod zostaje na ścieżce klas
- Najpierw wszystkie JAR-y trafiają na ścieżkę modułów jako automatyczne
- Najpierw migruje się aplikację główną
- Migruje się wszystko naraz
E: Bottom-up zaczyna od najniższych warstw; moduły nazwane mogą wtedy wymagać tylko innych modułów nazwanych.

#Q
Q: Na czym polega migracja od góry (top-down)?
+ Wszystkie JAR-y przenosi się na ścieżkę modułów (jako automatyczne), a potem zamienia się na nazwane, zaczynając od najwyższych
- Najpierw migruje się biblioteki bez zależności
- Usuwa się ścieżkę modułów
- Zamienia się wszystkie klasy na rekordy
E: Top-down pozwala od razu zmodularyzować aplikację, korzystając z modułów automatycznych dla bibliotek jeszcze niezmodularyzowanych.

Q: Która kombinacja modułów tworzy kompletny mechanizm usługi?

#EX
P: Jakie dyrektywy może zawierać plik module-info.java?
H: Zależności, eksport, refleksja, usługi.
S: requires (zależność od modułu), requires transitive (zależność przekazywana dalej), requires static (zależność tylko w czasie kompilacji), exports (udostępnienie pakietu), exports ... to (udostępnienie wybranym modułom), opens (dostęp refleksyjny w czasie działania), uses (korzystanie z usługi) i provides ... with (dostarczenie implementacji usługi). Cały moduł można też oznaczyć jako open module.

#EX
P: Czym różnią się exports i opens?
H: Kompilacja a refleksja.
S: exports udostępnia publiczne typy pakietu innym modułom w czasie kompilacji i działania. opens pozwala na głęboki dostęp przez refleksję w czasie działania (także do prywatnych składowych), ale nie udostępnia pakietu do kompilacji. Frameworki korzystające z refleksji zwykle wymagają opens.

#EX
P: Co daje requires transitive?
H: Moduły zależne od Twojego modułu.
S: Jeśli moduł A ma requires transitive B, to każdy moduł, który wymaga A, automatycznie czyta też B, bez osobnej dyrektywy. Stosuje się to, gdy typy z B występują w publicznym API modułu A.

#EX
P: Jakie są rodzaje modułów i czym się różnią?
H: Nazwane, automatyczne, nienazwany.
S: Moduł nazwany ma module-info i leży na ścieżce modułów. Moduł automatyczny to zwykły JAR bez module-info umieszczony na ścieżce modułów — eksportuje wszystkie pakiety, czyta wszystkie moduły, a nazwę bierze z Automatic-Module-Name w MANIFEST.MF albo z nazwy pliku. Moduł nienazwany obejmuje wszystko z classpath — czyta wszystkie moduły, ale moduły nazwane nie mogą go wymagać.

#EX
P: Jak skompilować i uruchomić aplikację modułową?
H: Opcje javac i java.
S: Kompilacja: javac -d out --module-source-path src -m moduł albo javac -p mods -d out pliki. Uruchomienie: java -p (lub --module-path) ścieżka -m moduł/pakiet.KlasaGłówna (skrót od --module). Opcja -d przy javac wskazuje katalog wyjściowy.

#EX
P: Jakie polecenia i opcje służą do analizy modułów?
H: describe-module, list-modules, jdeps, jlink.
S: java --list-modules wypisuje moduły dostępne w JDK, java --describe-module (-d) i jar --describe-module (-d) opisują moduł, java --show-module-resolution pokazuje rozwiązywanie zależności, jdeps analizuje zależności (z --jdk-internals wykrywa użycie wewnętrznych API JDK), a jlink buduje własny, okrojony obraz środowiska uruchomieniowego.

#EX
P: Z jakich części składa się mechanizm usług (ServiceLoader) w modułach?
H: Interfejs, dostawca, konsument, lokalizator.
S: Interfejs usługi jest w module eksportującym jego pakiet. Dostawca implementuje interfejs i deklaruje provides Interfejs with Implementacja. Konsument deklaruje uses Interfejs i ładuje implementacje przez ServiceLoader.load(Interfejs.class), który zwraca obiekt iterowalny, a stream() daje strumień obiektów Provider. Dostawca musi mieć publiczny konstruktor bezargumentowy albo publiczną statyczną metodę provider().

#EX
P: Czym różni się migracja top-down od bottom-up?
H: Od którego końca grafu zależności zaczynamy.
S: Bottom-up: najpierw zamienia się na moduły nazwane biblioteki bez zależności, a reszta zostaje na classpath, aż wszystko jest zmodularyzowane. Top-down: wszystkie JAR-y przenosi się na ścieżkę modułów jako moduły automatyczne, a potem zamienia na nazwane, zaczynając od modułów najwyższego poziomu. Cykliczne zależności między modułami są niedozwolone.
